# 第三方 OS 模块同意卡 —— 方案（CONSENT-0）

> 2026-11-17。只写方案，不含代码。行号对应当前工作区 `docs/third-party-consent-plan`。
> 原则：只做主干。边缘情况写在文末 FU，这期不做。

## 1. 现状

今天没有第三方内核能力同意卡。装得上的 OS 模块，内核能力按「它声明的 ∩ 宿主愿意给的」发放，不再问用户。

### 1.1 谁装得上

macOS 上，包要过文件哈希，还要过离线验签：Developer ID、受信团队、Hardened Runtime。`os install` 用 `VerifyMode::AtRest`，不在线查公证（`rust/crates/agent24-os-packages/src/install.rs:198-212`）。这和 S1-9 r3 一致（`docs/tracking/2026-11-04/S1-9-OS-PACKAGE-INTEGRITY-DESIGN.md:116`）。

默认只信本方团队 `HYAP444FN9`（`rust/crates/agent24-os-proc/src/lib.rs:231-234`，`rust/crates/agent24-os-packages/src/trusted_teams.rs:14-16`）。别的团队：签名读出来了、但不在名单里，安装失败并清掉暂存目录，扫描也不让它挂上。用户可见的话是 `signature_rejected: <团队>；如信任该开发者：agent24 os trust-team <团队>`（`rust/crates/agent24-components/src/integrity.rs:165-168`，判定在 `signature.rs:83-92`）。

用户可以加团队：`agent24 os trust-team`，写到数据目录的 `os-trusted-teams.json`。内置团队删不掉（`trusted_teams.rs:111-116`）。这条命令在 capabilities 模式下要桌面在场确认一次（`rust/apps/agent24-cli/src/main.rs:2735-2758`）。

签名坏、团队号不合法：同样拒绝，不给「信任团队」提示。

非 macOS：签名检查直接放过（`signature.rs:64-66`）。还要过文件哈希和「必须是本平台原生可执行文件」。Linux 上没有团队这一关。

调试构建可以认 ad-hoc 签名，发行构建不行（`signature.rs:123-140`）。这不是产品路径。

装上不等于「第三方被同意」。`os install` / `os uninstall` 会先作废这个模块已有的**工具**授权；作废失败就不改包文件（`main.rs:1730-1749`、`:1802-1820`）。没有内核能力的同意记录。

### 1.2 装上之后拿到什么

三处发放都传 `Consent::FirstPartyEnabled`，这个值不删任何能力（`rust/apps/agent24d/src/capabilities/requires.rs:131-136`、`:286-292`；调用在 `domain.rs:1657-1662`、`domain.rs:2120-2125`、`attach_grant.rs:41`，展示用的解析在 `component_routes.rs:288`、`:324`）。

进程外 OS 模块的上限是：事件、审批、记忆、定时任务、模型（`requires.rs:73-79`）。声明里多要的，交集丢掉。声明不合法则一项都不给，模块仍可运行（`requires.rs:287-288`）。

来源标签固定是 `unknown`，不参与发放（`requires.rs:137-145`）。登记进程的签名白名单验的是桌面 / CLI / daemon，不是 OS 包（`enroll_endpoint.rs:32-34`、`:62-66`）。C9 方案写的 `:21-23`、`:51-55` 在本工作区对不上，以这两处为准。

没写进 `os.json` 的模块默认启用（`os_config.rs:54-61`）。所以包一旦通过扫描，下次 daemon 挂载就拿到上面的交集，不必再点一次「启用」。

桌面自带的文档模块走另一条安装：应用启动时用 `agent24 os install` 装 `Resources/documents-module/`，装上即启用（`apps/desktop/src/main/documents-module.ts:1-7`）。它也走同一套「启用即同意」，没有单独的卡。

### 1.3 在哪被挡

| 关口 | 挡什么 | 不挡什么 |
|---|---|---|
| 哈希 + macOS 受信团队 | 没进信任名单的团队、坏签名、改过的文件 | 信任名单里的团队；非 macOS 的团队身份 |
| 宿主上限 | 声明里超出上限的内核能力 | 上限之内的，不再问用户 |
| 沙箱（macOS OS 模块） | 家目录和直接联网 | 已经授予的内核调用（事件、记忆、模型等仍经内核） |
| 工具授权 | 另一套账，见下 | 内核能力 |

沙箱已接上。macOS 上 OS 模块在组件列表里标 `isolated` / `seatbelt`；别的平台标未隔离（`component_routes.rs:113-133`）。这个标不探测进程是不是真在沙箱里（`docs/tracking/2026-11-14/MODULE-SANDBOX-PLAN.md:82`）。

工具授权是 K1-6a 的逐工具记录，存在数据目录的 `agent24.db`。在宿主核验来源之前，每条摘要都记成手动安装、高风险（`rust/crates/agent24-policy/src/tool_summary.rs:13-15`、`:47`）。总开关 `A24_MODULE_TOOL_GRANTS` 默认关；开了之后有效期默认 30 天，最长 90 天（`consent_routes.rs:428-466`）。CLI 能看卡片、提交决定、列出（`module_tools.rs:4-31`，`query.rs:88-97`）。这不是内核能力同意卡，这期不改它的规则。

能力中心对宿主显示实际拿到的内核能力，文案是机器名，例如「内核能力：events」（`apps/desktop/src/renderer/pages/Capabilities.i18n.ts:60`，测试 `Capabilities.test.tsx:180`）。非宿主视图没有 `kernel_grants`（`component_routes/tests.rs:267-270`）。

### 1.4 已经拍过的板

- 第一方签名、随桌面装的模块：启用即同意，只展示拿到了哪些内核能力。第三方同意卡以后再做（ADR-038 D7，`docs/adr/ADR-038-component-contract-v1.md:292-300`；ADR-K1-03 §4 同一句，`docs/adr/ADR-K1-03-enable-authorization-trust-revocation.md:54-56`；C9 `docs/tracking/2026-11-12/C9-REQUIRES-AUTHZ-PLAN.md:10-11`、`:162-165`）。
- 需要同意的模块：权限指纹没变就沿用；新增能力才重新问；少了的直接收回。有效期复用 `max_days`，不另定 180 天（C9 `:139-142`、`:165`）。
- 许可必须有期限，不许永不过期（ADR-K1-03 §3，`:42-44`）。安装、签名有效，本身都不是同意（`:32`、`:54`）。
- 第三方发布者的信任根、密钥轮换、吊销，不在组件契约 v1（ADR-038 `:181`、`:399`）。
- 撤销即时生效、在途复验、同意随启用纪元作废：C9 明确推到同意卡这一期（`:142`）。纪元表现在在 `module_consents.rs:565-610`、`:889`。C9 写的 `:866-915` 在本工作区对不上。

OSI-1（Sin90 按需安装）在本工作区没有方案也没有实现。未核实。本方案不依赖它。

## 2. 目标流程

签名门不动。同意卡只回答下一句：这个已经允许装载的 OS 包，给不给它声明的内核能力。

### 2.1 谁免卡，谁要卡

免卡（维持今天的启用即同意）必须同时满足：

1. 模块名在随包名单里。名单是 `documents` 和 `sin90`（OSI-2 #1891 已随包发 `sin90`）。经 OSI-1 按需升级的 sin90 也按随包对待：名单按模块名，不按安装途径。
2. macOS 上，包内可执行文件的团队是内置团队 `HYAP444FN9`。

少一条就要卡。本方团队、但是用户自己 `os install` 的包，要卡。`trust-team` 加进来的别的团队，要卡。

非 macOS 没有团队可验。名单里的随包模块维持免卡。名单外的包要卡。Linux 上有人连 `files.json` 一起改掉随包模块，清单拦不住，这是 S1-9 已写的边界，不用同意卡去补（S1-9 `:7`）。

attach、MCP 不在这期。它们继续走今天的交集。

### 2.2 什么时候问

模块默认启用，所以用户感觉到的时刻就是「装好、马上要用」。

1. 要卡的模块，第一次要发内核能力时问。没人回答，模块可以装上、也可以按沙箱跑，内核能力是空的。
2. 用户事先关掉的模块，打开时若没有未过期的同意，再问。有同意就不问。
3. 权限指纹变了：多了能力，整张重问（默认再次全部勾上，用户仍可勾掉）。少了能力，不问，直接按新的交集收回。比不了，当成变了，重问。

指纹是排序后的 `requires.kernel` 名字，不含版本。`requires.operations` 今天真实组件是空的（C9 `:12`）；一旦有，也算进指纹。

不在这些时刻问：每次启动、只改版本号、只删能力、免卡模块。

### 2.3 卡上写什么

文案由宿主写，不用模块自己的说明。

- 谁签的：macOS 团队号。读不到写「这个系统上看不到签名团队」。
- 从哪来的：模块名，加上「桌面自带」或「本机安装」。不把绝对路径放进非宿主能看到的地方。
- 版本：清单里的版本。
- 要的内核能力，一条一句人话。对照 `Capability` 的定义（`rust/crates/agent24-domain/src/lib.rs:163-176`）：
  - events：以这个模块的名字发出事件
  - models：让内核替它调用模型
  - scheduler：登记和查看定时任务
  - memory：使用只属于它自己的那一份记忆
  - approval：发起审批、查询审批结果
- 沙箱：沿用 `/components` 已有的隔离字段。macOS OS 模块写「已隔离」；其他写「未隔离」。不另做探测。

每项能力默认勾上，用户可以勾掉其中几项。一项都没勾，等同于拒绝，不写记录，内核能力保持为空。

渲染进程里的卡片只负责展示和勾选。原生在场对话框才是信任锚：框里逐条列出最终要给的能力，用户在原生框里点「同意」才写入记录。渲染进程不能绕过原生框直接写同意。

### 2.4 存在哪，多久，怎么撤

新的一行，放在现有 `agent24.db`，不塞进逐工具那张表，也不看 `A24_MODULE_TOOL_GRANTS` 开没开。记：模块名、指纹、同意的能力集合、当时的团队号、版本、决定时间、到期时间。

到期时间用决定当下的 `GrantSettings.max_days`。默认 30 天，环境变量可改，最长 90（`consent_routes.rs:450-457`）。过期后下一次发放为空，直到重新同意。

卸载删掉这一行。升级先比指纹：没变且没过期就留着；变了或过期了就删，等下一次问。不要沿用今天「一安装就作废工具授权」的做法来对待这一行，否则指纹没变也会被清掉，和已拍板的「没变就沿用」冲突。

撤销入口：

- 桌面：能力中心该模块上一颗「停止授权」。点完，下一次挂载的 `kernel_grants` 为空。
- CLI：`agent24 os consent show|grant|revoke <模块>`。`grant` 必须带上刚看过的指纹，对不上就拒绝写入。

已经在跑的调用这期不追撤。下一道内核调用才看见撤销或过期。见 FU。

### 2.5 谁弹窗

复用在场确认，不新开一条通道。

- 桌面模式：daemon 把挑战放进现有队列，桌面主进程弹出原生对话框再回答（`presence_desktop.rs:1-10`）。没有新鲜的桌面轮询，就不发能力。
- 服务模式：桌面另开一条在场连接（`presence_service.rs:1-16`）。连着，就在那台桌面弹同一张卡。没连着，`confirm` 立刻是不可用，内核能力保持为空。
- CLI：capabilities 模式下沿用 `presence_required` → 提升一次 → 重试（`main.rs:1422-1426`）。有终端、且用户就在终端里装，可以在终端打字确认，仍然要 daemon 核对指纹。没有终端、也没有桌面：安装成功，能力为空，并写明去桌面或有终端的 CLI 再同意。

服务模式下没有人值守，就不弹、不默认同意。

## 3. 分片与验收

四片。每片都能单独合。前一片合进去之后，桌面自带的文档模块行为不变。jason 11-18 拍板：第 1 问甲、第 2 问改成可勾选（默认全选）、第 3 问甲。存储仍是「同意了哪些能力」。发放是「声明 ∩ 上限 ∩ 同意集合」。

### CONSENT-1 分类和指纹（还不改变发放）

算出每个 OS 包是免卡还是要卡，以及内核指纹。`/components` 先不改发放。要卡的包多一个宿主字段 `kernel_consent: missing`，免卡的是 `exempt`。字段先只表示「将来要问」，能力仍按今天发，避免这一片单独合进去时把别人的包突然变空。

验收：`documents` 且团队是内置团队 → `exempt`。同名但团队不是内置团队 → `missing`（macOS）。名单外的包 → `missing`。指纹不含版本；只改版本，指纹不变；加上 `models`，指纹变。非宿主视图看不到这个字段。

### CONSENT-2 发放门和 CLI

要卡且没有未过期、指纹相符的记录：内核能力为空。免卡：与今天逐项相同。记录对得上：发「声明 ∩ 上限 ∩ 同意集合」。少了的能力不在交集里。多了的能力让记录作废，回到空。字段在有未过期且指纹相符的记录时是 `granted`，这样桌面不会把已经同意的模块再当成 `missing`。

CLI：`show` 打出第 2.3 节的人话；`grant` 回传指纹；`revoke` 删记录。卸载删记录。升级按第 2.4 节比较后再删。

验收：先写一条反例，证明修复前失败——已信任的外团队包，修复前 `kernel_grants` 含它声明且在上限内的项；修复后、未 `grant` 前为空，`grant` 后等于交集。`documents` 随包路径的授予集合与修复前逐项相同。过期时间早于现在 → 空。指纹少一项 → 不重问，那一项不在授予里。卸载后再挂载 → 空。

### CONSENT-3 桌面卡

安装后即将挂载、以及打开一个还没有同意的模块时，走在场确认。卡上是第 2.3 节五项。同意写入 CONSENT-2 的记录；拒绝或超时不写，能力为空。服务模式没有在场连接时同样为空。

验收：测试里的在场通道回答允许 → 下一次读取 `kernel_grants` 等于交集。回答拒绝、或通道不可用 → 保持空，模块状态不是失败（包仍在，只是没有内核能力）。免卡模块不产生挑战。

### CONSENT-4 撤销和能力中心

能力中心用第 2.3 节的人话替换现在的 `events` 这种机器名，并给要卡的模块放「停止授权」。CLI `revoke` 与按钮同一条 daemon 路由。撤销后下一次 `GET /api/v1/components` 的 `kernel_grants` 为空。

验收：撤销前有授予，撤销后为空。免卡的文档模块没有这颗按钮。非宿主视图仍然没有授予明细。

## 4. 请 jason 拍板

分片先按下面的推荐做。三问都是产品选择。

**1. 别人签的模块，同意卡能不能代替「信任团队」？**

现在的门是：macOS 上先把团队加进信任名单，才能装。装上之后今天直接给内核能力。

甲：信任名单不动。没进名单的仍然装不上。同意卡只决定给不给内核能力。本方团队、但不是桌面自带的，也要这张卡。乙：只要是本方团队签名就不弹卡，卡只给别的团队。丙：用户在卡上点同意，就可以装一个还没信任的团队。

推荐甲。丙是用一次点击换掉签名检查。乙会让以后按需装的本方模块不经用户点头就拿到内核能力，和 11-12 那句「只有随桌面装的免确认」不一致。

**2. 卡上的能力能不能一条条取消？**

甲：看清楚每一项，只能全部同意或全部拒绝。模块少要了某一项，我们直接不给，不用再问。乙：用户可以勾掉其中几项，只同意剩下的。

jason 11-18 拍板乙。每项默认勾上，可以勾掉。一项都没勾等同于拒绝。原生在场对话框列出最终要给的能力，点「同意」才落记录。模块少要了某一项，仍然不问，直接按新的交集收回。

**3. 同意默认多久？**

甲：30 天，和现在工具授权的默认一样，最长仍是 90 天。乙：7 天。丙：一直有效，直到撤销，或者它要了新能力。

推荐甲。现成的期限能用，不用再做一个。丙和 ADR-K1-03 的「不许永不过期」冲突；要选丙，得先改那条 ADR。

## 5. FU

- 撤销和过期不追停已经在跑的内核调用。下一道调用才看见。
- 同意不随启用纪元作废。关掉再打开，指纹没变且没过期就沿用。
- 已拍板可逐项勾选（默认全选）。一项都没勾等同于拒绝。渲染进程不能绕过原生在场框写同意。
- attach、MCP 不收进这张卡。
- 不用同意卡补 Linux 没有代码签名的洞，也不做第三方密钥吊销。
- 沙箱那一行不探测进程是否真在沙箱里。
- 同意写入和挂载撞在一起的极端交错，不专门做。没写上就保持空发放。
- OSI-1 未在本工作区核实。它若把名单外的包装进来，按第 2.1 节要卡。
- 同意之后、下次启动之前，已经挂着的进程不会拿到新句柄。GET 立刻按记录显示。
- 声明里重新加回仍在旧指纹里的能力，不重问。
- 桌面用卸载再安装升级第三方模块会删掉未过期的同意，下次重问。指纹没变的原地升级（daemon 扫描）沿用。
- 已经借出的记忆分区要等下次启动才收回。
- 声明变少之后，已经挂着的进程要等下次启动才按新交集收回；GET 立刻按新交集显示。
