# 上下文准入（Context Admission）

> 什么可以进入 agent 的上下文。规则与形状见 [`README.md`](README.md)。
> 立于 2026-09-02。来源：`vendor/Proma` 的指令解析边界（`reference-notes/proma.md` §4）+
> `vendor/LongHorizon-Harness` 的证据边界（`reference-notes/longhorizon-harness.md` §3）。

**读这一节前先知道一件事**：本文件里的**每一条今天都成立**，
因为 Agent24 目前**根本没有从文件系统发现指令文件的代码路径**（核实见 §0）。

**这不是「我们已经做对了」，是「这条路还没修，所以现在划线最便宜」。**
M4 Cos72 workspace 会引入项目根与工作区的概念，那时一定会有人想加「从项目目录读 `AGENTS.md`」——
本文件存在的意义，就是让那个 PR 在写第一行代码之前就撞上这些条款。

## 0. 核实记录（2026-09-02）

在把这些写成法律之前先查了现状，避免把一条不存在的缺陷写成已知问题：

| 查了什么 | 结果 |
|---|---|
| 全仓是否有指令文件发现路径（`CLAUDE.md` / `AGENTS.md` / `instructions.md`） | **没有。** 仅 `knowledge.rs` 与 `0008_instructions.sql` 的注释里把 `CLAUDE.md` 当**语义类比**提及 |
| MD-7 `KnowledgeBase`（层级指令层）是否读文件系统 | **不读。** `agent24-memory/src/knowledge.rs` 零 `std::fs` / `Path` 引用 —— 它是纯 DB 的：priority 升序合并、触发注入、审核门控 inbox。「层级 markdown」指的是**优先级模型**，不是扫目录 |
| 已有的目录读取（MD-2c 对账 `observe_dir`）是否跟随符号链接 | **不跟随。** `symlink_metadata` + `is_symlink()` → 拒绝，且有测试 `observe_dir_hashes_files_and_refuses_symlinks` |

所以下面的 L-CTX-1 / 2 / 3 **今天由「不存在那条代码路径」保证**，
这是最强也最脆的一种保证 —— 加一个功能就没了。

## 法律

### L-CTX-1 · 指令文件只在已授权的根内解析

**系统在发现指令文件（`AGENTS.md`、`CLAUDE.md` 或任何等价物）时，
MUST 只在用户显式授权的根目录及其子树内查找；
MUST NOT 向上遍历祖先目录、MUST NOT 使用进程 cwd、MUST NOT 从任何未经授权的附加目录发现。**

**挡的是什么**：向上走目录找指令文件，等于**任何能在你的祖先目录里放一个文件的人，
都能往你的 agent 上下文里注入指令**。在多用户机器、共享挂载、`/tmp` 下的工作目录、
或者一个被克隆下来的仓库里，这是一条真实的提示词注入路径 —— 而且它是静默的：
用户永远不会知道有一份他没写的指令正在指挥自己的 agent。

`git` 会向上找 `.git` 是安全的，因为它找的是**数据**；
向上找指令文件不安全，因为找到的是**权威**。

**今天靠什么保证**：**没有机制，只有这条法律** —— 因为没有任何代码在做指令文件发现（§0）。
第一个引入该功能的 PR 必须同时提供机制与测试。

---

### L-CTX-2 · 注入上下文的每一份来源都必须可点名

**任何被注入 agent 上下文的指令来源，MUST 记录其规范化路径（canonical path）、
作用子树、以及内容哈希；MUST 有单份与总量的字节上限。**

**挡的是什么**：三件事。
① **审计**——出问题时必须答得出「当时到底注入了什么」，而不是「大概是那几个文件」；
② **符号链接逃逸**——规范化（`realpath`）是发现「授权根内的一个链接指向根外」的唯一办法，
仅靠字符串前缀匹配会被 `root/link → /etc` 骗过；
③ **上下文预算**——没有上限时，一个巨大的指令文件可以把真正的任务挤出上下文窗口，
这既是可用性问题也是**拒绝服务**面。

**今天靠什么保证**：**没有机制，只有这条法律**（同 L-CTX-1，无该功能）。
参考量级：Proma 用 64 KB 单份 / 128 KB 总量。

---

### L-CTX-3 · 兼容性输入不得改写用户的文件

**为向后兼容而读取的指令文件（如遗留的 `CLAUDE.md`），MUST 只作为输入；
MUST NOT 被自动覆盖、合并、重命名或删除。**

**挡的是什么**：「帮你迁移到新格式」是一个非常容易顺手写下、且不可逆的动作。
被改写的是**用户的文件**，不是我们的产物，而它往往在用户自己的 git 仓库里 ——
一次静默改写就是一次别人历史里的脏提交。

**今天靠什么保证**：没有机制，只有这条法律。

---

### L-CTX-4 · 系统自己的运行记录不是任务的完成证据

**当系统需要判断一件工作是否完成时，MUST NOT 把自身产生的运行记录
（提示词、轨迹、角色输出、历史报告、审计日志）当作完成证据。**

**挡的是什么**：**自我确认。** 如果「我写下了我做完了」可以充当「我做完了」的证据，
那么系统的成功率就与它的实际能力脱钩了 —— 它只会越来越擅长写记录。

这条与本仓库反复出现的那个病同源：F1/F8 二十余轮复审抓到的几乎全是**措辞比机制强**。
`vendor/LongHorizon-Harness` 把这件事变成了一条给审计角色的硬规则
（"Harness prompts, trajectories, role outputs, and prior reports are run records,
**not task deliverables or standalone completion evidence**"），
并且**用路径级的 deny 规则让审计角色根本读不到 harness 自己的目录** —— 机械边界，不是提示词请求。

**反向的过度严格同样要挡住**：不得因此要求每个子任务都必须产出一个文件 ——
当一件工作的真实结果本来就是应用状态、面向用户的回复或可独立观察的外部状态时，
那就是它的交付物。

**今天靠什么保证**：**部分成立，且是结构性的** —— agent loop today 没有独立验证环节，
所以也不存在「拿运行记录当证据」的判定点。
但 MD-8 的 `TaskTrace`（工具日志落 `refs/*.md`）与 MD-2 的 `ArtifactStore` 共用同一套内容寻址存储，
**「哪些是任务产物、哪些是运行记录」今天没有一个类型层面的区分。**
这条法律先立，等 FU-24（是否引入独立 Auditor 角色）裁决后再决定要不要给它一个机制。
