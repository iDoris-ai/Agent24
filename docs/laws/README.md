# 架构法律（Architectural Laws）

> 立于 2026-09-02。来源：`vendor/berd/LAWS/` 的形态 + 本仓库 F1/F8 二十余轮复审的教训。

架构法律定义 Agent24 **必须**具备、或**绝不**允许的行为与边界。
它们是**产品与内核做什么**的权威，与当前实现如何组织无关。

本目录中的 **MUST** / **MUST NOT** / **必须** / **不得**，按 [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119) 解释。

---

## 为什么建这个目录

`docs/decision.md`（ADR）记**为什么这么选**，`docs/specs/` 记**怎么做**，
`docs/agent/architecture.md` 的「不可动摇的边界」记**不许什么** —— 最后这一节已经是法律的雏形，
但它混在架构文档里、是散文而非可逐条引用的编号条款，**而且没有闭环**。

F1 与 F8 加起来二十余轮对抗复审，抓到的几乎全是同一类问题：**措辞比机制强**。
那正是「法律与实现不一致」的另一种说法 —— 而今天它只能靠复审者的人肉记忆去发现。

**这个目录补的就是那条闭环。**

## 法律的规则

- 法律**必须**描述**可观察**的行为或边界，**不得**描述实现细节。
- 法律**必须**表达**刻意确立的、持久的**不变量；「已定 + 可观察」**不足以**成为法律，
  必须是我们明确选择把它封为长期约束。
- 每条法律**必须**只表达一个要求。
- 每条法律**必须**编号，且编号**永不复用** —— 废止的法律标 `【已废止】`并写明被什么取代，不删行。
- 法律**必须**说明**它挡的是什么**。一条读者不知道在防什么的法律，会在第一次不方便时被绕过。
- **代码与测试必须符合法律。**

## 与 PR 的闭环（这一条才是目录的价值）

**改变可观察行为的 PR，必须指出它影响了哪几条法律，并让代码、测试、法律三者一致。**

三种合法结局，缺一不可：

| 情况 | 该做什么 |
|---|---|
| PR 符合现有法律 | 在 PR 描述里点名，说明凭什么符合（最好指向测试） |
| PR 与现有法律冲突 | **改 PR**，不是改法律 —— 除非下一行 |
| 法律本身错了 | **单独一个 PR 改法律**，写清为什么，再回来改代码。**不得**在同一个 PR 里既改法律又改行为 |

最后一条是刻意的：把「我们决定改变边界」和「我实现了一个功能」放进同一次评审，
评审者只会看后者。

## 一条法律的形状

```markdown
### L-<域>-<序号> · 一句话标题

**<MUST / MUST NOT 的正式表述，一句话。>**

**挡的是什么**：具体的失败场景。
**今天靠什么保证**：机制 / 测试 / 或者诚实地写「今天没有机制，只有这条法律」。
```

**最后那一栏是本仓库特有的，且必须诚实填写。**
`vendor/LongHorizon-Harness` 在自己的权限模块里写下「剩下的 deny-list 表达的是角色分离，
**不是文件系统或进程沙箱**」—— 那种诚实正是我们复审在追的东西。
一条写着「今天没有机制」的法律**仍然有价值**：它让下一个人知道这里是薄的。
