# K1-6a-G —— 模块工具的内核授予路径

> 状态：设计，2026-10-21。负责人：David。任务：#705 剩余部分的 A 线（DOC-1-06b §4）。
> 依据：ADR-K1-01 §2.2–§2.4；ADR-K1-02 §2.5；ADR-K1-03 §1、§3、§4；ADR-K1-04 §2.1；K1-06a-resource-scope（下称「资源契约」）；APPROVAL L-APPR-7 与 #1123；DOC-1-06b §0、§4（`ab/documenting`）。
> 本文只定对外接口、守卫顺序和安全前提。表结构、函数拆分和界面细节交给实现片，用代码和测试验证。

## 0. 结论

- 补齐生产里缺的授予入口：宿主生成确认卡片 → 用户确认（带资源范围、期限）→ 存成授予记录 → 派发时按记录填 `authorized_resources`。
- 授予入口合入时**默认关闭**，由宿主配置项打开。打开之前要同时满足：K1-6a 与 K1-6b 都验收、B（Documenting 资源校验）合入、#1123 关闭且 L-APPR-7 修订已合入、#1022 遗留的 F1/F3/F6/F7 已修（§2.1），以及 §3 末段列出的各片合入。所以代码可以先合，产品行为不变。
- **两道守卫先于授予入口落地，最晚同一片**：派发时重查远端档位守卫（§2.4），撤销会停掉在途调用（§2.5）。不能先有授予，再补守卫。
- 风险等级「跟随工具声明」会让读类工具在授予后免去逐次审批，实际上就是读类常驻授权。所以这一步除了要等 #1123 关闭且 L-APPR-7 修订合入，还要求宿主能核验模块来源（ADR-K1-03 §4）；做到之前一律 `External`、每次调用都审批（§2.3）。**这意味着在来源核验落地之前，文档工具每次调用都要用户审批，读取和搜索也一样。**

## 2. 契约与安全前提

### 2.1 确认卡片和授予接口

- **摘要只由宿主生成**：用一个函数，从 manifest 的工具声明（`risk`、`output_privacy`、`resource_kinds`、`reversible_draft`）和宿主判定的来源、风险，生成 `ToolPermissionSummary`。启动装配和授予接口用同一个函数，所以授予时存的指纹和派发时算的指纹逐字节相同；不同即 `Stale`，拒绝。模块自报的描述文字不进摘要。
- `GET /api/v1/module-consents/modules/{module}/tools/{tool}/card`：返回卡片，内容是 ADR-K1-03 §1 的四项、可授予的资源种类、摘要指纹、模块版本和制品身份。
- **制品身份**：宿主对模块安装目录（`mount_package` 读取的包目录）递归遍历，不跟随符号链接：常规文件取（路径，长度，SHA-256），符号链接取（路径，`symlink`，链接目标字符串），遇到其他类型的条目即算失败；按相对路径字节序排序，整张列表再取 SHA-256，写成 `sha256:` 加 64 位小写十六进制。宿主在模块每次启动（建立新 generation）时计算，随 generation 保存；卡片、授予和派发都用当前 generation 的值。它只证明「运行的就是当时被确认的那份文件」，不代替来源核验（ADR-K1-03 §4，§5 不做）。算不出来（目录不可读、文件在计算中变化、模块未运行）时 fail closed：卡片不生成，`POST` 返回 409，派发按 `Stale` 拒绝。
- `POST /api/v1/module-consents/modules/{module}/tools/{tool}`，正文 `{decision: "granted"|"denied", fingerprint, module_version, artifact, resources: [...], expires_at}`（`artifact` 是卡片上的制品身份）：
  - `fingerprint`、`module_version` 和制品身份都必须等于宿主当下的值，任一不同就返回 409，不写记录。指纹不含版本（`module_consents.rs:143-150`），只比指纹会让用户对 v1 的确认落到同范围的 v2 上（ADR-K1-03 §1、§4：许可绑定精确版本，同范围更新也要重新核验）。
  - `resources` 每项符合资源契约 §2.1，种类在该工具声明的 `resource_kinds` 内，最多 256 项；否则返回 422，不写记录。
  - `expires_at` 必填，且不晚于当下加宿主上限：上限由宿主配置，默认 30 天，不得超过 90 天；超过上限或缺省都返回 422，不接受「永久」。
  - 收窄、扩大都写新记录（资源契约 §3.2）；扩大必须走这个接口重新确认。
- **与模块生命周期的顺序**（#1022 遗留项，A4 必须先修或同片修）：
  - F7：现状是禁用和停止时撤销（`os_routes.rs:478` 只在 `!enabled` 时、`:964` 在 `stop_now_os` 时调 `invalidate_module_consents`），启用时不撤。授予只能在模块已启用且正在运行时写入，否则 `POST` 返回 409。
  - F3：**启用纪元**。存储为每个模块持久保存一个只增不减的启用纪元，以及上次观察到的启用状态和该模块的条目摘要（`os.json` 中该模块的条目加上它的启用标记，见下）。纪元在以下任一情况前进（取一个新的写入代次，不复用）：经路由或 CLI 启用；daemon 启动或重新加载 `os.json` 时，发现该模块现在是启用的，而上次观察到的是禁用、没有记录、或条目摘要不同；`stop` 之后再启动。授予记录写入当时的纪元，派发时纪元不等于当前值就是 `Stale`。所有写 `os.json` 的地方（路由、CLI、ephemeral daemon）在把模块设为启用时，都先在 `os.json` 旁的 `os-enable-marks.json` 里为该模块写入新的随机启用标记，再写 `os.json`；标记不写进 `os.json` 条目本身，免得改动它的格式。所以经别的进程启用一定会改变条目摘要。路由在写 `os.json` 之前先加纪元，加纪元失败就不写；写完后按新摘要记一次观察，免得下次启动把这次启用当成变化、误判此后的授予为 `Stale`。剩下检测不到的只有一种：daemon 不在运行期间，有人手工关了又开、条目内容最终逐字节不变。这时宿主从未观察到禁用，按「没有变化」处理。
  - F1：CLI 撤销或卸载在存储写失败时必须以非 0 退出，再次执行不能因「没有可删的」就报成功；授予是否仍然有效，以存储里的结果为准。
  - F6：ephemeral（`--ephemeral`）模式的授予存储不跨重启，`POST` 一律返回 403，派发不承认任何授予。它和常驻 daemon 共用 `os.json`，经它启用的模块会在 `os-enable-marks.json` 写入新的启用标记，常驻 daemon 下次加载时据此加纪元（见 F3）。ephemeral daemon 启动时不做观察，因此不承认任何授予。
- 这两个接口和现有的 consent 路由一样走内核认证（`server.rs:1081-1093`），只接受用户身份。Agent、模块和 creative 身份都不能调用（creative 已被拒，`server.rs:3641`）。模型能用的工具里，没有任何一个能到达这两个接口。
- **默认关闭**：宿主配置项（例如 `module_tool_grants.enabled`，默认 `false`）关闭时，`POST` 返回 403，`GET card` 照常（便于界面开发）。这是授予前的机械门；如果 #1123 的修订要求别的机制，由 A4 在打开开关之前实现。打开条件见 §0，打开本身是一次单独的发布决定，不随代码合入。

### 2.2 授予记录、资源集合与引用

- 资源集合存进授予记录（新增列或子表），随记录持久化；存储写失败就不产生授予。读到没有资源集合的旧记录，按空集合处理。
- 制品身份也存进授予记录。派发时的查找除了版本和权限指纹，还要比对当前运行的制品身份；不一致就是 `Stale`，拒绝（ADR-K1-03 §4：同版本换包也要重新核验）。读到没有制品身份的旧记录，按 `Stale` 处理。
- **授予代次**：每次写入授予、拒绝或撤销，都由存储分配一个只增不减、永不复用的代次号（不依赖墙上时钟），和记录一起保存。撤销是否覆盖某次授予按代次比较，不再用 `revoked_at >= decided_at`（`module_consents.rs:564`），避免时钟回拨让撤销失效。
- 资源集合摘要：对去重、按字节序排序后的元素集合做规范编码，再取 SHA-256。
- **`authorization_ref` 改成单个摘要**：`ga1:` 加 SHA-256(授予代次, 权限指纹, 资源集合摘要, 制品身份, `decided_at`, `expires_at`) 的 64 位小写十六进制，共 68 字节，满足审计的长度和字符集要求。原先直接拼接会超过 128 字节。因为含代次号，任何一次替换授予（哪怕范围、时间都相同）都会得到新引用，§2.5 用它判断在途调用是否失效时不会出现 ABA；范围一变，引用也变（资源契约 §5 第 8 条）。
- 审计 `resource_ref` 记 `rs:<个数>:<资源集合摘要>`，不记具体 ID（资源契约 §2.4）。
- ConsentGate 放行时带出记录里的资源集合；适配层按记录原样填进 `authorized_resources`。派发前再校验一遍格式和上限，不合规就拒绝这次调用（`permission_denied`），不截断。

### 2.3 风险等级

- `HostRiskLevel` 和 `ConsentSource` 不变：在宿主能核验来源（ADR-K1-03 §4，签名或来源校验）之前，一律按 `ManualInstall` + `High` 处理，不因自报第一方而降级。
- `RiskClass` 跟随声明的 `risk`（DOC-1-06b §4 第 2 条）要同时满足三个条件：该工具有当前有效的授予；#1123 关闭且 L-APPR-7 修订已合入；宿主已核验模块来源为第一方，并核验了该工具的实际动作（ADR-K1-03 §1、§4：自报风险不能降低宿主定级，确认后免逐次审批只给第一方）。任何一项做不到，或宿主无法判定，都保持 `External`，每次调用都审批。`ConsentGate` 是否要求逐次审批由 `RiskClass` 决定（`consent_gate.rs:372`；可逆草稿例外另需第一方来源），所以这三个条件必须在设定 `RiskClass` 时检查，不能交给来源或 `HostRiskLevel`。
- 跟随之后，读类工具免去逐次审批；写和执行类仍按 L-APPR-5 逐次审批，包括其中的第一方可逆草稿例外。A7 接线时以合入时 main 上的 L-APPR-5 为准，满足其中的接线闸门（来源核验、External 负例、按次核验）后才接。宿主可以收紧，不能放宽。
- Guardian 不能代替逐次审批，也不能创建、扩大或替换授予；对模块工具的逐次审批一律交给人（现有 `module_per_call` 分支保持）。
- 逐次审批的卡片绑定当时的 `authorization_ref`；批准之后、派发之前引用变了，就作废这次批准，重新询问。

### 2.4 派发时重查远端档位守卫

- 守卫放在 `ModuleTool::call_with_invocation` 里，先于授权查询，所以 `dispatch` 和 `execute_preapproved` 两条路径都会经过。按名字直接调用被守卫挡下的工具，返回 `permission_denied`，并写审计。
- 守卫每次读当前的档位配置，不用启动时的快照（`server.rs:1618`）。读不到时按「有远端档位」处理。
- 撤掉守卫的条件仍按 ADR-K1-02 §2.5，本文不改。

### 2.5 撤销、到期与在途调用

- 每个在途调用记下它开始时用的 `authorization_ref`。**凡是让这个引用不再是当前有效引用的事件**，都要取消这次调用：撤销（工具级或整个模块）、到期、收窄或扩大（换发新记录）、改为拒绝。授予和拒绝的写入也要发通知，不能只有撤销发（现在 `grant`/`deny` 只做 upsert，`module_consents.rs:505,518`）。
- 到期不依赖定时器存活：每次调用的期限取 `min(timeout, expires_at)`。
- 订阅落后（`Lagged`）时，不知道丢了哪些事件，就对所有在途调用按存储重新查一次授权，引用不再有效的全部取消；这次重查失败时，取消全部在途调用。
- 取消后的终态：确认在派发给模块之前就停下的，记 `cancelled`，模型看到 `permission_denied`；可能已经派发、又没有可信终态的，记 `result_unknown`，并禁止自动重试（ADR-K1-01 §2.5）。
- 调用返回后、把结果交给模型之前，核对这次调用的 `authorization_ref` 仍是当前有效的引用（完整查询，不只看撤销）；不是就丢弃结果，返回 `permission_denied`。
- **通知模块**：撤销或到期时，内核向模块发 `POST /api/v1/<module>/_a24/authorization/revoked`，正文 `{operation, revoked_at}`，其中 `operation` 为 `"*"` 表示整个模块。模块收到后，停止由该操作发起、尚未结束的后台工作（资源契约 §3.5），到达安全点再返回 2xx。要停的是收到通知之前已接受的该操作全部调用的工作，包括已排队、尚未开始的（按调用归属，不按开始时间或墙钟）。通知与重新授予可能交错，内核不保证通知先于重新授予送达，所以新授予下刚被接受的调用也可能被一并停掉：这是偏保守的取舍，宁可多停，不可漏停。内核等这个应答，或者等到期限，才把撤销记为完成；失败或超时时，在审计和授权列表里标注「停止未确认」，不报告成功（ADR-K1-03 §3）。
- 模块后台工作没有豁免：文本层生成同样属于已接受调用的延续（资源契约 §3.5），收到通知后停在安全点。经内核回调访问模型等出口的后台工作，另外还由内核出口门按当前授权复验（K1-6b）。

### 2.6 manifest 与兼容

- `RawToolDeclaration` 加可选字段 `resource_kinds`（资源契约 §2.3）。
- `DAEMON_PROTOCOL_VERSION` 在 A2 合入时目标分支的值上加 1（`ab/kernel` 现在是 1，main 已是 2，同步 main 之后应为 3），带 `resource_kinds` 或实现了撤销通知端点的模块，其 manifest 的 `min_daemon_protocol` 取这个新号。低一号的内核加载这样的 manifest 时，在版本检查处明确拒绝，而不是在 `deny_unknown_fields` 处报未知字段。
- 授予只对声明了新协议号的模块开放：manifest 的 `min_daemon_protocol` 低于新号的模块，视为不支持撤销通知，卡片不生成、`POST` 返回 409，避免出现永远「停止未确认」的授予。

### 2.7 模型可见的函数名

- 发给 provider 的函数名把 `.` 换成 `__`（`documents.list` → `documents__list`），回放和解析工具调用时按同一规则还原。内部全名、审计、授予记录仍用 `module.op`。生成的名字若和已注册的工具冲突，或超过 64 字符，注册时报错。

## 4. 反例测试（实现片先写，并证明修复前失败）

1. 有授予、有远端档位：按名字直接 `dispatch` 文档工具 → 被拒，有审计（A1）。
2. 运行中加入远端档位：下一次调用被拒（A1）。
3. 在途调用中撤销 → 派发前停下的记 `cancelled`、模型看到 `permission_denied`；已派发未终态的记 `result_unknown`、不自动重试；新调用被拒（A1）。
3a. 在途调用中收窄或扩大范围、改为拒绝、撤销整个模块、同一毫秒内同范围「拒绝再授予」→ 同第 3 条（A1、A3）。
3b. 订阅落后（`Lagged`）→ 引用失效的在途调用被取消；重查本身失败 → 全部在途调用被取消（A1）。
4. 到期时刻在调用中间到达 → 同第 3 条（A1）。
5. 调用返回后、结果交出前被撤销或收窄 → 结果被丢弃（A1）。
6. 卡片指纹、模块版本或制品身份和当下不一致 → 409，无记录；授予后同版本换包（按 §2.1 的定义改动安装目录里任一文件后重启模块）→ 派发得到 `Stale`；制品身份算不出 → 卡片不生成、`POST` 409；期限超过宿主上限 → 422；资源越界、种类未声明、257 项、无期限 → 422，无记录（A4）。
7. 开关关闭 → `POST` 返回 403，无记录（A4）。
8. Agent、模块、creative 身份调用授予接口 → 被拒（A4）。
9. 授予不带资源 → 派发的列表为空；范围变化 → `authorization_ref` 变化；审计里没有资源 ID（A3）。
10. 存的资源集合被改坏（格式错误、超过 256 项）→ 派发拒绝，不截断（A3）。
11. 撤销后模块通知失败或超时 → 撤销状态标注「停止未确认」，不报成功（A5）。
12. 声明 `read` 的工具，在 #1123 关闭（L-APPR-7 修订合入）且来源核验之前仍逐次审批；手动安装的模块自报 `read` 也逐次审批；来源已核验、工具动作未核验时仍逐次审批（A7）。
13. 撤销后模块的文本层生成等后台工作停在安全点（A5 与 Documenting 通知接收片）。
14. 以下每种情况，旧授予都不生效：包不变、离线改 `os.json` 中该模块的条目再启动 daemon；包不变、经 ephemeral daemon 关闭再启用；`stop` 后重新启用；经路由禁用后再启用。另外，模块未运行时 `POST` → 409；ephemeral 模式 `POST` → 403；宿主配置的期限上限超过 90 天时启动报错（A4）。
15. 存储写坏时第二次 `os uninstall` / 撤销 → 非 0 退出（A4）。
16. 时钟回拨后「先授予、后撤销」→ 撤销仍然生效（A3）。
17. 逐次审批批准后、派发前引用变了 → 重新询问（A1）。
