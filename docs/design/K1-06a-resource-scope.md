# K1-6a-R —— 模块工具的资源范围（`authorized_resources`）契约

> 状态：设计，2026-10-21。负责人：David。任务：#705 剩余部分的前置（内核授予路径 A 与 Documenting 资源校验 B 共用的接口）。
> 依据：ADR-K1-01 §2.3、§5 第 3/9 条；ADR-K1-03 §1、§3；ADR-K1-02 §2.2、§2.5；ADR-KB-01「必须冻结的约定」；DOC-1-06b §4 第 5 条（`ab/documenting`）。
> 本文只定对外行为和安全前提。存储结构、界面、错误码映射细节、分页实现交给各自的实现片。

## 0. 结论

- 冻结 `authorized_resources` 每个元素的格式和整份列表的语义。内核授予路径（A，`ab/kernel`）按本文填，模块（B，先做 Documenting，`ab/documenting`）按本文校验。本文同时冻结 manifest 里可授予种类的声明（§2.3）和 Documenting 的种类与 ID 写法（§4.3），所以本文合入后 A、B 并行：B 的校验在模块里按本文写死 `doc`，不读 manifest；manifest 真正写上声明是 DOC-1-06b 片 E，片 E 依赖 A 的 manifest 解析和 B 都合入。
- 线上类型不变：`ModuleToolContext.authorized_resources: Vec<String>`（`agent24-tools/src/lib.rs:579`）。不修改 ADR-K1-01，本文是它 §2.3「本次已授权的资源范围」的细化。
- 首版只授予**精确的资源 ID**，不支持通配。这和 DOC-1 的「显式文档」范围一致，也满足 APPROVAL L-APPR「高风险不取得宽泛授权、常驻授权按确切目标收窄」（生产里模块工具一律按 `ManualInstall` + `High` 处理，`agent24d/src/server.rs:1576-1604`）。

## 2. 契约

### 2.1 元素格式

- 每个元素是 `<kind>:<id>`。`kind` 匹配 `[a-z][a-z0-9_]{0,31}`；`id` 匹配 `[A-Za-z0-9_-]{1,128}`；以第一个 `:` 切分。区分大小写，按整串精确比较。
- 元素只属于本次调用的 `context.module_id`，不带模块前缀。内核不得把别的模块的资源放进本次列表。
- 首版没有通配：`*`、前缀匹配、范围、空 `id` 都不是合法元素。以后要加，另出设计，并按 ADR-K1-03 §1 作为扩权重新同意。
- 每次调用最多 256 个元素。超出时内核在派发前拒绝，不截断。

### 2.2 列表的语义

- **空列表表示没有任何资源权限**，不是「不限」。任何访问资源的操作都拒绝；列表类操作返回空结果。
- 列表不是「非空才检查」：每次调用、每个资源参数都按本次列表检查，列表为空时检查照样执行。
- 模块收到的上下文缺少这个字段，按空列表处理。字段存在但形状不对（不是数组、元素不是字符串、元素不合 2.1、`kind` 不是模块声明的可授予种类、超过 256 个）：整次调用返回 `permission_denied`，`retryable:false`，不读存储。这是宿主侧的错误，不当成某个资源不存在。

### 2.3 根资源与派生资源

- 内核只授予模块声明为**可授予**的根种类。声明放在 manifest 每个工具的声明里，可选字段 `resource_kinds: [<kind>, …]`，每项符合 2.1 的 `kind` 语法、不重复，否则整份 manifest 不合法（与 `tools` 其他字段一致：取值由 `validate_tools` 校验，`agent24-domain/src/tool.rs:235`；未知字段由 `:150` 的 `deny_unknown_fields` 拒绝）。缺省或空列表表示这个工具的授予不带任何资源，派发的列表恒为空。旧内核不认这个字段、会拒绝整份 manifest，所以带这个字段的 manifest 只能配合含 A 解析片的内核发布。模块的声明只用于生成权限摘要和界面；授予哪些具体 ID 由宿主按用户确认决定（ADR-K1-03 §1），manifest 没有声明的种类一律不授予。
- 派生资源（模块内部生成、归属于某个根资源的对象，例如抽取任务和抽取结果归属于文档）不出现在列表里。模块按自己的存储把派生 ID 追溯到根资源；根在列表里才可访问。追溯不到（孤儿、数据损坏）就拒绝。
- 在一个根资源上创建派生资源（例如对文档提交抽取），要求这个根在列表里。新建根资源的操作（上传、导入）首版不作为模块工具暴露，本文不定义它的范围规则。

### 2.4 拒绝时不泄露存在性

- 资源在列表外，和资源不存在，返回**相同**的结果：同一个错误码，同样的 `retryable` 和 `details`，不能从响应区分两者。用模块自己的「不存在」码（Documenting 是 `not_found`）。
- 校验在读取任何内容之前做。派生资源只读到追溯所需的归属字段为止，追溯失败或根不在列表里，与不存在同样处理。
- 列表、搜索、分页类操作只返回列表内的条目。条目数、总数、游标、`next_cursor` 都不能反映列表外的条目。一个游标拿到另一份范围下使用，也只能翻出新范围内的条目。
- 错误 `details` 和日志里不写列表外的 ID。

### 2.5 每次调用独立

- 模块只用本次 `context` 里的列表。不跨调用、跨会话、跨 run 缓存或合并范围，不从 `tool_call_id`、`session_id`、模块名推导范围（ADR-K1-01 §2.3）。
- 参数里的 ID、文档正文里出现的 ID、模型或文档提供的 `authorized_resources` 都只是待校验的输入，不能扩大范围。只读宿主注入的 `context`。

## 3. 内核侧前提（A 必须满足）

1. 列表只从当前有效的授予记录生成，不从模型参数、模块响应或会话文本生成。
2. 资源范围是授予记录的一部分，并进入范围指纹，因此也进入 `authorization_ref`：范围变了，旧授予失效，审计能对上调用当时的范围。进入指纹的是去重、按字节序排序后的元素集合，编码要能无歧义地还原出集合，不能拼进现有的自由文本字段。现在的指纹不含资源（§1），A 要补上。收窄和扩大都换发新的授予记录，旧记录不再被派发使用；扩大后的新记录在重新同意之前也不派发（第 4 条）。
3. 授予了工具但没有选资源是合法状态，结果是这个工具对任何资源都拒绝。不能把「没选」填成通配或「全部」。
4. 扩大范围按 ADR-K1-03 §1 重新同意，未同意前不得用新范围调用。收窄和撤销对新调用立即生效；对排队和在途调用按 ADR-K1-03 §3 处理。
5. 工具调用返回之后，模块因这次调用在后台继续的工作（Documenting 的抽取任务、文本层生成）算这次调用的延续，属于 ADR-K1-03 §3 的「已接受的调用」。§2.5 只规定模块不得自行扩大范围，不排除宿主另行通知撤销。撤销怎样送达模块、模块在哪些点停，由 K1-6a.3（A）和 B 的设计各自写明并验收；后台工作经内核回调访问模型等出口时，由内核出口门按当前授权复验（ADR-K1-02 §2.2、§2.4）。两者都交付前按第 6 条不授予。
6. 远端档位守卫的派发重查不晚于授予落地（DOC-1-06b §0）；K1-6a 与 K1-6b 都验收、且 B 合入之前，不为文档工具产生授予。

## 4. 模块侧前提（B 必须满足）

1. 校验放在工具入口统一执行，不靠每个操作自己记得做。新增操作如果没有写明资源参数和追溯规则，默认拒绝。
2. B 合入之前，模块不能在 manifest 里声明工具（DOC-1-06b 片 E 依赖 B）。
3. Documenting 唯一的根种类是 `doc`，`id` 是存储里完整的文档 ID（含 `doc_` 前缀，`agent24-documents/src/id.rs:1`），例如 `doc:doc_01K74Z3QJ8V5N2W9RTX6YB4MCD`。七个工具都声明 `resource_kinds: [doc]`（片 E）。任务和抽取结果是派生，不可授予。每个操作的检查点、列表和搜索的过滤、片 1 现有测试的调整（包括 `tools.rs:698` 不合格式的 `"doc_01"`）写进 B 的设计。
4. REST 和 UI 路径不走本契约。UI 与 Agent 共用一个业务授权权威是 ADR-K1-04 §2.4 的另一项工作，B 不改 REST 行为。

## 5. 反例测试（实现片先写，并证明修复前失败）

1. 空列表：每个访问资源的操作都拒绝，列表类操作返回空。
2. 列表是 `[doc:A]`：请求存在的 B 和不存在的 C，两个响应除请求 ID 外逐字段相同。
3. 归属于 B 的派生资源（任务、抽取结果），在 `[doc:A]` 下与不存在相同。
4. 非法元素：`doc:*`、`doc:`、`Doc:A`、未声明的种类、非字符串元素、257 个元素 → `permission_denied`，存储没有被读。
5. 列表和搜索的条目、计数、游标不含列表外条目；`[doc:A, doc:B]` 下拿到的游标在 `[doc:A]` 下只翻出 A 的条目。
6. `arguments` 里夹带 `authorized_resources` 或 `context` 字段：被忽略或按参数校验失败，不扩大范围。
7. 上一次调用范围大、下一次范围小：下一次只按小范围。
8. （A）授予时没选资源 → 派发的列表为空；扩大范围但未重新同意 → 新范围的调用被拒；范围变化后 `authorization_ref` 变化。
