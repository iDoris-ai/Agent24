## 0. 问题

**思考模型在 Ollama 上带 schema 抽取时，会「想对写错」。**

- 文档模块的每次抽取调用都带 `response_format: json_schema`（`extract/prompt.rs:84` 的 `answer_format`），不声明 `complexity`（`extract/run.rs:134`）。
- 内核只在模块**显式**传 `complexity: "simple"` 时设 `disable_thinking`（`agent24d/src/model_callback.rs:172`）；就算设了，也只对 oMLX 发 `chat_template_kwargs`，对 Ollama 什么都不发（`agent24-models/src/lib.rs:783`，`router.rs:346` 构造 ollama 时 `allow_ctk = false`）。
- Ollama 上的思考模型（qwen3.x 等）默认就会思考，所以今天文档模块在这类模型上，**一定是「先思考、再按 schema 输出」**。

Ollama 0.40.4 上这个组合会出错。s01-01 第 4 个窗口（第 27–33 页，全是收费目录）：

| 同一个请求原样重放 | 20 个字段的回答 |
|---|---|
| 思考开 + schema（今天的做法） | 20 个 `present`，全错。思考过程明明写着「这几页都没有，全部 missing」 |
| 关思考，保留 schema | 19 个 `missing`、1 个 `present`，基本正确 |
| 保留思考，去掉 schema | 20 个 `missing`，正确 |

原生 `/api/chat` 也一样，问题不在 OpenAI 兼容层。

上游有一个**可能相关**的未修问题：Ollama 自 0.34.4 起，对思考模型把「思考 + 答案」当作一个整体语法来约束；模型不经思考直接作答时，schema 会被跳过（ollama/ollama#18774，修复 PR #18783 尚未合并）。我们观察到的现象与它不同：模型确实思考了，输出却写错，所以不能断定是同一个问题，也就不能指望升级 Ollama 解决，要我们自己避开这个组合（另有 ollama/ollama#15260 的线索，未核实）。关掉思考后 schema 照常生效，这一点只在 `qwen3.8:27b`、`qwen2.5:7b` 上核实过：`qwen3.8:27b` 见上表第二行和 §2.1 的 A 组，都是「关思考 + schema」，回答全部通过模块自己的 `parse`；不会思考的 `qwen2.5:7b` 见 §4（带 `"none"` 照常作答，schema 照常生效）。

**为什么现在要定**：本机默认的 `qwen2.5:7b` 不会思考，今天不受影响；但抽取质量的下一步是换更大或会思考的模型（7B 必答 43/115，`qwen3.8:27b` 能到 82–84，见 §2）。只要用户在 Ollama 上换成思考模型，就会撞到这个问题。

## 1. 目标

1. 思考模型在 Ollama 上抽取，不再出现「想对写错」。
2. 尽量保住思考带来的收益：在 S01 上，思考比不思考多答对 7–9 个必答字段（§2）。
3. 不会思考的模型（本机默认 `qwen2.5:7b`）必答正确和严重错误不变差（§2.2：实测这两项反而变好；背景正确少 1、待复核多 5、耗时多约 40%）。
4. 线上接口不变：模块不必知道后端是什么、模型会不会思考。

### 2.2 不会思考的模型（本机 M4，`qwen2.5:7b`）

- 材料：`runs/2026-10-16-s01-qwen3.8-27b-module-two-pass/`（`comparison-7b.md`、`7b-r4-*`）。

所以在 Ollama 上，C 不用区分模型会不会思考。oMLX 上没测过（§4、R-g）。

### 2.4 为什么不选 B

- 要在内核的通用 OpenAI 兼容 provider 里加 Ollama 专属的两遍逻辑和一个 JSON Schema 校验器（内核今天不校验 schema），并处理两遍共用 ME4-S2a 的进展计时与截止时间。
- 「答案合不合格」模块自己最清楚：`prompt::parse`（`extract/prompt.rs:308`）已经逐字段校验，还会区分「截断」和「格式不对」，内核只能按 schema 判。
- C 的效果与 C+ 相当，B 能做到的 C 都做到了，内核却要多背一套逻辑。

## 3. 建议：A + C

- **内核（A 的那一处）**：Ollama provider 遵守 `disable_thinking`，发 `reasoning_effort: "none"`（§4）。
- **文档模块（C）**：第一遍自由作答；不合格时，第二遍显式传 `complexity: "simple"` 并带 schema，也就是 A 的调用（§5）。

这样：
- 思考模型拿到 C 的收益（S01 82/115；今天 71，加分段提示 75）；第一遍写不完的调用，退回到 A 的质量。
- 不会思考的本机默认模型也受益（43 → 51/115，严重错误 29 → 19），代价是耗时多约 40%（§2.2）。

**新模块装在老内核上**：老内核不对 Ollama 关思考，第二遍会「思考 + schema」，也就是今天的做法。所以这种组合不会比今天差，不需要升协议版本（对比 ME4-S2b §4，那次老内核会拒绝新字段）。

## 4. 内核：Ollama provider 遵守 `disable_thinking`

- `OpenAiCompatProvider` 加一个按实例开启的能力，和 `supports_chat_template_kwargs` 同一种做法（`lib.rs:244`、`:285`）：`supports_reasoning_effort()`。
  - 只有 `router.rs` 构造的 `ollama` provider，而且只在它判定为本地（loopback）时打开；remote 和 oMLX 都不开。
  - 开了以后，`req.disable_thinking` 为真时，请求体写入 `"reasoning_effort": "none"`；为假时不写，请求体与今天逐字节相同。
  - 能力判定写成纯函数（例如按 tier 返回 ollama 的能力），J3 直接测它：`from_env` 把 provider 包成 `Arc<dyn ModelProvider>` 后，测试读不到能力位。
- **400 后去掉关思考的字段重发一次**：请求带了 `reasoning_effort` 或 `chat_template_kwargs` 而回 400 时，provider 去掉这个字段，把同一请求重发一次，记 warn；重发仍是 400 就照常报 `Rejected`。这样某个 Ollama 版本或模型不认 `"none"`，或者 `OMLX_URL` 指向的本地服务不认 `chat_template_kwargs`（`router.rs:303-311` 的 Review H2 说过这种可能）时，所有显式传 `complexity: "simple"` 的调用方（文档模块的第二遍、AgentEar）都退回今天的行为，而不是失败（R-f）。真正的 400（例如输入太长）只多一次被拒的往返。
- **为什么是 `reasoning_effort: "none"`**：它是 OpenAI 兼容接口的字段，Ollama 的 `/v1/chat/completions` 把它映射为关思考。2026-10-16 在本机 Ollama 0.40.4 上核实：
  - 不会思考的 `qwen2.5:7b`：带 `"none"` 照常作答，`json_schema` 约束照常生效；
  - 同一个模型带 `"high"` 会被 400 拒绝（「does not support thinking」）。**所以只发 `"none"`，永远不发要求思考的值**；
  - 思考模型（`qwen3.8:27b`，Modal）带 `"none"` 不再思考：§2.1 的 A 那一组就是这样跑的。
- **流式**：今天模块调用都走流式（ME4-S2a）。思考的增量（`delta.reasoning`）也是 `data:` 事件，照常推动计时器；内核只收集 `content`，思考文本不进回答，这一点不变。
- **影响到的其他调用方**：只有显式传 `complexity: "simple"` 的模块会设 `disable_thinking`。据 `model_callback.rs` 的注释，这个开关（ME4-S2-thinking）是为 AgentEar 加的：语音场景里 Qwen3 会把整段思考念出来。这类调用在 oMLX 上已经关思考，在 Ollama 上今天仍会思考；改后在 Ollama 上也关，这正是 `complexity: "simple"` 原本的意思。400 后重发也会改变 AgentEar 在 oMLX 上的行为：`OMLX_URL` 指向的本地服务不认 `chat_template_kwargs` 时，今天这类调用直接失败；改后去掉该字段重发，能作答，但模型开着思考，可能把思考念出来。David 定（2026-10-17）：保留重发，能作答好过失败。两处都在 PR 里知会 jason。
- 路由不变：`complexity` 缺省时本来就按 `Simple` 选路（`model_callback.rs` 的 `into_request`），显式传 `"simple"` 只多了关思考这一个效果。
- **oMLX**：`from_env` 先放 oMLX（`router.rs:339-346`），两者都在本地时先试 oMLX。文档模块在 oMLX 上的第二遍会经 `chat_template_kwargs` 关思考（已有行为），第一遍自由作答。oMLX 上的 Qwen3 可能把思考写进正文（AgentEar 就把整段 `<think>` 念了出来，`model_callback.rs:193-196`），所以 §5.1 第 2 步会先去掉开头的 `<think>…</think>`。S01 从没在 oMLX 上跑过，今天的做法也没有，所以这条路径的效果未知（R-g）。

## 5. 文档模块：两遍

### 5.1 一次调用的流程（改 `extract/run.rs` 的 `answer`）

今天的规则（`run.rs:233-266`）：截断就把字段拆半，不占重试；完整 JSON 但格式不对，同一个带 schema 的请求再问一次，再不对就失败。改后：

1. **第一遍**：请求同今天，但 `response_format: None`、`complexity: None`；系统指令后追加「答案的形状」一段（§5.2）。
2. 读回答（两遍都这样读）：
   - 先看截断：`CompleteResult.usage.completion_tokens` 达到请求的 `max_tokens`，就算截断，包括思考写满、正文为空。不看正文是否碰巧完整，与转发器见到 `length` 就丢弃一致；
   - 再去掉正文的包装（第 2 片实现时按评审改定，详见 §2.3）：先 strip；开头的 `<think>…</think>`（§4 的 oMLX），只有开头的 `<think>` 没闭合时算截断；第一遍里去掉开头思考后整段不能直接解析为 JSON 时，最后一个 `</think>` 之前都是思考（模板自己开了思考，正文里只剩结尾），只取它之后的部分，后面不是答案就按格式不对落到第二遍；开头的 Markdown 代码块围栏（```` ```json ```` 或 ```` ``` ````），答案取到它的 JSON 结束为止，收尾围栏和后面的文字丢掉；
   - 交给 `prompt::parse`：通过就用这个答案，结束；`Truncated`（正文写到一半）也算截断；其余是格式不对。没写满（`completion_tokens` 大于 0、小于上限）却什么也没写（例如 `</think>` 之后为空）算格式不对，不算截断；`usage` 缺失（为 0）时仍由 `parse` 判截断（第 2 片评审补充）；
   - 第一遍截断或格式不对：这一批字段**改用第二遍**，记下落下来的原因。
3. **第二遍**就是今天的请求（窗口不是全文时带分段提示，§5.3）加 `complexity: Some(Simple)`，即带 schema、关思考：
   - 格式不对：同一请求再问一次，再不对就失败（今天的规则）；
   - 截断：拆半（今天的规则）。两半从哪一遍开始，看这批当初为什么落到第二遍：
     - 第一遍**截断**：两半都直接用第二遍。思考的长度与字段多少关系不大，让两半重走第一遍，很可能又写满，调用次数会成倍增加；
     - 第一遍**格式不对**（写完了但不合格）：两半从第一遍重新开始。字段少了，第一遍可能答对；§2.2 的 7B 组跑到的正是这种情形，拆出的后一半就用了第一遍的答案（§2.3）；
     - 第一遍**被拒**（第 4 步）：两半都直接用第二遍，同一窗口的第一遍还会被拒；
   - 被拒（`request_rejected`），也看这批为什么落到第二遍：
     - 第一遍被接受过（截断或格式不对）：**不拆窗**，job 以 `engine_unavailable` 失败，消息写明「第二遍请求被拒」，不断言原因。第一遍的提示更长且已被接受，所以这里的拒绝不会是输入太长：可能是第二遍独有的 `response_format` 被拒（关思考的字段已由内核去掉重发过，§4），也可能是 408、409 这类偶发拒绝，模块看不到状态码（`model_callback.rs:619` 都映射为 `request_rejected`）。今天的「被拒就拆窗」此时只会多跑几轮第一遍，最后仍然失败，或者用拆小后的窗口悄悄得出不同的结果；
     - 第一遍也被拒：这才可能是输入太长，按今天的规则拆窗，拆出的两个窗口各从第一遍开始。但这一批在同一窗口的第二遍已被接受过（格式不对后的重问，或截断后拆出的两半；按批算，不跨批）再被拒，同样不会是输入太长，按上一条失败、不拆窗（第 2 片评审补充）；
   - 所以每一批字段（包括拆出的每一半、每个窗口）最多比今天多一次调用，就是它的第一遍。
4. 从第一遍落到第二遍的，只有「答案不合格」和「被拒」两种。`call` 里的等待和重试（忙、限流、超时重试一次、`no_provider` 等待，`run.rs:121-186`）对两遍一样适用，第一遍里出了这些错，按今天的方式处理，不改用第二遍：
   - 例如第一遍连续两次超时，job 照今天以 `engine_unavailable` 失败；
   - 第一遍被拒：先在同一窗口改用第二遍。第二遍的提示少一段答案形状，接近模型上下文上限的窗口可能装得下，这样不会比今天多出失败，结果也与今天整窗作答一致；第二遍也被拒，按第 3 步拆窗。
5. 每次调用记一条 info 日志：窗口、字段数、第几遍、`completion_tokens` 与 `max_tokens`、结果（采用、截断、格式不对、被拒，或 `call` 的其他错误），以及落到第二遍的原因。抽取记录不变，所以事后从记录看不出某个值来自哪一遍，要看日志。

### 5.2 第一遍的提示

没有 schema 约束时，模型要从提示里知道答案的形状。系统指令后追加一段英文，内容与实验转发器的 `with_shape` 相同：

- 写出「每个字段答案」的 JSON Schema。各字段相同，所以只写一份；
- 给两个示例：`{"missing": {"reason": "not_in_document"}}` 和一个 `present`；
- 写明「状态是属性名，不要把 missing 写成值」。2026-10-15 的第一版两遍法（带思考的 C+ 形态）没有给出答案形状，第二遍照抄了思考里「status: missing」的说法，出了几个「值是字面上的 missing」的严重错误（NOTES.md 一处记 4 个、一处记 6 个，`two-pass/report.md` 的必答严重错误共 7 个）；加上答案形状和这一句后，这类错误全部消失。
