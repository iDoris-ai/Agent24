## 0. 问题

**思考模型在 Ollama 上带 schema 抽取时，会「想对写错」。**

- 文档模块的每次抽取调用都带 `response_format: json_schema`（`extract/prompt.rs:84` 的 `answer_format`），不声明 `complexity`（`extract/run.rs:134`）。
- 内核只在模块**显式**传 `complexity: "simple"` 时设 `disable_thinking`（`agent24d/src/model_callback.rs:172`）；就算设了，也只对 oMLX 发 `chat_template_kwargs`，对 Ollama 什么都不发（`agent24-models/src/lib.rs:783`，`router.rs:346` 构造 ollama 时 `allow_ctk = false`）。
- Ollama 上的思考模型（qwen3.x 等）默认就会思考，所以今天文档模块在这类模型上，**一定是「先思考、再按 schema 输出」**。

Ollama 0.40.4 上这个组合会出错。s01-01 第 4 个窗口（第 27–33 页，全是收费目录）：

| 同一个请求原样重放 | 20 个字段的回答 |
|---|---|
| 思考开 + schema（今天的做法） | 20 个 `present`，全错。思考过程明明写着「这几页都没有，全部 missing」 |
| 关思考，保留 schema | 19 个 `missing`、1 个 `present`，基本正确 |
| 保留思考，去掉 schema | 20 个 `missing`，正确 |

原生 `/api/chat` 也一样，问题不在 OpenAI 兼容层。

上游有相关的未修问题：Ollama 自 0.34.4 起，对思考模型把「思考 + 答案」当作一个整体语法来约束；模型不经思考直接作答时，schema 会被跳过（ollama/ollama#18774，修复 PR #18783 尚未合并）。所以不能指望升级 Ollama 解决，要我们自己避开这个组合。

**为什么现在要定**：本机默认的 `qwen2.5:7b` 不会思考，今天不受影响；但抽取质量的下一步是换更大或会思考的模型（7B 必答 43/115，`qwen3.8:27b` 能到 82–84，见 §2）。只要用户在 Ollama 上换成思考模型，就会撞到这个问题。

## 1. 目标

1. 思考模型在 Ollama 上抽取，不再出现「想对写错」。
2. 尽量保住思考带来的收益：在 S01 上，思考比不思考多答对 7–9 个必答字段（§2）。
3. 不会思考的模型（本机默认 `qwen2.5:7b`）结果不变差（§2.2：实测反而变好）。
4. 线上接口不变：模块不必知道后端是什么、模型会不会思考。

## 2. 候选方案与实测

| 代号 | 做法 | 在哪做 |
|---|---|---|
| **A** 关思考 | 抽取时显式传 `complexity: "simple"`，内核对 Ollama 也关思考 | 内核一处 + 模块一行 |
| **B** 内核两遍 | 内核的 Ollama provider 在遇到「带 schema 的请求」时自己分两遍 | 内核 |
| **C** 模块两遍 | 第一遍：不带 schema、不关思考，提示里写明答案的形状；答案能通过校验就用。否则第二遍：关思考、带 schema，即 A 的调用 | 模块；第二遍要用到 A 的内核那一处 |
| **C+** 模块两遍、带思考 | 同 C，但第二遍把第一遍的思考放回上下文 | 要让内核把思考文本传给模块：新线上字段 |

### 2.1 思考模型（Modal L40S，`qwen3.8:27b`，温度 0，S01 全 8 份，机械评分，各跑一次）

| | 今天（不带分段提示） | 今天 + 分段提示 | **A** 关思考 | C+ 带思考两遍 | **C** 模块两遍 |
|---|---|---|---|---|---|
| 必答正确 /115 | 71 | 75 | 75 | 84 | **82** |
| 背景正确 /35 | 26 | 26 | 30 | 29 | **30** |
| missing 判对 /20 | 16 | 18 | 19 | 20 | **20** |
| conflict 判对 /2 | 2 | 2 | 2 | 2 | **2** |
| 必答严重错误 | 23 | 19 | 4 | 2 | **3** |
| 必答待复核 | 19 | 19 | 33 | 27 | **27** |
| 有值候选带锚点 | 92% | 92% | 97% | 88% | **96%** |
| 抽取总耗时 / 最长一份 | 12 / 4 分 | 11 / 3 分 | 5 / 1 分 | 9 / 3 分 | **10 / 3 分** |

- 第一列是今天的真实做法；后四列用同一个文档模块构建：`extractor_version` 3，加上「分段提示」（窗口没覆盖全文时，提示「本段没写就答 missing」，见 §5.3）。所以 A、C+、C 要和第二列比；分段提示本身的作用是第一列到第二列。
- 内核是只在本机做实验的 `.exp-t0`（温度写死 0、**非流式**）。两遍由转发器模拟，与本设计的差别见 §2.3。
- 材料：`tools/modal-ollama/runs/2026-10-15-s01-qwen3.8-27b-window-prompt/`（前四列；NOTES.md 是分析）和 `runs/2026-10-16-s01-qwen3.8-27b-module-two-pass/`（C；`comparison.md`、`proxy.log`）。仓库外，不提交。
- **C 的 16 个不同请求里，13 个直接用了第一遍的答案**；3 个第一遍以 `finish_reason: length` 结束（思考写满了 `max_tokens`），走了第二遍。
  - `proxy.log` 里共 17 次，多出的一次是验收 ACC-IDEM-2 对 s01-07 的重抽，请求与第一次完全相同。
- **C 与 C+ 只差 2 个必答字段**，而且 C 的锚点更好（96% 对 88%）。所以第二遍不必带上第一遍的思考，**不需要新线上字段**，C+ 不采用。
  - C+ 的两遍都走 Ollama 原生 `/api/chat`（第一遍 `think: true`、按 `done_reason` 判断写没写完；第二遍 `think: false`、`format`），C 的两遍都走 `/v1/chat/completions`。所以两者相差的 2 个字段（如 s01-07：C+ 10/17，C 8/17）不能只归因于第二遍带不带思考。C+ 与本设计要发的请求不同，只作参考。
- A 的代价主要是「判对 → 待复核」（值取得偏短），另有两处真正的退步（s01-07 一个值被拆成两个，s01-08 一处漏答）。

### 2.2 不会思考的模型（本机 M4，`qwen2.5:7b`）

**第一遍不受约束，会不会让不会思考的小模型变差？** 实测结果反而变好：

| | 直通（今天） | **C** 模块两遍 |
|---|---|---|
| 必答正确 /115 | 43 | **51** |
| 背景正确 /35 | 19 | 18 |
| missing 判对 /20 | 14 | **16** |
| conflict 判对 /2 | 0 | 0 |
| 必答严重错误 | 29 | **19** |
| 必答待复核 | 37 | 42 |
| 有值候选带锚点 | 66% | **81%** |
| 抽取总耗时 / 最长一份 | 24 / 12 分 | 33 / 16 分 |

- 两组用的都是 #979 的发布构建：内核走流式、按进展计时；文档模块 `extractor_version` 4，**不带**分段提示。两遍由转发器模拟：它在上游做完两遍期间，每 15 秒给内核发一个不带内容的 `data:` 事件（`delta` 为空对象），推动进展计时，最后一次性送回答案。
- 直通组的 43/115、严重错误 29，与 #978 的正式证据相同，说明这套环境能复现之前的测量。
- C 的 19 次调用（含 ACC-IDEM-2 的重抽）里，12 次直接用了第一遍的答案，7 次第一遍格式不对，走了第二遍。7B 自由写 JSON 的合格率比思考模型低，但第二遍兜住了。
- 代价是耗时多约 40%：第一遍不合格的那些调用要再算一遍。
- 材料：`runs/2026-10-16-s01-qwen3.8-27b-module-two-pass/`（`comparison-7b.md`、`7b-r4-*`）。

所以 C 不用区分模型会不会思考，对两类模型都适用。

### 2.3 实验没有测到的部分

转发器模拟与本设计有这些差别，所以 §7 用正式构建再测一次（J9、J10）：

| 差别 | 影响 |
|---|---|
| 判断第一遍合格，转发器用的是自己的 schema 校验（`free_answer` + `valid`），设计用的是 `prompt::parse` | `parse` 更严：重复的键判为格式不对（转发器的 `json.loads` 只留最后一个）、逐字段检查是否自洽。所以设计里落到第二遍的会多一些 |
| 转发器见到 `finish_reason: length` 就丢弃第一遍；模块看不到 `finish_reason`，只看正文 | 正文恰好是完整 JSON 时，设计会采用它。罕见 |
| 思考模型那组的内核是非流式的 | 正式构建走流式。思考的增量（`delta.reasoning`）会推动计时（`stream.rs:141-146` 只看事件是否为空），但没有实测过 |
| 「第二遍截断 → 拆半」只在 7B 组跑到一次：s01-01 第 2 个窗口第 1 批，第一遍格式不对，第二遍写满 4096（`7b-r4-module-proxy.log` 19:01:15）。转发器让拆出的两半都从第一遍重新开始：前一半第一遍不合格、第二遍答完，后一半第一遍合格、直接采用。思考模型组的第二遍都没有写满 | 这次的情形（第一遍格式不对）在 §5.1 第 3 步里同样让两半从第一遍开始，与实验一致。「第一遍截断、第二遍又截断」没有跑到，只靠单元测试（J7） |

### 2.4 为什么不选 B

- 要在内核的通用 OpenAI 兼容 provider 里加 Ollama 专属的两遍逻辑和一个 JSON Schema 校验器（内核今天不校验 schema），并处理两遍共用 ME4-S2a 的进展计时与截止时间。
- 「答案合不合格」模块自己最清楚：`prompt::parse`（`extract/prompt.rs:308`）已经逐字段校验，还会区分「截断」和「格式不对」，内核只能按 schema 判。
- C 的效果与 C+ 相当，B 能做到的 C 都做到了，内核却要多背一套逻辑。

## 3. 建议：A + C

- **内核（A 的那一处）**：Ollama provider 遵守 `disable_thinking`，发 `reasoning_effort: "none"`（§4）。
- **文档模块（C）**：第一遍自由作答；不合格时，第二遍显式传 `complexity: "simple"` 并带 schema，也就是 A 的调用（§5）。

这样：
- 思考模型拿到 C 的收益（S01 82/115，今天是 75）；第一遍写不完的调用，退回到 A 的质量。
- 不会思考的本机默认模型也受益（43 → 51/115，严重错误 29 → 19），代价是耗时多约 40%（§2.2）。

**新模块装在老内核上**：老内核不对 Ollama 关思考，第二遍会「思考 + schema」，也就是今天的做法。所以这种组合不会比今天差，不需要升协议版本（对比 ME4-S2b §4，那次老内核会拒绝新字段）。

## 4. 内核：Ollama provider 遵守 `disable_thinking`

- `OpenAiCompatProvider` 加一个按实例开启的能力，和 `supports_chat_template_kwargs` 同一种做法（`lib.rs:244`、`:285`）：`supports_reasoning_effort()`。
  - 只有 `router.rs` 构造的 `ollama` provider，而且只在它判定为本地（loopback）时打开；remote 和 oMLX 都不开。
  - 开了以后，`req.disable_thinking` 为真时，请求体写入 `"reasoning_effort": "none"`；为假时不写，请求体与今天逐字节相同。
- **为什么是 `reasoning_effort: "none"`**：它是 OpenAI 兼容接口的字段，Ollama 的 `/v1/chat/completions` 把它映射为关思考。2026-10-16 在本机 Ollama 0.40.4 上核实：
  - 不会思考的 `qwen2.5:7b`：带 `"none"` 照常作答，`json_schema` 约束照常生效；
  - 同一个模型带 `"high"` 会被 400 拒绝（「does not support thinking」）。**所以只发 `"none"`，永远不发要求思考的值**；
  - 思考模型（`qwen3.8:27b`，Modal）带 `"none"` 不再思考：§2.1 的 A 那一组就是这样跑的。
- **流式**：今天模块调用都走流式（ME4-S2a）。思考的增量（`delta.reasoning`）也是 `data:` 事件，照常推动计时器；内核只收集 `content`，思考文本不进回答，这一点不变。
- **影响到的其他调用方**：只有显式传 `complexity: "simple"` 的模块会设 `disable_thinking`。据 `model_callback.rs` 的注释，这个开关（ME4-S2-thinking）是为 AgentEar 加的：语音场景里 Qwen3 会把整段思考念出来。这类调用在 oMLX 上已经关思考，在 Ollama 上今天仍会思考；改后在 Ollama 上也关，这正是 `complexity: "simple"` 原本的意思。PR 里知会 jason。
- 路由不变：`complexity` 缺省时本来就按 `Simple` 选路（`model_callback.rs` 的 `into_request`），显式传 `"simple"` 只多了关思考这一个效果。
- **oMLX**：`from_env` 先放 oMLX（`router.rs:339-346`），两者都在本地时先试 oMLX。文档模块在 oMLX 上的第二遍会经 `chat_template_kwargs` 关思考（已有行为），第一遍自由作答。S01 从没在 oMLX 上跑过，今天的做法也没有，所以这条路径的效果未知（R-g）。

## 5. 文档模块：两遍

### 5.1 一次调用的流程（改 `extract/run.rs` 的 `answer`）

今天的规则（`run.rs:233-266`）：截断就把字段拆半，不占重试；完整 JSON 但格式不对，同一个带 schema 的请求再问一次，再不对就失败。改后：

1. **第一遍**：请求同今天，但 `response_format: None`、`complexity: None`；系统指令后追加「答案的形状」一段（§5.2）。
2. 读回答：去掉可能包着的 Markdown 代码块（```` ```json ````），交给 `prompt::parse`。
   - 通过：用这个答案，结束。
   - 截断（`Unanswered::Truncated`，包括思考写满 `max_tokens`、正文为空）或格式不对：这一批字段**改用第二遍**，记下落下来的原因。
3. **第二遍**就是今天的请求加 `complexity: Some(Simple)`，即带 schema、关思考：
   - 格式不对：同一请求再问一次，再不对就失败（今天的规则）；
   - 截断：拆半（今天的规则）。两半从哪一遍开始，看这批当初为什么落到第二遍：
     - 第一遍**截断**：两半都直接用第二遍。思考的长度与字段多少关系不大，让两半重走第一遍，很可能又写满，调用次数会成倍增加；
     - 第一遍**格式不对**（写完了但不合格）：两半从第一遍重新开始。字段少了，第一遍可能答对；§2.2 的 7B 组跑到的正是这种情形，拆出的后一半就用了第一遍的答案（§2.3）；
   - 被拒（`request_rejected`）：**不拆窗**，job 以 `engine_unavailable` 失败，消息写明「模型拒绝了按 schema、关思考的请求」。第二遍只发生在第一遍被接受过的窗口上，第一遍的提示还更长，所以这里的拒绝不会是输入太长，而是第二遍独有的 `reasoning_effort` 或 `response_format` 被拒（R-f）。今天的「被拒就拆窗」此时只会多跑几轮第一遍，最后仍然失败，或者用拆小后的窗口悄悄得出不同的结果；
   - 所以每一批字段（包括拆出的每一半）最多比今天多一次调用，就是它的第一遍。
4. 只有「答案不合格」才从第一遍落到第二遍。`call` 里的等待和重试（忙、限流、超时重试一次、`no_provider` 等待，`run.rs:121-186`）对两遍一样适用。第一遍里出了这些错，或者第一遍被拒，都按今天的方式处理，不改用第二遍：
   - 例如第一遍连续两次超时，job 照今天以 `engine_unavailable` 失败；
   - 第一遍被拒按「输入太长」拆窗，拆出的两个窗口仍从第一遍开始：窗口变短，第一遍可能写得完。
5. 每次调用记一条 info 日志：窗口、字段数、第几遍，以及落到第二遍的原因（截断或格式不对）。抽取记录不变，所以事后从记录看不出某个值来自哪一遍，要看日志。

### 5.2 第一遍的提示

没有 schema 约束时，模型要从提示里知道答案的形状。系统指令后追加一段英文，内容与实验转发器的 `with_shape` 相同：

- 写出「每个字段答案」的 JSON Schema。各字段相同，所以只写一份；
- 给两个示例：`{"missing": {"reason": "not_in_document"}}` 和一个 `present`；
- 写明「状态是属性名，不要把 missing 写成值」。2026-10-15 的第一版两遍法缺这一句，出了 4 个「值是字面上的 missing」的严重错误，加上后全部消失。

### 5.3 一并纳入：分段提示

§2.1 的四组都带着「分段提示」：窗口不是全文时，系统指令后追加一段，要求「本段没写就答 `missing`（`not_in_document`），不要拿别的条目、费用或日期凑数」（实验补丁 `window-prompt.diff`，`prompt.rs` 加 12 行）。

在思考模型上它把 missing 判对从 16 提到 18（NOTES.md），在 7B 上没有单独测过。因为 §2 的结论都是带着它测的，同一片一起做（§9 Q2）。

### 5.4 版本与记录

- `extractor_version` 4 → 5：提示和调用方式都变了。
- ADR-DOC-02：
  - 版本清单加一条「5：先自由作答、不合格再关思考按 schema 重答（日期）」，分段提示也写在这一条里；

  - 第 153 行的重试规则（「截断对半拆、格式不对同一请求再问一次」）按 §5.1 改写，补上「第一遍不合格改用第二遍」和第二遍被拒的处理；
  - 第 156 行「用 `response_format` 的 JSON Schema 约束」改为：第二遍用 schema 约束，第一遍按提示里的形状作答，两遍都由 `prompt::parse` 校验；
