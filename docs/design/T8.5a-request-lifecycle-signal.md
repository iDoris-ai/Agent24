# T8.5a —— 请求生命周期信号（闭 FU-54）

> **设计已冻结**（v2，2026-09-17）。Codex 第 2 轮复核结论：**批准**——v1→v2 修的 C1/H1/M1/L1/L2 五项均为实质性修正，机制本身（`bind_to_lifecycle` 用可控 stub future 独立验证）经得住核实，不需要再送一轮设计评审。第 2 轮另发现 4 处**实现阶段顺手修**的小问题（不改设计，纯机械修正）：
> 1. **H-new1**：`events_emit.rs` 接入点示例代码里 `bind_to_lifecycle(lifecycle, sink.emit(kind, payload))` 编译不过（`sink.emit(...)` 是值不是 `Future`），实现时要写成 `bind_to_lifecycle(lifecycle, std::future::ready(sink.emit(kind, payload)))`。
> 2. **M-new1**：决策 5 代码示例里 `budget: Duration` 的注释仍写着"proxy.rs 传 `UPSTREAM_DEADLINE`"，与决策 3/具体改动清单已改成 `state.limits.total` 矛盾，实现时按 `state.limits.total` 为准，顺手把这行注释也改掉。
> 3. **M-new2**：`LifecycleTimeout` 把"预算耗尽"（请求可能还活着）和"请求已结束"两种不同语义折叠成同一句"the request this callback was bound to has already ended"文案，在预算耗尽分支这句话不准确。实现时给 `LifecycleTimeout` 加一个内部原因区分两个分支，或改成不预设"已结束"这个具体事实的中性措辞（如"this callback's request-bound time budget was exhausted"）。
> 4. **L-new1**（仅记录，可不改）：`bind_to_lifecycle` 内部直接调用 `Instant::now()` 而非显式参数化，判据 9a 里"remaining 自然耗尽"这一半测试没法完全避免真实等待；可接受，把测试 `remaining` 设成几十毫秒即可，`proxy.rs` 现有 504 路径测试就是同一模式。

## v1 → v2 改动（Codex 第 1 轮：1 Critical / 1 High / 1 Medium / 2 Low）

- **C1（决策 3、判据 9）**：v1 选 `events_emit.rs` 的 `sink.emit(...)` 作为参考实现/判据載体，但核实 `EventSink::emit`（`agent24-domain/src/lib.rs:1037`）、`EventBroadcast::send` trait 方法、生产实现 `HubBroadcast::send`（`domain.rs:141`）全部是**同步**函数，不是 `Future`——`tokio::time::timeout(remaining, work)` 套不上去，即使包一层 `async{}`，这个 work 会在第一次 poll 就同步跑完，`ended()`/超时分支永远赢不了，判据 9 声称的"handler 刻意不完成、约 1 秒后收到 timeout"在真实 `sink.emit` 上不可能发生。核实过 `ApprovalBackend`/`ApprovalFuture`（Codex 建议的备选，在 `agent24-domain`/`domain.rs` 里）后确认它是完全不同的机制——面向**进程内**模块的审批请求接口，根本不经过 `Generation::admit_callback`/`request_lifecycle`，拿它当这个信号机制的参考实现是张冠李戴，比"诚实承认没有现成异步载体"更混乱。**改法**：把决策 3 拆成两层——① 抽出一个独立的、不依赖任何具体业务 handler 的小函数 `bind_to_lifecycle`，用一个可控的 stub future（测试里手写的、能人为不完成的 async 块）直接证明"选中 timeout/ended 分支"这件事本身是对的；② `events_emit.rs` 仍然是本轮唯一的真实接线点，但如实降级为"路由正确性"的证明（`Some`/`None` 分支选得对、调用了 `bind_to_lifecycle`），不再声称能演示"长任务被真的裁短"——那件事要等 T8.5c 有真正异步的业务 handler 才能端到端验证。判据 9 拆成 9a（机制本身，stub future）+ 9b（events_emit 接线正确性，不断言裁剪时机）。同时这个改法顺手也解了 M1。

## 与 T8.5 的关系，以及为什么要拆出来单独做

T8.5 原计划一次性交付 ME-3d 记忆回调，送了 3 轮 Codex 对抗性设计评审都没有收敛。3 轮共同指向同一个根因：**"把回调绑定到请求生命周期"这件事本身没有被设计成一个独立机制**——它被埋在"记忆回调怎么落地"这个更大的问题里，于是每一版都在同时回答两个正交的问题（"回调超时该怎么绑定请求" + "记忆 RPC 该怎么设计"），互相污染对方的判据，也搞坏了 `agent24-os-proto/src/drain.rs` 里现有的、生产在用的不变式。

T8.5a 把"请求生命周期信号"整个拆出来，单独设计、单独评审、单独实现，不碰 memory RPC 的任何内容。做完之后，`admit_callback`/未来的 `_a24/memory/*`/已有的 `_a24/approval/*` 都可以在需要时调用同一个原语；T8.5（或它的后继任务）到时候只需要接线，不需要再重新发明这一层。

**范围边界（读到最后一节前先声明）**：本轮只交付 `Generation` 一侧的信号原语，以及把它接到 `_a24/events/emit`（`admit_callback` 现有的唯一调用点）作为参考实现和判据載体。`_a24/approval/gate`/`advise`/`status`（走 `admit_approval_callback`，跟 `admit_callback` 是两条不同的、T7b 就已经分道扬镳的路径）要不要、什么时候接入这个信号，是它们自己未来的决定，不在本轮强制交付范围——但下面的接口设计对它们同样适用，接入代价是常数级的（几行）。

## 现状复盘：`in_flight` 这张表，谁读、谁写

先把账算清楚，因为这是前三轮翻车的地方。`agent24-os-proto/src/drain.rs` 的 `Inner.in_flight: HashMap<String, ApprovalToken>`，在一把 `Mutex<Inner>` 后面：

**写者**（entry 的生老病死，今天只有两个生、两个死）：
- `admit_request`：唯一的插入点，`Running` 态下把 `id → ApprovalToken{hash, used:false}` 塞进去，跟返回 `InFlight` 是同一次调用、同一把锁。
- `InFlight::finish(self)`：唯一"正常死亡"，`inner.in_flight.remove(&self.id)`，跟读 `state == Revoked` 是同一把锁下的同一步。
- `impl Drop for InFlight`：唯一"非正常死亡"（handler 提前 return / panic / 被 `$/cancelRequest` abort 掉整个 task），`!self.finished` 时同样 `remove`。
- `Generation::revoke()`：**不删** `in_flight` 的任何条目——这是故意的（模块文档原话："The in-flight set is kept: an `InFlight` finishing after this point learns that it was abandoned from `InFlight::finish`"）。它只翻 `state` 到 `Revoked`，并把已发送/未发送的 id 各自拷贝一份分区到 `Revocation::abandoned`/`never_sent` 里。

**读者**（这三个必须在新设计下拿到跟今天完全一样的答案）：
1. `progress(now)`——`in_flight.len()`：drain 是否空闲、还剩几个在等。**只关心"这张表现在有多少条"**，不关心每条的时间戳或令牌状态。
2. `revoke()`——`in_flight.keys()` 按 `dispatched` 分区成 `abandoned`/`never_sent`：**只关心"现在这张表里有哪些 id"**，不读 token、不读时间。
3. `admit_approval_callback(request_id, token)`——`in_flight.get_mut(request_id)` 拿 `ApprovalToken`，校验哈希、原子标记 `used`：**只关心这一条的 token 字段**，且要求"已经 `finish()` 过的 id 必须查不到"（T7b 判据 6 的原文测试 `a_finished_requests_token_is_refused`）。
4. `admit_callback(request_id)`（Draining 态分支）——`in_flight.contains_key(id)`：只关心"这个 id 现在还在不在表里"。

四个读者的共同点：**全部只问"现在这张表里有没有这一条"或"现在这张表一共有几条"，没有一个读者需要知道"这条曾经存在过、但已经死了、死于什么时候"**。这是 T8.5a 设计的立足点：只要新加的字段是**跟 entry 同生共死的**、不改变 entry 何时被插入/删除，四个读者就不需要改一行逻辑——它们看到的表跟今天一模一样，只是表里每条的值多了两个字段。

## 决策 1：新增两个字段，跟 `ApprovalToken` 一样"随 entry 生、随 entry 死"——不建墓碑、不建第二张表

把 `in_flight` 的值类型从裸 `ApprovalToken` 换成一个新的 `InFlightEntry`：

```rust
struct InFlightEntry {
    token: ApprovalToken,        // 原有字段，原样保留
    deadline: Instant,           // 新增：这个请求自己的绝对到期时刻
    ended: watch::Sender<bool>,  // 新增：这个请求是否已经结束——不是事件流，是可查询的当前状态
}
```

`deadline`/`ended` 跟 `token` 完全同一条生命线：`admit_request` 一次性把三者一起插入（跟"令牌铸造与登记必须在同一次 `admit_request` 调用里完成"是同一条纪律的延伸——不存在"先插入 id、后面再补一个 deadline"的第二次写，那会留一个 id 已经存在但 deadline 未知的窗口）；`finish()`/`Drop` 一起把整条 remove 掉。**没有第三张表，没有"已结束 id"的独立登记簿，没有任何东西需要在"下一次 `admit_request`"或"下一次扫描"时被清扫**——因为这条记录本来就在 `finish()`/`Drop` 那一刻被整个丢弃，跟今天的 `ApprovalToken` 一样，表的基数上界完全不变，还是 `MAX_INFLIGHT_PER_MODULE`（64）。这是对坑 2（"墓碑堆积到 generation 销毁"）的正面回答：**不是把墓碑清扫得更勤，是设计成根本不产生墓碑**。

`progress`/`revoke`/`admit_approval_callback`/`admit_callback` 四个读者只需要机械地把 `in_flight.get(id)` 之类的返回值从 `&ApprovalToken` 改成 `&InFlightEntry` 后再 `.token`/`.len()`/`.contains_key()`——**没有一个读者的判断逻辑改变**，因为它们本来就只看"这一条在不在"，不看新字段。

## 决策 2："已结束"是可查询的当前状态，不是一次性事件——用 `watch::Sender<bool>`，且只在 entry 还活着的时候才谈得上"迟到订阅"

坑 1 的真实语义（不是猜测，是 tokio 文档明确写的）：`watch::Sender::send()` 在没有 receiver 时返回 `Err`，且**不为以后才出现的 receiver 保留这次的值**——如果拿它当"广播一次'已结束'事件"用，任何比这次 `send` 晚订阅的人都读不到。`send_replace`/`send_modify` 不同：它们**总是**更新发送端持有的当前值；无论调用时有没有 receiver，之后任何时刻 `subscribe()` 出来的新 receiver，第一次 `borrow()`/`wait_for()` 看到的都是这个当前值，不是"没有收到过任何事件"。这正是 `Generation` 自己已经在用、且已经被测试钉住的模式（`revoked: watch::Sender<bool>`，`revoke()` 里 `self.revoked.send_replace(true)`，测试 `waiting_for_a_revocation_ends_when_it_happens` 专门验证"迟到的等待者也能拿到"）——T8.5a 不发明新原语，只是给每个 `InFlightEntry` 也配一个同款的 `watch::Sender<bool>`，语义上回答"这个请求是否已经结束"这个布尔量本身，而不是"结束事件的流"。

查询接口：

```rust
impl Generation {
    /// 这个请求现在是否还活着，活着的话还剩多久——查不到就是 `None`：从未在这个
    /// generation 被 `admit_request` 过、或者已经结束（`finish`/`Drop` 两种路径不
    /// 区分）。两种"查不到"合并成一种，跟 `admit_approval_callback` 把"从未存
    /// 在"和"已经用过"合并成同一个 `TokenInvalid` 是同一个理由：调用方（下面决
    /// 策 3 的默认 30s 兜底）对两者要做的事完全一样，更细的答案没有用武之地。
    pub fn request_lifecycle(&self, id: &str) -> Option<RequestLifecycle> {
        let inner = self.lock();
        inner.in_flight.get(id).map(|entry| RequestLifecycle {
            deadline: entry.deadline,
            ended: entry.ended.subscribe(),
        })
    }
}

pub struct RequestLifecycle {
    deadline: Instant,
    ended: watch::Receiver<bool>,
}

impl RequestLifecycle {
    /// `now`由调用方传入（见决策 5）——这个类型自己不读时钟。
    pub fn remaining(&self, now: Instant) -> Duration {
        self.deadline.saturating_duration_since(now)
    }

    /// 一旦这个请求结束就返回——如果拿到这个 `RequestLifecycle` 的时候它已经结
    /// 束了，立刻返回，不会错过（跟 `Generation::revoked`/`InFlight::revoked`
    /// 完全同一个理由：`subscribe()` 在任何时刻调用，看到的都是当前值）。
    pub async fn ended(&mut self) {
        let _ = self.ended.wait_for(|ended| *ended).await;
    }
}
```

**故意的范围边界**：`request_lifecycle(id)` 在 entry 已经不在表里时返回 `None`，**不区分"这个 id 从未存在过"和"存在过、但已经结束了"**——因为一旦 entry 被 `finish()`/`Drop` 移出表，这个请求就再也没有剩余时间可言（它已经彻底结束，不是"剩余时间为零"，是"这个问题对它不再有意义"），调用方在这两种情况下能做的事完全一样：退回默认的 30s（决策 3）。**这不是漏洞，是不需要再解决的问题**——只有当调用方在 entry **还在表里的时候**就已经拿到了 `RequestLifecycle`（并留着它自己的 `watch::Receiver`），才谈得上"之后这个请求才结束、我需要被通知"；那种情况下，请求结束时 entry 从表里消失，不影响调用方手里已经 `subscribe()` 出来的 receiver 继续正常工作（`send_replace` 发生在 remove 之后、receiver 被丢弃之前——见下面决策 4 的时序）。真正会撞上"None"分支的，只有**回调发起时这个请求已经彻底结束**的情况——FU-54 的验收原文只要求"请求剩余 1s 时开始的回调在约 1s 时回 timeout"，从未要求覆盖"请求已经结束之后才开始的回调"，所以退化到默认 30s 是忠实于原始判据的选择，不是偷懒。

**（v2 新增）这个范围边界带一个方向性权衡，明说而不是带过**：`admit_callback` 本身（Draining 态之外，即今天最常见的 Running 态）对任何 `request_id` 一律放行，**不检查它是否还在 `in_flight` 表里**（`drain.rs:420`，`DrainState::Running => Ok(())`）。也就是说，一个早就 `finish()` 过的 `request_id`，只要 generation 还是 Running，回调依然会被 `admit_callback` 接受，然后 `request_lifecycle` 返回 `None`，拿到满额 30s——这是把"这个请求已经结束"这个本来已知的信息**丢弃**、退化成"完全不知道"再给最宽松的兜底，方向上是**放宽**，不是收紧。跟 FU-54"提前结束应该被更快感知"的精神有一点点张力，但没有严重到需要在本轮解决：`admit_callback` 的准入判定是它自己独立的职责（Draining/Revoked 才收紧），T8.5a 只负责"如果查得到这个请求，就给出准确的剩余时间"，不改变"要不要放行这次回调"这个更上游的判断。记在这里是为了未来收紧 `admit_callback`（比如 Running 态下也检查 `in_flight` 成员）时，设计者知道这不是一个从没被考虑过的角落。

## 决策 3：`min(30s, 剩余时间)` 落在哪一层——不碰 `rpc.rs`，业务 handler 自己接

`rpc.rs`（ME-3c）今天用一个连接级常量 `Limits::call_timeout`（= `CALL_TIMEOUT` = 30s）统一包住每一个 `handler.call(params)`：

```rust
let timeout = self.limits.call_timeout;
let handle = self.handlers.spawn(async move {
    tokio::time::timeout(timeout, handler.call(params)).await
});
```

`rpc.rs` 自己的模块文档说得很清楚：它是纯粹的"帧怎么分类、一条连接怎么跑多个并发调用"，不知道也不该知道 `Generation`/drain 状态——`admit_callback`/`admit_approval_callback` 今天都是由具体的 `Handler::call()` 自己在函数体内部调用的，`rpc.rs` 的通用分发循环从不感知它们。T8.5a 延续这条既有分工：**不改 `Handler` trait，不改 `Conn`/`serve()`，`rpc.rs` 一行都不动**。`Limits::call_timeout`（30s）继续原样作为每个调用的硬顶——这一点很重要：它是安全网，不是本设计依赖的机制,即使某个 handler 自己的绑定逻辑写错了，最坏情况也就是退化到今天的行为（等满 30s），不会更差。

真正的 `min(30s, remaining)` 逻辑收在一个**独立于任何具体业务 handler** 的共享 helper 里——这既是对 v1 决策 3 的延续，也直接回应 Codex 第 1 轮 C1/M1：C1 指出 v1 唯一的参考实现（`sink.emit`）是同步函数，套不进 `tokio::select!`，判据 9 声称的"长任务被裁短"在那上面不可能发生；M1 指出"每个 handler 各自手写 `tokio::select!`"容易复刻出错——而 v1 唯一的示例代码恰好就是错的，印证了这个担忧不是假设。修法是把这段逻辑从"handler 自己写"变成"handler 调用一个签名清楚、独立测试过的函数"：

```rust
/// 把一段业务 future 绑定到（可能存在的）请求生命周期上：有绑定就在
/// `min(remaining, 自然完成)` 与"请求已结束"之间 race；没有绑定就直接
/// `await`，不改变任何现有行为。独立于任何具体 handler，可以脱离
/// `EventsEmitHandler`/`sink.emit` 单独测试——这是 C1 的核心修复：判据
/// 9a 直接对着这个函数、用一个可控的 stub future 验证"裁剪"这个动作
/// 本身，不依赖任何真实业务操作恰好是异步的。
pub async fn bind_to_lifecycle<T>(
    lifecycle: Option<RequestLifecycle>,
    work: impl Future<Output = T>,
) -> Result<T, LifecycleTimeout> {
    match lifecycle {
        Some(mut lifecycle) => {
            let remaining = lifecycle.remaining(Instant::now());
            tokio::select! {
                r = tokio::time::timeout(remaining, work) => r.map_err(|_| LifecycleTimeout),
                () = lifecycle.ended() => Err(LifecycleTimeout),
            }
        }
        // 没有绑定（没有 request_id，或 request_id 查不到，决策 2 的范围
        // 边界）——直接 await，外层 `rpc.rs` 的 30s 兜底，行为跟今天完全一样。
        None => Ok(work.await),
    }
}

pub struct LifecycleTimeout;
```

**接入点，本轮唯一的一个，如实降级为"路由正确性"的证明**：`EventsEmitHandler::call()` 里，`admit_callback` 检查通过之后：

```rust
let lifecycle = request_id.as_deref().and_then(|id| generation.request_lifecycle(id));
match bind_to_lifecycle(lifecycle, sink.emit(kind, payload)).await {
    // `sink.emit` 是同步函数，`work` 传给 `bind_to_lifecycle` 时已经跑完
    // 求值到 `Result<()>`——`bind_to_lifecycle` 里的 `work` 实际类型是
    // `Ready<Result<()>>`，第一次 poll 就 `Ready`，`tokio::select!` 里
    // timeout/ended 分支没有机会先赢。这条接入点因此只能证明"路由选对了
    // 分支、`bind_to_lifecycle` 被正确调用"（判据 9b），不能证明"长任务
    // 真的被裁短"——那件事要等 T8.5c 有真正异步的业务 handler（比如一次
    // memory RPC 的 DB 写）才能端到端验证。如实写在这里，不假装
    // `events_emit.rs` 证明了它没有能力证明的事。
    Ok(result) => result.map(...),
    Err(LifecycleTimeout) => Err(RpcError::application(
        ErrorKind::Timeout,
        "the request this callback was bound to has already ended",
    )),
}
```

**没有 `request_id` 的路径完全不动**：`EventsEmitParams.request_id: Option<String>` 为 `None` 时（后台工作，SPEC §5 的"background work has no request at all"），`lifecycle` 恒为 `None`，`bind_to_lifecycle` 直接落到 `work.await`，被外层 `rpc.rs` 的 30s 兜住——一个字节的行为改变都没有。`ErrorKind::Timeout` 复用既有的闭集变体，不新增 wire 层的错误种类：从模块的角度看，"回调超时"和"回调绑定的请求已经先结束了"都是同一件事——没等到答案——SPEC 的错误分类关心的是"给操作员看的原因"，这两者原因相同（都是"这次调用没有机会跑完"），不需要拆成两个 `kind`。

`budget` 从哪来（**v2 修正，H1**）：v1 曾打算直接用 `agent24-os-proto/src/proxy.rs` 的 `UPSTREAM_DEADLINE = Duration::from_secs(30)` 常量。核实 `proxy.rs` 后发现这是错的——`admit_request` 的调用点（`proxy()` 函数体内，1011 行）此时 `state: ProxyState` 已经在作用域内，`state.limits.total`（`Limits` 结构体的文档注释原话："Deadlines, as data rather than as constants read at the call site... a test can reach the 504 branch in milliseconds"）就是"代理请求从读客户端 body 到拿到模块最后一个字节，总共能用多久"这个"总额"的**权威来源**，常量只是它的默认值（`impl Default for Limits { total: UPSTREAM_DEADLINE, ... }`）。同一个文件里已经有两条回归测试专门盯防"读常量而不是读配置态"这个错误形状——`the_head_budget_is_what_is_left_of_the_total_not_a_constant`（2898 行）、`the_overload_message_names_the_ceiling_that_applies`（3048 行），`capacity` 字段的文档注释原话："today the two are equal in production... the day this becomes per-module the text starts lying with nothing to catch it"。`admit_request` 的 `budget` 参数改传 `state.limits.total`，不传常量。

## 决策 4：请求提前结束时怎么通知/中止在跑的回调——协作式，如实说明它不是抢占

时序（对应决策 1 的两个写者）：

```rust
pub fn finish(mut self) -> Result<(), Abandoned> {
    let (revoked, dispatched, entry) = {
        let mut inner = self.generation.lock();
        let entry = inner.in_flight.remove(&self.id);   // 改动点：保留返回值
        let dispatched = inner.dispatched.remove(&self.id);
        (inner.state == DrainState::Revoked, dispatched, entry)
    }; // 锁在这里释放
    if let Some(entry) = entry {
        let _ = entry.ended.send_replace(true);          // 新增：锁外翻状态
    }
    self.finished = true;
    if revoked { Err(Abandoned { dispatched }) } else { Ok(()) }
}

impl Drop for InFlight {
    fn drop(&mut self) {
        if !self.finished {
            let entry = {
                let mut inner = self.generation.lock();
                inner.dispatched.remove(&self.id);
                inner.in_flight.remove(&self.id)          // 改动点：保留返回值
            };
            if let Some(entry) = entry {
                let _ = entry.ended.send_replace(true);    // 新增：锁外翻状态
            }
        }
    }
}
```

`send_replace` 在锁**外面**调用——跟 `revoke()` 翻 `self.revoked` 的既有写法（"After the state is Revoked, so a woken request that re-checks the state sees the revocation"）同一个理由：不在持有 `Mutex<Inner>` 的同时去碰 `watch::Sender` 自己的内部锁，两把锁永远不嵌套，不引入新的锁序问题。`finish()` 的两条出路（`Ok`/`Err(Abandoned)`——正常完成、或被 `revoke()` 抢先）和 `Drop`（handler 提前 return / panic / 被 `$/cancelRequest` abort 整个 task，也覆盖"客户端断开连接"——hyper 在这种情况下直接丢弃 `forward()` 的 future，`InFlight` 随之被 drop）**这三条路径都会翻 `ended`**——FU-54 原文说的"正常完成或客户端断开"两种提前结束，在这个设计里走的是同一条代码路径（`Drop`），不需要分情况处理。

`Generation::revoke()` **不需要改**：它本来就不删 `in_flight` 的条目，也就不会误翻还在跑的请求的 `ended`——一个被 revoke 但还没 `finish()` 的请求，它的回调如果查询 `request_lifecycle`，看到的仍然是"活着，还有多久"（用 revoke 之前算好的 `deadline`），直到它自己的 `finish()`（这次会拿到 `Err(Abandoned)`）才真正翻 `ended`。这跟 `admit_callback` 在 Draining 期间仍然放行"绑定在途请求"的回调是同一个精神：revoke 之后，正在跑的东西还是要能把手上的事做完或者体面地收场，不是被硬拔电源。

**如实说明**：`tokio::select!` 丢掉的是 `work`（`sink.emit(...)`，或未来 memory RPC 里的一次 DB 写）这个 **future**，不是已经跑起来的、可能带副作用的操作本身——如果 `work` 内部已经把一次写提交到数据库,丢掉 future 不会把它撤销。这跟今天 `$/cancelRequest` 的既有免责声明是同一件事（"cancelled by $/cancelRequest; any side effect already committed stays"），而且比 `$/cancelRequest`（直接 `abort()` 整个 task）更温和——`$/cancelRequest` 已经要求每个 handler 对"未跑完就被打断"是安全的,这里没有引入新的、handler 没有准备好应对的取消面。**这不是"立即抢占正在执行的异步任务"**：它依赖 handler 自己在下一个 `.await` 点（`tokio::select!` 的轮询点）把控制权交回来才能生效，如果 `work` 是一段长时间不 `.await` 的同步计算（今天的 `sink.emit`/未来的 DB 写都不是),`ended()` 赢了这场 race 也要等到 `work` 下一次让出执行权才能真正切换分支。

## 决策 5：可测试性——沿用 drain.rs 自己已经写在模块文档里的法则："本模块不持有时钟，`now` 由调用方传入"

`drain.rs` 模块文档"# No clock, no waiting"一节原文已经把这条法则定死了：`begin_drain(now, grace)`、`progress(now)` 都不读 `Instant::now()`，`now` 全部由调用方传入。坑 3 的根源正是**没有把这条已有法则也用在请求的 deadline 上**——`admit_request` 今天不接收时间信息，`deadline` 只能等以后某个不确定的地方用真实时钟算,于是测试只能靠真 `sleep` 伪造"已经过了 29.9 秒"。T8.5a 的修法不是发明一个新的可注入时钟抽象（`events_emit.rs` 已经有一个 `Clock` trait,但那是给 `RateLimiter` 的刷新算法用的,`drain.rs` 明确不想要这种依赖注入——它想要的是"根本不问时钟,只吃调用方给的数字"),而是让 `admit_request` 也遵守同一条法则：

```rust
pub fn admit_request(
    self: &Arc<Self>,
    id: String,
    token_hash: [u8; 32],
    now: Instant,       // 新增，调用方传入——proxy.rs 传 `Instant::now()`，测试传任意固定值
    budget: Duration,   // 新增，调用方传入——proxy.rs 传 `UPSTREAM_DEADLINE`
) -> Result<InFlight, RequestRefused> {
    let deadline = now.checked_add(budget).unwrap_or(now); // 见下方溢出说明
    ...
}
```

溢出处理跟 `begin_drain` 的既有选择在精神上一致（"Computed BEFORE touching the state...An unrepresentable grace is refused instead"），但落点不同：`begin_drain` 拒绝整个操作是因为一次 drain 失败没有下游代价；`admit_request` 是热路径,拒绝一个本该被接受的代理请求代价太大,而这种溢出在生产环境里只有 `now` 已经逼近 `Instant` 能表示的上限（相当于系统已经连续运行到单调时钟耗尽）才会发生——现实中不可达。选择"失败朝向保守"而不是"失败朝向拒绝"：溢出时 `deadline = now`,效果是这个请求的 `remaining` 恒为 `Duration::ZERO`（决策 3 的 `min(30s, 0) = 0`，回调立刻超时),而不是意外变成"无限期"。这是一个刻意的、朝着"更快失败"而不是"更慢失败"的选择,不是被忽略的角落。

有了 `now`/`budget` 两个显式参数,测试不需要真 sleep、不需要 mock 时钟,直接构造两个 `Instant` 值：

```rust
let t0 = Instant::now();
let in_flight = g.admit_request("r1".into(), [0; 32], t0, Duration::from_secs(30)).unwrap();
let lifecycle = g.request_lifecycle("r1").unwrap();
assert_eq!(lifecycle.remaining(t0 + Duration::from_secs(29)), Duration::from_secs(1));
```

`ended()` 那一半的异步测试同样不需要真 sleep——精确复刻 `waiting_for_a_revocation_ends_when_it_happens` 已经验证过的写法：`tokio::time::timeout(短的测试超时, lifecycle.ended())`,`finish()`/`drop()` 之后立刻 resolve。

## 判据

1. 请求于 `t0` 以 `budget=30s` admit；`request_lifecycle` 在 `t0+29s` 查询算出 `remaining≈1s`——用固定 `Instant` 值验证，不依赖真实 sleep。**正对照**：同一个请求在 `t0+1s` 查询,`remaining≈29s`——证明绑定的确随查询时刻变化,不是写死的短值。
2. 没有 `request_id` 的 `_a24/events/emit` 调用,不受任何其他请求剩余时间的影响,行为与今天完全一致（`admit_callback` 通过、`sink.emit` 直接 `.await`,外层 30s 兜底）。
3. `request_id` 指向一个从未在这个 generation 被 admit 过的 id（陌生 id、或另一个 generation 的旧 id）,`request_lifecycle` 返回 `None`,回调退回默认 30s——即使同一个 generation 里**同时**有另一个请求即将到期,这条陌生 id 的回调也不提前超时（证明没有跨请求串扰）。
4. 一个仍在等待 `lifecycle.ended()` 的回调,在其绑定请求 `finish()`（`Ok(())` 路径）之后,在远小于原定 `remaining` 的时间内收到 `timeout`——测试只用 `tokio::time::timeout(短测试超时, ...)` 包裹，不用真实等待。**正对照**：绑定在另一个仍然在飞的请求上的回调不受影响。
5. 同上,但触发方式换成 `drop(in_flight)`（不调用 `finish()`,模拟 handler panic / 被 cancel / 客户端断连）——`ended()` 同样及时 resolve,证明 `Drop` 路径和 `finish()` 路径对回调是等价的。
6. `finish()`/`Drop` 之后,`progress`/`revoke`/`admit_approval_callback` 三个既有读者的行为与 T7b/ME-3b-5 已有测试逐条比对,零回归（本轮不新增这三者的判据,直接复用 `drain.rs` 现有的测试名单——`draining_refuses_new_requests_but_not_the_ones_in_flight`、`revoking_refuses_every_callback_including_in_flight_ones`、`a_finished_requests_token_is_refused` 等——把它们的 `admit_request` 调用点换成带 `now`/`budget` 的新签名后必须原样通过）。
7. 一个被 `revoke()` 但尚未 `finish()` 的请求,它的回调查询 `request_lifecycle` 仍然拿到 `Some`（沿用 revoke 之前的 `deadline`）,直到它自己 `finish()`（拿到 `Err(Abandoned)`）才翻 `ended`——证明 revoke 不提前打断一个仍被允许把回调做完的请求（呼应 SPEC §4 "在途的仍可用"这一条既有不变式）。
8. `admit_request` 的 `now.checked_add(budget)` 溢出时（用一个逼近 `Instant` 上限的构造值触发,而不是真的等系统时钟耗尽）,`deadline = now`、`remaining` 恒为零、请求本身仍然被正常 admit（不因为这个边界情况被拒绝）——区别于 `begin_drain` 对溢出的处理方式,并显式测试这个差异是刻意的。
9a.（**v2 修正 C1**）机制本身，不依赖任何真实业务 handler：直接对 `bind_to_lifecycle` 用一个可控的 stub future（例如 `std::future::pending::<()>()`，或一个手写的、只有测试代码能让它 resolve 的 future）测试——绑定了一个剩余 1 秒的 `RequestLifecycle`、`work` 本身刻意不完成,约 1 秒后 `bind_to_lifecycle` 返回 `Err(LifecycleTimeout)`；换成"其绑定的请求被 `finish()`/`drop()`"触发,同样在远小于 `remaining` 的时间内返回 `Err(LifecycleTimeout)`（这条实质上复用判据 4/5 的 `ended()` 验证,但改成穿过 `bind_to_lifecycle` 整个函数,不是只测 `RequestLifecycle::ended()`）。**正对照**：`work` 提前正常完成时,`bind_to_lifecycle` 返回 `Ok(..)`,不受未到期的 `deadline`/未触发的 `ended` 影响。这条判据直接对应 FU-54 验收原文"请求剩余 1s 时开始的回调在约 1s 时回 timeout"，且不依赖"恰好有一个异步的业务操作"这个本轮不成立的前提。
9b.（**v2 修正 C1**）接线正确性，`events_emit.rs` 作为本轮唯一的真实接入点：`_a24/events/emit(request_id: Some(..))` 在其绑定请求尚未结束时调用,返回值与"不接入 `bind_to_lifecycle` 直接 `sink.emit`"完全一致（因为 `sink.emit` 同步跑完,`bind_to_lifecycle` 的 `Some` 分支里 `tokio::time::timeout(remaining, work)` 第一次 poll 就 `Ready`）；`request_id` 缺失或查不到时同样一致。**如实声明这条判据只证明"路由选对了分支、参数传对了",不证明"长任务被真的裁短"**——那件事由 9a 单独证明,两条判据合起来才是完整的证据链,任何一条单独都不够。

## 不改的东西

- `Generation::admit_callback`/`admit_approval_callback` 的错误矩阵、`Draining`/`Revoked` 状态下的既有判定——一个字符没改,只是内部字段访问路径变了。
- `Generation::revoke()`/`Revocation`/`KillPermit` 的整套撤销机制——完全不碰,新字段对它不可见。
- `progress()`/`DrainProgress` 的语义与既有测试——`in_flight.len()` 的计算方式不变。
- `rpc.rs` 的 `Handler` trait、`Conn`/`serve()`、`Limits::call_timeout`（30s 硬顶继续对每个调用生效,不管有没有绑定请求）。
- 没有 `request_id` 的回调路径（后台工作）——继续是无条件的默认 30s。
- wire 协议本身——不新增 `ErrorKind`、不新增 REST/WS 字段,模块只会看到"这次调用比以前更早地收到了 `timeout`",错误种类不变。
- `agent24-scheduler`/`ModuleApproval`/T7b·T7c 已经交付的一切——本设计完全不涉及审批的持久化状态,只涉及代理请求本身的、纯内存的生命周期信号。

## 自审：逐条核对三个已知的坑，以及新引入的风险

**坑 1（迟到订阅者读不到"已结束"）**：用的是 `watch::Sender` + `send_replace`（不是裸 `send`）+ 每次查询都重新 `subscribe()`（不是复用一个建立更早的 receiver）——`subscribe()` 的返回值语义是"给我当前值",跟这次 subscribe 发生在 `send_replace` 之前还是之后无关。这是 `Generation::revoked` 已经在生产代码里跑着、且有专门测试钉住的同一个原语,不是新猜测。已在决策 2、判据 4/5 验证。

**坑 2（不能靠留着墓碑实现迟到查询）**：正面回避了这个问题,而不是把墓碑做得更精巧——`InFlightEntry` 跟 `ApprovalToken` 同生共死,`finish()`/`Drop` 依然是仅有的两个删除点,`in_flight` 的基数上界还是 `MAX_INFLIGHT_PER_MODULE`。代价是"entry 消失之后的查询一律退化成默认 30s",这个代价被验证为忠实于 FU-54 原始验收文本（决策 2 的范围边界一段）,不是为了绕开问题而悄悄改写需求。`progress`/`revoke`/`admit_approval_callback` 三个读者未改逻辑,已在决策 1、判据 6 验证。

**坑 3（没有可注入的时钟/deadline seam）**：延续 `drain.rs` 自己已经写明的"不持有时钟,`now` 由调用方传入"法则,而不是引入 `events_emit.rs` 那种 `Arc<dyn Clock>` 依赖注入（那是给需要反复读时钟的刷新算法用的,`admit_request`/`request_lifecycle`/`remaining` 都只需要调用方给一次性的值,更轻）。已在决策 5、判据 1/8 验证。

**新的锁序检查**：新代码只用到两把锁——`Generation` 已有的 `Mutex<Inner>`,和 `watch::Sender` 自己内部的锁。`send_replace` 全部在 `Mutex<Inner>` 的 guard 已经离开作用域之后调用（决策 4 的代码块),两把锁从不同时持有,不存在嵌套顺序,因而不存在新的死锁风险。`request_lifecycle` 里的 `entry.ended.subscribe()` 在持有 `Mutex<Inner>` 期间调用,但 `subscribe()` 是否会阻塞或递归回到 `Mutex<Inner>`？不会——`watch::Sender::subscribe` 只碰它自己的内部状态,不知道也不需要知道 `Generation`,不构成嵌套。

**新的内存无界性检查**：每个 `InFlightEntry` 比今天的 `ApprovalToken` 多了一个 `Instant`（16 字节）和一个 `watch::Sender<bool>`（内部是一次共享堆分配,量级跟一个 `Arc` 相当）——常数级增量,乘的还是同一个、本来就有界的并发请求数（`MAX_INFLIGHT_PER_MODULE = 64`）。`RequestLifecycle`（调用方持有的查询结果）里的 `watch::Receiver<bool>` 跟着调用方自己的 handler 任务的生命周期走,handler 结束时自然释放,不会在 `Generation` 一侧堆积——它甚至不在 `Generation` 内部,只是 `request_lifecycle` 的返回值,`Generation` 自己不持有任何"曾经发出去过多少个 receiver"的记账。
