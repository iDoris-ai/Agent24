> 1. **M1**：流中反序列化失败的行（`Some(Err(_))`）没有在 `scanned += 1` 之前退出，导致这类错误行的结算少算一行（应是 `scanned+10` 不是 `scanned+9`）。实现时把"扫描行"的计数点挪到"consumer 已观察到 stream item"（拿到 `Some(row_result)` 就立刻计数），而不是"成功转换成 `StoredEvent`"之后。
> 2. **M2**：`page_from_stream` 仍独立接收 `match_policy`/`needle`/`method_tag` 三个参数，类型层面没有堵死"matcher 用 Needle A、cursor 指纹用 Needle B"这种错配（当前调用点碰巧写对了，但不是类型强制）。实现时收敛成单一参数，比如 `enum PageMode<'a> { Recall(&'a Needle), Recent }`，由 `page_from_stream` 内部同时派生 matcher/method tag/fingerprint needle。
> 3. **M3**：判据 9b 的"真实占连接"模型里，对处于 `acquire_owned()` 排队阶段（还没拿到 permit）的 waiter 做取消断言的方式不对（release 的名额是否被其他排队者拿到需要排两个 waiter 分别验证，不能对一个还没拿到 permit 的调用做"permit 释放"式断言）；另外判据没有要求 holder/contender 跨模块，验证不了这是 daemon 级单例而不是"每模块一个 semaphore"。实现时按这两点补全判据。
> 4. **M4**：`row_buffer_size(8)`（在 `KvStore::open` 设置）和 `ROW_BUFFER_MARGIN=9`（在别处定义）不是同一个配置源，`KvStore::open_memory` 等其它构造路径也可能不经过 `open` 从而不受这个设置约束。实现时定义唯一共享常量（如 `MEMORY_SQLITE_ROW_BUFFER_SIZE=8`），所有能产生 `EventLog` 的 pool 构造路径都引用它，`ROW_BUFFER_MARGIN` 由它 `+1` 编译期算出。
> 5. **M5**：判据 7d（3 行数据、`page_size=10`，应精确结算 3）的算式仍写成 `3 + ROW_BUFFER_MARGIN` 钳制到 10，跟本轮引入的"自然耗尽精确结算 `scanned`"这条新语义直接矛盾。实现时改成断言精确结算 3，另加一条"提前返回、未观察到 `None`"的场景验证 `scanned+9` 分支。
> 6. **L1（仅记录）**：几处旧措辞没清理干净（`scan_stream` 残留"应该是零"的旧注释、判据 7b 的算式没跟着 `ROW_BUFFER_MARGIN` 从 8 改成 9、§12 "在 async move 块内部构造"的表述可以再统一成"由 work future 独占持有"）。实现时顺手清理，不影响架构。

## 1. 现状复盘（读代码复核，不是转述）

读了 `rust/apps/agent24d/src/os_memory.rs` 全文（1625 行）和

  `EventQuery::owner(&self.key).newest().limit(size)`，再 `self.events.scan(&q)`。

  今天一次内部批取 `RECALL_PAGE = 500` 行（`os_memory.rs:126`），`recent` 的批

- `Page` 结构体（`os_memory.rs:544`）带 `oldest_seq`（这批里最小的 `seq`）和
  `short`（`rows.len() < size`）两个字段——`short` 是"这批 DB 取到的行数比要求的
  少"，不是"分区里没有更早的行了"的直接证明（虽然两者在**没有并发写入且没有内部

- `EventQuery::limit(n)`（`event.rs:241`）对 `n` 做 `.max(1)`——如果 wire 层不做
  显式校验，`page_size=0` 会被这一层悄悄改写成 1，这正是 T8.5c v1 D2.3 已经拍板
  要在 handler 里前置拦截的问题，本文档继续沿用，不重新论证。
- `seq` 列是 `INTEGER PRIMARY KEY AUTOINCREMENT`（`migrations/0011_events_owner_trim.sql:31`），
  SQLite 的 `AUTOINCREMENT` 保证单调递增、不重用、起始值为正——这是 L1 修法
  （`seq` 必须 `>= 1`）的存储层依据，不是本文档臆造的约束。
- `sqlx` 依赖（`agent24-memory/Cargo.toml:16`）是
  `features = ["runtime-tokio", "sqlite", "migrate", "macros"]`——`Query::fetch()`

- `EventStore` trait 目前只有一个实现者：`EventLog`（`rg` 全仓搜索没有第二个

  （`remember_checked`/`recall_page`/`recent_page` 都是 inherent，不进
  `ScopedMemory` trait），本文档的 `scan_stream` 延续同一个模式。

## 2. 决策 P1：游标语义重定义——"最后一个已解决行"，不是"最后一个被检查行"，也不
   是"最后一个被接纳行"

### 2.1 为什么两种直觉都不够精确

Codex 的原话给出了两个候选修法："返回该行的 seq"（数据丢失，被否）和"返回上一行
的 seq"（不丢但违反 T8.5c v1 的定义）。本文档把"上一行"精确定义为**上一个已解决
的行**，理由是这个定义同时满足两个互相牵制的要求：

1. **绝不允许游标跳过一个已经匹配、但因为字节预算没能装进响应的行**——这是 C1
   要求的正确性下限。
2. **绝不应该让游标为了"保险"而回退到比必要更早的位置**——如果游标一律回退到
   "最后一次被响应接纳的行"（字面意义上的"已接纳"），那么两次接纳之间所有被扫描
   过、确认不匹配的行会在下一次调用里被重新扫描一遍。这不会造成数据丢失，但会让
   `MEMORY_SCAN_ROW_BUDGET` 的"扫描预算"这个概念失去意义——一个几乎不匹配的
   `query`，只要偶尔撞上一次字节预算边界，就要不断重新扫描已经确认过的非匹配行。

**"已解决"（resolved）的精确定义**：一行在下列两种情况之一发生时变为已解决，且
从那一刻起，游标可以安全地越过它（下次调用不会再看到它，也不需要再看到它）：

- （recall 专属）**确认不匹配**——它已经被 `matches(row, query)` 判定过，结果是
  假。这个判定结果对同一个 `query` 永远成立（`mem_events` 是仅追加的事件日志，
  已写入的行不会被修改，见 `event.rs` 的 `INSERT ... ON CONFLICT DO NOTHING`
  与本文件 `os_memory.rs` 头部注释"the isolation is enforced by the kernel, not
  the schema"——没有 UPDATE 路径），所以"确认不匹配"是一个可以安全永久跳过的
  事实，不是这次调用才成立的临时状态。
- （recall 与 recent 共同）**匹配且被成功接纳进响应**——它已经计入 `items`，字节
  预算允许它进入响应。

**一行在什么情况下"未解决"，从而游标绝不能越过它**：它匹配了 `query`（或
`recent` 语境下无条件"匹配"），但把它加入响应会让累计字节数超过
`MEMORY_PAGE_RESPONSE_BUDGET_BYTES`。这一行的"是否会被返回"这件事还没有答案——
它可能在下一次调用里、在一个从零开始计的新字节预算下被成功接纳。游标必须停在它
之前最后一个已解决的行，让下一次调用的 `before` 边界重新看到它。

### 2.2 为什么这个定义对 `recall` 和 `recent` 是同一套，不需要两套状态机

`recent` 不过滤，每一行天然"匹配"，所以它没有"确认不匹配"这个分支——它的状态机
是本文档下面状态机的一个子集（跳过"非匹配"分支），不是另一套逻辑。这修正了
T8.5c v1 的一个说法："recall 的游标复杂，recent 的游标简单，两者不共享一段推导
逻辑"——本文档反过来：两者共享同一个"已解决行"状态机，`recent` 只是矩阵里"非匹配"
那一列恒为空。实现时建议（不强制）用同一个内部函数处理两者，用一个类型化的
`MatchPolicy`（`enum MatchPolicy<'a> { Substring(&'a str), Always }`）而不是裸
`always_match: bool` 来复用同一段循环——裸 bool 在调用点看不出"true 是恒匹配还是
恒不匹配"，`MatchPolicy::Always` 自解释，且后续如果需要更复杂的匹配规则（比如
未来加前缀匹配），加一个枚举分支比新增第二个 bool 参数更不容易在调用点排列
组合出矛盾状态。这是本轮顺手采纳的实现建议（v2 改动记录），不是新的强制要求。

**v4 补充（M2，§4.2 的 `page_from_stream` 需要）**：

```rust
impl MatchPolicy<'_> {
    fn matches(&self, item: &Recollection) -> bool {
        match self {
            MatchPolicy::Substring(needle) => item_matches_substring(item, needle),
            MatchPolicy::Always => true,
        }
    }
}
```

`item_matches_substring` 是决策 P1 §2.1 里"`matches(row, query)`"这个匹配
判断的具体实现（子串/大小写折叠等规则留给实现阶段），挪到 `MatchPolicy` 的
方法里之后，`page_from_stream`（§4.2）不需要单独区分"这次调用是 recall 还是
recent"——它只调用 `match_policy.matches(&recollection)`，`recent_page`
传 `MatchPolicy::Always` 时这个方法直接返回 `true`，不经过子串匹配逻辑。

## 3. 决策 P2：扫描物化开销收窄——流式消费，不是"先整批拉到内存再限流"

### 3.1 为什么"缩小内部批量大小"不是本文档选择的主方案

任务描述给了两个选项：缩小内部批大小，或者流式处理。缩小批大小（比如把
`RECALL_PAGE` 从 500 降到几十）能把最坏情况的物化量降到可接受范围，但它仍然是
"先攒一批、再逐行处理"的形状——一旦某次调用的字节预算或扫描预算在这一批**中途**
被触发而提前退出，批里剩下的、已经从 DB 取出并反序列化到内存的行是白取的。批越
小这个浪费占比越高（更多次触发"取了一批却只用了几行"），批越大又回到 Codex 指出
的问题。这是一个没有好选点的权衡，因为问题的根源不是"批多大"，是"批"这个概念
本身跟"逐行判断是否继续"这件事不匹配。

> **v2 更正（sqlx 预取 High）**：`scan_stream` 换成 `Query::fetch()` 本身并不
> 自动把"批"这个中间层去掉——见 §3.2 的 v2 更正。这不推翻本节"不选缩小批大小"
> 的结论（流式设计仍然从代码结构上消除了 M1 的病灶，见 §4.1），只是 §3.3 的
> "O(1) 物化"这个具体数字需要重新核算。

### 3.2 主方案：`EventLog::scan_stream`，逐行消费，不预先物化整批

> **v2 更正（sqlx 预取 High，正式选定方案一）**：读了
> `sqlx-sqlite-0.8.6/src/options/mod.rs:211`（`SqliteConnectOptions` 的
> `Default` 实现，`row_channel_size: 50`）和
> `sqlx-sqlite-0.8.6/src/connection/worker.rs:160-206`（`Command::Execute`
> 分支：SQLite 专属的单一 worker 线程同步跑 `execute::iter`，对每一行调用
> `tx.send(res)`——`tx`/`rx` 是 `flume::bounded(chan_size)`，`chan_size` 就是
> `row_channel_size`）之后确认：`Query::fetch()` 返回的 stream 不是"逐行请求
> SQLite"，是 worker 线程**主动**把行 blocking-send 进一个容量 50 的有界
> channel——`.next().await` 只是从这个 channel 里取一条已经在里面的行，worker
> 线程会一直跑在消费者前面，直到 channel 被灌满（阻塞）或者被消费跟上。这与
> `fetch_all`（`try_collect` 整个 stream）的区别只是"channel 满了之后消费者要
> 不要继续问"，不是"每次 `.next()` 触发一次新的 SQLite 读"。
>
> **正式选定的修法**：在打开 memory 的 `SqlitePoolOptions::connect_with` 时，
> 用 `SqliteConnectOptions::row_buffer_size(8)`（`options/mod.rs:454` 暴露的
> builder 方法，直接设置 `row_channel_size`）显式调小这个 channel，而不是接受
> 默认的 50，也不是改用小批量 `LIMIT` 轮询（任务给出的三个选项里的第二、三个）。
> 理由：
> 1. 这是一个连接选项（`connect_with(options)`），只需要在 `KvStore::open`
>    （`agent24-memory/src/lib.rs:205` 附近）设一次，对整个共享池的所有查询
>    统一生效，不需要给 `scan_stream` 单独发明一种"手动小批量重复查询"的形状
>    ——后者本质上是把"批"这个已经被 §3.1 否掉的中间层用 SQL `LIMIT` 重新造
>    一遍。
> 2. 对共享池的影响是**正面**的，不是额外代价：`row_buffer_size` 调小之后，
>    进程内 `ScopedMemory` trait 仍然用的 `fetch_all`（本质是对同一个 stream
>    `try_collect`）不受语义影响——它还是拿到完整结果，只是 worker 线程分批
>    往 channel 里塞的粒度变小，总吞吐量不变（消费方是同进程 Rust 代码，不是
>    网络 IO，没有"多几次 channel 阻塞"就显著变慢这回事）；对 `scan_stream`
>    新路径，则是把最坏情况的额外预取行数从 50 压到 8。
> 3. `8` 不是任意选的：它比"决策 P3 判据里可能出现的最小合法 `page_size`（1）"
>    留出足够余量避免频繁阻塞 worker 线程，又比默认 50 小一个数量级，让 §3.3
>    的物化上界公式（`(B+1) × 单条记录最坏字节数`，`B=8`）保持在“个位数条记录”
>    的量级，跟"流式设计"这个名字要传达的直觉相符。
>
> 这个决定影响 §3.3 的物化上界推导（下方已更新）和 §8（P7 取消语义）"至多一行
> 在飞"的说法（那里已经按 `B=8` 改写）。

新增一个 `EventLog` 的 inherent 方法（不进 `EventStore` trait，理由见第 1 节——
它只有一个实现者，本文档遵循 T8.5c v1 决策 D4 已经确立的"OOP 专属行为走 inherent
方法，不动 trait"这条先例）：

```rust
// agent24-memory/src/event.rs，EventLog 的 inherent impl 块

/// 逐行流式扫描，不预先把整批结果物化进内存。
///
/// 与 `EventStore::scan`（`fetch_all`，一次性拉完 `q.limit` 条）的关系：`scan`
/// 面向进程内调用方，它们的调用方（`OsScopedMemory::recall`/`recent` 的
/// `ScopedMemory` trait 实现）本来就打算把整批结果收集成 `Vec` 返回——物化开销
/// 是它们契约的一部分，不是意外。`scan_stream` 面向 OOP wire 层的
/// `recall_page`/`recent_page`：它们的字节预算/扫描预算可能在任意一行提前生效，
/// 提前生效之后"已经取出但还没用上"的行应该是零，不是一批的剩余部分。
///
/// SQL 层面仍然带 `LIMIT`（`q.limit`，调用方按决策 P3 传
/// `MEMORY_SCAN_ROW_BUDGET`/`page_size`），作为纵深防御——即使调用方的循环逻辑
/// 有 bug 忘记提前 break，数据库本身也不会被要求准备无限行。
///
/// v2 更正：这条 `LIMIT` 同时是"worker 线程最多能往 channel 里塞多少行"的
/// 上界——`row_buffer_size`（连接级选项，见调用方 §3.2 的 v2 更正）只影响
/// worker 领先消费者多少行，不影响 worker 总共会产出多少行，后者恒由这条
/// `LIMIT` 决定。
///
/// v4 更正（L1，第三轮评审）：上面一段原来还写着"提前退出后已经取出但还没用上
/// 的行应该是零"——这句话是本文档 v1 阶段的残留，跟 §3.3/§6.4/§8 已经证明的
/// "最多 `ROW_BUFFER_MARGIN`（9）个已被 SQLite 真实产出、但 consumer 从未
/// `.next()` 到的行"直接矛盾，本轮删掉，不再声称"零"——提前退出/取消之后，
/// 已经被 worker 读出但没被消费者看到的行最多是 9 行（channel 里最多 8 行 +
/// worker 可能正阻塞发送的第 9 行），不是零，但也远小于旧"整批 fetch_all"
/// 设计下会剩下的行数。
pub fn scan_stream<'a>(
    &'a self,
    q: &'a EventQuery,
) -> impl futures::Stream<Item = Result<StoredEvent>> + Send + 'a {
    // 与 `scan` 共用同一段 SQL 构造逻辑（提取成一个私有 helper，`scan` 和
    // `scan_stream` 都调用它）——两条路径的 WHERE/ORDER BY/LIMIT 语义必须逐字
    // 一致，这是一个值得在实现阶段用同一个函数返回 (sql, binds) 来保证的性质，
    // 不是两份手写 SQL 靠肉眼对齐。
    let (sql, owner, session, after, before, limit) = build_scan_query(q);
    let mut query = sqlx::query(&sql).bind(owner);
    // …按 scan() 今天的绑定顺序原样绑定 session/after/before/limit…
    query
        .fetch(&self.pool)
        .map(|r| r.map_err(Into::into).and_then(|row| Self::row_to_stored(&row)))
}
```

`recall_page`/`recent_page`（`os_memory.rs` 新增的 inherent 方法，T8.5c v1 决策
D4 已经规划了这两个方法的存在，本文档给出它们的内部实现）改为对这个 stream 逐行
`.next().await`，而不是调用 `self.page(...)`。**`self.page(...)`/`RECALL_PAGE`
两者原样保留，供 `ScopedMemory` trait 的进程内 `recall`/`recent` 继续使用**——
那条路径不经过 wire，没有响应字节预算这个概念（返回值就是 `Vec<Recollection>`，
调用方是同进程的 Rust 代码），T8.5c v1"现状复盘"一节已经论证过这个区分是刻意的，
本文档不改变它。

### 3.3 物化行数上界：有界，不是一个精确的字节数

> **v2 更正（sqlx 预取 High）**：原表述"O(1) × 64 KiB"不成立——sqlx 的
> `fetch()` 不是逐行请求 SQLite，是 worker 线程往容量 `row_buffer_size` 的
> 有界 channel 里主动预取（§3.2 的 v2 更正）。正确的上界要把这个 channel
> 算进去。
>
> **v3 更正（M1，第二轮评审）**：v2 在这里给出的
> `(row_buffer_size + 1) × MAX_SINGLE_RECORD_WIRE_BYTES ≈ 578 KiB` 有两个
> 问题，本轮都改正，不再保留：
>
> 1. **行数本身算漏了一行**：任意时刻可能同时存在的行对象最多是 **10** 个，
>    不是 9 个——consumer 当前正在处理的 1 行（已经从 channel `.next()` 出来，
>    还没被丢弃或推进 `hits`）+ channel 里排队的最多 `row_buffer_size`（8）
>    行 + worker 线程可能正阻塞在把第 9 行 `blocking-send` 进一个已满 channel
>    的路上（这一行已经从 SQLite 读出、存在于 worker 的栈帧里，只是还没进
>    channel）——`1 + 8 + 1 = 10`。（这跟 §6.4/§8 用来算"追不回的行数"的 9
>    是同一个物理现象下两个不同的计数口径：那里数的是"consumer 从未见过、
>    没被计入 `scanned` 的行"（channel 8 + worker 阻塞的 1 = 9），这里数的是
>    "任意时刻内存里同时存在的行对象总数"——consumer 手上那 1 行已经被
>    `scanned` 计过，但对象本身仍然占内存，所以要算进来。两个数字都对，只是
>    回答的问题不同，不应该混用。）
> 2. **`MAX_SINGLE_RECORD_WIRE_BYTES` 不是 resident memory 的准确上界**：它是
>    "序列化成最终 wire 格式之后"的字节数上界（§5.1 的逐字段推导，专门针对
>    `{"id":...,"kind":...,"body":...,"at":...}` 这个 JSON 输出）。但
>    `SqliteRow`（sqlx 从 SQLite C API 拷贝出来的原始行，channel 里排队的
>    正是这个类型）包含的列比 wire 格式多——`mem_events` 表还有 `scope`/
>    `origin`/`causal` 等不出现在 `Recollection` JSON 里的列，这些列同样占
>    内存，`MAX_SINGLE_RECORD_WIRE_BYTES` 没有算它们。反过来，
>    `serde_json::Value` 这棵解码后的节点树（`row_to_stored` 之后、
>    `estimate_item_bytes` 序列化之前的中间表示）通常比它最终编码出的字节数
>    更大——`Value::Object`/`Value::String` 等节点各自带 `HashMap`/`Vec` 的
>    容量开销和指针/长度/对齐填充，不是紧凑的字节数组。这两个方向的偏差（少算
>    列 vs. 解码开销更大）不会刚好互相抵消到等于 wire 大小，不能假装
>    `MAX_SINGLE_RECORD_WIRE_BYTES` 可以直接套用在三种完全不同的表示上
>    （原始 `SqliteRow`、解码后的 `serde_json::Value`、已接纳进响应的编码
>    字节）。

**修法**：这一节只承诺**行数**有界，不承诺一个精确的内存字节数。

流式消费下，任意时刻内存里最多驻留的行对象数量有一个精确、可核实的上界：
worker 线程已经产出、还在 channel 里排队等消费者取走的行（最多
`row_buffer_size` 条，v2 选定 `row_buffer_size=8`，见 §3.2）+ worker 可能正
阻塞在把下一行送进一个已满 channel 的路上（最多再加 1 条）+ 消费者当前正在
处理的那一条（channel 之外，最多再加 1 条）：

> **物化行数上界**：`row_buffer_size + 2 = 10`（v2 选定 `row_buffer_size=8`
> 时）。这个上界不含已经被接纳进 `hits` 的若干条 `Recollection`——那部分的
> 上限本来就是响应字节预算（决策 P4）本身要控制的东西，不是这里的新增开销。

最坏情况的行对象数量从"跟内部批大小（500）成正比"降到"跟一个被本文档显式
选定、比默认值 50 小一个数量级的连接选项（8）成正比且封顶在 10"——这个数字
是可以在实现阶段继续调小（代价是 worker 线程阻塞更频繁）或调大（代价是驻留
行数线性增长）的旋钮，不是一个凭空出现的常量。第 10 节自审第 2 条要求的
"峰值内存不随分区大小线性增长"这条集成测试结论改写为：断言的是"任意时刻，
已经从 SQLite 读出但尚未被 consumer `.next()` 到的行数峰值不超过 9"这个可
观察的行为（给 `EventLog` 包一层计数测试替身即可统计），不是断言一个具体的
字节数阈值。

如果实现阶段确实需要一个字节数量级估算（比如做容量规划），要分别对下面三种
表示给出粗略上界，不要合并成一个公式：

| 表示 | 粗略上界的来源 | 备注 |
|---|---|---|
| 原始 `SqliteRow`（channel 里排队的类型） | 表的全部列（含 `scope`/`origin`/`causal`），不只是 wire 格式用到的四个字段 | 需要读 `mem_events` 的表结构才能给出准确列表，本文档不重复维护一份 |
| 解码后的 `serde_json::Value` 树（`estimate_item_bytes` 序列化之前） | 没有已知的精确系数，只知道方向是"通常大于编码后字节数" | 需要精确值时应该在实现阶段用真实数据做内存分析，不是靠公式推导 |
| 已接纳进响应的编码字节（`hits` 里的内容） | `MEMORY_PAGE_RESPONSE_BUDGET_BYTES`（决策 P4 已经证明的上界） | 唯一一个本文档已经有严谨证明的字节上界，只覆盖响应本身，不覆盖扫描过程中的临时对象 |

## 4. 决策 P3：状态机与 M1 的修正

### 4.1 M1 的病灶，用流式设计直接消除，不是绕过

M1 的原话："`hits.len() == page_size` 时提前 return，到不了 `batch.short ->
None` 分支，wire 语义和测试无法同时满足。" 病灶在于 T8.5c v1 的伪代码依赖一个
**派生信号**——"这批 DB 取到的行数是不是比要求的少"——来推断"分区是不是真的到
底了"，而这两件事只在没有内部分批截断时恰好重合。流式设计换了一种问法：不再
问"这批是不是短批"，改成直接问"这次 `.next().await` 调用本身返回的是不是
`None`"——这不是派生信号，是**事实本身**。只要满足下面这条不变式，`None` 就
可以被无条件信任为"分区真的到底了"：

> **不变式**：只有在 `scanned < MEMORY_SCAN_ROW_BUDGET`（尚未触发扫描预算）时
> 才会去 `.next().await` 拉下一行。反过来说：一旦 `scanned == MEMORY_SCAN_ROW_BUDGET`，
> 循环在**看到这一行的处理结果之后立即返回**，不会再多拉一行去"顺便看看是不是
> 也到底了"。

这条不变式保证了：**能观察到 `None` 的唯一路径，是 SQL 的 `WHERE` 条件下确实
没有更多行了，而不是 `LIMIT` 子句把它截断的**——因为 `LIMIT` 定的就是
`MEMORY_SCAN_ROW_BUDGET`（`recall_page`）或 `page_size`（`recent_page`），跟
"最多允许 `.next()` 被调用多少次"是同一个数字，而我们从不在等于这个数字之后再
多调用一次。`LIMIT` 截断与真正到底，在这个设计下永远不会被混淆成同一个信号
——M1 描述的歧义不是被"处理"了，是这个歧义赖以存在的前提（"批"这个中间层）
被拿掉了。

### 4.2 完整状态机（`recall_page`，`recent_page` 是 `MatchPolicy::Always` 的子集）

> **v4 更正（M5，第三轮评审）**：`recall_page` 原来自己执行
> `let needle = normalize(query);`，但 handler 层为了校验 cursor 指纹
> （§7.1）已经需要规范化一次同一个 `query`——两条独立调用点"看起来一样"，
> 不是"只算一次"。新增一个只能通过一个函数构造的 `Needle` newtype，把
> "整条调用链路只算一次 needle"从文档约定升级成类型签名：

```rust
/// v4 新增（M5）：整条调用链路里唯一允许持有的"已规范化 query"。只能通过
/// 下面这两个关联函数构造——handler 对 `recall` 用真实 `query` 调用
/// `Needle::normalize`，对 `recent`（没有 query）用 `Needle::none_for_recent`
/// 固定空串哨兵（延续 §7.1 v3 的约定，只是现在这个空串只能从这一个函数产生）。
/// 构造出来的同一个值，之后既喂给 `decode_cursor`（校验指纹）又喂给
/// `page_from_stream`（匹配 + 编码新指纹）——`decode_cursor`/`recall_page`/
/// `page_from_stream` 都不再接受裸 `&str`/`query: &str` 参数，堵死"各自独立
/// 再规范化一遍"这条路，不依赖文档里的一句"约定"。
#[derive(Clone)]
pub struct Needle(String);

impl Needle {
    /// 唯一的非空构造入口。`normalize_impl` 的具体规则（trim/大小写折叠…）
    /// 留给 W 在接线时决定，不影响这里的正确性论证（论证只依赖"整条调用
    /// 链路只算一次、且这个值同时喂给 matcher 和指纹"，不依赖规则内容本身，
    /// 见 §7.1 的 M3 更正）。
    pub fn normalize(query: &str) -> Needle {
        Needle(normalize_impl(query))
    }

    /// `recent` 没有 query——固定空串哨兵，跟 v3 已经确立的编码约定一致，
    /// 只是现在只能从这一个函数拿到，调用点不能手写 `Needle(String::new())`
    /// （字段是私有的）。
    pub fn none_for_recent() -> Needle {
        Needle(String::new())
    }

    fn as_str(&self) -> &str {
        &self.0
    }
}
```

> **v4 更正（H1，第三轮评审）**：v3 的 `Reservation<'a>` 借用 `&RateLimiter`、
> 用 `Cell` 存 `touched`/`scanned`，被留在 `bind_to_lifecycle` 包裹的 work
> future **外层**，扫描循环通过 `&Reservation` 跨越多个 `.await` 更新它——
> 这要求 `Reservation: Sync`（跨 `.await` 持有的共享引用 `&T` 要成为
> `Send`，需要 `T: Sync`），但 `Cell` 是 `Send` 不是 `Sync`，这条件在
> `Reservation` 持有 `Cell` 字段时永远不成立。而 `agent24-os-proto/src/rpc.rs`
> 的 `Handler::call` 要求返回值是
> `type CallFuture = Pin<Box<dyn Future<Output = Result<Value, RpcError>> + Send>>`
> ——`dyn Future + Send` 后面没有写生命周期参数，按 Rust 的 trait 对象默认
> 生命周期规则，这个位置的省略默认补 `'static`，所以 `CallFuture` 实际上是
> `'static + Send`，且这个类型上完全没有调用方能传入的生命周期参数可以给
> `Reservation<'a>` 的 `'a` 绑定。v3 的形状因此从两头被卡死：要么
> `Reservation: Sync`（`Cell` 做不到），要么给 `Reservation` 一个非
> `'static` 的生命周期（`CallFuture` 的签名不允许）。
>
> **修法（照 Codex 给的方向改）**：`Reservation` 改成**拥有**一个
> `Arc<RateLimiter>`（不再借用），去掉生命周期参数；整个 guard 移到
> `bind_to_lifecycle` 包裹的 work future **内部**（`async move` 捕获它的
> 所有权，而不是外层持有、内层借用）；扫描函数从 `&Reservation` 换成
> `&mut Reservation`；字段从 `Cell<bool>`/`Cell<u32>` 换成普通 `bool`/`u32`
> ——`&mut` 独占访问不需要内部可变性。`&mut T: Send` 只要求 `T: Send`（不要求
> `T: Sync`，这是 `&T`/`&mut T` 在 `Send` 上天生的不对称），`Arc<RateLimiter>`
> +`bool`+`u32` 组成的 `Reservation` 显然是 `Send`（假设 `RateLimiter: Send +
> Sync`，它已经在跨线程共享的 mount 层单例里被这样使用），所以
> `&mut Reservation` 跨 `.await` 持有也满足 `Send`；`Reservation` 不再借用
> 任何东西，天然 `'static`。正常路径在 work 内部结算（`commit()` 在
> `async move` 块返回之前被调用）；取消时整个 work future（连同它内部按值
> 持有的 `Reservation`）被 `bind_to_lifecycle` 一并 drop，`Reservation::Drop`
> 自然触发结算——外层 `match bind_to_lifecycle(...).await { ... }` 之后的代码
> **不再触碰 `Reservation`**，这是跟 v3 最大的结构差异（v3 是外层
> `reservation.commit(...)`，v4 是内层 `reservation.commit()`，见 §6.5）。
> permit 排队阶段 `Reservation` 还没 `mark_touched()`，取消仍然全额退款，
> 这条行为不变。详细的自洽核对见新增的 §10d 第 1/3 条。

```rust
/// v4 新增（M2，判据 2b 的测试 seam）：状态机的核心循环，生产路径
/// （`recall_page`/`recent_page`）和判据 2b 的测试都调用这一个函数——测试
/// 可以传入一个恒 `Poll::Ready` 的假 stream，不需要另外维护一条"看起来
/// 一样"的实现。`stream` 已经 pin 好，由调用方构造（生产路径是
/// `self.events.scan_stream(&q)`；测试路径是任意实现了
/// `futures::Stream<Item = Result<StoredEvent>>` 的假对象）。
async fn page_from_stream<S>(
    mut stream: std::pin::Pin<&mut S>,
    match_policy: MatchPolicy<'_>,
    needle: &Needle,       // v4（M5）：只用于编码/指纹，跟 match_policy 里的
                            // 子串引用同一个规范化来源，不是又算一遍
    method_tag: u8,
    page_size: usize,
    row_budget: usize,     // recall_page 传 MEMORY_SCAN_ROW_BUDGET，
                            // recent_page 传 page_size（v3 L2：这是预留量）
    mut resolved_seq: Option<i64>,
    // v4（H1）：`&mut`，不带生命周期参数——见上面 H1 的更正。调用方（生产
    // 路径是 §6.5 work future 内部的局部变量；测试路径是测试函数自己）拥有
    // 一个 `Reservation`，这里只借用它跑完这次调用，不拿走所有权——所有权
    // 留在调用方手里，才能在这个函数返回之后由调用方决定何时 `commit()`。
    reservation: &mut Reservation,
) -> Result<RecallPage, MemoryRpcError>
where
    S: futures::Stream<Item = Result<StoredEvent>>,
{
    let mut hits = Vec::with_capacity(page_size);
    let mut scanned = 0usize;
    let encode = |seq: i64| encode_cursor(seq, method_tag, needle);
    // 固定的信封开销：`{"items":[...],"cursor":"..."}` 的大括号/键名/引号，
    // 加上 cursor 本身编码后的长度上界（"v2:" + i64 十进制（至多 19 位）+
    // ":" + 16 位十六进制指纹（FNV-1a 64 位，见 §7.1 的 M3 更正）+ base64
    // 膨胀，仍然远小于 MEMORY_RESPONSE_ENVELOPE_BYTES=128 这个预留的宽松
    // 上界）。
    let mut response_bytes = MEMORY_RESPONSE_ENVELOPE_BYTES;

    // v4（H1）：从这一刻起，这次调用已经准备真正触碰 DB（下一行就是第一次
    // `stream.next().await`）——见 §6.4 的 M3 更正："touched" 表示"已进入
    // DB admission 阶段"，不精确等于"SQL 已经提交给 worker"。
    reservation.mark_touched();

    while scanned < row_budget {
        let Some(row) = stream.next().await else {
            // scanned < row_budget 时看到 None：LIMIT 从未被触发，这是分区
            // （在 `before=resolved_seq` 这个边界之内）真正的尽头。
            // v4 新增（M1）：告诉 `Reservation` 这次是自然耗尽——channel 和
            // worker 此刻都已经排空，结算应该精确等于 `scanned`，不应该再
            // 无条件叠加 `ROW_BUFFER_MARGIN`，见 §6.4。
            reservation.mark_exhausted();
            return Ok(RecallPage { items: hits, cursor: None });
        };
        let row = row.map_err(|e| MemoryRpcError::Store(e.to_string()))?;
        scanned += 1;
        // v4（H1）：普通字段写入，不再是 `Cell`——`page_from_stream` 独占
        // 持有 `&mut reservation`，不需要内部可变性。
        reservation.record_scanned(scanned);
        // 决策 4.5：显式让出点，见 §4.5——不依赖 `stream.next().await`
        // 天然会不会 yield。
        if scanned % SCAN_YIELD_INTERVAL_ROWS == 0 {
            tokio::task::yield_now().await;
        }
        let recollection = to_recollection(row.clone());
        let is_match = match_policy.matches(&recollection); // recent_page: 恒真

        if is_match {
            let item_bytes = estimate_item_bytes(&recollection)?; // 见 4.3
            if response_bytes + item_bytes <= MEMORY_PAGE_RESPONSE_BUDGET_BYTES {
                hits.push(recollection);
                response_bytes += item_bytes;
                resolved_seq = Some(row.seq);
                if hits.len() == page_size {
                    // 命中数够了。不再多拉一行去确认"是不是也恰好到底"——那要
                    // 多付一次 DB 往返，换来一个这次调用用不上的事实。游标保守
                    // 地非空；如果客户端确实已经翻到底，下一次调用会诚实地
                    // 观察到上面的 `None` 分支并返回 cursor=None，只是多一次
                    // 无害的往返（这是 T8.5c v1 D2.3"哨兵探测行"思路里唯一还
                    // 保留的部分——见 4.4 的对照表）。这次没有观察到 `None`，
                    // 不是自然耗尽，不调用 `mark_exhausted()`。
                    return Ok(RecallPage {
                        items: hits,
                        cursor: Some(encode(resolved_seq.expect("just set above"))),
                    });
                }
            } else {
                // 字节预算拒绝：这一行未解决，游标必须停在它之前。同样不是
                // 自然耗尽。
                if hits.is_empty() {
                    // 连这次响应里的第一条都装不下——见决策 P4 的不变式证明，
                    // 这只应该在配置错误时发生，不能静默退化。
                    return Err(MemoryRpcError::Store(
                        "a single record's wire size exceeds \
                         MEMORY_PAGE_RESPONSE_BUDGET_BYTES; the budget is \
                         misconfigured relative to MAX_BODY_BYTES".into(),
                    ));
                }
                return Ok(RecallPage {
                    items: hits,
                    cursor: Some(encode(resolved_seq.expect(
                        "hits is non-empty, so at least one earlier row was resolved",
                    ))),
                });
            }
        } else {
            // 确认不匹配：永久已解决，游标可以越过它。
            resolved_seq = Some(row.seq);
        }
    }
    // scanned == row_budget：我们自己的预算生效，不是分区到底，不是自然耗尽。
    // resolved_seq 此时一定是 Some——循环体至少跑了一次（row_budget 在决策
    // P4 里被要求 >= 1）。
    Ok(RecallPage {
        items: hits,
        cursor: Some(encode(resolved_seq.expect(
            "the loop ran at least once because row_budget >= 1",
        ))),
    })
}

/// `recall_page` 只负责准备参数（构造 SQL、pin 住生产用的 `scan_stream`），
/// 核心状态机委托给上面的 `page_from_stream`。
async fn recall_page(
    &self,
    needle: &Needle,        // v4（M5）：handler 已经算好、同一个值也喂给过
                             // decode_cursor 校验指纹，这里不再重新 normalize
    page_size: usize,       // 已经在 handler 层校验过 1..=MEMORY_MAX_PAGE_SIZE
    cursor: Option<Cursor>, // 已经在 handler 层用同一个 needle 通过
                             // decode_cursor 校验过指纹
    // v4（H1）：`&mut`，不带生命周期参数——`recall_page` 现在活在 §6.5 work
    // future 内部（调用方 `async move` 块拥有 `reservation` 这个局部变量），
    // 不是被外层借用进来。
    reservation: &mut Reservation,
) -> Result<RecallPage, MemoryRpcError> {
    let resolved_seq: Option<i64> = cursor.map(|c| c.seq);
    let q = EventQuery::owner(&self.key)
        .newest()
        .limit(MEMORY_SCAN_ROW_BUDGET as i64);
    let q = match resolved_seq {
        Some(s) => q.before(s),
        None => q,
    };
    let mut stream = std::pin::pin!(self.events.scan_stream(&q));
    page_from_stream(
        stream.as_mut(),
        MatchPolicy::Substring(needle.as_str()),
        needle,
        METHOD_TAG_RECALL,
        page_size,
        MEMORY_SCAN_ROW_BUDGET,
        resolved_seq,
        reservation,
    )
    .await
}

/// `recent_page`——同一个 `page_from_stream`，`MatchPolicy::Always`、
/// `row_budget = page_size`（v3 L2：这是预留量，不再声称"恒等于实付量"，
/// 见 §6.3 的 L2 更正）、`needle` 固定用 `Needle::none_for_recent()` 这个
/// 只能从一处产生的空串哨兵。
async fn recent_page(
    &self,
    page_size: usize,
    cursor: Option<Cursor>,
    reservation: &mut Reservation,
) -> Result<RecallPage, MemoryRpcError> {
    let needle = Needle::none_for_recent();
    let resolved_seq: Option<i64> = cursor.map(|c| c.seq);
    let q = EventQuery::owner(&self.key)
        .newest()
        .limit(page_size as i64);
    let q = match resolved_seq {
        Some(s) => q.before(s),
        None => q,
    };
    let mut stream = std::pin::pin!(self.events.scan_stream(&q));
    page_from_stream(
        stream.as_mut(),
        MatchPolicy::Always,
        &needle,
        METHOD_TAG_RECENT,
        page_size,
        page_size,
        resolved_seq,
        reservation,
    )
    .await
}
```

`recall_page`/`recent_page`/`page_from_stream` 三者的拆分方式本身可以在实现
阶段调整（比如把 `MatchPolicy` 的匹配逻辑内联），但"生产路径和测试路径调用
同一个循环体"这条约束（M2）和"`Reservation` 只在 work future 内部被构造/
结算"这条约束（H1）需要保留。§4.5（H1 的显式让出点）和
`reservation.mark_touched()`/`record_scanned()`/`mark_exhausted()`（结算漏洞
High/M1，§6.4）对 `recall_page`/`recent_page` 同样适用——它们挂在
`page_from_stream` 这个共享的循环体上，不是 `recall_page` 专属的旁支逻辑。

### 4.3 `estimate_item_bytes`——不是估算，是精确值

```rust
/// 一条记录序列化进 `items` 数组后贡献的确切字节数（数组元素本身的 JSON 长度
/// + 一个逗号分隔符；数组的方括号计入 `MEMORY_RESPONSE_ENVELOPE_BYTES`）。
/// 叫 `estimate_` 是因为它在"这一行最终会不会被接纳"这个决策**之前**被调用，
/// 但它算出来的数字本身不是估计——`serde_json::to_vec` 用的正是响应最终会用
/// 的同一套 `Serialize` 实现，两者不会走漏。
fn estimate_item_bytes(item: &Recollection) -> Result<usize, MemoryRpcError> {
    let bytes = serde_json::to_vec(item)
        .map_err(|e| MemoryRpcError::Store(format!("item is not serialisable: {e}")))?;
    Ok(bytes.len() + 1) // +1 是数组里这一项跟下一项之间的逗号（首项也保留这个
                         // 余量，宁可略微保守，不为省一个字节让边界判断更复杂）
}
```

### 4.4 与 T8.5c v1 D2.3"哨兵探测行"概念的对照——保留一半，去掉一半

| T8.5c v1 D2.3 的歧义来源 | 本文档处理方式 |
|---|---|
| "这批 DB 取到的行数比要求的少" 是否等于 "分区到底了"（M1 的病灶） | **完全消除**——流式设计下 `None` 只能来自真正的 SQL 结果耗尽，不再是派生信号（决策 P3 4.1） |
| "命中数恰好等于 `page_size`" 是否恰好也是分区的最后一行 | **保留**，用同一套"下次调用会诚实观察到 `None`"的机制解决，多付一次可能无意义的往返（决策 P3 4.2，`hits.len() == page_size` 分支的注释） |

第二行是本文档跟 T8.5c v1 唯一还保留"下一次调用去确认"这个思路的地方，但它已经
不再叫"哨兵探测行"——它就是这个状态机在"命中数够了"这个分支里诚实地不去多做一次
DB 调用的自然结果，不是一个专门设计出来解决歧义的机制。

### 4.5 决策 P3b：显式让出点，不依赖"天然会有 IO 等待"（H1，第二轮评审）

**问题**：v2 的 §8（P7 取消语义）声称"每一行之间都有一个真实的 `.await` 点
（`stream.next()`）"，暗示这个 `.await` 点本身就足以让 `bind_to_lifecycle` 的
取消/超时信号生效。这个推理有一个没有被检验的前提：`.await` 只有在它对应的
future 真的返回 `Poll::Pending` 时才会把执行权交还给 executor；如果
`stream.next()` 在 channel 里已经有缓冲行时立即返回 `Poll::Ready`，这次
`.await` 在字节码层面只是"取值继续往下执行"，不经过 executor 的调度点。

核对 `agent24-os-proto/src/rpc.rs`（`Handler::call` 文档，约 337-345 行）确认
这不是一个可以放松的假设，是这个 crate 明文写死的不变式：

> "**And the future must yield.** Cancellation, the call timeout and the
> shutdown when the connection ends all take effect at an `.await`; a `poll`
> that loops or blocks synchronously cannot be interrupted by anything in
> this process — `serve` then does not return until it does."

再核对 `agent24-os-proto/src/drain.rs` 里 `bind_to_lifecycle` 的实现（约
710-744 行）：它是 `tokio::select! { biased; work, lifecycle.ended() }`，注释
明确写着"a pending `work` still lets `ended()` be polled on every subsequent
wakeup"——反过来说：如果 `work`（也就是整个 `recall_page`/`recent_page`
调用）的 poll 从来不返回 `Pending`，直到自己跑完才返回 `Ready`，那么
`lifecycle.ended()` 这个分支只会在最开始被 poll 一次，之后没有第二次机会，
跟 `work` 内部循环了多少行完全无关。

而 §3.2（sqlx 预取 High）已经确认 `stream.next().await` 背后是一个容量
`row_buffer_size`（v2 选定 8）的有界 channel：sqlx-sqlite 的 worker 线程持续、
同步地往 channel 里 blocking-send 行（`connection/worker.rs:160-206` 的
`Command::Execute` 分支）。当 worker 线程持续领先消费者时，`.next()` 观察到
的是"channel 里已经有值"——异步 channel 的 receiver 在这种情况下不需要注册
waker、也不需要向 executor 让出，直接同步返回 `Poll::Ready`。如果 worker 线程
始终比消费者快（比如整个分区在 OS page cache 里，没有真实磁盘 IO 造成的自然
阻塞间隙），`recall_page` 的循环体理论上可以在一次 poll 内部连续吃掉全部
`MEMORY_SCAN_ROW_BUDGET`（2000）行都不返回 `Pending`——这不是一个理论上不可能
发生的边界情况，是这个设计明确依赖、但从未被验证过的假设。

**修法（选定：`tokio::task::yield_now().await`，不是把 `lifecycle` 下沉进扫描
循环内部再 `select!`）**：

```rust
/// v3 新增（H1）：扫描循环里显式让出执行权的间隔。选 32：比 `row_buffer_size`
/// （8，§3.2 v2 选定值）大几倍，避免比 sqlx 本身的预取粒度更频繁地触发调度
/// 开销；同时远小于 `MEMORY_SCAN_ROW_BUDGET`（2000），保证最坏情况下"取消
/// 信号最多被推迟 32 行才生效"这个上界是一个远小于 2% 扫描预算的量，不是可以
/// 无限膨胀的东西。跟本文档其它未经运营数据校准的常量（`row_buffer_size`、
/// `MEMORY_RATE_CAPACITY` 等）一样，这个数字给方向和量级，不假装精确。
const SCAN_YIELD_INTERVAL_ROWS: usize = 32;
```

在 §4.2 状态机的循环体里，每处理完一行（`scanned` 递增之后）检查一次：

```rust
scanned += 1;
if scanned % SCAN_YIELD_INTERVAL_ROWS == 0 {
    tokio::task::yield_now().await;
}
```

**为什么选 `yield_now()` 而不是把 `lifecycle` 下沉进扫描循环、在循环内部
`select!`**：

1. **不改变分层**：§6.5（决策 P8）已经把 `bind_to_lifecycle` 放在
   `recall_page`/`recent_page` 调用的**外层**。如果扫描循环内部还要再拿到
   `lifecycle` 引用去 `select!`，`recall_page` 的签名就要多一个跟"取消"相关
   的参数，把 P 这一层本来只关心"分页/游标/计费状态机"的纯函数式方法，变成
   一个需要知道 `RequestLifecycle` 存不存在、怎么 `ended()` 的方法——这跟第 0
   节"范围边界"里"不碰挂载时序/鉴权"的立场是同一类越界，只是换了一个机制
   （取消）。`yield_now()` 不需要知道取消从哪来、怎么判断——它只是诚实地把
   "这个 future 应该在这里给 executor 一个重新调度的机会"这件事做对，取消
   判断完全留在 `bind_to_lifecycle` 已有的外层 `select!` 里，不重复一份。
2. **不产生双重竞态窗口**：如果循环内部也 `select!` 一份 `lifecycle.ended()`，
   就会有两处独立的取消检查点（外层 `bind_to_lifecycle` 一处、内层循环一处），
   两者对"取消是否已经发生"在极短时间窗口内可能给出不一致的答案——这类"同一
   件事被两套独立机制分别判断"的模式正是 §6.5 协同自审明确要避免的（该节
   原话："两套互相不知道对方存在的限流/准入机制"）。`yield_now()` 不引入
   判断，只引入一个调度点，不会跟外层 `select!` 的取消判断产生第二个权威
   来源。
3. **判据可以只测"让出"这件事本身，不需要一起搭一个假 lifecycle**：见第 9
   节新增判据 2b。

**这条机制到底保证了什么，不多也不少（v4 更正，M2，第三轮评审）**：之前的
表述容易被读成"每 32 行 yield 一次就能保证取消在扫描预算耗尽前生效"——这个
说法在方向上没错，但不够精确，容易被误读成"取消总能在 32 行内生效"这种更强
的、本节机制实际给不出的承诺。准确的表述是：**从 `lifecycle` 变为 ready（比如
超时、连接断开、显式 `$/cancelRequest`）的那一刻起，`work` 最多再处理一个
`SCAN_YIELD_INTERVAL_ROWS`（32）行的让出间隔，除非 `work` 在下一个 yield 点
之前自然完成（正常返回或出错）**——"lifecycle ready"和"下一次 `yield_now()`
真的把控制权交还给 executor"之间有一个真实的窗口，这个窗口的上界是"下一个
让出点前还没处理的行数"，不是"从调用开始算起的 32 行"。这条更精确的表述同时
是 §8（P7）取消响应窗口描述的依据，也是判据 2b（第 9 节，v4 更新为覆盖多个
phase offset）要验证的确切声称。

**跟 §6.4（H2/M1 的 reservation 结算）的接口关系**：`yield_now()` 只是在循环体
中间插入一个 `.await` 点，不修改、不重置、不暂停 `scanned` 计数器的值——
`scanned` 在 `yield_now().await` 前后是同一个局部变量，取消发生在
`yield_now().await` 期间等价于取消发生在"已经从 stream 取得第 `scanned`
行"这个时刻（v4 更正，L1：原表述"处理完第 `scanned` 行、还没处理第
`scanned+1` 行"不准确——§4.2 的伪代码顺序是先 `stream.next().await` 取出
这一行、`scanned += 1`、`record_scanned(scanned)`，然后才是 `yield_now()`，
再往后才是 `to_recollection`/匹配/序列化这些真正的"处理"；`yield_now()`
发生时这一行只是"已经从 stream 取出、计入 `scanned`"，还没被真正处理，这个
措辞不准确不影响计费结论——`scanned` 计数本身没错，只是文字描述跟伪代码的
实际顺序对不上，本轮改正）。这正是 §6.4 结算公式本来就假设的取消发生位置——
`scanned` 在取消那一刻的值不会因为多了这个让出点而变得不准确或者需要额外
处理（详见第 10c 节自审，以及新增的 §10d 第 3 条）。

## 5. 决策 P4：响应字节预算与"单条记录必须小于页预算"不变式

### 5.1 不变式的具体证明，不是断言

> **v2 更正（const assert Medium）**：原表述里 `kind` 字段的最坏字节数直接用
> `MAX_KIND_BYTES = 128` 加引号余量，没有考虑 JSON 转义膨胀——`kind` 是调用方
> 提供的字符串，`MAX_KIND_BYTES` 限的是**原始 UTF-8 字节数**（`os_memory.rs:576`
> 的 `what.kind.len() > MAX_KIND_BYTES` 是对原始 `&str` 调用 `.len()`），但
> `serde_json` 序列化时，字符串里的每个控制字符（`U+0000`..`U+001F`，1 字节）
> 最坏情况会被转义成 `\u00xx`（6 字节）——所以 128 字节原始输入的最坏 JSON
> 输出不是 128+2（引号），是 `128 × 6 + 2 = 770` 字节。原表述的 `131` 是一个
> 手写死的魔法数字，既没有引用 `MAX_KIND_BYTES`，也没有算转义，下面的推导和
> 编译期断言都已改写。

`recall_page`/`recent_page` 的循环在 `hits.is_empty()` 时遇到字节预算拒绝会返回
显式错误（决策 P3 4.2），这条分支只有在下面的不变式被违反时才会被触发——本节
证明这个不变式在当前常量下成立，且给出它未来被破坏时的检测手段。

**单条记录最坏情况 wire 大小的上界**（`Recollection` 序列化为
`{"id":"...","kind":"...","body":{...},"at":"..."}`）：

| 字段 | 最坏情况字节数 | 依据 |
|---|---|---|
| `id` | 39 | `osmem:` (6) + ULID (26) + JSON 引号/转义余量 (7) |
| `kind` | 770 | `MAX_KIND_BYTES = 128`（`os_memory.rs:135`）个原始字节，**全部**是控制字符时最坏转义成 `\u00xx`（每字节 6 倍），即 `128 × 6 = 768`，加引号 (2) |
| `body` | 65_539 | `MAX_BODY_BYTES = 64 * 1024`（`os_memory.rs:141`，写入前已强制）+ 大括号已含在内，留 3 字节键名/冒号余量 |
| `at` | 34 | ISO 8601 带时区，`"YYYY-MM-DDTHH:MM:SS.sssZ"` 量级 + 引号 |
| 字段名与结构 | ~40 | `"id":`/`"kind":`/`"body":`/`"at":`/大括号/逗号 |
| **合计** | **≈ 66_422 字节 ≈ 64.9 KiB** | |

> `body` 字段没有同样的转义膨胀问题：`MAX_BODY_BYTES` 本来就是对
> `serde_json::to_vec(&what.body)` **编码之后**的字节数做的限制
> （`os_memory.rs:584` 的 `encoded.len() > MAX_BODY_BYTES`，`encoded` 是已经
> 序列化的结果），不是对原始结构体做的限制，所以这里不需要再叠加一次转义
> 系数——这正是本节要提醒的：同一份代码里两个"MAX_*_BYTES"常量约束的对象不同
> （一个是原始输入、一个是已编码输出），逐字段核对依据不能想当然地套同一个
> 公式。

**结论**：`MEMORY_PAGE_RESPONSE_BUDGET_BYTES = 512 * 1024 = 524_288` 字节
（T8.5c v1 D2.2 已定的值，本文档沿用），对比单条最坏情况 ≈ 66_422 字节，仍有
**约 7.89 倍余量**——`MEMORY_RESPONSE_ENVELOPE_BYTES`（信封开销，本文档定为
`128`，远小于这个余量）加进去也不会撼动这个结论。

**把这条证明变成可核实的东西，不是留在文档里的一段推理**：

```rust
/// 一个原始字节在 JSON 里最坏情况下的转义膨胀系数——控制字符（`U+0000`..
/// `U+001F`）被转义成 `\u00xx`，1 字节变 6 字节。`kind` 是唯一一个用原始长度
/// （不是已编码长度）做限制的字段（见 §5.1 的 v2 更正），所以只有它需要乘这
/// 个系数；`body`/`id`/`at` 的常量本身已经是编码后的字节数或者受控的固定格式
/// （ULID/ISO 8601 不含需要转义的字符），不重复应用。
const JSON_ESCAPE_WORST_CASE_FACTOR: usize = 6;

/// 单条记录的最坏情况 wire 大小上界——见设计文档 §5.1 的逐字段推导。
const MAX_SINGLE_RECORD_WIRE_BYTES: usize = 39 /* id */
    + MAX_KIND_BYTES * JSON_ESCAPE_WORST_CASE_FACTOR + 2 /* kind，含转义膨胀 */
    + MAX_BODY_BYTES /* body，已经是编码后字节数，见 §5.1 的旁注 */
    + 34 /* at */
    + 40 /* 结构 */;

const _: () = assert!(
    MEMORY_PAGE_RESPONSE_BUDGET_BYTES
        >= MAX_SINGLE_RECORD_WIRE_BYTES + MEMORY_RESPONSE_ENVELOPE_BYTES,
    "a single worst-case record must fit in one page's response budget, or \
     recall_page/recent_page can get stuck rejecting the very first candidate",
);

/// v2 新增（const assert Medium）：上面这条断言只证明"一条记录装得进一页"，
/// 没有证明"一页装得进一个 JSON-RPC 响应帧"——两者是不同的常量、不同的层。
/// `agent24-os-proto` 的帧协议（`frame.rs::MAX_FRAME_BYTES = 1024 * 1024`）
/// 限的是整条换行分隔的 JSON-RPC 消息，页预算之外还要再加 JSON-RPC 的外层
/// 信封（`{"jsonrpc":"2.0","id":...,"result":{...}}`）和最大 `request id`。
/// 最大 `request id` **不是**本文档臆造的数字——`agent24_os_proto::rpc` 已经
/// 有一个真实的公开常量 `MAX_ID_BYTES = 256`（`rpc.rs:92`，`rpc.rs:546` 的
/// `s.len() <= MAX_ID_BYTES` 就是这条限制的强制点），`initialize.rs` 自己的
/// "最大 initialize 装得进一帧"这条既有测试（`the_largest_possible_initialize_
/// fits_in_one_frame`）就是直接引用这同一个常量（`"x".repeat(crate::rpc::
/// MAX_ID_BYTES)`），本文档直接复用它，不重新估一个数字。
const MAX_JSONRPC_ENVELOPE_BYTES: usize = 96; // `{"jsonrpc":"2.0","id":"…","result":…}` 骨架，留宽松余量

/// v3 新增（M2，第二轮评审）：`MAX_ID_BYTES`（`rpc.rs:92`，256）限制的是原始
/// Rust 字符串的字节长度，不是它序列化进 JSON-RPC 帧之后的长度——`rpc.rs:546`
/// 的 `s.len() <= MAX_ID_BYTES` 校验的正是原始 `&str`，跟上面 `kind` 字段
/// （§5.1 开头的表格）同一类问题：256 个字节全部是控制字符的最坏输入，
/// 序列化后不是 `256 + 2`，是 `256 × 6 + 2 = 1538` 字节（每个控制字符转义成
/// `\u00xx`，6 倍膨胀；`+2` 是两侧引号——跟 `kind` 用的是同一个
/// `JSON_ESCAPE_WORST_CASE_FACTOR`）。原来的断言直接用 `MAX_ID_BYTES`（256）
/// 参与计算，等于假设 `id` 不含任何需要转义的字符——这个假设从未被
/// `MAX_ID_BYTES` 的校验点强制过，不能当成前提。（`+2` 的引号跟下面
/// `MAX_JSONRPC_ENVELOPE_BYTES` 骨架字符串里已经写的那一对引号有 2 字节
/// 重复计算——`MAX_JSONRPC_ENVELOPE_BYTES=96` 本来就是"留宽松余量"的估计，
/// 重复计 2 字节只会让这条断言更保守，不会让它变得不正确，不需要为了省
/// 2 字节去精确切分两个常量各自负责哪一半引号。）
const MAX_ID_WIRE_BYTES: usize =
    agent24_os_proto::rpc::MAX_ID_BYTES * JSON_ESCAPE_WORST_CASE_FACTOR + 2;

const _: () = assert!(
    MAX_JSONRPC_ENVELOPE_BYTES
        + MAX_ID_WIRE_BYTES
        + MEMORY_PAGE_RESPONSE_BUDGET_BYTES
        < agent24_os_proto::frame::MAX_FRAME_BYTES,
    "a full page response, wrapped in the JSON-RPC envelope with the largest \
     allowed request id (worst-case JSON-escaped), must still fit under one \
     frame, or a maximally-full recall_page/recent_page response can never be \
     sent as a single frame",
);
```

这是两个 `const` 上下文里的 `assert!`（Rust 1.57+ 支持在 `const` 求值里
panic），**编译期失败**，不是运行期才发现——任何人改动 `MAX_KIND_BYTES`/
`MAX_BODY_BYTES`/`MEMORY_PAGE_RESPONSE_BUDGET_BYTES`/`MAX_FRAME_BYTES` 让
其中任意一条不变式不再成立，代码直接编译不过，不需要等到跑判据（见第 9 节）
才发现。第一条断言证明"单条记录装得进页"，第二条断言证明"整页（含 JSON-RPC
信封与最大 request id）装得进帧"——两条链在一起才是"一次 `recall_page`/
`recent_page` 调用的响应，无论多满，总能作为一个合法帧发出"这个完整声称，
少一条都只是部分证明。

### 5.2 运行时防线：不变式万一被绕过（比如两个常量之外还有别的贡献者算错了）

决策 P3 4.2 的 `hits.is_empty()` 分支是运行时的最后一道防线——即使编译期的
`const_assert` 因为某种原因被移除或绕过，这个分支保证"连第一条都装不下"永远
表现为一个显式的 `internal` 错误，而不是：
- 静默返回空 `items` + `cursor: None`（等价于"这个分区没有匹配"，是错的——
  数据仍然存在，只是没被检查到就被误判成"没有"）；
- 静默返回空 `items` + `cursor: Some(同一个位置)`（游标没有前进，调用方重试
  会死循环）。

两条防线一起构成"证明 + 兜底"，不是只有其中一条。

## 6. 决策 P5：限流成本模型重设计（M2）

### 6.1 M2 指出的两个问题，分开处理

> `try_acquire()` 固定扣一个令牌；`remember`/`recall`/`recent`（最多检查 2000
> 行）成本差异巨大；每模块一桶也不能限制多模块并发打满共享连接池。

第一句是**单个 Generation 内部**的成本模型问题——6.2/6.3 直接解决，v2 在 6.4
把"预收费"改成"预留+结算"两阶段（预扣计费 High）。第二句是**跨 Generation
（跨模块）**的问题——加权令牌桶这一层确实看不到别的模块，但"看不到就不设计"
在 v1 里被写成了"划给 W 决定要不要做"，这是本轮**连接池准入 High** 指出的问题：
共享连接池会被并发 OOP recall 饿死是一个必然发生、不是"看情况"的事实（sqlx
的 stream 在整个生命周期持有一个池连接，见 6.5 的代码证据），v2 把它改写成对
W 的 MUST 契约，不再是留白声明。

### 6.2 加权令牌桶：`RateLimiter::try_acquire_weighted`

`crate::events_emit::RateLimiter`（`events_emit.rs:90`）今天只有
`try_acquire(&self) -> bool`，固定扣 1。新增一个加权版本，`try_acquire` 保留、
定义为 `try_acquire_weighted(ScanCost::ONE)` 的语法糖——**不改变**
`_a24/events/emit` 现有调用点的行为，纯加法：

> **v2 更正（负成本 Low）**：`cost: f64` 这个签名允许调用方传负数或 `NaN`——
> 负数会让 `bucket.tokens -= cost` 变成给桶"充值"（绕过限流甚至让桶溢出容量
> 检查前的中间态），`NaN` 会让 `bucket.tokens >= cost` 恒为 `false`（比较涉及
> `NaN` 恒假），效果是恒定拒绝，不是崩溃，但一样不是这个类型该允许调用方触发
> 的状态。原文用 `debug_assert!(cost > 0.0)` 防呆——release 构建里
> `debug_assert!` 直接被编译掉，等于没有防护。v2 把 `cost` 的类型从裸 `f64`
> 换成一个只能持有非负整数的 newtype，让"负成本"在调用点的类型层面就不可
> 构造，不依赖任何运行时检查（更不依赖只在 debug 构建生效的检查）：

```rust
/// 一次 `try_acquire_weighted` 调用要扣的令牌数。整数、非负——由类型保证，
/// 不是运行时检查：这个类型的值只能通过下面这几个关联函数或字面量常量得到，
/// 构造路径上没有一个允许负数或非数字（`f64` 的 `NaN`/`Infinity`）进来，所以
/// release 构建和 debug 构建对这条约束的保证力度相同。
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub struct ScanCost(u32);

impl ScanCost {
    pub const ONE: ScanCost = ScanCost(1);

    /// `recall`/`recent` 的扫描成本恒是行数（决策 P5 6.3），行数天然是
    /// 非负整数，`usize -> u32` 的溢出（单次调用扫超过 40 亿行）不是这个系统
    /// 会出现的场景，但仍然用 `try_from`/`expect` 而不是裸 `as` 截断，保持
    /// "构造失败就是编译期或调用点立刻可见的错误，不是静默截断"这条原则。
    pub fn from_rows(rows: usize) -> ScanCost {
        ScanCost(u32::try_from(rows).expect("row counts fit in u32 for any bucket this system uses"))
    }

    /// `from_rows` 的 `const fn` 版本，专用于定义 `MEMORY_COST_RECALL` 这类
    /// 编译期常量（`const fn` 里不能 `.expect()` 一个 `Result`，所以这里用
    /// `usize as u32` 的直接转换——调用点永远是本文档写死的字面量常量
    /// （`MEMORY_SCAN_ROW_BUDGET = 2_000`），不是任意运行时输入，截断风险
    /// 不适用，跟 `from_rows` 对运行时输入的防御不是同一个场景）。
    ///
    /// v3 更正（L1，第二轮评审）：这个函数本身在 v2 里没有任何防护——今天
    /// 唯一的调用点（`MEMORY_SCAN_ROW_BUDGET = 2_000`、`ROW_BUFFER_MARGIN`
    /// 用的 `8`）都远小于 `u32::MAX`，所以截断不会真的发生，但"今天的调用点
    /// 都安全"不等于"这个函数本身安全"——如果将来有人在这里传入一个超过
    /// `u32::MAX`（约 42.9 亿）的常量，`rows as u32` 会静默截断，得到一个
    /// 错误但看起来合法的 `ScanCost`，编译不会报错，问题要等到运行时才可能
    /// 被发现（甚至可能永远不被发现，只是限流额度算错了）。`assert!` 在
    /// `const fn`/`const` 上下文里的 panic 是编译期失败（Rust 1.57+，第 5.1
    /// 节两条 `const _: () = assert!(...)` 已经在用同一个机制），加一行就能
    /// 把这类错误从"运行时静默变小"变成"编译不过"，成本几乎为零：
    pub const fn from_rows_const(rows: usize) -> ScanCost {
        assert!(
            rows <= u32::MAX as usize,
            "ScanCost::from_rows_const: rows must fit in u32, or the cast below \
             silently truncates a compile-time constant"
        );
        ScanCost(rows as u32)
    }

    /// 饱和加法——用于 6.4 结算时给 `scanned` 叠加 `row_buffer_size` 保守
    /// 余量，溢出封顶在 `u32::MAX`（实践中不会触达，因为结算侧还会再用
    /// `min(reserved)` 钳一次，这里只是不让加法本身 panic）。
    pub const fn saturating_add(self, other: ScanCost) -> ScanCost {
        ScanCost(self.0.saturating_add(other.0))
    }

    fn as_f64(self) -> f64 {
        self.0 as f64
    }
}

impl RateLimiter {
    /// 与 `try_acquire` 同一把锁、同一次 refill 计算，只是扣的不是固定的 1，
    /// 而是调用方给出的 `cost`——`ScanCost` 的类型本身已经排除了负数/`NaN`，
    /// 这里不需要也不做防御性检查。
    pub fn try_acquire_weighted(&self, cost: ScanCost) -> bool {
        let cost = cost.as_f64();
        let mut bucket = self.bucket.lock().unwrap_or_else(PoisonError::into_inner);
        let now = self.clock.now();
        let elapsed = now.saturating_duration_since(bucket.last).as_secs_f64();
        bucket.tokens = (bucket.tokens + elapsed * self.refill_per_sec).min(self.capacity);
        bucket.last = now;
        if bucket.tokens >= cost {
            bucket.tokens -= cost;
            true
        } else {
            false
        }
    }

    pub fn try_acquire(&self) -> bool {
        self.try_acquire_weighted(ScanCost::ONE)
    }

    /// v2 新增（决策 P5b，6.4）：把之前扣掉的令牌还回桶里，钳制在
    /// `capacity`——跟 `try_acquire_weighted` 共用同一把锁，"退款"和"扣款"
    /// 对同一个 `bucket.tokens` 的读改写不会交错出竞态。退款不触发 refill
    /// 计算（`bucket.last` 不变）：退款是把预留的一部分还回去，不是时间流逝
    /// 带来的自然恢复，两件事分开记账更不容易在审计时混淆"这次多出来的配额
    /// 是退的还是补的"。
    fn refund(&self, amount: u32) {
        let mut bucket = self.bucket.lock().unwrap_or_else(PoisonError::into_inner);
        bucket.tokens = (bucket.tokens + amount as f64).min(self.capacity);
    }
}
```

### 6.3 三个方法的准入成本——按最坏情况预收费，不是按实际用量事后结算

**为什么是"预收费"而不是"用完再扣"**：令牌桶的意义是准入控制——在工作开始之前
决定要不要放行。如果改成"这次 `recall` 实际扫了多少行，事后再扣相应的令牌"，
那么令牌桶在工作**开始前**完全不起限制作用——一个模块可以并发发起任意多个
"事后才计费"的 `recall`，等它们都跑完了才发现桶早就透支了，这时候连接池已经被
打满，限流本该防止的事情已经发生了。所以必须按**这次调用可能达到的最坏成本**
预先扣款：

```rust
pub(crate) const MEMORY_RATE_CAPACITY: f64 = 4_000.0;
pub(crate) const MEMORY_RATE_REFILL_PER_SEC: f64 = 1_000.0;

/// `remember` 是一次写入，不扫描——恒定成本。
const MEMORY_COST_REMEMBER: ScanCost = ScanCost::ONE;
/// `recall` 最坏情况下要扫 `MEMORY_SCAN_ROW_BUDGET` 行才能给出答案（哪怕一条都
/// 不匹配）——用这次调用**可能**造成的扫描上限预收费，而不是"平均情况"或
/// "这次实际扫了多少"（那两者都要工作做完之后才知道，无法用来做准入判断）。
/// v2：这只是**预留**（reservation）的量，不是最终一定会扣的量——见 6.4。
const MEMORY_COST_RECALL: ScanCost = ScanCost::from_rows_const(MEMORY_SCAN_ROW_BUDGET); // = 2_000
/// `recent` 的准入**预留**量恒等于调用方请求的 `page_size`（T8.5c v1 D2.1
/// 已经论证：一条 `ORDER BY seq DESC LIMIT page_size`，没有 Rust 侧过滤，
/// 分区够长时扫描即返回）——用调用方实际请求的 `page_size`，不是
/// `MEMORY_MAX_PAGE_SIZE` 的上限。
///
/// v3 更正（L2，第二轮评审）：这只是**预留**量，不再声称"预留恒等于实付"。
/// v2 曾经在这里论证"recent 没有提前找到匹配就停这回事，所以预留量本身就是
/// 精确值，6.4 的 reservation/refund 模型对 recent 是恒等映射"——这句话只在
/// "分区剩余行数 >= page_size 且响应字节预算够用"这个子情形里成立：分区剩余
/// 行数少于 `page_size`（`.next()` 提前观察到 `None`），或者响应字节预算在
/// 凑够 `page_size` 条之前就被打满（§4.2 状态机"字节预算拒绝"分支），这两种
/// 场景下 `recent` 实际扫描的行数都会小于 `page_size`。既然 §6.4 已经引入了
/// 统一的 reservation/refund 结算模型，`recent` 不应该单独保留一条"预留=实付，
/// 不需要退款"的旧例外——它跟 `recall`/`remember_checked` 走同一套结算公式
/// （`actual = scanned + ROW_BUFFER_MARGIN`，钳制在 `reserved` 之内），只是
/// `recent` 在分区够长、字节预算够用的常见情况下，结算值会非常接近预留值，
/// 不是数学上恒等于它。
fn memory_cost_recent(page_size: usize) -> ScanCost {
    ScanCost::from_rows(page_size)
}
```

`MEMORY_RATE_CAPACITY = 4_000`、`MEMORY_RATE_REFILL_PER_SEC = 1_000` 是本轮的
猜测值（同 T8.5b 对配额默认值、T8.5c v1 D10 对原有 `MEMORY_RATE_CAPACITY=30` 的
态度一致——运营数据出来之前不假装精确）：按这两个数字，一个模块连续发起满预算
的 `recall`（每次扣 2000）大约每 2 秒能发起一次，突发情况下桶里的 4000 容量够
连续发两次满预算 `recall` 或者更多小请求的组合，具体调参留给实现阶段结合真实
延迟数据校准。

**三个方法继续共用同一个 `RateLimiter` 实例**（T8.5c v1 D10 已经论证的理由：
分开计量会让"交替调用三个方法绕开单独的桶"变得容易；本文档在这个决策上不变，
只是把"扣多少"从固定 1 换成加权）。

> **v2 更正（限流身份 Critical）**：原文这里写"每代重建（进内层闭包，同
> D10……崩溃重启不能用来刷新配额）"——这句话内部自相矛盾：memory
> `RateLimiter` 如果真的在 `methods_for` 闭包内部创建（"每代重建"），那么
> 重启（= 新一代）就恰好会得到一个全新的满桶，跟同一句话后半句"崩溃重启不能
> 用来刷新配额"直接冲突。核对 `agent24d/src/domain.rs:1327-1337`：现有
> `_a24/events/emit` 的 `RateLimiter` 确实是"每代重建"——`Arc::new(move
> |generation| { let limiter = Arc::new(RateLimiter::new(...)); ... })`，
> `limiter` 在闭包**内部**构造，闭包本身就是 `methods_for`，每次
> `(re)start`（每一代）都会重新跑一遍闭包体，得到一个全新的桶。这是
> **events 专属**的先例（`events_emit.rs` 自己的设计取舍，本文档第 1 节已
> 指出这条先例被 D4/D10 沿用来做别的决定），但 SPEC §5 对 memory 限流的要求
> 是"以稳定 `(module, partition)` 为键、跨 restart generation 生效"——这跟
> events 的要求相反，不能照抄。
>
> **修法**：memory 的 `RateLimiter` 在 **mount 层**创建一次，不在
> `methods_for` 闭包内部创建。"mount 层"指的是 `mount_package`
> （`domain.rs:1218`）/`lend()`（`domain.rs:282`）这一层——它们只在模块
> **挂载**时跑一次（对一个正在运行的模块，重启不会重新跑 `mount_package`，
> 只会重新跑 `methods_for` 闭包），`OsScopedMemory`/`event_sink`/
> `approval_broker` 这些已经需要跨代存活的东西都是在这一层构造、再作为闭包
> 捕获变量 `clone()` 进 `methods_for` 的——memory 的 `RateLimiter` 走同一条
> 已经存在的路径，不需要新发明一层"跨代存活"的基础设施。构造点与
> `OsScopedMemory::new` 同层（`domain.rs:291` 附近，`lend()` 返回
> `Arc<OsScopedMemory>` 的地方），身份就是它天然绑定的 `(module, partition)`
> ——`lend()` 本来就是按模块、按分区各调用一次，不需要额外的 `HashMap` 键控
> 结构。
>
> 这条修法只挪动**限流桶的身份**（`RateLimiter` 实例本身何时创建、生存多
> 久），6.2/6.3 的**加权成本模型**（扣多少）完全不变；6.4 的 reservation/
> refund 模型建在这个正确身份之上。判据 8（第 9 节）已按这个新语义重写。

### 6.4 决策 P5b：预收费改成"预留 + 结算"两阶段（预扣计费 High）

**问题**：6.3 的预收费模型按 `MEMORY_COST_RECALL = MEMORY_SCAN_ROW_BUDGET`（最
坏情况）扣款，但决策 P3 的状态机在命中 `page_size` 条或遇到第一个不匹配的匹配
边界就可能提前返回——一个 `page_size=1` 且第一行就命中的 `recall`，实际只扫了
1 行，却按 2000 行收费，被高估最多约 2000 倍。调大 `MEMORY_RATE_CAPACITY`/
`MEMORY_RATE_REFILL_PER_SEC` 治不了这个问题：那只是把"高估"这件事的后果变得
不那么疼，"扫 1 行的调用挤占跟扫 2000 行一样多的额度"这个错误比例关系本身没变，
调大容量到能容纳更多"1 行 recall"的同时，也会让"故意发起满预算 recall 打满
`MEMORY_SCAN_ROW_BUDGET` 应该被限住"这条判据（第 9 节判据 6）的阈值一起松动
——这是一个此消彼长、没有单一旋钮能同时解决的矛盾，根源是模型本身（预收费按
最坏情况、不结算），不是参数选得不对。

**修法**：两阶段——`try_acquire_weighted` 在调用**开始前**按最坏情况预留（这一
步不变，保留决策 6.1 的论证：准入判断必须在工作开始前用最坏情况做，否则起不到
限流作用），调用**结束后**按实际发生的成本结算，多退。

> **v4 更正（M1，第三轮评审）**：v3 这里把 `ROW_BUFFER_MARGIN` 定义成
> `from_rows_const(8)`，但改动表（第 56 行）自己说的是"应该是 `scanned + 9`，
> 不是 `scanned + 8`"——`8` 是 channel 容量（`row_buffer_size`），但 worker
> 线程领先消费者的真实上界不止 channel 里排队的这 8 行：worker 还可能正阻塞
> 在把**第 9 行**送进一个已经满了的 channel 的路上（这一行已经被 SQLite
> 真实读出，只是还没排进 channel）——这第 9 行是 §3.3 的"物化行数上界"和
> §8（P7）"追不回的窗口"两处都已经在用的同一个数字，唯独 §6.4 这里定义
> 常量时漏了它。v3 的 §10c 第 2 条自审（"H2"）反过来论证"余量本来就该等于
> `row_buffer_size`（8），不是 `row_buffer_size + 1`"——这条自审的结论是
> **错的**：它把"consumer 手上那 1 行"（已经计入 `scanned`，不需要再算进
> 余量）跟"worker 阻塞发送的第 9 行"（**没有**计入 `scanned`，需要算进
> 余量）混成了同一件事。两者是不同的行——前者是 §3.3"10"这个总数里的
> "consumer 当前手上 1 行"，后者是 channel 之外、worker 栈帧里的另一行，
> 两者都不在 `scanned` 里，但只有后者需要被计入结算余量。v4 改正：
> `ROW_BUFFER_MARGIN` 是 `channel 容量（8）+ worker 阻塞发送的这一行（1）
> = 9`，§10c 第 2 条自审的错误结论已经在该处追加更正说明（见 §10c）。
>
> **v4 更正（M1 的第二部分）**：v3 的结算公式对"consumer 已经观察到流结束
> （`None`）"和"提前返回/取消/出错"两种情况一视同仁，都无条件加
> `ROW_BUFFER_MARGIN`——但前者的 channel 和 worker 此刻都已经排空（SQL 的
> `WHERE` 条件下确实没有更多行了，见决策 P3 4.1 的不变式），不应该再叠加
> 一个"worker 可能领先"的余量，成本应该精确等于 `scanned`。v4 给
> `Reservation` 新增一个 `exhausted` 状态区分这两种情况（见下面
> `mark_exhausted`），并把 `commit()`/`Drop` 的结算公式统一收进一个
> `settle_amount()` 方法，不再各自维护一份公式。

```rust
/// v4 更正（M1，第三轮评审）：结算/取消时都要用到的保守余量——worker 线程
/// 可能领先消费者最多这么多行（channel 容量 `row_buffer_size`=8 + worker
/// 正阻塞发送的第 9 行）。8 → 9 是本轮改正的口径错误，见上面的 v4 更正。
/// 定义在这里（`Reservation::settle_amount` 需要它），§6.5 直接复用这个
/// 常量，不再各自维护一份字面量。
const ROW_BUFFER_MARGIN: ScanCost = ScanCost::from_rows_const(9);

/// 一次 `RateLimiter` 预留的 RAII 守卫。构造时已经从桶里扣掉了
/// `reserved`——`RateLimiter` 内部账本上，这些令牌已经不在桶里了，不是"承诺
/// 会扣"。结算（`commit()`/`Drop`）把 `reserved - actual` 退回桶里，
/// `actual` 由 `settle_amount()` 统一计算。
///
/// **v4 更正（H1，第三轮评审）——所有权模型全部重写**：v3 版本是
/// `pub struct Reservation<'a> { limiter: &'a RateLimiter, ... touched:
/// Cell<bool>, scanned: Cell<u32>, ... }`，借用 `RateLimiter`、用 `Cell`
/// 支持"外层持有、内层通过 `&Reservation` 跨 `.await` 更新"这个用法。这个
/// 形状跟 `agent24-os-proto::rpc::CallFuture`（`Pin<Box<dyn Future<Output =
/// ...> + Send>>`，隐式 `'static`）不兼容——见 §4.2 开头的 H1 详细论证。
/// v4 改成**拥有**一个 `Arc<RateLimiter>`，去掉生命周期参数，字段从 `Cell`
/// 换成普通字段（不再需要内部可变性，因为访问方式从 `&Reservation` 换成了
/// `&mut Reservation`，见 §4.2 的 `page_from_stream`）。`Reservation` 现在
/// 整个生命周期都在 §6.5 的 work future **内部**（`async move` 块拥有它的
/// 所有权），不再是外层持有、内层借用。
///
/// **不再有"整个调用全额退款"这一条捷径**（H2 结论，v3 已经确立、v4 沿用）：
/// - 还没进入扫描循环/执行写入（`Semaphore::acquire` 阶段就被取消、或者
///   `try_acquire_weighted` 之后、扫描/写入开始之前的任何提前失败）——
///   `touched` 仍是 `false`，没有产生任何真实的 DB 成本，全额退款。
/// - 已经进入扫描循环或执行写入（`touched == true`，见下面 `mark_touched`）
///   ——不管这次调用最终是正常完成、出错还是被取消，都按 `settle_amount()`
///   结算，`commit()` 和 `Drop` 用的是同一个方法，不是两份独立的公式（v3
///   在这里是 `commit(actual)` 由调用方传参、`Drop` 自己算一遍，两处容易
///   在改动时失去同步——v4 把这两条路径收敛成一个方法）。
#[must_use = "a reservation that is silently dropped without commit() settles \
              by its recorded scanned/exhausted state instead, never refunds \
              everything once DB scanning has started"]
pub struct Reservation {
    limiter: Arc<RateLimiter>,
    reserved: ScanCost,
    /// 扫描循环/写入路径有没有真的开始过——决定结算走哪条分支。普通
    /// `bool`：`Reservation` 现在只通过 `&mut self` 被访问（H1），不需要
    /// `Cell` 提供的内部可变性。
    touched: bool,
    /// 扫描循环里已经真实处理过的行数，实时写入——即使这个值所在的 future
    /// 在循环中途被 `bind_to_lifecycle` 取消（drop），只要取消发生之前至少
    /// 跑过一次 `record_scanned`，这个值就已经是最新的，`Drop` 能读到它
    /// （`Reservation` 现在按值存在于 work future 内部，取消 = 整个 work
    /// future 被 drop，`Reservation` 随之被 drop，触发它自己的 `Drop`）。
    scanned: u32,
    /// v4 新增（M1）：这次扫描是否已经自然耗尽——`page_from_stream` 在观察
    /// 到真正的 `None`（决策 P3 4.1 的不变式保证的"分区真的到底了"）时调用
    /// 一次 `mark_exhausted()`。耗尽时 channel 和 worker 都已经排空，结算
    /// 不应该再叠加 `ROW_BUFFER_MARGIN`。
    exhausted: bool,
    committed: bool,
}

impl Reservation {
    /// 用 `cost` 全额预留，预留失败（桶里不够）时不产生 `Reservation`——跟
    /// `try_acquire_weighted` 今天的语义一致，只是把"扣款"这个副作用包进一个
    /// 会自动退款/结算的守卫里。v4：`limiter` 现在是按值传入的
    /// `Arc<RateLimiter>`（调用方 `clone()` 一份），不是借用。
    fn reserve(limiter: Arc<RateLimiter>, cost: ScanCost) -> Option<Self> {
        limiter.try_acquire_weighted(cost).then(|| Reservation {
            limiter,
            reserved: cost,
            touched: false,
            scanned: 0,
            exhausted: false,
            committed: false,
        })
    }

    /// 标记"这次调用已经准备真正触碰 DB"——`recall_page`/`recent_page`
    /// （经由 `page_from_stream`）/`remember_checked` 在进入各自的扫描循环
    /// 或执行 `INSERT` 之前调用一次。之后即使立刻被取消，结算也会认为这次
    /// 调用产生过真实成本，不走全额退款。
    ///
    /// **v4 更正（M3，第三轮评审）——这个边界具体指什么，说清楚，不夸大**：
    /// 调用点在 `stream.next().await`/`append(...).await` **之前**，但这两个
    /// `.await` 本身可能先阻塞在从共享 `SqlitePool` 里 `acquire()` 一个连接
    /// 上（§6.5 的 admission permit 只保证"允许尝试"，不保证连接立刻可用；
    /// `busy_timeout=5s` 意味着写路径还可能在拿到连接后继续阻塞等 SQLite
    /// 写锁）——所以 `touched=true` 精确表示的是"这次调用已经通过全局 admission
    /// permit、即将尝试对共享连接池做一次真实操作"，也就是**已进入 DB
    /// admission 阶段**，不精确等于"SQL 已经被交给 SQLite worker 执行"这个
    /// 更晚、更难观察的时刻。选择这个更保守的计费边界（选项①，而不是把
    /// `touched` 信号下沉到真正拿到连接/提交命令之后才置位的选项②）：① 不
    /// 需要改动 `agent24-memory` 存储层内部（`touched` 完全是 P 这一层自己
    /// 维护的状态，选项②需要在 sqlx 连接获取路径上插一个钩子，那是存储层的
    /// 改动，超出本文档"只设计状态机"的范围）；② 计费边界比物理写入边界更
    /// 保守，意味着"多收一点点"（取消发生在 admission 之后、连接还没到手
    /// 之前，仍然按已触碰计费），不是"少收"——跟决策 P4 的错误处理原则一致
    /// （宁可保守，不要在计费方向上给调用方可乘之机）；③ 这个边界和 §8
    /// （P7）"已经执行的写不回滚"这条论证描述的是两件不同的事——P7 说的是
    /// **物理副作用**能不能追回，这里说的是**要不要收费**，两者不要求
    /// 精确重合，§8 的写场景已经补充说明这一点。
    pub fn mark_touched(&mut self) {
        self.touched = true;
    }

    /// 扫描循环每处理一行调用一次，记录目前已经真实处理过的行数——这是"DB
    /// 扫描进行到哪里了"这件事在 `Reservation` 内部唯一的证据来源，结算时
    /// 直接读它。v4：普通字段写入（`&mut self`），不再是 `Cell`。
    pub fn record_scanned(&mut self, scanned: usize) {
        self.scanned = u32::try_from(scanned).unwrap_or(u32::MAX);
    }

    /// v4 新增（M1）：`page_from_stream` 在观察到真正的流耗尽（`.next()`
    /// 返回 `None`，且 `scanned < row_budget`，见决策 P3 4.1）时调用一次。
    pub fn mark_exhausted(&mut self) {
        self.exhausted = true;
    }

    /// v4 新增（M1）：`commit()`/`Drop` 共用的唯一结算公式——不再有两份
    /// 独立维护、容易失去同步的公式。
    fn settle_amount(&self) -> u32 {
        if !self.touched {
            return 0; // 全额退款：结算成本为 0。
        }
        if self.exhausted {
            // 消费者已经观察到流结束：channel/worker 都已排空，没有"领先但
            // 未观察到"的行，成本精确等于 scanned。
            self.scanned.min(self.reserved.0)
        } else {
            // 提前返回/取消/出错：channel 里最多 ROW_BUFFER_MARGIN（9）行
            // 已经被 SQLite 真实产出但消费者从未观察到，计入成本；`min` 钳制
            // 在 `reserved` 对应的行数内（SQL 层的 `LIMIT` 保证 worker 一次
            // 调用总共产出的行数不会超过这个数，这个 `min` 不会削掉任何真实
            // 发生的成本，只是防止保守加法本身超过物理不可能达到的上限）。
            self.scanned.saturating_add(ROW_BUFFER_MARGIN.0).min(self.reserved.0)
        }
    }

    /// 正常完成路径显式调用——不再需要调用方自己传 `actual`：
    /// `settle_amount()` 已经知道 `touched`/`scanned`/`exhausted`，调用方
    /// 不用（也不能）在外面重新算一遍这个公式。
    pub fn commit(mut self) {
        let actual = self.settle_amount();
        self.limiter.refund(self.reserved.0.saturating_sub(actual));
        self.committed = true;
    }
}

impl Drop for Reservation {
    fn drop(&mut self) {
        if self.committed {
            return;
        }
        let actual = self.settle_amount();
        self.limiter.refund(self.reserved.0.saturating_sub(actual));
    }
}
```

**跟 sqlx 预取 High 的选定方案（`row_buffer_size=8`）与 M1 的协同**：
`settle_amount()` 里的 `scanned`（§4.2 的 `scanned` 变量）只是"消费者从
stream 里 `.next()` 出来处理过几行"，但 §3.2 已经确认 worker 线程在消费者
背后是**领先**消费的：`.next()` 返回 `None`、循环提前 `return`、或者外层
future 被取消导致 stream 被 drop 的那一刻，worker 线程完全可能已经把最多
`ROW_BUFFER_MARGIN`（9 = channel 容量 8 + worker 阻塞发送的第 9 行）行
消费者从未 `.next()` 过的行读出——那些行是 SQLite **真实执行过**的读，是
这次调用对连接池/CPU 造成的真实成本的一部分，只是没有被 Rust 侧的循环体
"看到"。`exhausted` 状态把"consumer 已经诚实观察到 `None`（这种情况下这个
领先的余量必然是空——SQL 层已经证明没有更多行了）"和"提前退出（这种情况下
余量可能非空，必须保守地算上）"分开，不再对两种情况一视同仁。

**这条修法只影响结算，不影响连接池占用**：预留/结算管的是 `RateLimiter`
这个逻辑配额（决定"要不要放行下一次调用"），跟 6.5（决策 P8）管理的物理连接
槽位是两个不同的资源——6.5 会说明两者的获取顺序和互不知情的边界，这里先只
说明结算本身怎么算。

**跟 6.3 常量表的关系**：`MEMORY_COST_RECALL`/`memory_cost_recent` 现在是
`Reservation::reserve` 的输入（预留量），不再是最终一定花掉的量——6.3 的表格
本身不用改，改的是"扣了就不退"这个假设。

### 6.5 决策 P8：跨模块连接池准入许可（连接池准入 High，MUST）

**v2 新增**：v1 把这一节写成"P 暴露几个接口，W 决定要不要在这之上加信号量"，
本轮评审指出这个措辞本身就是问题——共享连接池被饿死不是"要不要加保护"的设计
选择，是当前架构下**必然发生**的事实。证据（读代码复核）：

- `agent24-memory/src/lib.rs:205`：`KvStore`/`EventLog` 共用同一个
  `SqlitePoolOptions::max_connections(5)` 的池——这是一个**跨模块共享**的
  单一物理资源，不是每个模块各有一份。
- `sqlx-core-0.8.6/src/pool/executor.rs:17-35`：`impl Executor for &Pool` 的
  `fetch_many` 实现是
  ```rust
  Box::pin(try_stream! {
      let mut conn = pool.acquire().await?;
      let mut s = conn.fetch_many(query);
      while let Some(v) = s.try_next().await? { r#yield!(v); }
      Ok(())
  })
  ```
  `conn` 在 `try_stream!` 生成的 generator 里，从 `acquire()` 成功那一刻起，
  跨过**每一次** `r#yield!`，直到这个 `Box::pin` 的 stream 被完整消费或者被
  drop 才会被释放——一个 `scan_stream`（`&self.pool` 是 `&Pool`）只要还没被
  轮询到底，就一直占着一个连接，不是"用一下就还"。
- 直接结论：**5 个并发的 `recall_page`/`recent_page` 调用（不管是同一个模块
  连续发起还是不同模块各发起一个）就能把这个池的 5 个连接全部占满**，此时任何
  第 6 个想用这个池的调用方——不管是另一个 OOP 模块的 memory 调用，还是
  `ScopedMemory` trait 的进程内调用——都会在 `pool.acquire()` 上排队，直到
  某个 stream 被消费完或者超时/取消。这不是理论风险，是 `max_connections(5)`
  这个当前值和"stream 持有连接直到耗尽"这个 sqlx 行为组合之后的算术必然。

> **v3 更正（H3，第二轮评审）**：v2 在这里把 `remember_checked` 排除在 permit
> 之外，理由是它"单条 `INSERT` 不经过流式 `fetch_many`"——这个理由只说对了
> "`remember_checked` 不会像 `scan_stream` 一样长期持有连接直到整批耗尽"，
> 没有考虑到它仍然要从共享 pool 里 `acquire()` 一个连接，而 SQLite 是单写者：
> `KvStore::open`（`agent24-memory/src/lib.rs:203-205` 附近）给这个共享池
> 配了 `busy_timeout(Duration::from_secs(5))`——一次 `remember_checked` 的
> `INSERT` 如果撞上另一个写入者持有的写锁，可以在拿着一个 pool 连接的同时
> 阻塞长达 5 秒去等这把锁，这段时间里这个连接跟一个慢 `scan_stream` 占着
> 连接没有本质区别。更麻烦的是：如果只给读路径设 permit、放任写路径不受限，
> 多个模块可以各自发起 `remember_checked`，每个都先从 pool `acquire()` 成功
> （因为它们没有被任何 permit 挡住），然后各自阻塞在等 SQLite 写锁上——这些
> 连接全部被真实占用，跟决策 P8 想防止的"并发占满连接池"是同一件事，只是
> 触发路径从"读的 stream 没耗尽"换成了"写的锁竞争"。
>
> **两个候选修法**：① 三个方法（`remember_checked`/`recall_page`/
> `recent_page`）共享同一个 admission permit；② 给读、写各定义一个独立
> 预算，证明两者之和严格小于 `max_connections`。本文档选①，理由：SQLite 的
> 写并发本质上是"单写者"，但这不代表*并发发起*写请求的数量有界——多个模块
> 可以同时调用 `remember_checked`，每个都先拿到一个 pool 连接、再排队等写锁，
> 如果给写路径单独开一个预算，这个预算本身也需要被限制得足够小（否则"写请求
> 各自占一个连接排队等锁"这个场景照样能吃光连接），而且还要重新证明
> "读预算 + 写预算 < max_connections"在写预算被调整时依然成立——这是一个需要
> 持续维护的不变式，比"只有一个总预算，改一个数字"更容易在未来被无意打破。
> 一个统一的 admission permit 不需要证明这类"两个数字之和"的不变式，正确性
> 只依赖 permit 总数本身小于 `max_connections`，选①更简单也更不容易腐化。

**MUST 契约**（P 对 W 的强制要求，不是可选实现建议）：

1. **必须有一个全局共享的 admission permit**，限制"同一时刻有多少个会真正
   触碰共享 `SqlitePool` 连接的 `_a24/memory/private/*` 调用——
   `recall_page`/`recent_page` 的 `scan_stream`，以及 `remember_checked` 的
   写入——可以同时持有池连接"。三者**共享同一个** permit，不给
   `remember_checked` 开一条不受限的旁路（见上面 H3 的 v3 更正）。
2. **持有者是谁、共享范围多大**：permit（建议
   `Arc<tokio::sync::Semaphore>`）必须在**与共享池本身相同的作用域**创建——
   即 `server.rs`（`agent24_memory::KvStore::open` 被调用的地方，`server.rs`
   附近，这是目前唯一一处打开这个共享池的地方）创建**一次**，作为daemon 级
   单例，再向下传给每个模块的 `mount_package`/`methods_for`。**不能**是
   "每个 catalog 一个"或者"每个模块 mount 一个"——那样又回到"各自为政、互相
   看不见"的老问题，跟当前"只有一个共享池"的架构事实不匹配。
   - **给进程内路径留 headroom**：permit 总数应该**小于** `max_connections`
     （建议 `max_connections - 1 = 4`），不是等于——固定预留至少 1 个连接
     给不经过这个 permit 的调用方（`ScopedMemory` trait 的进程内
     `recall`/`recent`，以及 `KvStore` 自己的其它查询），否则 OOP 路径打满
     4 个连接之后，第 5 个连接理论上还空着，但如果 permit 数等于
     `max_connections`，OOP 路径自己就能连这最后一个也占满，进程内路径一样
     会被饿死——留 headroom 的意义就是不让"跨模块保护"这件事本身耗尽保护对象。
3. **permit 等待必须在 `bind_to_lifecycle` 包裹的同一个 future 里**——不能
   写成"先在生命周期信号之外 `semaphore.acquire().await` 排队，排到了再把
   剩下的工作包进 `bind_to_lifecycle`"。理由：T8.5a 的
   `bind_to_lifecycle`（`agent24-os-proto/src/drain.rs`，`events_emit.rs:289`
   的既有调用点是这个机制唯一的实际接线示例）存在的意义就是让一次 RPC 调用
   受它自己的请求生命周期（超时/连接断开）约束——如果排队等 permit 这一步
   被放在 `bind_to_lifecycle` 之外，一个已经超时或者连接已断开的调用方仍然会
   占着"排队中"的位置，直到轮到它才发现自己其实已经该被取消了，这跟决策 P7
   第 3 类场景（"排队中、尚未开始的工作可以被自由丢弃"）的前提矛盾——那条
   前提成立的条件正是"排队本身在生命周期信号覆盖范围内"。
4. **取消时的释放**：`tokio::sync::Semaphore::acquire` 返回的
   `SemaphorePermit`/`OwnedSemaphorePermit` 是 RAII 守卫，`Drop` 释放——只要
   第 3 点做到了（permit 获取和 `scan_stream` 循环体在同一个被
   `bind_to_lifecycle` 包裹的 future 里），`bind_to_lifecycle` 对这个 future
   的取消（drop）会自动级联 drop 这个 permit 守卫，不需要额外的手动释放代码，
   跟决策 P7 第 2/3 类场景已经描述的"drop 即释放"是同一个机制的复用，不是
   新发明一套。
5. **判据**：**v3 更正（H3）**：v2 这里写的是"用测试专用的、卡住不返回第一行
   的假 `EventStore` 实现"——这个判据方案本身有两个问题，不能直接采用：
   一，`scan_stream` 是 `EventLog` 的**inherent** 方法（第 1 节已经论证过这个
   决定，理由跟 `remember_checked`/`recall_page`/`recent_page` 是同一套：
   `EventStore` trait 只有 `EventLog` 一个实现者），不在 `EventStore` trait
   上——测试没有一个"实现 `EventStore` trait 的假对象"可以拦截
   `recall_page`/`recent_page` 实际调用的 `scan_stream`，"卡住不返回第一行的
   假 `EventStore`"这个构造在类型层面就接不上真实调用路径。二，即使能 mock，
   mock 也证明不了"真实的物理连接被占住"这件事——它只能证明"调用方的 Rust
   代码在等一个 mock 返回"，不涉及 pool 里的连接槽位有没有被真实 `acquire()`
   占用，测不出 H3 想验证的那类"多个并发调用把 5 个连接占满"的真实资源竞争。

   > **v4 更正（M4，第三轮评审）**：v3 这里把修法定成"开一个真实连接执行
   > `BEGIN IMMEDIATE`/慢查询"——这确实证明了"pool 会被真实占用"，但证明不了
   > H3 真正要求的那件事：`remember_checked`/`recall_page`/`recent_page`
   > **三个方法接的是同一个 permit**。如果判据只是"发起四个某种调用，占满
   > 4 个连接，第五个排队"，即使三个方法各自偷偷拿了独立的 permit（比如实现
   > 阶段有人把 §6.5 第 1 点"三者共享同一个 permit"这条 MUST 契约做错，各自
   > 建了一个 `Semaphore`），只要单独测一个方法，判据一样会通过——因为它测的
   > 只是"这一个方法自己的准入行为"，没有测"三者是不是共用同一份配额"。

   **修法（v4，改成能证明"共享同一个 permit"的模型，不是只证明"pool 会被
   占用"）**：

   1. **pool 之外**开一个独立的 SQLite 连接（不经过 `agent24_memory::KvStore`
      的共享池，直接 `sqlx::SqliteConnection::connect` 或等价方式连到同一个
      数据库文件），执行 `BEGIN IMMEDIATE` 并保持事务开着——这把数据库层面的
      写锁真实持有住，不占用共享池里的任何一个连接槽位（这个连接本身在
      permit/pool 之外，是纯粹的锁竞争源，不是被测对象）。
   2. 通过**真实的** OOP handler（走完整的 `Handler::call` → `bind_to_lifecycle`
      → 本节的准入序列，不是直接调 Rust 函数）发起 **4 个** `remember_checked`
      调用——每个都应该成功拿到一个 admission permit、成功从共享池
      `acquire()` 一个连接，然后各自阻塞在等步骤 1 持有的写锁上（`INSERT`
      撞上 `busy_timeout`）。到这一步，4 个 permit（`max_connections - 1`）
      全部被这 4 个 `remember_checked` 调用占用，且它们确实各自持有一个
      真实的 pool 连接（在等锁，不是在等 permit）。
   3. **（WAL 模式下）** 用第 5 个、**不经过 admission permit** 的路径——
      `ScopedMemory` trait 的进程内 `recall`（`fetch_all`，T8.5c v1 决策 D4
      已经论证这条路径不占用本节的 permit）——发起一次真实的进程内读，
      断言它能**正常返回**。WAL 模式下写事务不阻塞并发读，这条读会走
      共享池里第 5 个连接（`max_connections=5`，前 4 个已被步骤 2 占住）；
      断言它成功，证明"给进程内路径留的 headroom"这条 MUST 契约（本节第 2
      点）是真实生效的，不是文档里的一句空话。
   4. 再发起**第 5 个** OOP 调用（`remember_checked`/`recall_page`/
      `recent_page` 任选一个，测三种组合覆盖三个方法）——断言它卡在
      `Semaphore::acquire()` 上，拿不到 permit（不是"池里理论上还有连接"
      就绕过 permit——池确实还有第 5 个连接，但这个 OOP 调用被挡在 permit
      这一层，根本没有走到 `pool.acquire()`）。
   5. **v4 新增（M4 明确要求）**：不能只测 `remember_checked`。对
      `recall_page`/`recent_page` 各补一条同构的测试——先用步骤 2 那 4 个
      `remember_checked` 占满 4 个 permit，再分别发起一个 `recall_page`/
      `recent_page` 调用，断言它们**同样**卡在 `Semaphore::acquire()` 上
      （不是各自有独立的准入判断、只是走了不同的方法名字）。这五条测试
      （4 个 `remember_checked` 打底 + `recall_page`/`recent_page`/第 5 个
      `remember_checked` 三选一组合各测一次）合在一起才真正证明"三个方法
      接入了同一个 permit"，只测其中一个方法组合不能代表另外两个也验证过。

   这条判据直接对应"跨模块占满连接后进程内路径不被饿死"以及"三个方法共享
   同一份准入配额"这两条 MUST 契约的可观察结果，写进第 9 节判据列表（判据
   9b，v4 已重写）。

**与 6.4（reservation/refund）的协同，不是两套互不知情的机制**：`RateLimiter`
（6.3/6.4）和这里的 `Semaphore`（本节）管的是两种不同的资源——前者是"每
`(module, partition)` 的逻辑扫描配额"（防止单个模块用高频/满预算调用挤占
自己的份额，是一个**速率**限制），后者是"全体模块共享的物理连接槽位"（防止
并发请求耗尽一个硬性有限的资源，是一个**并发度**限制）。两者都要经过，顺序
固定为**先 `RateLimiter` 后 `Semaphore`**：`RateLimiter::try_acquire_weighted`
是纯内存操作、非阻塞、立即返回成功或失败；`Semaphore::acquire` 可能真的
`.await` 排队。先做便宜且可能瞬间失败的检查，再做可能昂贵的等待——如果反过来
（先排队等 permit，permit 到手后才发现被 `RateLimiter` 拒绝），一个注定会被
拒绝的调用会白白占着一个稀缺的连接槽位排队名额，直到轮到它才被拒绝，这正是
"跨模块保护机制自己造成新的饥饿"的另一种形式。伪代码顺序（供 W 实现
`recall_page`/`recent_page` 时参考，不是本文档新增的状态机分支，只是把 §4.2
现有状态机和这两个准入检查按顺序串起来）：

> **v4 更正（H1，第三轮评审）——两处伪代码都按新的 `Reservation` 所有权
> 模型重写**：v3 版本在 `bind_to_lifecycle` **外层**构造 `reservation`
> （`Reservation::reserve(&limiter, ...)`，借用），把 `&reservation` 借给
> work future 内部用，再在 `match` 的成功分支里从外层调用
> `reservation.commit(...)`。这个形状要求 `Reservation: Sync`（§4.2 已经
> 论证过为什么行不通）。v4 的形状是：`reservation` 仍然在 `bind_to_lifecycle`
> **之前**用 `Reservation::reserve(limiter.clone(), ...)` 构造（这一步本身
> 不 `.await`，构造完之后立刻要么整体移交给 work future、要么在预留失败时
> 直接返回——外层代码在这一步之后不再持有它），然后用 `async move` 把它的
> **所有权**移进 work future；`commit()` 在 work future **内部**、`Ok` 返回
> 之前被调用；外层 `match bind_to_lifecycle(...).await { ... }` 的每一个分支
> 都不再触碰 `reservation`——取消/出错时它已经随 work future 一起被 drop，
> `Drop` 自己结算。permit 也换成 `Arc<Semaphore>::acquire_owned()`
> （返回 `OwnedSemaphorePermit`，不借用 `Semaphore` 的生命周期）而不是
> `acquire()`（返回的 `SemaphorePermit<'_>` 会绑定 `Semaphore` 的生命周期，
> 同样跟 `CallFuture` 需要的 `'static` 冲突）——两处需要的都是"整个 work
> future 除了通过 `Arc`/`Arc`-like 类型之外，不借用任何外部状态"这同一条
> 原则，`Reservation`（H1）和 permit 是这条原则在两个不同资源上的应用。

```rust
// `ROW_BUFFER_MARGIN` 定义在 §6.4（`Reservation::settle_amount` 需要它），
// 这里直接复用同一个常量，不重复定义。

let Some(reservation) = Reservation::reserve(limiter.clone(), MEMORY_COST_RECALL) else {
    return Err(MemoryRpcError::application(ErrorKind::RateLimited, "…"));
};
let admission = memory_connection_admission.clone(); // Arc<Semaphore>，读写共享同一个 permit（H3）
match bind_to_lifecycle(lifecycle, async move {
    // v4（H1）：`acquire_owned()`，不是 `acquire()`——排队等待也在生命周期
    // 信号覆盖范围内，且不借用 `admission` 之外的任何东西。
    let _permit = admission.acquire_owned().await?;
    // §4.2 的 `recall_page`（内部委托 `page_from_stream`）；`reservation` 在
    // 这里是被这个 `async move` 块按值捕获的局部变量，`&mut reservation`
    // 借给 `recall_page`，循环体内部调用 `mark_touched()`/`record_scanned()`/
    // `mark_exhausted()`。
    let page = self.recall_page(&needle, page_size, cursor, &mut reservation).await?;
    // v4（H1/M1）：结算发生在 work **内部**——`settle_amount()` 已经知道
    // `touched`/`scanned`/`exhausted`，这里不需要调用方再传 `actual`。
    reservation.commit();
    Ok(page)
})
.await
{
    Ok(Ok(page)) => Ok(page),
    // 取消/出错（外层 `LifecycleTimeout` 或内层 `MemoryRpcError`）：整个
    // `async move` 块（连同它按值持有的 `reservation`、`_permit`）已经被
    // `bind_to_lifecycle` 一起 drop——`Reservation::Drop` 按 §6.4 的
    // `settle_amount()` 结算（没碰过 DB 全额退款，碰过 DB 按
    // touched/scanned/exhausted 结算），`OwnedSemaphorePermit` 的 `Drop`
    // 自动释放 permit（本节第 4 点）——两个 RAII 守卫都在 work future 内部，
    // 独立退出，互不依赖对方的清理逻辑，顺序不影响正确性。这个 `match` 之后
    // **没有任何代码**需要知道 `reservation`/`_permit` 的存在，`map_error`
    // 只是把 `LifecycleTimeout`/`MemoryRpcError` 统一映射成对外的错误类型。
    other => map_error(other),
}
```

**v3 新增（H3）：`remember_checked` 走同一条准入路径**——形状跟上面一致，只是
`recall_page` 换成一次 `INSERT`，`MEMORY_COST_RECALL` 换成
`MEMORY_COST_REMEMBER`（恒为 `ScanCost::ONE`）；v4 同样按 H1 的新所有权模型
重写：

```rust
let Some(reservation) = Reservation::reserve(limiter.clone(), MEMORY_COST_REMEMBER) else {
    return Err(MemoryRpcError::application(ErrorKind::RateLimited, "…"));
};
let admission = memory_connection_admission.clone(); // 跟 recall_page/recent_page 同一个 permit
match bind_to_lifecycle(lifecycle, async move {
    let _permit = admission.acquire_owned().await?;
    // 即将执行 INSERT——`mark_touched()` 标记的是"已进入 DB admission 阶段"
    // （见 §6.4 的 M3 更正），不精确等于"SQL 已经交给 worker"；即使这一步
    // 之后立刻被取消，也按已触碰计费，不做全额退款。
    reservation.mark_touched();
    let seq = self.events.append(&event).await?;
    // `remember` 的成本恒为 1（决策 6.3），没有"扫描到一半"这回事，也没有
    // "自然耗尽"这个状态（`exhausted` 保持 `false`）——`settle_amount()` 算出
    // `min(0 + ROW_BUFFER_MARGIN, reserved=1) = 1`，等价于全额收费。
    reservation.commit();
    Ok(Remembered { seq })
})
.await
{
    Ok(Ok(remembered)) => Ok(remembered),
    // 取消/出错：`reservation`/`_permit` 随 work future 一起 drop，各自的
    // `Drop` 结算/释放——跟 P7 决策 1"已经执行的写不回滚，不是尽力而为之外的
    // 什么优待"一致；touched 边界比物理写入边界更保守这件事，§6.4 的 M3 更正
    // 和 §8 的 P7 场景 1 都已经说明，这里不重复论证。
    other => map_error(other),
}
```

## 7. 决策 P6：`decode_cursor` 显式拒绝非正数（L1）与绑定 query/方法（游标未绑定 query Medium）

T8.5c v1 D9 的 `decode_cursor` 已经对"无法 base64 解码"和"版本前缀不是 `v1:`"
两种情况返回 `invalid_params`（不是静默 `None`）——这部分不重新设计。L1 指出的
缺口是**能解析、但语义非法**的情况：`v1:-1`、`v1:0`。原因是 `str::parse::<i64>()`
对负数和零都成功返回 `Ok`，`decode_cursor` 原来的 `match` 只检查了"能不能
`.parse().ok()`"，没有检查解析出来的值是否是一个合法的 `seq`。

修法（`seq` 的合法范围来自第 1 节确认的存储层事实：`AUTOINCREMENT` 保证
`seq >= 1`）——**v2 在这个修法之上叠加游标未绑定 query 的修法，不是替换它**：

### 7.1 v2 新增：cursor 必须绑定"是哪次调用产生的"（游标未绑定 query Medium）

**问题**：本文档第 2 节的正确性论证（"确认不匹配"对同一个 `query` 永远成立）
依赖一个从未被显式检查过的前提——调用方翻页时，`cursor` 和 `query` 是配套
传入的。但 `cursor` 目前只编码 `seq`，没有编码它是哪个方法（`recall` 还是
`recent`）、哪个 `query`（`recall` 的情况）产生的。如果调用方把
`recall(query="A")` 返回的 `cursor` 传给 `recall(query="B")`——不管是
客户端的 bug，还是恶意/误用（同一条私有 RPC 通道上，调用方是被挂载的模块，
不是本文档信任边界之外的实体，但"信任模块不会犯 bug"跟"允许模块的 bug 导致
数据看起来'丢失'"是两回事）——之前因为不匹配 A 被判定"已解决、可以越过"的
行，在 B 的语境下可能是匹配的，但游标已经越过了它，B 不会再看到它。这不是
"字节预算丢数据"（C1 的场景），是"跨 query 复用 cursor 丢数据"，两者是不同
的漏洞，本文档 v1 只处理了前者。`recall`/`recent` 之间互换 cursor 是同一类
问题的另一种形式（`recent` 的"确认不匹配"分支恒为空，把 `recent` 的 cursor
喂给 `recall`，`recall` 会把"从 `recent` 的位置继续"误当成"从一个已经确认过
所有非匹配的位置继续"，但那个位置从未在 `recall(query)` 的语境下被检查过）。

**修法（选定：cursor 携带并校验 fingerprint，拒绝而不是放行）**：相比"cursor
只是裸位置语义，允许换 query，但撤回'代表已解决行'这个更强声称"这个替代方案
——后者要求把第 2 节现在给出的、可以直接支撑判据 1/3c 的强正确性证明降级成
一个更弱的、"调用方必须自己保证不换 query"的免责声明，这既削弱了本文档最核心
的交付物（C1 的修复依赖的正是那条强证明），也没有真正消除 bug（只是把责任推
给调用方，调用方犯错的后果还是"看起来丢数据"，只是现在文档不再对此负责）。
本文档判断：这是一个内部私有 RPC，调用方数量有限（挂载的 OOP 模块），提前用
一个便宜的指纹校验把"用错 cursor"变成一个显式 `invalid_params`（调用方能立刻
看到、能修的 bug），比允许它静默产生一个"部分行为什么好像不见了"的诡异现象、
让使用方自己去猜原因，对这个方法族的实际使用场景更合适。

```rust
/// cursor 编码升级到 `v2:`——不是重新设计整个编码方案，是在 `v1:<seq>` 的
/// 基础上插入一个指纹字段。指纹只需要"实践中不会意外碰撞"，不需要抵抗蓄意
/// 构造的碰撞（内部私有 RPC，调用方是被挂载模块，不是需要防御主动攻击者的
/// 公网 API）。
///
/// v3 更正（M3，第二轮评审）：FNV-1a 从 32 位换成 64 位——32 位在极小的调用
/// 规模下本来就"实践中不会意外碰撞"，但把它换成 64 位的代价几乎是零（多算
/// 32 位、多存 8 个十六进制字符，仍然远小于 MEMORY_RESPONSE_ENVELOPE_BYTES
/// 的余量），却能把偶然碰撞的概率降低多个数量级——这是评审指出的"几乎没有
/// 成本、值得直接采纳"的改动，不是因为 32 位被证明不够用。
fn cursor_fingerprint(method_tag: u8, needle: &Needle) -> u64 {
    let mut hash: u64 = 0xcbf2_9ce4_8422_2325; // FNV-1a 64 位初值
    for byte in std::iter::once(method_tag).chain(needle.as_str().bytes()) {
        hash ^= byte as u64;
        hash = hash.wrapping_mul(0x0000_0100_0000_01B3);
    }
    hash
}

const METHOD_TAG_RECALL: u8 = 1;
const METHOD_TAG_RECENT: u8 = 2;

fn encode_cursor(seq: i64, method_tag: u8, needle: &Needle) -> String {
    let fp = cursor_fingerprint(method_tag, needle);
    base64_url_no_pad_encode(&format!("v2:{seq}:{fp:016x}"))
}

fn decode_cursor(
    token: &str,
    method_tag: u8,
    needle: &Needle,
) -> Result<i64, MemoryRpcError> {
    let decoded = base64_url_no_pad_decode(token)
        .map_err(|_| MemoryRpcError::Invalid("cursor is not a recognizable token".into()))?;
    let rest = decoded
        .strip_prefix("v2:")
        .ok_or_else(|| MemoryRpcError::Invalid("cursor is not a recognizable token".into()))?;
    let (seq_part, fp_part) = rest
        .split_once(':')
        .ok_or_else(|| MemoryRpcError::Invalid("cursor is not a recognizable token".into()))?;
    let seq: i64 = seq_part
        .parse()
        .map_err(|_| MemoryRpcError::Invalid("cursor is not a recognizable token".into()))?;
    let fp = u64::from_str_radix(fp_part, 16)
        .map_err(|_| MemoryRpcError::Invalid("cursor is not a recognizable token".into()))?;
    if seq < 1 {
        // AUTOINCREMENT 的 seq 从 1 开始且单调递增——0 或负数不可能是任何一行
        // 真实的 seq。悄悄当成 None 会让"游标传错"看起来像"重新翻到最前面"，
        // 比报错更容易被忽略（T8.5c v1 D9 对"无法解析"分支的论证延伸到"能
        // 解析但不合法"这个分支）。
        return Err(MemoryRpcError::Invalid(
            "cursor does not refer to a valid position".into(),
        ));
    }
    if fp != cursor_fingerprint(method_tag, needle) {
        // v2 新增：cursor 是给另一个 method/query 组合发的，不是这次调用的
        // "上一个已解决行"。放行会让第 2 节"确认不匹配对同一个 query 永远
        // 成立"这条证明的前提失效——拒绝，而不是当成一个合法但陌生的位置。
        return Err(MemoryRpcError::Invalid(
            "cursor was issued for a different method or query".into(),
        ));
    }
    Ok(seq)
}
```

> **v3 更正（M3，第二轮评审）**：v2 在这里只要求"encode 和 decode 用同一个
> 规范化函数"——这个约束不够强，一个恒返回空字符串的 `normalize` 也满足它
> （encode 和 decode 确实调用了"同一个函数"），但完全起不到区分不同 query
> 的作用：所有 query 的指纹都会撞在同一个值上，第 9 节判据 5b（不同 query
> 之间不能互相复用 cursor）会失效。
>
> **更强的不变式**：指纹使用的规范化值，必须与 `matches(row, query)`（决策
> P1，§2.1）实际用来做匹配判断的那个值**完全相同**，不是"看起来做了差不多
> 的规范化"。最稳妥的实现方式是整条调用链路只算一次 `needle`（规范化后的
> 查询串）——这一个值既喂给匹配逻辑，也喂给 `cursor_fingerprint`；不允许
> 指纹计算和实际匹配各自独立调用一遍"看起来一样"的规范化函数。两份独立
> 实现即使今天字面相同，也没有任何机制保证未来被同步修改（比如有人只改了
> 匹配逻辑里的大小写折叠规则，忘记同步指纹那一份的规范化逻辑）——一旦两者
> 产生分歧，指纹校验通过之后，第 2 节"确认不匹配对同一个 query 永远成立"
> 这条核心证明的前提会在悄无声息之间失效，这正是指纹机制本来要防的那类
> bug，不能让指纹自己的实现引入同一类风险。
>
> **v4 更正（M5，第三轮评审）**：v3 这里的不变式是"整条调用链路只算一次
> `needle`"——但这只是**文档约定**：v3 §4.2 的 `recall_page` 伪代码自己
> 执行 `let needle = normalize(query);`，跟 handler 层为了校验 cursor 指纹
> （本节，decode_cursor 必须在进入 `recall_page` 之前跑）已经需要的那次
> 规范化，是**两条独立的调用点**——即使今天两处都调用名字相同的
> `normalize` 函数、字面上"看起来只算一次"，类型系统完全不阻止将来有人
> 在其中一处悄悄改了规则、忘记同步另一处，那正是上面 M3 更正想防的同一类
> bug，只是发生的位置从"指纹 vs. 匹配"换成了"handler vs. recall_page"。
>
> **修法（选定方案①，用类型签名强制，不再是文档约定）**：新增
> `Needle` newtype（定义见 §4.2），构造入口唯一（`Needle::normalize`/
> `Needle::none_for_recent`）。`decode_cursor`/`encode_cursor`/
> `cursor_fingerprint`（本节，上面已经改写）和 `recall_page`/
> `recent_page`/`page_from_stream`（§4.2）现在**都**接受 `&Needle`，不再
> 接受裸 `&str`/`query: &str`——handler 只能构造一次 `Needle`，同一个值
> 既传给 `decode_cursor` 做指纹校验，也传给 `recall_page` 做匹配和编码新
> 指纹。这条路径上没有第二个函数签名允许"再传一个 `&str` 进来"，"只算
> 一次"从文档里的一句话变成编译器会检查的事情——如果有人在 handler 层
> 之外的某处又想规范化一次 query，他手里根本没有能喂给 `decode_cursor`/
> `recall_page` 的 `&str` 参数位置可用，唯一能用的入口就是
> `Needle::normalize`。
>
> 相比另一个候选方案②（cursor token 直接传入 page body 内部，由 page body
> 自己做"一次 normalize、然后 decode+match+encode"）：方案②要求把
> `decode_cursor` 的调用点从 handler 层挪进 `recall_page`/`recent_page`
> 内部，这跟第 0 节"范围边界"和本节开头"cursor 必须在进入 `recall_page`
> 之前由 handler 解码并校验"这条已经确立的分层（校验在 handler、状态机
> 只处理"已经校验过"的输入）冲突，需要重新论证这条分层——方案①不改变
> 现有分层，只是把"handler 传什么类型给 `recall_page`"从 `&str` 换成
> `&Needle`，改动范围更小，选①。

`normalize_impl`（原样传入 vs. trim 空白 vs. 大小写折叠）的具体规则留给
handler 层决定——只要 `Needle` 只能通过 `Needle::normalize` 构造一次、
之后被同一个值喂给 `decode_cursor` 和 `recall_page`/`page_from_stream`
（不是各自独立调用一遍名字相同的函数），指纹就能正确往返；本文档不在这里
规定具体的规范化规则，那是 T8.5c-W 接线时的细节，不影响这里的正确性论证。

## 8. 决策 P7：取消语义三分（M5，跟分页强相关的部分）

T8.5c v1 决策 D6 已经把"连接级"与"目标级"取消分开写，但对"存储层操作本身不是
抢占式"这件事只用一句话带过。本文档在分页状态机（决策 P3）已经把"批"这个中间态
换成逐行流式之后，这句话需要被拆成三个精确场景，理由是三者在"取消发生后已经
造成的副作用/资源占用"上是不同的：

1. **已经执行的写（`remember_checked` 的 `INSERT`）**——不回滚。一旦这条 SQL
   语句被交给 sqlx 的连接 worker，取消调用方这一侧的 future 追不回已经提交给
   worker 的语句；它会照常跑完（提交或者失败，取决于语句本身）。这与 T8.5a
   决策 4 已经确立的"取消是尽力而为，不是抢占式"完全一致，`remember_checked`
   没有引入任何比这更强或更弱的保证。
   >
   > **v4 更正（M3，第三轮评审）**：这条场景描述的是**物理副作用能不能追回**
   > 这个边界——"SQL 已经被交给 worker"。§6.4 的 `Reservation::mark_touched()`
   > 用来**计费**的边界（"已进入 DB admission 阶段"）比这个物理边界稍早
   > （`mark_touched()` 在 `append(...).await` 之前调用，而这个 `.await` 本身
   > 可能先阻塞在 `pool.acquire()`/SQLite `busy_timeout` 上，见 §6.4 的 M3
   > 更正）——一次 `remember_checked` 可能在"已经 `mark_touched()`、已经被
   > 计费，但 SQL 还没真正交给 worker"这个窗口里被取消，这时候按这里的定义，
   > 物理写**还没发生**（"不回滚"这条承诺无从谈起，因为压根没有写要回滚），
   > 但 `Reservation` 仍然会按已触碰计费。这不是本条场景的论证有问题，是
   > 计费边界和物理副作用边界这两件事本来就不要求精确重合——一个更保守（早
   > 收费），一个更精确（真正执行才算数），两者的差异已经在 §6.4 的 M3 更正
   > 里说明，这里不重复展开。
2. **正在产出行的读（`recall_page`/`recent_page` 内部的 `scan_stream`）**——
   decision P3 的状态机在每一行之间都有一个真实的 `.await` 点（`stream.next()`）；
   **receiver（调用方的 future）被 drop 之后，这个 stream 不会再被 poll**——但
   这不是抢占式中断，而且**不止"这一次 fetch 会跑完"这么简单**。
   >
   > **v3 更正（H1，第二轮评审）**：上一句"每一行之间都有一个真实的 `.await`
   > 点"本身**不足以**保证取消/超时信号有机会生效——`.await` 只有在对应
   > future 真的返回 `Poll::Pending` 时才会把执行权交还给 executor；sqlx
   > 预取领先消费者时，`stream.next().await` 可能连续多次同步返回
   > `Poll::Ready`（决策 4.5 的详细论证）。本节"取消发生后追不回的窗口最多
   > `row_buffer_size + 1`（9）行"这个结论，依赖的是决策 4.5 新增的显式
   > `tokio::task::yield_now()` 让出点，不是单纯"存在 `.await` 点"这件事本身
   > ——没有显式让出点时，取消理论上可以被推迟到整个
   > `MEMORY_SCAN_ROW_BUDGET`（2000）行扫描预算耗尽才生效，那时"追不回的
   > 窗口"就不是 9 行，是最多 2000 行。决策 4.5 把这个理论上限重新收紧回本节
   > 原本想表达的"个位数量级"，判据 2b（第 9 节）直接验证这一点。
   >
   > **v2 更正（呼应 sqlx 预取 High 的结论）**：原表述"至多一行在飞"不成立。
   > §3.2 已经确认 sqlx-sqlite 的 worker 线程是同步领先消费者产出行的——drop
   > 发生的那一刻，worker 线程可能已经把最多 `row_buffer_size`（v2 选定 8）
   > 条消费者从未见过的行 blocking-send 进了 channel（或者正卡在往一个已满的
   > channel 送第 9 行的路上）。这些行是 SQLite **真实执行过、真实读出来**
   > 的，不是"排队等待、尚未发生"的工作——它们只是恰好没有人来取。取消这个
   > stream，"已经在飞、追不回"的部分是**最多 `row_buffer_size + 1`（9）行**
   > 的读，不是 1 行。这个数字直接对应 §6.4 的结算修正（`actual = scanned +
   > row_buffer_size`）——两处描述的是同一个物理现象（worker 领先消费者），
   > 一处用来算钱，一处用来说取消语义，数字必须一致，这里已经保持一致。
   >
   > 跟"已经执行的写"的区别仍然成立：写的副作用是持久化的（提交到磁盘），读的
   > "副作用"只是消耗了一点 CPU/IO 后被丢弃（channel 被 drop，里面还没被取走
   > 的行连同它们的内存一起释放），不留下任何需要关心的持久状态——**这一点
   > 没有被 v2 推翻，被推翻的只是"追不回的量有多大"这个具体数字**。
   > **逐行流式相对 T8.5c v1 原本"整批 `fetch_all`"设计仍然是实质收紧**：旧
   > 设计下取消发生在 500 行还没取完的中途时，"已经在飞、追不回"的部分最多是
   > 500 行；v2 修正后的新设计是最多 9 行——仍然是接近两个数量级的收紧，只是
   > 不是"收紧到 1 行"这个更强的（错误的）说法。
   >
   > **v4 更正（M2，第三轮评审）**：上面的"9 行"（v4：`ROW_BUFFER_MARGIN`
   > 已经从 8 改成 9，见 §6.4 的 M1 更正）说的是"SQLite 已经真实产出、但
   > consumer 从未观察到"的行数——这是**计费**要用的数字，也是"worker 领先
   > consumer 多少"这一件事本身的物理上界。但它**不是**完整的"取消响应
   > 窗口"：从 `lifecycle` 变为 ready（超时/断开/显式取消）到 work future
   > 真的被 `bind_to_lifecycle` drop 之间，还有决策 4.5 论证过的另一段真实
   > 时间——`work` 可能已经过了最近一次 `yield_now()`，正在处理接下来最多
   > `SCAN_YIELD_INTERVAL_ROWS`（32）行，直到下一个让出点才会把执行权交还给
   > executor、`bind_to_lifecycle` 的 `select!` 才有机会真正选中
   > `lifecycle.ended()` 分支。这 32 行本身**不是计费漏洞**——它们会被
   > `page_from_stream` 正常地 `.next()`、`record_scanned()`，正常计入
   > `scanned`，跟"追不回、未观察到"的 9 行是完全不同的两件事（前者是
   > consumer 确实处理过、只是恰好在取消信号已经 ready 之后才处理的行；后者
   > 是 consumer 压根没处理过、只在 worker 那边发生过的行）。准确的"从
   > lifecycle ready 到实际 drop"这段保守工作窗口，应该表述为：**consumer
   > 最多继续推进一个 `SCAN_YIELD_INTERVAL_ROWS`（32 行）的让出间隔，加上
   > worker 最多额外领先 `ROW_BUFFER_MARGIN`（9 行）**——不是笼统地写成
   > "9 行"（那只是这个窗口里"未被观察到"的那一部分，不是整个窗口）。
   > §4.5 已经按这条更准确的表述改写了它自己的"保证"措辞，本节跟 §4.5
   > 保持一致，不再单独简化成"9 行"。

   **§4.5 的取消保证（v4 引用，避免两处各写一份）**：从 `lifecycle` ready
   到 `work` 真的被 drop，保守上界是"`work` 最多再处理一个 `yield` 间隔
   （32 行），除非它在下一个 yield 点之前自然完成"——这条表述本身、以及它
   跟本节"追不回 9 行"的关系，见 §4.5 的 v4 更正段落，这里不重复第二份。
3. **排队中、尚未开始的工作**——两类：（a）正在等
   `RateLimiter::try_acquire_weighted` 之外的东西，比如尚未进入 §6.5 决策 P8
   那个 `bind_to_lifecycle` future 的调用；（b）**v2 新增，v3（H3）扩大到写
   路径**：正在等决策 P8 的全局连接 admission permit
   （`Semaphore::acquire().await`）、但还没拿到手、还没执行任何存储层交互的
   调用——`recall_page`/`recent_page`/`remember_checked` 三者现在共享同一个
   permit（§6.5 的 H3 更正），三者排队等 permit 时都属于这一类。
   `RateLimiter::try_acquire_weighted` 本身是非阻塞的即时失败，不产生"排队中"
   这个状态，真正会排队等待的是 permit；`Reservation::mark_touched()` 也
   还没被调用（§6.4/§6.5 的伪代码都在 permit 到手**之后**才调用
   `mark_touched()`），所以这一类同时也是"§6.4 的 `Reservation::Drop` 会
   全额退款"的那一类——取消语义（这里）和计费语义（§6.4）在"排队等 permit"
   这个阶段给出的是同一个答案（无条件干净），不是两套互相独立、可能矛盾的
   判断。这两类都可以被自由丢弃：没有任何存储层交互发生过，不需要"尽力而为"
   这个限定词，是无条件干净的取消——这与 §6.5 第 3/4 点"permit 等待必须在
   `bind_to_lifecycle` 内部、取消时 RAII 自动释放"是同一个结论在两个角度
   （这里是"调用方能不能安心取消"，那里是"实现上怎么保证释放"）下的复述。

**这条判据留给谁**：连接断开/`$/cancelRequest` 的通用机制本身（future 被
`JoinSet::shutdown()`/目标 id 匹配后 drop）是 ME-3c 已经交付的基础设施，T8.5c v1
决策 D6 已经确认三个 memory handler 的 `call()` 不需要为此写专门代码——本文档
在这一点上不新增机制，只是把"取消之后到底发生了什么"按上面三种情况说清楚，
供 T8.5c-W 在写端到端取消测试时知道该断言什么、不该断言什么（尤其是不要断言
"取消能让已经提交的写消失"，那不是这个系统承诺的性质）。

## 9. 判据（可验证的测试场景）

沿用 T8.5c v1 判据 7/8/9/10 的编号习惯，但内容已经按本文档的新状态机重写；带
★的是任务明确要求、本文档认为是最核心的两条。

1. **★ C1 核心判据**：构造一个分区，让某一行匹配查询、且把它加入响应会让累计
   字节数超过 `MEMORY_PAGE_RESPONSE_BUDGET_BYTES`（用接近 `MAX_BODY_BYTES` 的
   记录体凑出这个边界）。断言：这一行**不在**这次响应的 `items` 里；返回的
   `cursor` 解码后等于**上一个已解决行**的 `seq`（不是这一行的 `seq`，也不是
   被这一行"挡住"之后、本该出现在它之后的下一行的 `seq`——用下一次调用去验证：
   传回这个 `cursor` 后，下一页的第一条必须正是被挡住的这一行）。
2. **★ 单条记录边界判据**：构造一条记录，其序列化后大小逼近
   `MAX_SINGLE_RECORD_WIRE_BYTES`（第 5.1 节推导的上界）但仍在预算内——断言
   它能被独立成一页正常返回（`items.len() == 1`，`cursor` 视后面是否还有数据而
   定），不触发决策 P4 5.2 的 `hits.is_empty()` 兜底错误路径；反过来，在测试专用
   的构造下把 `MEMORY_PAGE_RESPONSE_BUDGET_BYTES` 临时调小到刻意小于
   `MAX_SINGLE_RECORD_WIRE_BYTES`（只在测试里做这个覆盖，不动生产常量），断言
   这时候会得到决策 P4 的显式 `internal` 错误，而不是死循环、不是空转、不是一
   个游标不会前进的假页面。
2b. **v3 新增（H1 的判据，决策 4.5）——v4 更正（M2，第三轮评审）**：v3 版本
    只在"调用刚开始时"触发一次取消，只能证明"取消在调用早期能生效"，证明不了
    "取消在调用进行到任意位置时都能在一个 yield interval 内生效"这个更强、
    §4.5 实际做出的承诺。v4 改成覆盖多个 phase offset：
    - 用 §4.2 新增的 `page_from_stream` 泛型 helper（不是 `recall_page` 本身
      ——生产路径和这条判据调用同一个函数，不是两条"看起来一样"的实现，这是
      M2 明确要求的测试 seam），构造一个测试专用的、`.next()` 恒返回
      `Poll::Ready(Some(...))`（预先灌满 `MEMORY_SCAN_ROW_BUDGET` 行、从不
      返回 `Pending`）的假 stream。
    - 分别在观察到第 **33、1001、1985** 行时触发取消（覆盖调用刚开始之后
      不久、调用中段、调用接近尾声三个 phase offset，而不是只测调用刚开始
      这一个点）——每个 offset 独立跑一次：让 `page_from_stream` 正常推进到
      预定行数，此时通过一个测试用的取消钩子模拟
      `bind_to_lifecycle` 里 `lifecycle.ended()` 决出胜负。
    - 断言：对每一个 offset，要么（a）取消在"trigger_at 到
      trigger_at + SCAN_YIELD_INTERVAL_ROWS（32）"这个窗口内生效——观察到的
      `scanned` 落在这个区间内，不会一路扫到 `MEMORY_SCAN_ROW_BUDGET`；要么
      （b）`page_from_stream` 本身在不到 32 行内就自然完成（比如
      `trigger_at=1985` 时分区/预算可能已经很接近尾声，正常完成也是合法
      结果）——两者任一成立都满足"32 行内观察到取消，或 work 在不足 32 行
      内自然完成"这条 §4.5 的实际承诺，不能只验证"取消最终生效了"这种更弱
      的断言（那连旧的、没有显式让出点的设计也能满足，只是要等到整个
      2000 行扫完）。
    - 这条判据必须依赖决策 4.5 的显式 `yield_now()` 让出点，不能依赖"自然的
      IO 等待间隙"（假 stream 从不产生任何等待），否则判据本身测不出 H1 这
      个 bug；用同一个 `page_from_stream` 而不是重新实现一遍循环逻辑，保证
      判据测的是生产代码真实会跑的路径，不是一份平行维护的测试替身。
3. **M1 判据（用流式设计重新表述）**：
   - 3a：分区恰好有 `page_size` 行且全部匹配，其余没有更早的行——`recall`/
     `recent` 返回这 `page_size` 条，**这次调用内部**观察到的是"`.next()` 在拿
     满 `page_size` 条之后没有再被调用"（决策 P3 4.2 的保守分支），所以这次
     调用返回的 `cursor` 是非空的；断言：用这个非空 `cursor` 再翻一页，返回
     `items` 为空、`cursor: None`（在下一次调用里诚实地观察到 `None`，而不是
     这次调用凭空产出一个 `None`）。
   - 3b：分区有 `page_size` 行匹配、再往前还有更多（不管匹配与否）——返回
     `page_size` 条 + 非空 `cursor`；用这个 `cursor` 翻页必须能看到 3a 场景
     看不到的、更早的行。
   - 3c（M1 原始反例的直接复现）：一个几乎不匹配的 `query`，分区里恰好有
     `MEMORY_SCAN_ROW_BUDGET` 行都不匹配、且这些行不是分区的全部（再往前还有
     匹配的行）——断言返回 `items` 为空、`cursor` 非空；用这个 `cursor` 继续
     翻页最终能找到更早的匹配行，且总扫描行数不会在一次调用里超过
     `MEMORY_SCAN_ROW_BUDGET`（可以通过给 `EventLog` 包一层调用计数的测试替身
     来断言真实发生的 `.next()` 调用次数，而不是只看最终结果）。
4. `page_size == 0` → `invalid_params`，且不触碰数据库（沿用 T8.5c v1 判据 6，
   本文档不改变这条）。
5. `cursor` 传 `v2:0:xxxxxxxx`、`v2:-1:xxxxxxxx`、以及任何非 `v2:` 前缀、格式
   不对（缺指纹段）或无法 base64 解码的字符串 → 全部 `invalid_params`，不是
   静默退化成 `cursor: None` 的行为（决策 P6，直接对照修复前"`v1:-1` 被
   `.parse::<i64>()` 接受、静默变成一个不可能匹配任何行的边界"这条旧行为）。
5b. **v2 新增（游标未绑定 query Medium 的判据）**：`recall(query="A")` 拿到
    一个非空 `cursor`；把这个 `cursor` 传给 `recall(query="B")`（`A != B`）
    → `invalid_params`（"cursor was issued for a different method or
    query"），不是把它当成一个合法位置继续翻页。同理构造 `recall` 的 `cursor`
    传给 `recent`、`recent` 的 `cursor` 传给 `recall`，两个方向都要
    `invalid_params`。反过来：同一个 `query` 的 cursor 在同一个 `query` 下
    正常复用必须继续成立（不能因为加了指纹校验就误伤了正常翻页）——这条是
    这个判据组的正对照，缺了它，"指纹校验生效"和"指纹校验没把正常场景也拒了"
    是两件事，只测前者不能证明后者。
6. 一次 `recall` 调用命中 `MEMORY_SCAN_ROW_BUDGET` 行上限但一条也没匹配 →
   `items` 为空、`cursor` 非空（沿用 T8.5c v1 判据 8，状态机换了但结论不变，
   合并进上面的 3c）。
7. 加权限流：构造连续发起多次 `page_size=50` 的 `recall` 调用，断言令牌消耗
   速度显著快于连续发起多次 `remember` 调用（用注入的 `Clock` 精确控制时间，
   同 `events_emit.rs` 已有的测试模式）——证明"一次调用=一个令牌"这个旧模型
   已经被替换，不同方法/不同参数的调用消耗桶里不同数量的令牌。
7b. **v2 新增（预扣计费 High 的判据，决策 P5b）**：构造一个 `page_size=1`、
    分区里最新一行就匹配的 `recall`——断言这次调用实际消耗的令牌远小于
    `MEMORY_COST_RECALL`（2000），约等于 `1 + row_buffer_size`（决策 P5b 的
    结算公式）而不是 2000；用同一个 `RateLimiter` 连续发起这类"廉价"
    `recall`，断言能发起的次数远多于"如果每次都扣 2000"这个旧模型下的次数
    ——这条判据直接反驳"正常小查询被高估最多约 2000 倍"这个原始问题。反过来，
    构造一个几乎不匹配的 `query`（判据 3c 的场景，扫满 `MEMORY_SCAN_ROW_BUDGET`
    行）——断言这次实际消耗的令牌接近满额（`≈ MEMORY_SCAN_ROW_BUDGET`），
    证明"满预算扫描应该被限住"这条旧判据（现判据 6）在 reservation/refund
    模型下没有被削弱。
7c. **预扣计费 High 的取消判据**——**v3 更正（H2，第二轮评审）**：v2 这里
    断言"桶里的令牌被全额退回（等同于这次调用从未发生）"，这条断言本身就是
    H2 指出的漏洞（未 commit 就全额退款 = 限流可以被取消绕过）——改成两条：
    - 一个 `recall` 调用在**进入扫描循环之前**（比如还在排队等 §6.5 的
      connection admission permit 时）被取消——断言桶里的令牌被全额退回
      （`Reservation::touched` 从未被设为 `true`，等同于这次调用从未真正
      发生），这部分结论不变。
    - 一个 `recall` 调用在**扫描循环开始之后**（已经处理过若干行，
      `reservation.mark_touched()` 已经被调用过）被取消——断言桶里退回的
      令牌等于 `reserved - min(scanned观测值 + ROW_BUFFER_MARGIN, reserved)`，
      不是全额退回；构造"扫到接近 `MEMORY_SCAN_ROW_BUDGET` 才取消"的场景，
      断言这次调用几乎不获得退款（验证 H2 原始问题——"扫到接近预算再取消"
      不再是免费的）。
    这两条一起验证 §6.4 `Reservation::Drop` 的"没碰过 DB 全额退款、碰过 DB
    按已发生工作结算"两条分支，不是只测其中一条就假装覆盖了 H2。
7d. **v3 新增（L2 的判据，`recent` 并入统一结算）**：构造一个分区剩余行数
    少于 `page_size` 的 `recent` 调用（比如分区只有 3 行，`page_size=10`）
    ——断言这次调用实际结算的令牌等于 `实际产出行数（3）+ ROW_BUFFER_MARGIN`，
    不是恒等于预留量 `page_size`（10）；反过来，分区行数充足、字节预算也够用
    的正常场景下，结算值应该非常接近 `page_size`（允许 `+ ROW_BUFFER_MARGIN`
    的余量），验证"通常很接近"这个新表述没有被判据本身证伪。
8. 崩溃重启后（同一模块，新一代）**v2 更正（限流身份 Critical 的判据）**：
   ~~令牌桶是满的~~——这条断言本身就是错的，跟 SPEC §5"跨 restart generation
   生效"矛盾（见决策 6.3 的详细论证）。改成：构造一次调用把旧代的桶消耗到只剩
   少量令牌，让模块崩溃重启（新一代），断言**新一代的桶里令牌数等于旧代剩下
   的量**，不是恢复到 `MEMORY_RATE_CAPACITY` 满桶——这是本判据组里唯一一条
   从"断言恢复"改成"断言不恢复"的项，专门用来防止将来有人凭直觉把它改回
   "重启后应该是满的"（那正是限流身份 Critical 指出的 bug 本身）。
8b. **v2 新增（限流身份 Critical 的判据，反过来）**：同一个模块**连续两次**
    调用 `methods_for`（模拟同一代内部的两次 handler 构造，如果实现细节允许
    这样触发）不应该产生两个独立的桶——断言两次拿到的 `RateLimiter` 是同一个
    `Arc` 指向的实例（指针相等），证明"身份在 mount 层、不在 `methods_for`
    闭包内"这条修法真的生效了，不是文档说了但实现忘记挪。
9. 连接断开时，一个正处在 `recall_page`/`recent_page` 循环中间（某次
   `stream.next().await` 之后、下一次 `.next()` 之前）的调用不产生任何响应——
   沿用 ME-3c 已有的通用测试形态，验证对象换成新的逐行循环。
9b. **连接池准入 High 的判据（决策 P8）**——**v3 更正（H3，第二轮评审）**：
    v2 这里用"卡住不返回第一行之后的行的假 `EventStore` 实现"——§6.5 已经
    说明这个方案两个问题都不成立（`scan_stream` 不在 `EventStore` trait 上，
    mock 也证明不了真实连接被占用），改成用真实占住连接的操作。

    **v4 更正（M4，第三轮评审）**：v3 的模型（并发发起 4 个真实占住连接的
    操作，断言第 5 个排队）只证明了"pool 会被占用、第 5 个调用会排队"，
    证明不了 M4 指出的更具体的事情——`remember_checked`/`recall_page`/
    `recent_page` 三个方法是不是真的接入了**同一个** permit（哪怕实现阶段
    有人把三者各自建了独立的 `Semaphore`，这条判据一样会通过，因为它每次
    只测一种方法组合）。v4 按 §6.5 第 5 点已经重写的模型，把这条判据具体化
    成五个断言：

    - ① 在共享 pool **之外**开一个独立 SQLite 连接（连到同一个数据库文件，
      不经过 `KvStore` 的共享池），执行 `BEGIN IMMEDIATE` 并保持事务打开，
      真实持有 SQLite 写锁——这个连接本身不占用 permit 或 pool 槽位，只是
      锁竞争源。
    - ② 通过真实的 OOP handler（走完整 `Handler::call` → `bind_to_lifecycle`
      → §6.5 的准入序列）并发发起 **4 个** `remember_checked` 调用，断言
      它们各自成功拿到一个 admission permit、成功从共享池 `acquire()` 一个
      连接，然后阻塞在等①持有的写锁上（`busy_timeout` 生效）——此刻 4 个
      permit（`max_connections - 1`）全部被占用，且真实持有 4 个 pool
      连接（不是在等 permit，是在等锁）。
    - ③（WAL 模式）用**不经过 admission permit** 的进程内路径
      （`ScopedMemory::recall`，`fetch_all`，T8.5c v1 决策 D4 已论证不占用
      本节 permit）发起一次真实读，走共享池里第 5 个连接（`max_connections
      =5`，前 4 个被②占住）——断言它**正常返回**，证明"给进程内路径留
      headroom"这条 MUST 契约真实生效，不是文档里的一句话（WAL 模式下写
      事务不阻塞并发读，这条读不会卡在①的写锁上）。
    - ④ 再发起第 **5 个** OOP 调用——断言它卡在 `Semaphore::acquire()` 上，
      拿不到 permit（不是因为"池里没有连接了"，是因为 permit 数
      `max_connections - 1 < max_connections`，它根本没走到
      `pool.acquire()` 那一步）；取消这个排队中的调用（模拟连接断开）→
      断言它不产生任何响应，且释放的 permit 名额能被其它排队者用上（验证
      `bind_to_lifecycle` 取消路径下 `OwnedSemaphorePermit` 的 `Drop`
      确实执行了），同时验证它对应的 `Reservation` 仍然全额退款（`touched`
      从未被设置——排队阶段被取消，跟 §6.4/判据 7c 第一条是同一个结论）。
    - ⑤ **v4 新增（M4 明确要求）**：④这一步分别用
      `remember_checked`/`recall_page`/`recent_page` 各跑一次（不能只测
      `remember_checked`，那只证明了"写路径接入了 permit"，证明不了另外
      两个读方法也接入了同一个 permit）——三次断言都要通过，才代表"三个
      方法共享同一个 admission permit"这条 MUST 契约被真正验证过，而不是
      靠"测了其中一个，假装另外两个也测过"。
9c. **v2 新增（const assert Medium 的判据）**：这条本身是编译期断言（第 5.1
    节的两条 `const _: () = assert!(...)`），"判据"就是"改动
    `MAX_KIND_BYTES`/`MAX_BODY_BYTES`/`MEMORY_PAGE_RESPONSE_BUDGET_BYTES`/
    `MAX_FRAME_BYTES` 到刻意破坏其中一条不变式时，`cargo build` 必须失败"——
    这条不需要一个运行时测试用例，需要的是"这两条 assert 本身出现在代码里、
    没有被绕过"，实现阶段验证方式是故意改一次常量看编译是否真的红。
10. **留给 T8.5c-W 补充的判据（P 这边不设计，只声明依赖）**：任何需要真实
    `MemoryEntitlement`/挂载/授权判断才能构造的场景（比如"lend 失败时
    `recall_page` 根本不会被调用到"）不在本文档的判据列表里——P 只保证
    `recall_page`/`recent_page`/`remember_checked` 这几个纯函数式方法在**假设
    调用方已经通过鉴权**的前提下行为正确；端到端地验证"一个真实的、未授权的
    模块调用会在到达这几个方法之前就被拦下"是 T8.5c-W 的判据。

## 10. 自审：逐条核对 Codex 对 T8.5c v1 D2 的意见

1. **Critical C1**（响应字节预算没有并入游标状态机）——决策 P1 重新定义游标为
   "最后一个已解决行"，决策 P3 的状态机把字节预算检查和游标推进合并成同一步
   （只有接纳成功才推进 `resolved_seq`），判据 1/2 直接对着 Codex 给出的"50 行、
   前 8 行装得下、cursor 用第 50 行会跳过 9-50 行"这个反例的一般化版本设计。
   自查：状态机里有没有任何分支会在"这一行还没决定是否接纳"之前推进
   `resolved_seq`？——逐行读了决策 P3 4.2 的伪代码，`resolved_seq` 只在
   （a）接纳成功分支和（b）确认不匹配分支被赋值，字节预算拒绝分支明确不赋值，
   `hits.is_empty()` 特判也在赋值之前检查——没有找到反例。
2. **Critical C1 的第二部分**（`fetch_all` 先物化 500/50 行整批）——决策 P2 用
   `scan_stream` 替换掉 OOP wire 路径对 `page()`/`fetch_all` 的依赖，第 3.3 节
   给出物化上界从 O(500) 降到 O(1) 的论证。自查：有没有可能 sqlx 的
   `fetch()` stream 在某些驱动实现下其实也是先物化整个结果集、只是延迟返回？
   ——没有能力在这份文档里跑代码验证这一点（任务边界不允许写代码），标记为
   **实现阶段必须验证的假设**：sqlx SQLite 驱动的 `fetch()` 是否真的逐行拉取
   而不是内部预取全部结果集，需要在实现 `scan_stream` 时补一个"物化上界"的
   集成测试（比如构造一个超大分区，断言峰值内存不随分区大小线性增长）来验证，
   而不是只信任 sqlx 文档的描述。
   >
   > **v2 更新（sqlx 预取 High）**：这条"标记为待验证的假设"在本轮已经被
   > 验证，而且验证结果推翻了原文的"O(1)"结论——读了
   > `sqlx-sqlite-0.8.6/src/options/mod.rs:211`（`row_channel_size: 50` 的
   > 默认值）和 `connection/worker.rs:160-206`（worker 线程同步 blocking-send
   > 每一行进有界 channel）之后确认：`fetch()` 不是"先物化整个结果集"（原文
   > 担心的那种更糟的情况没有发生），但也不是逐行请求（原文"O(1)"暗示的那种
   > 更好的情况也没有发生）——是介于两者之间的有界预取，量级是
   > `row_channel_size`（默认 50，v2 显式调小到 8），不是 1、也不是分区大小。
   > §3.2/§3.3 已经按这个验证结果改写，"实现阶段必须验证的假设"这条待办本身
   > 已经完成，不再是遗留项——但"峰值内存不随分区大小线性增长"这条集成测试
   > 建议本身依然成立，且被判据 9c 之外新增的物化上界描述（§3.3）具体化了
   > 期望值（**v3 更正，M1**：是有界**行数**——10 个行对象——而不是一个精确的
   > 字节数；v2 版本这里曾经写"约 578 KiB"，§3.3 已经说明这个字节数不能从
   > `MAX_SINGLE_RECORD_WIRE_BYTES` 直接套出来，本节这句话同步改正，不再
   > 重复这个已经被撤回的数字）。
3. **Medium M1**（"短批恰好到页尾"判据与伪代码不一致）——决策 P3 4.1 论证了
   流式设计如何让这个歧义从代码结构上不可能发生（`None` 只能来自
   `scanned < MEMORY_SCAN_ROW_BUDGET` 时的真实流耗尽），判据 3a/3b/3c 分别覆盖
   "恰好到页尾"“到页尾但还有数据"“扫描预算耗尽但没到页尾"三种情况。自查：这
   三种情况的判据是否互相独立、有没有遗漏第四种组合？——枚举了 `(是否命中数够
   page_size, 是否流耗尽, 是否扫描预算耗尽)` 的可能组合："流耗尽"和"扫描预算
   耗尽"在设计里互斥（决策 P3 4.1 的不变式保证二者不会在同一次 `.next()` 调用
   上同时被观察到），所以实际只有三种可达状态，判据 3a/3b/3c 覆盖了全部三种。
4. **Medium M2**（`RateLimiter` 一令牌一调用）——决策 P5 6.2/6.3 给出加权版本
   与按方法/参数区分的成本常量，判据 7 验证消耗速度确实按方法区分。自查：
   `MEMORY_COST_RECALL` 取 `MEMORY_SCAN_ROW_BUDGET`（最坏情况）而不是某个更
   宽松的估计，是否会让正常的小查询也被不必要地重罚？——**v2 更新（预扣计费
   High）**：v1 在这里回答"是的，这是本文档明确接受的权衡"——本轮评审不接受
   这个权衡，指出"预收费用最坏情况"和"正常小查询不该被重罚"并不是真的互斥，
   只要把"预收费"和"最终扣多少"分成两步：决策 P5b（§6.4）的 reservation/
   refund 模型仍然按最坏情况**预留**（不然如 v1 所说，准入检查会失去意义），
   但**结算**按实际扫描行数（外加 sqlx 预取的保守余量）多退——`recall("几乎
   不匹配的 query")` 该被限住的场景（判据 6/3c）没有变松，因为那种场景实际
   扫描量本来就接近最坏情况、退不了多少；`page_size=1` 首行命中的场景不再被
   误伤。v1 的"不预先调参、留给运营数据"这个态度本身没有错，但它建立在"模型
   只能靠调参补救"这个前提上——本轮发现那个前提是假的，模型本身可以改，改完
   之后调参才有意义（否则不管怎么调 `MEMORY_RATE_CAPACITY`，比例失衡的问题
   都还在）。
5. **Medium M2 的跨模块部分**——**v2 更新（连接池准入 High）**：v1 在这里的
   立场是"决策 P5 6.4 明确声明这部分不在 P 的设计范围"，自查也据此认为"这个
   边界划分不是回避问题，是因为离开一个 Generation 的视角就无法设计"。本轮
   评审推翻了这个立场：跨模块连接池保护不需要挂在"哪个 Generation 能看到
   什么"这个视角上——它需要挂在"共享池本身在哪创建"这个视角上，而共享池
   （`agent24_memory::KvStore::open`）恰好就是在 `server.rs` 里、比任何一个
   模块的 `Generation` 都更早、更高的地方创建的**daemon 级单例**，一个同样
   在那个作用域创建的 `Semaphore` 完全够用，不需要发明"跨 Generation 共享
   状态"这种新机制（决策 P8，§6.5，已给出具体创建点和五条 MUST 契约）。回头
   看，v1 这里的自查问错了问题——"P 层的 `RateLimiter` 实例本来就是每
   Generation 一个，没有跨 Generation 的共享状态"这个观察是对的，但结论"所以
   这个问题设计不了"是错的，因为解决这个问题根本不需要用 `RateLimiter` 那套
   跨 Generation 机制，需要的是一个完全独立于 Generation 概念、直接挂在共享
   资源本身作用域上的新机制。任务原文"如果跟挂载/生命周期接线有关，可以只
   交代 P 这边需要暴露什么接口"这句话本身没有错，错的是 v1 把"可以只交代接口"
   理解成了"可以只交代接口、不用交代这是不是 MUST"。
6. **Low L1**（`decode_cursor` 对非正数游标静默退化）——决策 P6 加上
   `seq < 1` 的显式检查，判据 5 覆盖（v2 编码更新后的）`v2:0:…`/`v2:-1:…`。
   自查：`seq` 的上界（比如
   `i64::MAX` 或者超过当前实际最大 `seq` 的游标）要不要也拒绝？——不需要：一个
   大于当前最大 `seq` 的游标（比如客户端拿到一个游标之后，这段时间里分区又有
   新写入，但客户端传的还是旧游标——这在 `newest()`/`before()` 的降序查询里
   永远是合法的，`before_seq` 的 SQL 语义是 `seq < before_seq`，一个比现存所有
   行都大的 `before_seq` 只是让查询从"最新的一行"开始，不是一个错误状态，这是
   `page()`/`before` 机制原本就支持的、正常的"我从很久以前的某个点继续翻页"
   场景，不应该被拒绝。
7. **M5**（取消语义的三个场景被一句话概括）——决策 P7 把"已执行的写"“正在产出
   行的读"“排队等待的工作"分成三段，且指出流式设计相对 T8.5c v1 原方案收紧了
   第二种场景的"追不回的窗口"。自查：这三段描述有没有互相矛盾或者重叠不清的
   地方？——"已执行的写"和"正在产出行的读"都提到"已经交给 sqlx worker 的语句
   追不回"，这是同一条底层事实（sqlx 连接 worker 的行为）在两个不同调用形状上
   的体现，不是矛盾，是同一个机制在写路径（一次 `INSERT`）和读路径（多次
   `SELECT ... LIMIT` 的其中一次）上的重复应用——保留这种重复是刻意的，因为
   两条路径的判据（判据 1 是读路径的、`remember` 没有对应的"取消导致部分写入"
   判据，因为一次 `remember` 只有一条 INSERT，要么整条提交要么整条没提交，不
   存在"部分写入"的中间态）是分开写的，读者不需要跳到另一段去确认写路径的
   结论对不对。

**跟 T8.5c v1 已拍板决策的一致性检查**：本文档没有修改 `MemoryEntitlement`/
`MemoryRpcError`/`MEMORY_MAX_PAGE_SIZE=50`/
`MEMORY_PAGE_RESPONSE_BUDGET_BYTES=512KiB`/`MEMORY_SCAN_ROW_BUDGET=2000` 这些
已经在 v1 里定过的值和类型签名——只是重新设计了它们如何在状态机里被使用（游标
何时推进、批怎么取、令牌桶扣多少）。`OsScopedMemory::page`/`RECALL_PAGE` 的
既有进程内路径完全不受影响。
>
> **v2 更新**：上面这句话里"`encode_cursor` 的编码格式"这一项在 v2 里不再
> 成立——决策 P6/§7.1（游标未绑定 query Medium）把编码从 `v1:<seq>` 升级到
> `v2:<seq>:<指纹>`，这是本文档 v1 自己声明"不重新设计编码"的范围之外的一次
> 必要的例外，第一节的"v1 → v2 改动记录"已经写明这个判断（当时的评审对象
> 是这个编码方案在 v1 阶段还没暴露出来的一个真实 bug，不是本文档随意推翻自己
> 早先的决定）。除了这一项，其余常量/类型不变的结论继续成立。

## 10b. v2 自审：本轮 1 Critical + 3 High + 2 Medium + 1 Low 逐条核对

> 这一节核对的是本文档（T8.5c-P）v1 收到的**第一轮**评审——跟上面第 10 节
> （核对 T8.5c v1 D2 收到的评审）是两件事，见文档开头"v1 → v2 改动记录"的
> 命名提醒。

1. **限流身份 Critical**——决策 6.3 的 v2 更正把 memory `RateLimiter` 的创建点
   从 `methods_for` 闭包内部挪到 mount 层（`mount_package`/`lend()` 同层），
   身份变成稳定的 `(module, partition)`；判据 8 从"断言重启后满桶"改成"断言
   重启后继承剩余额度"，判据 8b 补充"两次同代构造拿到同一个 `Arc`"。自查：
   这条修法有没有可能反过来破坏"崩溃后不能无限重试来刷配额"这条 SPEC 要求
   本来想防的事？——没有反向破坏：SPEC 要的是"不能靠自崩溃刷新"，v2 的修法
   正是让崩溃**不再能**刷新（旧代剩多少新代就剩多少），如果 v2 之前的"每代
   重建"侥幸被实现出来，那才是真正违反 SPEC 的版本（重启=刷满）；v2 是修正
   方向而不是引入新风险。
2. **sqlx 预取 High**——决策 §3.2/§3.3 用读代码验证的事实（`row_channel_size`
   默认 50、worker 线程 blocking-send 预取）替换了"O(1)/一行在飞"的错误声称，
   正式选定 `row_buffer_size=8`，物化公式改写，§8 的取消语义同步改写为
   "至多 `row_buffer_size + 1`（9）行"。自查：`row_buffer_size=8` 这个具体
   数字有没有论证依据，还是拍的？——§3.2 给出的论证是"比最小合法 page_size
   (1) 留出避免频繁阻塞 worker 的余量，又比默认 50 小一个数量级"，这是一个
   方向性论证（够用、且远优于默认值），不是从吞吐量数据反推出的精确值——跟
   `MEMORY_RATE_CAPACITY` 等常量一样，本文档对这类还没有运营数据支撑的具体
   数字保持"给出方向和量级、留精确调参给实现阶段"的一贯态度，不假装这里的 8
   比别处的猜测值更精确。
3. **预扣计费 High**——决策 P5b（§6.4）把预收费改成"预留 + 按实际结算"两阶段，
   RAII `Reservation` 保证未 commit 时全额退款，结算量额外加上
   `row_buffer_size` 的保守余量（跟 sqlx 预取 High 的选定值联动）。判据 7b/7c
   验证退费生效、满预算场景不被削弱。自查：`Reservation` 的 `commit` 用
   `saturating_sub` 钳制、不允许"倒找"，这会不会在 `actual` 计算错误（比如
   实现 bug 算出一个比 `reserved` 还大的 `actual`）时静默吞掉一个本该被发现
   的 bug？——会，这是一个已知的、刻意的取舍：把它做成 panic 会让一个计费
   口径的 bug 变成一次 `recall` 调用崩溃（可用性问题），钳制是把它退化成一个
   "多收了但没少退"的静默计费误差（不影响调用方看到的结果，只影响限流的
   精确度）——两害相权，这里选了不让计费 bug 波及到调用方能不能拿到数据这件
   事，跟决策 P4 5.2"连接不上的资源错误必须显式"的态度不冲突：那里"装不下
   一条记录"是会直接影响响应正确性的错误，这里"算错了退多少"不影响响应正确性
   ，只影响限流的宽严，两者的错误严重度不一样，不需要用同一个应对策略。
4. **连接池准入 High**——决策 P8（§6.5）用读代码验证的事实（`&Pool` 的
   `fetch_many` 持有连接直到 stream 耗尽/drop）把"W 决定要不要做"改写成五点
   MUST 契约：单例创建点（`server.rs`，与共享池同作用域）、headroom（
   `max_connections - 1`）、`bind_to_lifecycle` 内等待、RAII 释放、判据。
   自查：这条契约会不会因为"P 只交代接口不写代码"这个任务边界，导致 W 拿到
   契约之后仍然有很大的自由裁量空间去做错？——契约里"必须小于
   `max_connections`"和"必须在同一作用域创建一次"这两条是可以脱离具体实现
   直接核查的（judgement 9b 就是直接测的行为，不依赖看代码结构），所以即使
   W 的具体接线方式跟本文档设想的不完全一样，判据 9b 仍然能捕捉到"没做"或
   "做错了范围"这两类最容易出错的情况——契约的可验证性不完全依赖代码审查。
5. **const assert Medium**——决策 §5.1 修正 `kind` 字段的转义膨胀系数，新增
   第二条"页预算装得进帧预算"的跨常量编译期断言，`MAX_ID_BYTES` 直接复用
   `rpc.rs` 已有的真实常量（不是本文档编的数字）。自查：`body` 字段有没有
   同样的转义膨胀问题被漏掉？——§5.1 的旁注专门核对过这一点：`MAX_BODY_BYTES`
   本来就是对编码后字节数的限制（`os_memory.rs:584` 的
   `encoded.len() > MAX_BODY_BYTES`），跟 `kind`（对原始字符串长度的限制，
   `os_memory.rs:576` 的 `what.kind.len()`）约束的对象不同，`body` 不需要
   再叠加一次转义系数——这正是本节强调的"同一份代码里两个同名模式的常量
   约束的对象可能不同，不能套同一个公式"，`id`/`at` 是本文档自己按固定格式
   （ULID/ISO 8601）推导的，不含用户可控的、需要转义的内容，同样不需要系数。
6. **游标未绑定 query Medium**——决策 P6/§7.1 给 cursor 编码加上
   `(method_tag, normalized_query)` 指纹，`decode_cursor` 校验不匹配则拒绝，
   判据 5b 覆盖跨 query/跨方法复用。自查：`recall`/`recent` 之间互换 cursor
   这个场景，本文档最初只想到"跨 query"，是评审明确点出"跨方法"也是同一类
   bug 的另一种形式后才补充的——那`method_tag` 只有两个值（1/2），会不会
   将来加第三个跟分页相关的方法时被遗漏？——这是一个实现阶段的可维护性风险
   （枚举值需要跟"这个模块有几种可分页的方法"保持同步），本文档不能用文字
   消除它，只能建议实现阶段把 `method_tag` 定义成一个穷尽式 `enum` 而不是裸
   `u8` 字面量，让编译器在漏处理新分支时报警（这是 §2.2 已经建议的
   `MatchPolicy` 枚举化思路在另一个地方的复用）。
7. **负成本 Low**——决策 §6.2 把 `cost: f64` 换成 `ScanCost(u32)` newtype，
   release/debug 构建保证一致。自查：`ScanCost::from_rows` 用
   `u32::try_from(rows).expect(...)`，在 `rows` 真的溢出 `u32`（超过 40 亿）
   时会 panic，这跟"负成本 Low"本来想避免的"运行时才炸"是不是同一类问题？
   ——不是同一类：负成本是一个**在正常业务范围内的输入**（`cost=0` 或负数
   在调用点很容易手滑写出来）会被静默接受、悄悄破坏桶的不变式；`rows > 
   u32::MAX` 是一个**远超这个系统任何真实场景**的输入（`MEMORY_SCAN_ROW_BUDGET
   =2000`、`MEMORY_MAX_PAGE_SIZE=50`，两者都以数量级差距小于 `u32::MAX`）
   ——用 `expect` panic 在这里是"绝不应该发生、发生了就是别处已经先坏掉"的
   防御性断言，跟"负成本"这种业务上真实可能出现的输入不是同一个风险等级，
   不需要用同一种处理方式（悄悄拒绝 vs. 类型层面不可构造）。

**7 条之间的协同自审（任务明确要求）**：预扣计费 High 的 `Reservation`（一个
逻辑配额账本）和连接池准入 High 的 `Semaphore`（一个物理连接槽位计数）是否
会变成"两套互相不知道对方存在的限流/准入机制"？——§6.5 已经把这个协同写清楚：
两者管理的是不同的资源（速率 vs. 并发度），获取顺序固定为先 `RateLimiter`
（便宜、非阻塞）后 `Semaphore`（可能阻塞），两个 RAII 守卫（`Reservation`
的 `Drop`、`SemaphorePermit` 的 `Drop`）各自独立退出，互不依赖对方的清理
逻辑——它们"互不知道对方存在"这件事本身不是问题（两个正交的资源本来就不需要
互相知道），会成为问题的只有"获取顺序颠倒导致一个稀缺资源被另一个机制的排队
占用"，这一点已经用固定顺序解决，§6.5 的伪代码把两者串在同一段调用序列里，
不是分散在文档两处、靠读者自己脑内拼接。

## 10c. v3 自审：本轮 3 High + 3 Medium + 2 Low 逐条核对

> 这一节核对的是本文档（T8.5c-P）v2 收到的**第二轮**评审——跟第 10/10b 节
> （核对更早两轮评审）是两件不同的事，命名规则同文档开头的提醒。

1. **让出点 High（H1）**——决策 4.5 新增显式 `tokio::task::yield_now()`，
   每 `SCAN_YIELD_INTERVAL_ROWS`（32）行让出一次，核实了 `rpc.rs` 的"future
   必须 yield"不变式和 `bind_to_lifecycle` 的 `select!` 实现（"pending work
   才能让 `ended()` 被再次 poll"）。自查：`yield_now()` 的让出频率（每 32 行）
   会不会因为太稀疏，导致某些取消场景下"最多推迟 32 行才生效"这个延迟本身
   在极端场景下也是不可接受的？——不会：32 行相对 `MEMORY_SCAN_ROW_BUDGET`
   （2000）是 1.6%，相对一次 SQLite 行读取的实际耗时（微秒到毫秒级）也是
   一个远小于典型 RPC 超时（秒级）的量，`SCAN_YIELD_INTERVAL_ROWS` 本身是一个
   本文档已经声明"给方向、留精确值给实现阶段"的旋钮（跟 `row_buffer_size`
   同一类），如果实现阶段发现 32 太大/太小，调整它不需要改变决策 4.5 的机制
   本身。
2. **结算漏洞 High（H2）**——决策 §6.4 给 `Reservation` 加上 `touched`/
   `scanned` 两个 `Cell`，`Drop` 按"是否已经触碰 DB"分两支结算，删除"未
   commit 就全额退款"这条路径；结算余量从 `scanned + 8` 改成
   `scanned + ROW_BUFFER_MARGIN`（8，等于 `row_buffer_size`），修正了行数
   本身（H2 原始描述里的"漏算一行"实际上是 §3.3 M1 的行数上界问题，不是
   `actual` 结算公式的余量算错——结算公式的余量本来就该等于
   `row_buffer_size`（消费者没见过的行数），不是 `row_buffer_size + 1`（这个
   +1 是 M1 的"任意时刻驻留的行对象总数"，两者是不同的计数口径，第 9 节判据
   之外 §3.3 已经专门核对过这一点，不在这里重复混用）。自查：`Reservation`
   的 `touched`/`scanned` 两个 `Cell` 会不会在多次调用之间被意外复用（比如
   同一个 `Reservation` 被 `commit` 之后又被拿去 `record_scanned`）？——不会：
   `commit(self, ...)` 按值消费 `self`（signature 是 `pub fn commit(mut
   self, ...)`），一旦 `commit` 被调用，`Reservation` 这个值本身就被移动
   消费掉了，Rust 的所有权系统在编译期就阻止"commit 之后继续调用
   `record_scanned`"这种用法，不需要运行时检查。
   >
   > **v4 更正（M1，第三轮评审）**：上面这条自审的核心结论——"结算余量本来
   > 就该等于 `row_buffer_size`（8），不是 `row_buffer_size + 1`"——是**错的**，
   > 本轮评审明确指出并要求改正。错误出在这条自审把两件不同的事混成了一件：
   > `ROW_BUFFER_MARGIN` 要覆盖的是"SQLite 已经真实产出、但没有被计入
   > `scanned` 的行"，这包括 channel 里排队的最多 8 行**以及** worker 正
   > 阻塞发送的第 9 行——后者是一行独立存在于 worker 栈帧里、还没进 channel
   > 的真实数据，不是"consumer 手上那一行"（consumer 手上那一行早就在
   > `.next()` 返回时被计入了 `scanned`，根本不需要出现在这个余量里）。这条
   > 自审把"worker 阻塞发送的第 9 行"错误地等同于"consumer 手上那一行"，
   > 才得出"+1 是 M1 的总数概念、不该出现在结算余量里"这个错误结论。v4 把
   > `ROW_BUFFER_MARGIN` 改成 9（§6.4），并把 `commit()`/`Drop` 的结算公式
   > 收进统一的 `settle_amount()`，同时新增 `exhausted` 状态区分"consumer
   > 已经观察到流结束"（成本精确等于 `scanned`，不叠加余量）和"提前返回/
   > 取消/出错"（成本按 `scanned + ROW_BUFFER_MARGIN` 计，钳制在
   > `reserved` 内）——后一条是 v3 这里完全没有考虑到的一个额外精度问题，
   > 详见 §6.4 的 M1 更正和新增的第 10d 节第 2 条。
3. **让出点 High 与结算漏洞 High 的协同（任务明确要求核对）**：决策 4.5 的
   `yield_now()` 插入点会不会导致 §6.4 的 `scanned` 计数时机不对？——不会，
   理由分三层：
   - **`yield_now()` 不跨越 `scanned` 的赋值点**：§4.2 的代码顺序是
     `scanned += 1;` → `reservation.record_scanned(scanned);` → （检查是否到
     `SCAN_YIELD_INTERVAL_ROWS` 的倍数）→ `if ... { yield_now().await }`——
     `record_scanned` 的调用**在** `yield_now()` **之前**，不是之后。也就是说
     不管 `yield_now().await` 这次是否真的把执行权交还给 executor、不管交还
     之后这个 future 会不会被取消，`reservation.scanned` 这个 `Cell` 在
     `yield_now()` 被调用的那一刻已经是"处理到这一行为止"的正确值——`Drop`
     不可能读到一个"这一行还没被计入、但让出点已经发生"的中间状态。
   - **`yield_now()` 之后如果被取消，不会有更多行被"漏记"**：`yield_now()`
     只是把控制权交还给 executor 一次；如果 `bind_to_lifecycle` 的
     `select!` 在这次让出的窗口里选中了 `lifecycle.ended()` 分支，整个
     `work` future（`recall_page_body` 所在的 async 块）被 drop，循环体
     不会再继续跑，所以不存在"取消发生后循环又偷偷多处理了几行、但
     `record_scanned` 没跟上"这种情况——`yield_now()` 之后本来就没有代码
     在它跟"循环体继续/被取消"之间插队。
   - **`yield_now()` 本身不是一个"可能丢失状态"的操作**：它是一个纯调度
     原语，不返回 `Result`、不涉及 IO、不会 panic（除非 executor 本身已经
     关闭，这种场景下整个 future 都不会再被 poll，`Reservation` 的 `Drop`
     会在任务被清理时正常执行），`scanned`/`touched` 这两个 `Cell` 的值
     不依赖 `yield_now()` 执行成功与否——它们是在 `yield_now()` 之前就已经
     写好的普通内存状态，`yield_now()` 让不让出、什么时候被重新 poll，都
     不会让已经写入的 `Cell` 值变化或丢失。
   
   结论：H1 的让出点和 H2 的结算计数器在设计上是正交的——`yield_now()`
   只影响"取消/超时什么时候有机会生效"，`scanned`/`touched` 只影响"取消
   生效的那一刻，账要怎么结"，两者的交界只有一处（`yield_now()` 必须排在
   `record_scanned` 之后，不能排在之前），§4.2 的代码顺序已经保证了这一点。
4. **连接池准入 High（H3）**——决策 §6.5 把 `remember_checked` 并入共享的
   admission permit，判据 9b 换成真实占住连接的模型。自查：三个方法共享
   一个 permit（大小 4）会不会让"读多写少"或"写多读少"的真实流量模式下，
   某一类调用被另一类长期饿死（比如大量 `recall_page` 排队把 permit 占满，
   `remember_checked` 迟迟拿不到）？——会，这是**公平性**问题，不是**正确性**
   问题：§6.5 的 MUST 契约保证的是"进程内路径不被 OOP 路径饿死"（headroom），
   不保证"OOP 内部三个方法之间公平轮转"——`tokio::sync::Semaphore::acquire`
   本身是 FIFO 排队（先到先得），不会无限期饿死某一类调用，只是不保证按
   方法类型均分。本文档判断这是实现阶段可以观察、必要时用带优先级的准入
   结构改进的问题，不是本文档需要在设计阶段解决的正确性缺陷——跟 §6.3 对
   `MEMORY_RATE_CAPACITY` 等常量的一贯态度一致（给出方向，把精确调优留给

5. **物化上界 Medium（M1）**——§3.3 改写为只承诺行数有界（10），字节数分

## 10d. v4 自审：本轮 1 High + 5 Medium + 1 Low 逐条核对

> 这一节核对的是本文档（T8.5c-P）v3 收到的**第三轮**评审——跟第 10/10b/10c
> 节（核对更早三轮评审）是不同的事，命名规则同文档开头的提醒。任务描述统计
> 为"1 High + 6 Medium + 1 Low"，逐条列出的实际是 1 个 High + 5 个 Medium +
> 1 个 Low（7 条）——本节按这 7 条逐一核对，不核对一条未被具体描述的第 6 个
> Medium。

1. **所有权模型 High（H1）**——`Reservation` 从借用 `&'a RateLimiter` +
   `Cell` 改成拥有 `Arc<RateLimiter>` + 普通字段，去掉生命周期参数，整个
   guard 移到 work future 内部构造/结算，扫描函数从 `&Reservation` 换成
   `&mut Reservation`。自查：这个新形状真的满足 `CallFuture = Pin<Box<dyn
   Future<Output = Result<Value, RpcError>> + Send>>`（`rpc.rs`，隐式
   `'static`）吗？——核对要点：① `Reservation` 不再包含任何借用字段
   （`Arc<RateLimiter>`/`ScanCost`/`bool`/`u32`/`bool` 全部是拥有的值），
   所以 `Reservation: 'static` 成立（前提是 `RateLimiter: 'static`，它是
   mount 层单例，没有借用任何调用方数据，成立）；② `Reservation` 是否
   `Send`：需要 `Arc<RateLimiter>: Send`，这要求 `RateLimiter: Send + Sync`
   ——`RateLimiter` 已经在 mount 层单例、跨多个并发 handler 调用共享
   `Arc` 使用（判据 8b 直接断言"两次拿到的是同一个 `Arc` 指向的实例"，
   隐含它本来就要在多任务间共享），这个前提本来就必须成立，不是本轮新增的
   要求；③ `&mut Reservation` 跨 `.await` 持有是否 `Send`：`&mut T: Send`
   当且仅当 `T: Send`（不要求 `T: Sync`，这是 `&T`/`&mut T` 在 `Send` 上
   天生的不对称——v3 的 bug 正是错误地依赖了 `&T: Send ⟺ T: Sync` 这条
   规则，用了 `&Reservation` 却没让 `Reservation: Sync`）——`Reservation`
   满足 `Send`（②已确认），所以 `&mut Reservation: Send` 成立。整条推理
   链没有依赖任何"假设编译器会怎样"的模糊说法，是逐个字段核对 `Send`/
   `'static` 的构造性论证，在脑子里过一遍类型检查（任务要求①）没有发现
   缺口。
2. **常量口径 Medium（M1）**——`ROW_BUFFER_MARGIN` 从 8 改成 9，新增
   `exhausted` 状态区分"自然耗尽"（精确等于 `scanned`）和"提前退出"
   （`scanned + 9`，钳制在 `reserved`）。自查：`mark_exhausted()` 只在
   `page_from_stream` 的 `None` 分支被调用——会不会漏掉某个"其实也应该算
   自然耗尽"的分支？——核对了 §4.2 的全部四个返回点：`None` 分支（调用
   `mark_exhausted()`，正确）；`hits.len() == page_size` 分支（游标非空，
   没有观察到 `None`，不是耗尽，正确不调用）；字节预算拒绝分支（同上，
   不是耗尽）；`scanned == row_budget` 分支（预算自己生效，不是分区到底，
   不是耗尽）——四个分支只有一个是真正的"流耗尽"，`mark_exhausted()` 的
   调用点唯一且正确。
3. **让出点与结算/所有权的三方协同（任务明确要求）**：新的 `Reservation`
   （拥有式、在 work future 内部）跟 §4.5 的 yield 机制、H3 的 permit
   机制，三者在真实 async 控制流里的先后关系需要交代清楚，逐一核对：
   - **permit 在最外层，`Reservation` 在 permit 之后**：§6.5 的伪代码顺序
     是 `Reservation::reserve(...)`（非阻塞，构造完立刻把所有权交给
     `async move` 块）→ `admission.acquire_owned().await`（可能阻塞排队）
     → `recall_page`/`remember_checked` 内部的扫描/写入循环。`Reservation`
     从构造到结算，全程都在这个 `async move` 块的所有权范围内，`permit`
     （`OwnedSemaphorePermit`）也是——两者是这个 future 内部先后创建的两个
     局部变量，不是谁包着谁，是顺序持有：permit 先于 `mark_touched()` 拿到
     手（§6.5 的伪代码顺序），`Reservation` 的 `touched` 状态因此永远只在
     "已经过了 permit 排队"这个阶段之后才可能变成 `true`——这与 §8 P7
     场景 3(b)"排队等 permit 时 `Reservation` 还没 `touched`，取消全额
     退款"这条结论完全对齐，不是两套独立机制凑巧给出一致答案，是同一段
     顺序代码决定的必然结果。
   - **yield 点在扫描循环内部，不跨越 `Reservation`/permit 的持有边界**：
     `yield_now().await`（§4.5）发生在 `page_from_stream` 循环体内部，此时
     `reservation`（`&mut` 借用）和 `_permit`（外层局部变量，扫描函数不
     直接持有它，只是活在同一个 `async move` 块的作用域里）都还没有被
     释放/消费——`yield_now()` 只是把控制权交还给 executor 一次，不改变
     这两个局部变量的生命周期。取消发生在 `yield_now()` 期间，触发的是
     整个 `async move` 块（连同它按值持有的 `reservation`、`_permit`）被
     `bind_to_lifecycle` 一起 drop——`Reservation::Drop` 和
     `OwnedSemaphorePermit::Drop` 各自独立执行，顺序由 Rust 的字段
     声明顺序/局部变量声明顺序决定（后声明的先 drop），但 §6.5 已经论证过
     两者的清理逻辑互不依赖对方（`Reservation::Drop` 不需要知道 permit
     是否已经释放，反之亦然），drop 顺序不影响正确性。
   - **不存在"work 内部又去 `select!` lifecycle"的第二个竞态来源**：§4.5
     已经论证过为什么 `page_from_stream` 内部不下沉 `lifecycle`（会产生
     双重取消检查点）；`Reservation`/permit 的所有权变化没有改变这条论证
     ——`page_from_stream` 仍然只接受 `&mut Reservation`，不接受
     `lifecycle`，取消判断完全留在 `bind_to_lifecycle` 唯一的外层
     `select!` 里。三者的协同关系是一条单向链：`bind_to_lifecycle` 的
     取消判断 → （生效时）drop 整个 work future → 级联 drop
     `reservation`/`_permit` → 各自的 `Drop` 独立结算/释放；没有反向的
     依赖（`Reservation`/permit 不会影响 `bind_to_lifecycle` 什么时候
     取消），也没有第三条并行的判断路径，不会"打架"。
4. **取消窗口表述 Medium（M2）**——§8 P7 场景 2、§4.5 的措辞都已经把"9 行"
   （未观察到）和"一个 yield interval（32 行，consumer 会正常处理并计入
   `scanned`）"分开描述；判据 2b 改成多 phase offset + `page_from_stream`
   测试 seam。自查：这条修法会不会让 §3.3 的"物化行数上界=10"和这里的两个
   数字（9、32）产生第三种容易混淆的计数口径？——不会：§3.3 的"10"回答的是
   "任意时刻内存里同时存在多少个行对象"，M2 的"9"回答的是"取消发生时未被
   consumer 观察到、但已被 SQLite 产出的行数"，"32"回答的是"取消信号 ready
   到 work 真正让出之间，consumer 还可能正常处理多少行"——三者回答的是
   三个不同的问题（内存驻留量 / 计费未观察量 / 取消响应延迟量），数值上
   `10 = 9 + 1`（consumer 当前手上那 1 行）是唯一的数值关联，`32` 跟另外
   两者没有数值关系，只是"三个都在 SCAN_YIELD_INTERVAL_ROWS/row_buffer_size
   这两个旋钮附近"这件事本身容易让读者以为是一回事——§3.3/§6.4/§8/§4.5
   四处现在都各自用一句话点明自己回答的是哪个问题，不指望读者自己拼图。
5. **touched 边界 Medium（M3）**——选定方案①：`touched` 表示"已进入 DB
   admission 阶段"，不精确等于"SQL 已交给 worker"，不改动存储层。自查：
   选①而不是②（把 touched 信号下沉到真正拿到连接/提交命令之后）会不会让
   计费在某些场景下变得不合理地重（比如一个调用长期卡在等 SQLite 写锁但
   最终被取消，从未真正执行）？——会更重，但这是刻意的取舍，不是疏漏：
   `busy_timeout=5s` 意味着这类"卡在锁竞争"的调用本身已经占用了一个稀缺的
   pool 连接槽位长达数秒（跟 §6.5 决策 P8 要防止的"连接被占满"是同一类
   真实成本），即使最终没有写入任何数据，它占用共享资源的时间也是真实
   发生的——按 admission 阶段计费，对这部分"占了坑但没干成事"的成本仍然
   计费，跟"限流本来就该反映真实资源占用，不只反映最终是否成功"这条
   §6.1 已经确立的原则一致，不是这里新引入的额外从严。
6. **判据模型 Medium（M4）**——判据 9b 重写为五步真实资源竞争模型，明确
   覆盖三个方法。自查：步骤③依赖 WAL 模式——如果实现阶段最终没有开启 WAL
   （比如出于其它权衡考虑用默认的 rollback journal 模式），这条判据会不会
   整体失效？——步骤③会失效（rollback journal 模式下写事务会阻塞并发读，
   断言"正常返回"不成立），但这是判据对存储层配置的一个显式依赖，不是
   判据设计本身的缺陷——W 接线时如果决定不用 WAL，需要把步骤③换成一个
   不依赖并发读写不冲突的验证方式（比如干脆在①释放写锁之后再验证进程内
   路径能正常读到），本文档在这里明确点出这个依赖，不是假装它不存在。
7. **needle 单一来源 Medium（M5）**——新增 `Needle` newtype，`decode_cursor`/
   `recall_page`/`page_from_stream` 都改成接受 `&Needle`。自查：`Needle`
   的字段是私有的（`Needle(String)`，字段不带 `pub`），这是否足以防止
   "有人在 handler 之外的某处手写一个 `Needle(some_str.to_owned())` 绕过
   `normalize`/`none_for_recent`"？——同一个 crate 内部，私有字段仍然可以
   被同 crate 其它模块访问（Rust 的可见性是按模块而不是按类型划分的）——
   如果 `Needle` 定义在跟 `recall_page` 不同的模块里，且该模块外没有
   `pub(crate)` 之类的放宽，字段确实对外不可见；但如果两者在同一个模块，
   裸构造在类型层面仍然可能发生。这是实现阶段需要注意的一个模块划分细节
   （`Needle` 应该定义在一个独立的、只导出两个构造函数的模块里），本文档
   点出这个要求，不假装类型系统在任何模块划分下都自动生效。
8. **残留注释 Low（L1）**——`scan_stream` 文档注释、§4.5 的 yield 点措辞
   都已改正。自查：这两处修正之外，还有没有其它地方残留"零行未使用"或
   "处理完第 scanned 行"这类跟当前结论矛盾的旧表述？——搜索全文"取出但
   未使用"/"处理完第"/"至多一行在飞"等关键短语，除了已修正的两处和 §8
   场景 2 里已经用 blockquote 明确标注"这个说法不成立"的历史更正段落
   （保留作为改动记录的一部分，不是当前结论）之外，没有发现第三处未被
   标注的残留。

**7 条之间以及跟更早几轮结论的协同自审**：v4 的改动全部是收口性质——`H1`
换所有权模型不改变 `Reservation` 对外可观察的计费行为（`settle_amount()`
的分支结构跟 v3 的 `commit`/`Drop` 逻辑等价，只是挪了个地方、去掉了内部
可变性）；`M1` 只让计费更精确（不改变哪些场景收费、哪些场景退款，只改变
"收多少"）；`M2`/`M3` 只是把已有的保守边界描述得更准确，没有放松任何一条
承诺；`M4` 只是让判据更贴近真实资源竞争，不改变 §6.5 的 MUST 契约本身；
`M5` 只是把一条已经在文档里写明的约定升级成类型约束；`L1` 是纯文字修正。
没有一条改动反过来削弱了第 10/10b/10c 节已经确认成立的结论（游标状态机、
字节预算证明、限流身份修法、P8 的设计结论本身）。

## 12. 遗留给 T8.5c-W 的接口清单

**以下几条是 MUST，不是"W 决定要不要做"的可选实现建议**：

- **memory `RateLimiter` 的创建点在 mount 层，不在 `methods_for` 闭包内**
  （决策 6.3 的 v2 更正，限流身份 Critical）——必须与 `OsScopedMemory::new`
  同一层级创建一次（`mount_package`/`lend()`，`domain.rs:282-293` 附近），
  身份是稳定的 `(module, partition)`，跨该模块的 restart generation 存活。
  **不能**沿用 `_a24/events/emit` 那个"每代重建"的先例（`domain.rs:1327-
  1337`）——两者对"崩溃重启要不要刷新配额"这件事的要求是相反的，是 events
  专属的取舍，不是通用先例。判据 8/8b（第 9 节）是这条契约的可观察验证点。
- **全局共享的连接 admission permit 是 MUST**（决策 P8，§6.5）——**v3 更正
  （H3，第二轮评审）**：这个 permit 现在覆盖 `remember_checked`/
  `recall_page`/`recent_page` **三个方法**，不再只覆盖读路径（v2 曾经把
  `remember_checked` 排除在外，理由不成立，见 §6.5 的 H3 更正）。单例创建点
  必须与共享 `SqlitePool` 同一作用域（`server.rs`，`agent24_memory::KvStore::
  open` 被调用的地方），permit 数必须小于 `max_connections`（建议
  `max_connections - 1`），等待必须在 `bind_to_lifecycle` 包裹的 future
  内部，取消时靠 RAII 自动释放（不需要手写释放代码）。**v4 更正（H1）**：
  必须用 `Arc<tokio::sync::Semaphore>::acquire_owned()`（返回
  `OwnedSemaphorePermit`），不是 `acquire()`（返回借用 `Semaphore` 生命周期
  的 `SemaphorePermit<'_>`）——整个 work future 必须是 `'static`（跟下面
  `Reservation` 同一个约束的来源），借用型的 permit 会破坏这一点。判据 9b
  （v4 改成能证明"三个方法共享同一个 permit"的真实资源竞争模型，不只是
  "pool 会被占用"）是这条契约的可观察验证点。§6.5 末尾给出了跟
  `Reservation`（下一条）协同的固定获取顺序（先 `RateLimiter` 后
  `Semaphore`），W 接线时不能颠倒这个顺序；新增第 10d 节第 3 条给出了
  `Reservation`/permit/yield 三者在真实 async 控制流里谁在里谁在外的完整
  交代。
- **扫描循环里的显式让出点是 MUST**（决策 4.5，§4.5，让出点 High）——
  `recall_page`/`recent_page`（经由共享的 `page_from_stream`，v4 新增，
  见 M2）的扫描循环必须每 `SCAN_YIELD_INTERVAL_ROWS`（32）行
  `tokio::task::yield_now().await` 一次，不能只依赖 `stream.next().await`
  本身"看起来是个 `.await` 点"就假设取消/超时会生效——sqlx 预取领先消费者
  时这个假设不成立（§4.5 的论证）。判据 2b（v4 改成覆盖多个 phase offset）
  是这条契约的可观察验证点。**v4 新增（M2）**：判据必须调用
  `page_from_stream` 这同一个函数，不能为了方便测试另外写一份"看起来一样"
  的循环逻辑。
- **`Reservation` 的 `touched`/`scanned`/`exhausted` 必须在扫描循环里实时
  维护**（决策 §6.4，结算漏洞 High + 常量口径 Medium）——`recall_page`/
  `recent_page`（经由 `page_from_stream`）进入扫描循环前必须调用一次
  `reservation.mark_touched()`，循环体每处理一行必须调用一次
  `reservation.record_scanned(scanned)`，观察到流真正耗尽（`None` 分支）
  时必须调用一次 `reservation.mark_exhausted()`（**v4 新增，M1**——漏掉这
  一步不会导致错误结果，但会让本该精确结算的场景多算 9 行，是一个计费
  精度问题）；`remember_checked` 在执行 `INSERT` 之前必须调用一次
  `mark_touched()`。**不能**只在成功路径上维护这几个值、指望 `Drop` 兜底
  全额退款——那正是 H2 指出的原始漏洞。**v4 更正（H1）**：`Reservation`
  现在是**拥有式**的（`Arc<RateLimiter>`，不带生命周期参数），必须在
  `bind_to_lifecycle` 包裹的 `async move` 块内部构造（`Reservation::
  reserve(limiter.clone(), cost)`）并把所有权移入这个块——**不能**像 v3
  那样在外层构造、借用进 work future，那个形状跟 `CallFuture` 要求的
  `'static + Send` 不兼容（第 4.2 节的 H1 详细论证）。

其余接口/依赖：

- `RateLimiter::try_acquire_weighted(cost: ScanCost) -> bool`（决策 6.2，v2
  把 `cost` 的类型从 `f64` 换成 `ScanCost(u32)` newtype——W 的调用点需要用
  `ScanCost::from_rows(usize)` 或编译期常量 `ScanCost::from_rows_const`
  构造，不能再传裸浮点数；v3（L1）：`from_rows_const` 现在带一条
  `assert!`，传入超过 `u32::MAX` 的编译期常量会直接编译失败）。
- **v4 重写（H1/M1）**：`Reservation::reserve(limiter: Arc<RateLimiter>,
  cost: ScanCost) -> Option<Reservation>`（不再接受 `&RateLimiter`）/
  `Reservation::mark_touched(&mut self)` / `Reservation::record_scanned(
  &mut self, usize)` / `Reservation::mark_exhausted(&mut self)`（v4 新增，
  M1）/ `Reservation::commit(self)`（v4：不再接受 `actual` 参数——结算公式
  已经收进 `settle_amount()`，调用方不需要也不能自己算）——W 的
  `recall_page`/`recent_page`/`remember_checked` 接线必须：① 在
  `bind_to_lifecycle` 的 `async move` 块**内部**构造并持有 `Reservation`

  ③ 扫描循环里每行调用 `record_scanned()`；④ 观察到流真正耗尽时调用
  `mark_exhausted()`；⑤ 正常完成时在 work future 内部显式调用
  `commit()`（无参数）。正常路径之外的每一个提前返回分支（错误、取消）都
  会让 `Reservation` 因为没有被显式 `commit` 而走 `Drop`——`Drop` 和
  `commit()` 现在共用同一个 `settle_amount()`，不是两份独立的公式，W 不能

- `MEMORY_COST_REMEMBER`/`MEMORY_COST_RECALL`/`memory_cost_recent(page_size)`

  预留量、不是最终一定扣的量；v3（L2）：`recent` 的预留量不再声称"恒等于
  实付量"，W 接线 `recent_page` 时同样要走 `commit()`/`Drop` 的结算路径，

- **v4 重写（M5）**：`Needle`（新增 newtype，§4.2）——handler 用
  `Needle::normalize(query)`（`recall`）或 `Needle::none_for_recent()`
  （`recent`）构造**一次**，同一个值传给 `decode_cursor(token, method_tag,

  `page_from_stream`）。`encode_cursor(seq, method_tag, &needle)` /
  `decode_cursor(token, method_tag, &needle)` /
  `cursor_fingerprint(method_tag, &needle)`（决策 P6/§7.1）现在都接受
  `&Needle`，不再接受裸 `&str`——W 不能在 handler 之外的任何地方再调用

- 第 9 节判据 10 明确列出的、需要真实挂载/授权状态才能验证的场景——W 在写
  `memory_callback.rs` 的集成测试时需要补上，P 这边的判据只覆盖"假设已授权"的

- `SqliteConnectOptions::row_buffer_size(8)`（决策 §3.2，v2 新增）——W 在
  `agent24-memory/src/lib.rs` 的 `KvStore::open` 里配置这个连接选项。**v4
  更正（M1）**：这个 `8` 和 `ROW_BUFFER_MARGIN`（§6.4）**不再是同一个数字**
  ——`row_buffer_size` 是 sqlx 连接选项本身（channel 容量），`ROW_BUFFER_
  MARGIN = 9 = row_buffer_size(8) + worker 阻塞发送的第 9 行`，两者相差 1

  代码 review 或者一条显式断言（比如 `const _: () = assert!(ROW_BUFFER_
  MARGIN.0 == 9)` 类似的自证性检查）保证，不完全依赖测试捕捉。

## 13. v5（2026-09-19）：ephemeral 池的 admission 适用范围——正式修订，不是附注

`T8.5c-W-mount.md` 评审时两轮都被指出同一个问题：本节"全局共享的连接
admission permit 是 MUST"这条契约要不要求"OOP memory 在任何池配置下都
必须发放这个能力"，v4 文本本身没有显式排除过 ephemeral
（`agent24-memory::KvStore::open_memory()`，`:memory:`，单连接）这种
池——本文档设计、验证、判据 9b 的五步模型全部只针对文件后端
（`KvStore::open`，WAL，`max_connections = 5`）这一种池形状，从未讨论过
ephemeral。round 2 评审进一步指出：把这段话作为一条"不改变 v4 冻结内容"
的附注追加在文末，本质上还是下游文档（或者本文档自己）在事后单方面改写
一份已经宣称冻结的契约，只是换了个位置——真正解决办法是像 v1→v2→v3→v4
一样，把这当成一次正式的版本修订。这里把它记作 **v5**，不再用"附注"这个
弱化的说法。

**v5 修订内容**：本节 MUST 契约管辖的前提是"存在一个可被多个 OOP 调用方
共享、可能被占满、且可以为共享方安全预留 headroom 的连接池"（文件后端
满足：5 个连接，WAL，`max_connections - 1 = 4` 个 permit 留给 OOP，
1 个连接永远留给进程内路径）。

**修正 round 2 指出的一处事实错误**：`open_memory()` 底下**确实是**一个
被共享的池——`SqlitePoolOptions::new().max_connections(1)` 建的是恰好
一个连接的 `SqlitePool`，`KvStore`（`#[derive(Clone)]`）克隆出的每一份
句柄都指向同一个 `pool`，多个调用方对它发起的查询会在 sqlx 内部排队
争用同一个连接——"不是共享池"这个说法是错的，物理上它就是一个共享池，
只是容量恰好是 1。真正的原因是：**这个池唯一的一个连接已经要留给
进程内路径使用，`max_connections - 1 = 1 - 1 = 0`，没有任何 headroom
可以让渡给 OOP 调用方**——0 个 permit 不是"更少的配额"，是"这个池
从容量上就不存在能分给第二个使用者的余量"。至于"能不能靠加连接数来
制造 headroom"，答案仍然是否定的，但理由是 §5.2 已经给出的另一条、
独立成立的事实：`open_memory()` 的每个 `:memory:` 连接是互相独立的
数据库，加连接数不会得到"同一份数据的更多并发访问能力"，只会得到
互相看不见彼此的多个空数据库——这条论证不变，只是不再跟"这个池是不是
共享池"混在一起说。

- 对文件后端，本节的公式（单例、`max_connections - 1`、`bind_to_lifecycle`
  内等待、`acquire_owned()`、drop 释放）**没有例外**，T8.5c-W-mount 必须
  一字不改地遵守。
- 对 ephemeral，本节的结论是：不发放 OOP `memory` 能力——不是因为这个池
  "不是共享池"，而是因为它是一个只有 1 个连接的共享池，进程内路径已经
  要用掉这唯一的连接，`max_connections - 1 = 0` 里没有能分给 OOP 的
  余量，套用 `KVSTORE_EPHEMERAL_MAX_CONNECTIONS - 1 = 0` 构造一个容量
  为 0 的 `Semaphore` 会让每次 OOP 调用永久排队而不是立即拒绝（见
  T8.5c-W-mount 决策 4 §5.1），所以选择压根不构造 admission、不发放
  这个能力，而不是构造一个数值上合法但语义上等同于永久拒绝服务的
  permit 数。
