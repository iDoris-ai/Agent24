## 2. 决策 1：`MemoryEntitlement` 类型（继承 v1 W1，未改动实质）

```rust
// rust/apps/agent24d/src/os_memory.rs（或独立的 memory_entitlement.rs 模块）

/// mount 层对"这个模块此刻能不能用 `_a24/memory/private/*` /
/// 未来的 `_a24/memory/scoped/*`"的唯一事实源。
///
/// 不变式：`private` 字段是 `Some` 当且仅当三个必需部件——真实拿到的
/// `Arc<OsScopedMemory>`、这个 (module, partition) 专属的 `Arc<RateLimiter>`
/// （决策 3）、daemon 级共享的 `Arc<Semaphore>`（决策 4）——全部齐备。没有
/// 任何构造路径能产出"字段是 Some 但内部某个 Arc 缺失"的值：
/// `PrivateMemoryHandle` 的三个字段都不是 `Option`，唯一能让
/// `MemoryEntitlement::private` 变成 `None` 的方式是整个 `Option` 取
/// `None`，不存在"半个 handle"的中间状态——这条不变式在决策 4 引入
/// ephemeral 分支之后依然成立：ephemeral 下压根不会走到构造
/// `PrivateMemoryHandle` 这一步（见决策 4 §5.3），不是构造出一个内部
/// 字段残缺的 handle。
#[derive(Clone)]
pub struct MemoryEntitlement {
    private: Option<PrivateMemoryHandle>,
    /// 恒为 `None`——SPEC §3 留门第 5 条：老 manifest 的 `memory` 只映射到
    /// private，`scoped` 是未来才实现的能力。今天没有任何构造路径能把它
    /// 设成 `Some`（`ScopedMemoryHandle` 未定义任何字段，见下）。
    scoped: Option<ScopedMemoryHandle>,
}

#[derive(Clone)]
pub struct PrivateMemoryHandle {
    pub memory: Arc<OsScopedMemory>,
    pub limiter: Arc<RateLimiter>,
    /// 恒为真实、恒有效的 `Arc<Semaphore>`——不是 `Option`。这个字段
    /// 为什么能在 ephemeral 下也保持"非 Option 但恒真"，见决策 4：
    /// `Option` 只出现在 `MemoryLease::admission()` 方法的返回值这一层
    /// （不是一个字段，见 §5.3 v4 更正），`PrivateMemoryHandle` 只在
    /// `MemoryLease::admission()` 返回 `Some` 时才会被构造出来。
    pub admission: Arc<Semaphore>,
}

/// 占位类型。今天没有任何字段——`Infallible` 使它成为不可构造的类型，
/// 把"scoped 今天不可达"从文档承诺升级成编译期事实。F8c/F9 真正设计
/// scoped 时，这个类型获得真实字段，`Option<ScopedMemoryHandle>` 的
/// 构造路径随之打开——不需要改 `MemoryEntitlement` 的形状。
// v3 更正（Codex round 2 指出 v2 的核实用错了复现片段）：v2 单独验证了
// `derive(Clone)` 能不能透传给一个自己也标了 `#[derive(Clone)]` 的
// wrapper（`Wrapper(Infallible)`），确认可以——但那不是 §2 实际的
// `ScopedMemoryHandle` 定义：这里从未给 `ScopedMemoryHandle` 本身标过
// `#[derive(Clone)]`。用 Codex 复现的确切写法（`ScopedMemoryHandle`
// 不带 derive）重新编译，`MemoryEntitlement` 的 `#[derive(Clone)]`
// 确实报 E0277（`ScopedMemoryHandle: Clone` 不满足）——v1 的原始发现
// 是对的，v2 的"假阳性"结论是错的，这里改正：
#[derive(Clone)]
pub struct ScopedMemoryHandle(std::convert::Infallible);

impl MemoryEntitlement {
    pub const NONE: MemoryEntitlement = MemoryEntitlement { private: None, scoped: None };

    pub fn private(handle: PrivateMemoryHandle) -> MemoryEntitlement {
        MemoryEntitlement { private: Some(handle), scoped: None }
    }

    pub fn private_handle(&self) -> Option<&PrivateMemoryHandle> {
        self.private.as_ref()
    }
}
```

### 2.1 三处消费者口径（继承 v1 §2.2 的表，补一行 ephemeral）

`Capability::Memory` 的粗粒度判断（`granted.has(Capability::Memory)`）和
`MemoryEntitlement::private.is_some()` 的细粒度判断**不总是相等**——决策
2（C1）让 `granted.has(Capability::Memory)` 对 OOP 模块也可能为真，但
`private` 是否为 `Some` 现在有**两条**独立的落空路径：`lend()` 失败
（v1 已覆盖）**和** ephemeral 下压根没有 admission 可用（决策 4 新增）。
三处消费者的依据不变：

| 消费者 | 依据 | 为什么 |
|---|---|---|
| `Handler::call()` 内部的 forbidden 判断（T8.5c-W-wire 实现） | `entitlement.private_handle().is_some()` | "有 handler 但没 grant" 与 "有 grant 但没 handle"（不管是 `lend()` 失败还是 ephemeral 无 admission）对调用方必须是同一个 `forbidden` |
| `Offer.provides` 是否含 `"_a24/memory/private/"` | `entitlement.private_handle().is_some()` | **不是** `granted.has(...)`——授予一个没有 handle 的能力就是撒谎，ephemeral 下这条规则第一次真正生效（v1 时代唯一的落空路径是 `lend()` 失败，理论上罕见；ephemeral 是决定性的、每次都会命中的落空路径） |
| `MountReport.granted`（`"memory"` 字符串是否出现） | `entitlement.private_handle().is_some()` | 同上，与 in-process 路径今天已有的过滤逻辑（`domain.rs:1174`）同一条规则，本文档把它搬到 OOP 路径 |
| `Methods` 是否注册 `_a24/memory/private/*` 三个方法（wire 实现） | 恒注册，不看 entitlement | 让 `forbidden`（方法存在、这次调用不被允许）与 `-32601`（方法根本不存在）保持可区分——这条边界属于 wire 文档，这里只说明它依赖 `entitlement` 而不是 `granted` |

## 3. 决策 2：`KERNEL_OOP_GRANTS` 加入 `Capability::Memory`（解决 C1）

### 3.1 改动


同时改写 `domain.rs:76-80` 的注释——它今天说"out-of-process Memory ...
需要自己的评估"，本文档就是那次评估，注释需要更新为类似：

> `Memory` joined in T8.5c-W-mount. Out-of-process access to the shared
> memory base goes through the OOP wire surface (`_a24/memory/private/*`,

### 3.2 为什么只加这一行不够——衔接决策 1 的表

加入 `Capability::Memory` 只解除了"永远不可达"这一个症状。真正让
`lend()` 被调用、`MemoryEntitlement` 被构造成 `Some`，还需要决策 3
（限流器）、决策 4（admission）、决策 5（catalog 两阶段）三块同时到位——
这正是 Codex 建议把 W1/W2/W3 打包收敛、不能只改一行了事的原因：C1 这一行
本身没有历史遗留的正确性风险，但它是整条 `lend → entitlement →
supervisor 注册 → catalog 激活` 链条的入场券，链条其余部分不到位，加了
这一行也只是把"entitlement 永远是 NONE"从"因为 grants 检查就被挡住"
换成"因为后面某一步落空"，外部可观察行为不变。

### 3.3 正向判据（C1 明确要求，之前 v1 完全没有；v2 更正：按实际可观测的返回值重写）

v1 写的判据假设 `mount_package` 会把 `Offer`/`memory_entitlement` 作为
返回值交给测试——读代码确认它的返回类型是 `(Router, MountReport)`，
`Offer` 在函数内部构造后直接传给 `supervise(...)`，从未被返回；
`memory_entitlement` 同样是函数内部的中间量。v2 把这条判据拆成两层，
分别标注各自的验证边界，不再假装四件事能在同一次 `mount_package`
调用里被同等程度地验证：

**第一层——纯函数/单元级，不需要 `mount_package`、不需要真实进程**：

1. `Grants::granting(manifest.kernel_capabilities(), KERNEL_OOP_GRANTS)`
   包含 `Capability::Memory`（证明决策 2 生效）——直接调用这个函数，
   传一个声明 `kernel_capabilities: [memory]` 的 manifest，不需要挂载。
2. `memory_grant_name(&entitlement)`（§5.3 新增的提取函数）在
   `entitlement` 是 `MemoryEntitlement::private(...)` 时返回
   `Some("memory")`，在 `MemoryEntitlement::NONE` 时返回 `None`——直接
   构造两种 `MemoryEntitlement` 值调用这个函数，不需要挂载、不需要
   `Offer`/`MountReport`。这条判据覆盖的正是 §5.3 新增代码要解决的
   "决策 2 生效后，`granted_names`/`provides` 不能无条件带上 memory"
   这条正确性要求。

**第二层——集成级，`mount_package`/`mount_all` 的真实返回值可以验证的
部分**：

3. 构造一个真实的 OOP 包（走真实 `discovery`/`Package` 构造路径），
   manifest 声明 `kernel_capabilities: [memory]`，针对文件后端
   （非 ephemeral）的 `MemoryLease` 调用 `mount_all(...)`（不是单独调
   `mount_package`——`mount_all` 才是暴露 `MountReport` 的公开入口），
   断言返回的 `reports[0].granted` 包含 `"memory"`，且
   `reports[0].outcome == MountOutcome::Mounted`。这是 `MountReport`
   作为真实返回值能验证的全部——`Offer` 本身（连同它最终是否真的被
   OOP 模块在 `initialize` 握手里收到）不在这个返回值里，见下面的
   "验收缺口"。

**验收缺口（H3 的一部分，老实记录，不假装已解决）**：`Offer` 在
`mount_package` 内部构造后立刻传给 `supervise(...)`，本文档没有、也
不打算新增一个测试专用返回值或 hook 把它导出来给 mount 层的判据用——
`Offer.provides` 里 `"_a24/memory/private/"` 是否真的出现在一次真实的
OOP `initialize` 响应里，需要 `host.supervisors`/`supervise` 真正跑
起来、模块完成握手，这已经超出"mount 层纯函数 + 已有公开返回值"的
范围，属于 T8.5c-W-wire 做集成测试时的责任——上面第 1/2 层判据已经
把"决定 provides 该不该含 memory"这条**逻辑**验证到了单元级，wire
只需要验证"这个逻辑算出来的值真的被传进了 `Offer`、`Offer` 真的被
握手带出去"，不需要重新验证逻辑本身。

## 4. 决策 3：限流器（`RateLimiter`）创建点与跨 generation 存活（继承 v1 W2 §3.2-3.4）

Codex 没有对这部分提出新的问题，原样继承，只更新代码位置引用以匹配决策
5 之后 `lend()` 的新签名。

### 4.1 创建点：mount 循环体内，`lend()` 成功之后，`methods_for` 闭包之外

**v3 更正（H2，Codex round 2 指出这段逻辑内联在 `mount_package` 里，
没有任何返回值/测试能单独观察它）**：把"给定一次 `lend()` 的结果，
构造 `MemoryEntitlement`"这一步提成一个独立的自由函数——不是为了给
生产代码加抽象层，是让这段本来就是纯计算（不做 I/O、不依赖
`mount_package` 的其它局部变量）的逻辑可以脱离整个挂载流程被直接
单元测试，跟 §5.3 的 `memory_grant_name` 是同一种手法：

**v4 更正（Codex round 3 指出：按下面的调用方式，`memory_lend` 会被
这个函数按值吃掉，而 §6.4 的 OOP `mark_mounted` 调用点后面还要读同一个
`memory_lend` 取 `partition`——这是一处会导致 `E0382`（use after move）
的编译错误）**。修法是让这个函数只拿它真正用到的两个字段
（`scoped`/`admission`），`partition` 留在调用方手里给 `mark_mounted`
用，不经过这个函数：

```rust
// domain.rs 的自由函数，紧邻 mount_package。纯函数：给定一次 lend()
// 的结果，构造这次挂载应该拿到的 MemoryEntitlement。不做 I/O，不依赖
// mount_package 内部任何其它局部变量——可以脱离整个挂载流程单独调用。
// 只接受 (scoped, admission) 二元组，不接受 partition——partition 是
// mark_mounted 才需要的东西，让它留在调用方手里，避免这个函数把整个
// memory_lend 按值吃掉导致调用方后面用不了。
fn build_private_memory_entitlement(
    lend: Option<(
        Arc<crate::os_memory::OsScopedMemory>,
        Arc<tokio::sync::Semaphore>,
    )>,
) -> MemoryEntitlement {
    match lend {
        Some((scoped, admission)) => MemoryEntitlement::private(PrivateMemoryHandle {
            memory: scoped,
            // 每次调用这个函数恰好创建一次——不在 methods_for 闭包里，
            // 闭包每次跑（每个 restart generation）只克隆这个 Arc，绝不
            // 重新构造（对照 domain.rs:1334-1337 的 events 限流器"故意
            // 每代重建"，这里刻意不这样做）。
            limiter: Arc::new(crate::events_emit::RateLimiter::new(
                crate::os_memory_page::MEMORY_RATE_CAPACITY,
                crate::os_memory_page::MEMORY_RATE_REFILL_PER_SEC,
            )),
            admission,
        }),
        None => MemoryEntitlement::NONE,
    }
}
```

`mount_package` 里的调用点——**借用** `memory_lend`、克隆需要的两个
`Arc`，原始的 `memory_lend`（连同 `partition`）保持完整、未被移动，
留给 §6.4 的 `mark_mounted` 调用点使用：

```rust
// mount_package 内，granted 计算之后，methods_for 闭包定义之前
let memory_lend = /* 决策 4 §5.3 给出的完整表达式 */;
let memory_entitlement = build_private_memory_entitlement(
    memory_lend
        .as_ref()
        .map(|(scoped, _partition, admission)| (scoped.clone(), admission.clone())),
);
// memory_lend 本身在这里之后仍然完整可用（上面只借用了它），§6.4 的
// `if let Some((_, partition, _)) = memory_lend { ... }` 不会遇到
// use-after-move。
```

`memory_entitlement` 跟 `granted`/`event_sink` 一样在闭包外层 `let` 一次、
`.clone()` 进闭包（`domain.rs:1323-1326` 已有的模式）。

**这解决了什么、没解决什么**：`build_private_memory_entitlement` 本身
可以在不跑 `mount_package`/`mount_all`/supervisor 的情况下直接单元
测试——构造两个 fake 的 `(scoped, admission)` 二元组（相同的
`Arc<Semaphore>`、不同的 `Arc<OsScopedMemory>`），调用两次，断言两次返回的 `.private_handle()
.unwrap().limiter` 指针不相等——这就是决策 3"每次调用恰好创建一次
limiter"的核心正确性，脱离挂载流程也能验证。**它没有解决**的是"两个
真实的、不同的 OOP 模块被真实 `mount_all` 挂载时，`agent24d` 是否真的
把同一个 daemon 级 `Arc<Semaphore>` 传给了这个函数两次"。**v5 更正
（Codex round 4 指出这段话仍在暗示"可以不做真实集成验证"，跟 §7.2
"必须交付，不是可选项"的口径矛盾）**：这条集成级验证**不是**留给
T8.5c-W-wire 自行判断要不要做的开放决定，§7.2 已经把它定为必须交付的
判据——真实挂载两个不同的 OOP 模块，让模块 A 通过真实
`Handler::call() → bind_to_lifecycle` 占满 4 个 permit，断言模块 B
的第 5 个调用真的卡住。"`mount_all` 只持有一个 `&MemoryLease` 引用"
这条类型论证不是"足够的替代证据"，只是解释了为什么这个 bug 类别
在类型层面不太可能发生——但"不太可能发生"从来不能替代 §7.2 要求的
那条真实断言，这里不再给出"接受间接证据"这个选项。

### 4.2 身份：为什么不需要显式查找表

`mount_package`/`mount_all` 的挂载循环本身按 catalogue 条目逐一执行，
`lend()`/`ensure_recorded()` 返回的 `partition` 是这次调用唯一确定的一个
——一次 `mount_package` 调用只可能对应一个 `(module, partition)` 组合，
"在这次调用里创建一个 `RateLimiter` 并只创建一次"本身就是"以
`(module, partition)` 为键"的具体实现。**前提**（继承 v1，Codex 已确认）
：今天不存在运行期热挂载/卸载，唯一调用者是 `server.rs:1277` 的一次
`mount_all(...)`，`agent24 os enable/disable` 不调用它们。

### 4.3 崩溃重启 vs daemon 重启（继承 v1 §3.4，未改动）

- **模块进程崩溃 → supervisor 重启**：新 `Generation`，重跑
  `methods_for` 闭包，`Arc<RateLimiter>`/`Arc<Semaphore>` 由闭包外层
  捕获，天然复用，配额不因崩溃重置——满足 SPEC §5。
- **daemon 进程整体重启**：`server.rs` 从 `open_memory_base` 到
  `mount_all` 全部重新执行，配额在这里被重置，且是正确行为——真正需要
  跨进程重启持久化的是用量的物理后果（`mem_owner_usage`，T8.5b 负责），
  不是 `RateLimiter` 的职责。
- **未来运行期热挂载**（今天不可达）：这个设计不会自动正确处理"卸载
  又重新挂载同一个模块"——`mount_package` 若被第二次调用，会创建
  **第二个** `Arc<RateLimiter>`，模块因此重新获得满额配额。**这不是
  本文档需要现在解决的问题**，如实记一笔留给那个未来改动的实现者。

## 5. 决策 4：admission `Semaphore` —— 单例、大小、ephemeral 边界（解决 C2，重新设计）

### 5.1 问题的确切位置

T8.5c-P §12 定的 MUST 契约：`recall_page`/`recent_page`/
`remember_checked` 三个方法必须共享**同一个**全局 admission permit，
大小是 `KVSTORE_MAX_CONNECTIONS - 1`（给进程内路径留至少一个连接的
headroom），在 `server.rs`、与共享 `SqlitePool` 同一作用域创建一次。

v1 的实现把这条契约字面套用到**唯一**一个 `MEMORY_CONNECTION_
ADMISSION_PERMITS` 常量上，从未考虑 `open_memory_base(ephemeral)`
两条路径的池大小不同：文件后端 `max_connections(5)` → 4 个 permit，
正确；ephemeral `max_connections(1)` → `1 - 1 = 0` 个 permit——一个
`Semaphore::new(0)` 意味着**任何** `_a24/memory/private/*` 调用都会
永久卡在 `acquire()` 上，直到这次调用自己的请求生命周期超时才被取消
（而不是立即被拒绝）。这比"没有这个能力"更糟：`Offer` 已经承诺了
`_a24/memory/private/`，调用方看到的是一个宣称存在、实际每次都超时的
能力。

### 5.2 三个候选方案评估

**方案①：让两种 pool 都具备可查询且一致的容量**（比如把
`open_memory()` 的 `max_connections` 也调到跟文件后端一样，统一用
`KVSTORE_MAX_CONNECTIONS - 1` 算 permit）——**否决**。§1 已经引用了
`open_memory()` 自己的文档字符串："a single connection: every
`:memory:` connection is a distinct database"。这不是"这个池连接数
偏少"的资源问题，是 SQLite `:memory:` URI 本身的语义：一个进程里两个
分别 `sqlite::memory:` 连接打开的是两个完全独立、互不可见的数据库。
简单地把 `max_connections(1)` 改成 `max_connections(5)`，池里会出现
5 个各自看到不同（且大部分是空的）数据库的连接——一次 `mount_package`
的 `ensure_recorded` 走连接 A 写入的分区身份，另一次 `remember_checked`
走连接 B 时读不到它，或者反过来把重复的身份行插两遍——这不是"容量不够"
，是"这个池从物理上就不是一个共享存储"，字面照抄方案①的做法会引入
比 C2 本身更严重的正确性问题（跨连接数据不一致），不是把它变得可查询
就能解决。

**方案②：ephemeral 使用支持多连接的共享内存/临时文件数据库**（比如
SQLite 的 shared-cache `:memory:` URI，或者换成临时文件 + WAL）——
**否决，理由是范围/架构一致性问题，不是技术不可行**：

- SQLite 的 shared-cache 模式即使能让多个 `:memory:` 连接共享同一份
  数据，WAL 模式本身要求一个真实文件（`-wal`/`-shm` 边车文件），
  `:memory:` 数据库结构性地用不了 WAL——退回到 rollback journal 意味着
  一个写事务会锁住整个数据库、阻塞所有并发读，T8.5c-P §12 判据 9b 第 3
  步"WAL 模式下写事务不阻塞并发读，第 5 个连接的进程内读应该正常返回"
  这条 headroom 验证在非 WAL 池上根本不成立——换句话说，方案②要么继续
  用 `:memory:`（headroom 验证失效），要么换成临时文件（下面第二条）。
- 换成临时文件数据库，技术上可行（拿到跟文件后端完全一样的
  `max_connections(5)` + WAL + headroom 语义），**但这直接违反
  `server.rs:1103-1110` 记录的、ME-1b-b 定下的既有设计原则**："an
  ephemeral instance's STORES were all in memory ... quietly starting to
  create per-module directories under the user's state dir would erode
  that"——把 ephemeral 的内存 KV 库换成一个临时文件，即使这个文件在
  `std::env::temp_dir()` 下、进程退出后大概率被系统清理，也是对这条
  已经写进代码注释、被前一轮评审明确认可的原则的一次修改，而"要不要
  修改 ephemeral 的存储后端架构"是一个比"mount 层怎么发放内存 entitlement"
  更大、需要独立评审的决定——不应该被这份控制面设计文档顺手改掉。
- **本文档的判断**：方案②是"正确"的长期方向（如果 ephemeral 未来
  需要真正支持 OOP 高并发内存访问），但代价（改动 ephemeral 的存储后端、
  引入落盘、需要新的清理策略、需要重新验证 WAL 假设）与"控制面/
  entitlement 设计"这个任务边界不成比例，留给需要它的人单独提，本文档
  不做。

**方案③（选定）：ephemeral 不发放 OOP `memory` 能力，结构性地不构造
admission，而不是构造一个容量为 0 的 admission**——理由：

- 不改动 `agent24-memory` crate 里任何一条现有的池配置——`open`/
  `open_memory` 的 `max_connections` 原样保留，避免触碰这个 crate 里
  可能依赖 `open_memory()` 单连接语义的其它测试/调用点（§1 已确认
  `open_memory_base` 是唯一的生产调用点，但 `open_memory()` 本身在
  `agent24-memory`/`agent24d` 两个 crate 的测试里被广泛复用，不应该
  因为 daemon 的一条 ephemeral 分支就改变它的通用行为）。
- 不违反 ME-1b-b 的既有原则——ephemeral 的内存数据库依然是纯内存、
  单连接，只是"OOP 模块拿不到这个能力"，跟"ephemeral 不往磁盘写模块
  数据"是同一种"ephemeral 功能范围比常驻 daemon 窄"的表达方式，不是
  新发明的例外。
- **诚实**：与其让 `Offer` 宣称一个结构上永远无法完成的能力（v1 的
  `0` 个 permit 场景），不如让 `granted.has(Capability::Memory)` 为真
  但 `MemoryEntitlement::private` 为 `None`——这正是决策 1 的表格已经
  覆盖的"grant 为真、handle 为假"状态，ephemeral 只是这个状态的第二条
  触发路径（第一条是 `lend()` 失败），wire 层的 `forbidden` 处理不需要
  为它新增任何分支。
- **in-process 模块不受影响**：in-process 的 `ScopedMemory` trait 路径
  从不读 `admission`（决策 3/T8.5c-P 已经确立），ephemeral daemon 下
  compiled-in 模块的内存能力（今天已经在工作的路径）行为完全不变。

### 5.3 具体设计（v2 改写：admission 从 `KvStore` 构造时派生，不再由调用方传入）

v1 让 `server.rs` 自己算 `Semaphore::new(KVSTORE_MAX_CONNECTIONS - 1)`，
再把它作为第三个参数传给 `MemoryLease::open`——Codex 指出这只是"调用方
按约定传对值"，`MemoryLease.admission: Option<Arc<Semaphore>>` 是公开
字段，类型上完全允许把文件后端的 `kv` 配一个 `None`，或者把 ephemeral
的 `kv` 配一个 `Some`，没有任何东西阻止这种错配；这个改动还额外要求
`domain.rs` 三处两参数测试调用点同步改成三参数。v2 把 permit 的构造
挪进 `KvStore` 自己的两个构造函数内部，让"这个池是不是文件后端"和
"要不要有 admission"在唯一一个地方决定，`MemoryLease::open` 的签名
完全不变：

**依赖改动（v3 更正：v2 的核实不够——`tokio` 今天根本不是
`agent24-memory` 的正式依赖）**：读 `agent24-memory/Cargo.toml` 确认
`tokio = { version = "1", features = ["macros", "rt-multi-thread"] }`
只出现在 `[dev-dependencies]` 段（第 28 行），库代码本身不链接
`tokio`。v2 只提议给这一行加 `"sync"` 特性，但 `[dev-dependencies]`
只在编译测试/示例时生效，**库代码**（`KvStore::open` 需要在正常构建
下构造 `Arc<tokio::sync::Semaphore>`）用不到它——这不是"缺一个
feature"，是"缺整个依赖"。正确改法：在 `[dependencies]` 段新增
`tokio = { version = "1", default-features = false, features = ["sync"] }`
（不需要 `"macros"`/`"rt-multi-thread"`，库代码不需要 `#[tokio::test]`
或独立运行时，只需要 `Semaphore` 这一个同步原语；`sqlx` 的
`"runtime-tokio"` 特性已经把真正的 tokio 运行时带进来了，这里只是
显式声明"需要 tokio 的 sync 模块"）。`[dev-dependencies]` 里原有的
`tokio`（给测试用 `#[tokio::test]`）保持不变。

**类型改动（v3 新增，Codex round 2 指出的类型不匹配）**：
`KVSTORE_MAX_CONNECTIONS` 之前定义成 `usize`，直接用在两个要求不同
整数类型的地方——`SqlitePoolOptions::max_connections` 在 sqlx 0.8 上
签名是 `max_connections(self, n: u32)`，而 `Semaphore::new(permits:
usize)` 要 `usize`。改成显式两处各自转换，不新增第二个常量制造"两个
数字是不是同一个"的疑问：

```rust
pub const KVSTORE_MAX_CONNECTIONS: u32 = 5;
```

`KvStore::open` 里 `.max_connections(KVSTORE_MAX_CONNECTIONS)` 不需要
转换（本来就是 `u32`）；构造 admission permit 的地方改成
`Semaphore::new((KVSTORE_MAX_CONNECTIONS - 1) as usize)`——`5 - 1 = 4`
在 `u32` 算术下不会下溢，`as usize` 是无损扩宽转换（`usize` 在所有
目标平台上都至少跟 `u32` 一样宽），不需要 `TryFrom`/`unwrap`。

**常量**（`agent24-memory/src/lib.rs`，与 `MEMORY_SQLITE_ROW_BUFFER_SIZE`
同一种"唯一共享常量"处理；**v4 更正：这里不再重复定义
`KVSTORE_MAX_CONNECTIONS`**——round 3 评审指出这里跟下面 §5.3 依赖
修复处新定义的 `u32` 版本互相矛盾，是同一个常量的两份声明。唯一的
权威定义在下面"类型改动"那段，是 `u32`；这里只说明 `open_memory`
那边不需要对应常量的原因）：

`KvStore::open` 内部的裸字面量 `5` 替换成引用下面"类型改动"给出的
`KVSTORE_MAX_CONNECTIONS`；`open_memory` 的 `max_connections(1)` 不
需要一个新常量——它从不构造 admission，`1` 就是字面量本身要表达的
"这个只有 1 个连接的共享池，没有余量分给 OOP"（P v5 §13 的结论，见
下面"依赖改动"之后的"类型改动"段落），不需要为了"跟 5 对称"而抽出
`KVSTORE_EPHEMERAL_MAX_CONNECTIONS` 这样一个从不参与除法的常量。

**`KvStore` 新增一个私有字段，随构造函数确定，调用方拿不到、改不了**：

```rust
// agent24-memory/src/lib.rs
#[derive(Clone)]
pub struct KvStore {
    pool: SqlitePool,
    /// `Some` 当且仅当这个 store 来自 [`KvStore::open`]（文件后端，多
    /// 连接、WAL）。`open_memory()` 恒 `None`——**不是**因为它"不是一个
    /// 共享池"（v3 更正，round 3 评审指出这个说法本身是错的：
    /// `open_memory()` 底下确实是一个 `SqlitePool`，`KvStore` 的每一份
    /// `clone()` 都指向同一个连接，多个调用方会在这个连接上排队争用，
    /// 这就是共享）——而是因为这个共享池只有 1 个连接，进程内路径已经
    /// 要用掉它，`max_connections - 1 = 0` 没有任何余量能让渡给 OOP
    /// 调用方（P v5 §13 的结论）。`0` 个 permit 不是"更少的配额"，是
    /// "这个池从容量上就不存在能分给第二个使用者的余量"。
    ///
    /// 私有字段，只能通过 [`KvStore::oop_admission`] 只读地拿到一份
    /// `clone()`——这是决策 4 v2 修正的核心：ephemeral/admission 的
    /// 对应关系由构造 `KvStore` 的这两个函数本身保证，不依赖调用方
    /// （`MemoryLease::open`/`server.rs`）各自记得传对值。
    oop_admission: Option<Arc<tokio::sync::Semaphore>>,
}

impl KvStore {
    pub async fn open(path: &Path) -> Result<Self> {
        // ... 现有逻辑不变 ...
        Ok(Self {
            pool,
            oop_admission: Some(Arc::new(tokio::sync::Semaphore::new(
                (KVSTORE_MAX_CONNECTIONS - 1) as usize,
            ))),
        })
    }

    pub async fn open_memory() -> Result<Self> {
        // ... 现有逻辑不变 ...
        Ok(Self { pool, oop_admission: None })
    }

    /// T8.5c-W-mount 决策 4：daemon 级单例，`agent24d` 的 OOP mount 路径
    /// 用它决定要不要尝试 `lend()`；in-process 路径从不读它。返回
    /// `clone()` 而不是引用，因为它本来就是 `Arc`，调用方（`MemoryLease`）
    /// 需要拥有一份能跨 `.await` 持有的所有权。
    pub fn oop_admission(&self) -> Option<Arc<tokio::sync::Semaphore>> {
        self.oop_admission.clone()
    }
}
```

**`MemoryLease` 的 `open` 签名不变**（相对 v1 的两参数版本——这正是
v1 finding 6"签名迁移遗漏 `domain.rs` 三处测试调用点"在 v2 不再存在的
原因：这三处测试连 `MemoryLease::open` 都不需要改），**但新增的
`admission` 字段是私有的**（v3 更正，Medium，Codex round 2 指出：如果
`admission` 也跟 `user`/`org`/`kv` 一样公开，调用方仍然可以绕过
`MemoryLease::open`，用 `MemoryLease { user, org, kv, admission }` 字面
量给一个文件后端的 `kv` 配 `None`、或者给一个 ephemeral 的 `kv` 硬塞一个
`Some(...)`）。**v4 进一步更正（round 3 指出私有化本身不够——`kv` 字段
仍然公开，`lease.kv = another_kv` 之后 `admission` 缓存的还是旧
`kv` 派生的值，两者会分叉）**：不缓存 `admission` 这个字段本身，改成
每次调用 `admission()` 都从 `self.kv` 现取——这样"`kv` 和 `admission`
来自同一个来源"变成了这个方法自己的实现方式，不是一条需要维护的
不变式，`kv` 改了什么值，下一次调用 `admission()` 立刻反映出来，
不存在两者分叉的中间状态：

```rust
pub struct MemoryLease {
    pub user: String,
    pub org: crate::os_memory::OrgId,
    pub kv: agent24_memory::KvStore,

        // ... 现有逻辑不变，不再需要在这里额外算 admission ...
        Some(Self { user: user.to_owned(), org, kv })
    }

    /// v4：每次调用都从 `self.kv` 现取，不缓存——`kv`/`admission`
    /// 不可能分叉，因为根本不存在第二份独立状态。`user`/`org`/`kv`

    /// 面对"要不要公开"这个问题。

    /// 调用方必须在确认挂载成功后另外调用 `OsMemoryCatalog::

        match catalogue.ensure_recorded(&self.org, &self.user, manifest, &self.kv).await {
            Ok(partition) => Some((

            )),
            Err(e) => {
                tracing::error!(module = manifest.name(), error = %e, "...");

            }
        }
    }
```

**`server.rs` 不再需要计算或传递 `memory_admission`**——`open_memory_base`
返回的 `kv` 已经带着正确的 `oop_admission`，`server.rs:1153` 的调用点
从 v1 提议的三参数改回原样的两参数（v1 之前就是两参数，v2 等于没有
改动这一行）：`MemoryLease::open(LOCAL_USER, kv).await`。

**v2 新增，v3 更正诊断措辞（Codex round 2 指出 v2 把两个不同方向的
问题混成了一句话）**：v1 的 §5.3 只给出了 `memory_lend` 的构造，没有
说清楚 `mount_package` 的 OOP 分支今天怎么构建 `Offer.provides`/
`MountReport.granted`——读代码（`domain.rs:1305-1318`）确认这两者今天
只看 `Capability::Events`/`Capability::Approval`。决策 2 把
`Capability::Memory` 加进 `KERNEL_OOP_GRANTS` 之后，这两处会分别朝
**相反**的方向出错，不是同一种"无条件出现"：

- **`granted_names`**（`granted.iter().map(...).collect()`，未过滤）
  会**过度发放**——一旦 `granted.has(Capability::Memory)` 为真，不管
  `entitlement.private_handle()` 是不是 `None`（`lend()` 失败或
  ephemeral），`"memory"` 都会被无条件收进 `MountReport.granted`。
  这正是决策 1 §2.1 表格明确禁止的"发放了一个没有 handle 的能力"，
  是一个真实的、需要修的 bug。
- **`offer` 的 `provides`**（只有 `if granted.has(Capability::Events)`/
  `if granted.has(Capability::Approval)` 两条 `push`，从来没有
  `if granted.has(Capability::Memory)` 这一条分支）会**发放不足**——
  即使 `entitlement.private_handle()` 是 `Some`（`lend()` 真的成功），
  `provides` 也不会出现 `"_a24/memory/private/"`，因为代码里根本没有
  对应的 `push` 语句。这不是"撒谎发放"，是"该给的能力没有被宣告"，
  但同样是决策 2 引入 Memory 之后必须补的一处接线，否则一个真正拿到
  handle 的 OOP 模块永远不会被 `Offer` 告知自己有这个方法可用。

两处都需要改，但改的理由不同：`granted_names` 是"堵一个会撒谎的
过滤漏洞"，`provides` 是"补一条从未写过的分支"。

把"要不要展示 memory 这个能力"提取成一个纯函数，用于 OOP 路径这两处
的过滤/补全（**不是**"in-process/OOP 两条路径共享同一个函数"——
in-process 路径今天用的是 `Option<Arc<OsScopedMemory>>`
（`scoped.is_some()`），从未构造 `MemoryEntitlement`，决策 1 引入的
类型本来就是给 OOP/wire 用的；in-process 保留它自己已有的
`granted_names.into_iter().filter(|c| c != Capability::Memory.as_str()
|| scoped.is_some())` 不变。两条路径的过滤**规则**是同一条——"没有
真实 handle 就不能出现在 granted 里"——但落在两个不同的类型/函数上，
不是同一段代码）：

```rust
// os_memory.rs 或 domain.rs 的自由函数，纯函数，无 I/O
pub(crate) fn memory_grant_name(entitlement: &MemoryEntitlement) -> Option<&'static str> {
    entitlement.private_handle().is_some().then_some("memory")
}
```

`mount_package` 里 `granted_names`/`offer` 的构造改成：

同一条过滤规则，只是过滤条件的判据换成了 `memory_grant_name`。

**签名改动（机械性的参数穿线，跟 T8.5c-P §12 列出的其它接线工作
同一性质，留给实现阶段按下面的形状穿好，不在这里展开每一行 diff）**：
`mount_package` 需要新增 `memory: Option<&MemoryLease>` 和

### 5.4 为什么不违反 T8.5c-P §12 的 MUST 契约（v2：不再是本文档单方面的解释）

v1 在这里自行论证"P 的契约只管辖多连接共享池存在的情况"——Codex 第一轮
指出这是本文档单方面给 P 的原文加了一个 P 自己没写的前提。v2 把这个
论证挪成一条"追加在 P 文末、不改动冻结正文"的附注，Codex 第二轮又指出：
这仍然是同一种"下游/事后单方面改写契约"，只是换了地方——真正的解法是
把这当一次正式版本修订。v3 把它落成 T8.5c-P 的 **v5**（`T8.5c-P-
pagination-cursor.md` §13，冻结横幅同步更新到"v4，2026-09-18；v5，
2026-09-19"）——由 P 自己在自己的版本历史里声明这条 MUST 契约管辖的
前提，不是被下游文档解释。v5 同时修正了 round 2 指出的一处事实错误：
`open_memory()` 底下**确实是**一个共享池（一个 `SqlitePool`，
`max_connections(1)`，多个 `KvStore` 克隆句柄共享同一个连接），真正的
理由不是"不是共享池"，是"这个共享池只有 1 个连接，进程内路径已经要用
掉它，`max_connections - 1 = 0` 没有余量分给 OOP"。

本文档在这个（已经由 P v5 自己确认的）范围内一字不改地遵守契约：文件
后端池的容量公式（`KVSTORE_MAX_CONNECTIONS - 1 = 4`）、单例创建点（现在
挪进 `KvStore::open` 内部，比 P 原文要求的"与 `server.rs` 的共享池同一
作用域"更严格——直接就是同一个函数）、`bind_to_lifecycle` 内等待、
`acquire_owned()`、drop 释放——决策 4 §5.3 的形状与 P 的设计逐条相同。
**跨模块共享这一点，本文档不声称已经证明**（v5 更正：§7.1 判据 4 只是
对纯函数的单元测试，不是对真实挂载路径的证明，真正的证明责任在
§7.2 要求 T8.5c-W-wire 必须交付的真实双模块测试）。ephemeral 池不
发放这个能力，是 P v5 明确
划定管辖范围之后，本文档在这个范围外做出的新决策，不是重新解释 P 已经
写过的文字。

## 6. 决策 5：`OsMemoryCatalog` 两阶段——`ensure_recorded` / `mark_mounted` / `touch_last_seen`（解决 H1 + M2）

### 6.1 H1 的确切病灶（复用 §1 的现状复盘）

`record()` 的持久写（`kv.record_os_partition`）和本轮内存清单
（`self.partitions.push`）焊在一次调用里。OOP 路径接上 `lend()` 之后，
`lend()` 成功、`start_with()` 失败的两个分支（`None`/`Some(Err(held))`）
会让"已经持久写入、且 `last_seen_at` 被推进到刚刚"和"这次运行根本没有
真的挂载"同时为真——运维读到的 `last_seen_at`/dormant 统计是假的。
migration 0012 的表注释（§1 已引用）说明这不是无关紧要的字段：这正是
运维区分"活分区"和"废弃分区"的**唯一**信号。

v1 提出的"`record`（幂等持久写）+ `mark_mounted`（本轮内存态）"两阶段
拆分方向是对的，但 v1 的 `record()` 本身仍然在**每次**调用时把
`last_seen_at` 推进到"刚刚"（因为它复用了没有改动的 `kv.
record_os_partition`，那条 SQL 的 `ON CONFLICT ... DO UPDATE SET
last_seen_at = excluded.last_seen_at` 本身就是这个问题的根）——v1 只是
把"幽灵记录"从"内存清单"搬到了"持久时间戳"，没有真正解决 H1。

**v2 更正（Codex 指出 v1 的这一步本身也是假阳性）**：v1 提交的修法只改了
`ON CONFLICT DO UPDATE` 分支（把它的赋值目标从 `last_seen_at =
excluded.last_seen_at` 换成一个自我赋值），但 SQL 里的 **`INSERT`
分支**——也就是这个 `(owner_key, ...)` 身份**第一次**被记录的那一条
路径——原封不动地把 `now` 同时绑给 `first_seen_at` 和 `last_seen_at`
两个位置。H1 描述的场景恰恰是"**首次**挂载、`ensure_recorded` 成功、
`start_with` 失败"——这条路径走的正是 INSERT 分支，不是后续重复调用
才会走到的 `ON CONFLICT` 分支。v1 的判据（原 §7.1 判据 5）之所以没有
抓出这个问题，是因为它验证的是"`last_seen_at == first_seen_at`"——按
v1 未改的 INSERT 语句，这个等式对**任何**首次插入都恒成立，跟挂载
到底成不成功无关，是一条永远为真、什么也没验证的判据。

### 6.2 修正：`last_seen_at` 改为可空列，`INSERT` 分支不再写入真实时间戳

真正堵住"首次挂载失败也被记成刚活跃"的做法，是让"这行有没有被真的
`touch` 过"本身可以被表达为一个独立于"这行存不存在"的状态——也就是
让 `INSERT` 分支写入的初始值本身不携带"活跃"的含义。选 `NULL` 作为
这个初始值（而不是"等于 `first_seen_at`"这种数值上可达但语义上要靠
额外记忆才能分清的哨兵），可以直接复用 SQL `IS NULL` 判断，不需要
新增任何应用层的"这个值是不是哨兵"的比较逻辑。

**v3 更正（Critical，Codex round 2 指出）**：v2 提议的 migration 编号
`0013` 与仓库里已经存在的 `0013_os_partitions_space.sql`（+
`0014_owner_usage_quota.sql`）冲突，而且 v2 的重建表语句照抄的是
**0012 时代的六列旧schema**（`owner_key/key_version/logical_user/
module_name/first_seen_at/last_seen_at`）——完全没有 0013 已经引入的
`org_id`（`REFERENCES mem_orgs(org_id)`）、`space_id` 两列，也没有
重建 0013 的 `UNIQUE INDEX mem_os_partitions_space(org_id, space_id)`。
按 v2 的写法执行，会把 F8（0013）已经上线的 org/space 身份列和它的

之所以没有在写 `record_os_partition` 的 SQL 时一起犯（那段 SQL 我
读的是**当前真实代码**，本来就含 `org_id`/`space_id`），只在临时起意

```rust
// 的组织方式一致）——与 agent24d::events_emit::Clock/
// agent24d::module_approval_broker::Clock 同一个形状，方便日后统一。
pub trait Clock: Send + Sync {
    fn now_epoch_secs(&self) -> u64;
}

#[derive(Debug, Default)]
pub struct SystemClock;

impl Clock for SystemClock {
    fn now_epoch_secs(&self) -> u64 {
        std::time::SystemTime::now()
            .duration_since(std::time::UNIX_EPOCH)
            .map(|d| d.as_secs())
            .unwrap_or(0)
    }
}
```

### 6.3 `agent24d::OsMemoryCatalog` 层的两阶段 API

```rust
impl OsMemoryCatalog {
    /// 只做持久身份写入，**不**更新本轮活跃清单，**不**推进
    /// `last_seen_at`。`&self`——不再需要 `&mut`，因为不再触碰
    /// `self.partitions`。调用方必须在确认这个模块真的挂载成功之后，
    /// 另外调用 `mark_mounted`。
    pub async fn ensure_recorded(
        &self,
        org: &OrgId,
        user: &str,
        manifest: &DomainOsManifest,
        kv: &agent24_memory::KvStore,
    ) -> Result<OsMemoryPartition, String> {
        let space = SpaceId::module_private(manifest.name());
        let p = OsMemoryPartition {
            key: partition_key(org, &space),
            org: org.clone(),
            space,
            user: user.to_owned(),
            module: manifest.name().to_owned(),
        };
        kv.record_os_partition(agent24_memory::OsPartitionIdentity {
            owner_key: &p.key,
            key_version: KEY_VERSION,
            org_id: p.org.as_str(),
            space_id: p.space.as_str(),
            user: &p.user,
            module: &p.module,
        })
        .await
        .map_err(|e| e.to_string())?;
        Ok(p)
    }

    /// 确认 `partition` 对应的模块这一轮**真的**挂载成功了——路由已经
    /// nest 上去（in-process），或者 supervisor 已经把它注册为运行中
    /// 的子进程（OOP，语义边界见 §6.6）。这是 `partitions()`（"这一轮
    /// 挂载了什么"）唯一的真实来源，也是唯一允许推进持久
    /// `last_seen_at` 的调用点。
    ///
    /// 幂等，按物理 `partition.key` 去重（M2）：对同一个 partition 的
    /// 第二次调用不产生第二条 inventory 记录，也不重复触发持久层写入
    /// 之外的任何副作用（持久层的 `touch` 本身天然幂等——重复 UPDATE
    /// 一个已经很新的时间戳是无害的——真正需要防止重复的是内存清单）。
    pub async fn mark_mounted(
        &mut self,
        partition: OsMemoryPartition,
        kv: &agent24_memory::KvStore,
        clock: &dyn agent24_memory::Clock,
    ) {
        if self.partitions.iter().any(|p| p.key == partition.key) {
            return;
        }
        // Best-effort：这个模块在这次调用之前已经被判定为"挂载成功"
        // （调用方的前置条件，见下面两条调用点），这个持久时间戳写入
        // 失败不应该让已经发生的挂载"变回没挂载"——只记日志。
        if let Err(e) = kv.touch_os_partition_last_seen(&partition.key, clock).await {
            tracing::warn!(
                module = %partition.module,
                error = %e,
                "mounted, but could not advance this partition's last-seen-at; \
                 the durable catalog will under-report its liveness until the \
                 next successful mount"
            );
        }
        self.partitions.push(partition);
    }
}
```

`lend()`（决策 4 §5.3 已给出新签名）内部调用 `ensure_recorded`，不再
调用旧的 `record`。

### 6.4 两条调用点

- **in-process**（`mount_all`，`domain.rs:1150-1156` 附近）：v1 把
  `mark_mounted` 紧跟在 `lend()` 之后调用，早于 `app.nest(...)`——
  Codex 指出这跟 `mark_mounted` 自己的文档字符串"确认这个模块这一轮
  **真的**挂载成功了才调用"矛盾，即使 `app.nest(...)` 本身今天不会
  失败（对 `Router` 调用 `.nest()` 是同步的路由表操作，不涉及 I/O 或
  可能返回 `Err` 的校验），让调用顺序和文档字符串的措辞相互印证比
  额外论证"提前调用为什么也安全"更直接、也更不容易在未来 `nest()`

  正确地把它算作"当前没有实际运行"。

### 6.5 为什么不是"失败时回滚 ensure_recorded"（继承 v1 论证）

`ensure_recorded` 内部的写入已经是幂等 UPSERT——"回滚"没有对应的
DELETE 语义可用（也不应该有：这一行代表"这个 org/space 曾经被这个
module 记录过"，是一条历史事实，不因为这次挂载失败而变得不曾发生过）。
拆分成"ensure_recorded（持久身份，幂等）+ mark_mounted（本轮内存态 +
last_seen_at，调用方决定时机）"避免了"什么时候该回滚"这个问题——根本
不需要回滚，只需要不把还没验证成功的挂载算进"活跃"，也不把它算进
"最近见过"。

### 6.6 语义边界的诚实声明（H1 后半段要求）

`start_with Some(Ok(()))` 只表示 supervisor slot 已占用、子进程任务
已经 `spawn`，**不表示**子进程完成了 handshake 或正在实际服务请求
——`mark_mounted` 这个名字和它触发的"活跃"信号，语义上对应的是"路由/
supervisor 已挂载"，不是"进程真的在跑並且已经完成初始化"。这跟
`MountOutcome::Mounted` 今天已有的措辞是一致的（`domain.rs:354-356`
的文档："Routes are live"，不是"the process has finished handshaking"）
——本文档不改变这条既有边界，只是在 `mark_mounted` 的文档字符串里把它
写清楚，不让读者以为"挂载"和"进程已经可用"是同一件事。真正的
"进程已经完成 handshake、正在服务"这个更强的信号，属于 supervisor/
proxy 层已有的状态机（`agent24_os_proto::supervisor`/`proxy::mount`），
不是本文档要新增的概念。

## 7. 判据设计

### 7.1 纯 mount 层判据（本文档负责，不依赖 wire 层的 `Handler`/JSON-RPC 往返）

1. **★ C1 正向判据（v2 按§3.3 的两层拆分重写）**：
   - 单元级：`Grants::granting(...)` 含 `Memory`；`memory_grant_name`
     对 `MemoryEntitlement::private(...)` 返回 `Some("memory")`、对
     `MemoryEntitlement::NONE` 返回 `None`。
   - 集成级：真实 OOP manifest 请求 `memory`，文件后端 lease，调用
     `mount_all(...)`，断言 `reports[0].granted` 含 `"memory"` 且
     `outcome == Mounted`。
   - `Offer` 是否真的携带这个值走完 OOP 握手：留给 T8.5c-W-wire（见
     §3.3"验收缺口"）。

2. **C1 对照（lend 失败）**：`granted.has(Capability::Memory)` 为真但
   `ensure_recorded` 失败（预先占用同一个 `(org, space)` 的 UNIQUE
   冲突这个测试替身）时，调用 `mount_all(...)` 断言 `reports[0].
   granted` 不含 `"memory"`，且 `partitions.partitions()`（本轮活跃
   清单）不包含这个模块的分区——这是 `MountReport`/`OsMemoryCatalog`
   两个真实返回值能验证的全部。`entitlement.private_handle()` 本身
   是不是 `None`、`Offer.provides` 是否因此不含这个前缀，跟判据 1
   一样，逻辑层面已经被 `memory_grant_name` 的单元判据覆盖
   （`lend()` 失败时 `memory_lend` 是 `None`，§5.3 决策 4 的
   `memory_entitlement` 构造对 `None` 走 `MemoryEntitlement::NONE`
   分支，跟单元判据用的是同一段代码），不需要重新验证。

3. **★ C2 ephemeral 边界判据**：用 ephemeral 构造（`kv.oop_admission()`
   为 `None`，跟 `KvStore::open_memory()` 真实会产出的值一致）调用
   `mount_all(...)` 挂载一个请求 `memory` 的 OOP manifest，断言
   `reports[0].granted` 不含 `"memory"`；**同一次测试里**，同一个
   ephemeral lease 下挂载一个请求 `memory` 的 in-process 模块，断言它
   的 `ctx.memory()` 正常拿到（正对照——证明 ephemeral 下"OOP 拿不到"
   是 admission 缺失导致的，不是 ephemeral 把 memory 能力整体关掉了）。

4. **限流器/admission 判据（v3：改成对 §4.1 新提取的
   `build_private_memory_entitlement` 直接单元测试，不再假设能从
   `mount_package`/`methods_for` 拿到内部值）**：
   - **单元级（真正可执行，不需要挂载）**：构造两个 fake 的
     `(scoped, admission)` 二元组——同一个 `Arc<Semaphore>`（模拟"同一个
     daemon 级 admission 被传给两次调用"）、两个不同的
     `Arc<OsScopedMemory>`——分两次调用
     `build_private_memory_entitlement`，断言：
     - 两次返回的 `.private_handle().unwrap().admission` 指针相等
       （`Arc::ptr_eq`）——验证函数把输入的 `Arc` 原样传递，不会
       意外克隆出一个新对象或丢弃共享关系。
     - 两次返回的 `.private_handle().unwrap().limiter` 指针**不**相等
       （`!Arc::ptr_eq`，**新增，Medium，缺负对照**）——验证每次调用
       都会新建一个 `RateLimiter`，不会被错误地做成 daemon 级单例。
       但**这条判据本身有一个已知局限（Codex round 2 指出）**：指针
       不相等只证明两次分配的外层 `Arc` 不同，证明不了两个
       `RateLimiter` 内部会不会共享同一个计数状态（比如内部持有同一个
       `Arc<Mutex<Bucket>>`）——今天 `RateLimiter` 直接拥有自己的
       `Mutex<Bucket>`（不是通过共享指针间接持有），所以指针不相等在
       当前实现下确实等价于隔离，但这是"读了当前实现细节才成立"的
       结论，不是这条判据自己能证明的。**新增（行为级负对照，v4 更正：
       round 3 指出用 `RateLimiter::new`——真实系统时钟、会持续
       refill——做"耗尽到失败"的循环不是确定性的，慢的 CI 机器上可能
       refill 跟消耗一样快，循环不保证及时终止）**：这条判据不通过
       `build_private_memory_entitlement`（那条路径固定用
       `RateLimiter::new`），而是直接用仓库已有的
       `RateLimiter::with_clock(capacity, refill_per_sec, frozen_clock)`
       （`events_emit.rs:173`，测试专用的固定/可推进时钟，`events_emit`
       自己的测试已经在用同一个模式）分别构造 A/B 两个 limiter、共享
       同一个冻结时钟（不推进），把 A 的配额耗尽（`try_acquire_weighted`
       到失败——时钟冻结，不会有 refill 干扰，循环次数是确定的：耗尽
       `capacity` 需要的调用次数是常数），断言 B 的 `try_acquire_
       weighted` 仍然成功——这条判据不依赖"今天 `RateLimiter` 怎么
       实现"，直接验证外部可观察的隔离行为，且用冻结时钟消除了真实时钟
       带来的不确定性；指针判据可以保留作为更便宜的构造级检查，但不能
       替代这条。
     - **v5 更正（Low，round 4 指出）**：验证 permit 数量时，`admission`
       必须来自真实的 `KvStore::open(tempfile).await.unwrap().
       oop_admission()`（文件后端，真实建库），**不能**在测试里自己写
       `Semaphore::new((KVSTORE_MAX_CONNECTIONS - 1) as usize)` 再拿
       同一个表达式去断言——那样测的是"测试自己抄的公式等于自己"，
       生产代码 `KvStore::open` 内部如果把容量算错了（比如手滑写成
       `KVSTORE_MAX_CONNECTIONS` 而不是 `- 1`），这条判据不会失败。
       断言从真实构造路径拿到的 `Arc<Semaphore>` 的
       `available_permits() == (agent24_memory::KVSTORE_MAX_CONNECTIONS
       - 1) as usize`（即 4，`KVSTORE_MAX_CONNECTIONS` 是 `u32`，
       `available_permits()` 返回 `usize`，判据代码需要这个转换）。
   - **集成级缺口（H2，老实记录，不假装已解决）**：上面这组判据证明的
     是"给定同一个 `Arc<Semaphore>`，`build_private_memory_entitlement`
     会正确处理它"，证明不了"两个真实的、不同的 OOP 模块被 `mount_all`
     真实挂载时，`agent24d` 确实把同一个 daemon 级 `Arc<Semaphore>`
     喂给了这个函数两次"——`mount_package` 只返回 `(Router,
     MountReport)`，今天没有任何测试捕获点能在真实挂载路径上取出
     `PrivateMemoryHandle`（跟 §3.3 的 `Offer` 验收缺口是同一类问题）。
     **v4 更正**：这不是一个留给下一轮决定的开放问题——§7.2 已经把
     "真实跨模块 admission 竞争"定为 T8.5c-W-wire 必须交付的判据（不是
     给 mount 层新增测试专用捕获点，而是直接用真实的
     `Handler::call()`/`bind_to_lifecycle` 往返验证，见 §7.2）。这里的
     单元级判据只负责证明"给定共享输入，纯函数处理正确"，跨模块共享
     本身的证明责任已经明确移交，不是"接受类型论证作为足够证据"这种
     弱化处理。

5. **catalog 两阶段判据（H1，v2：按 `last_seen_at` 可空列重写）**：
   - `ensure_recorded` 成功但 `host.supervisors.start_with(...)` 返回
     `Some(Err(_))`/`None` 时：`OsMemoryCatalog::durable_for_org` 能
     查到这条记录（持久身份写入不受影响），但 `partitions.
     partitions()`（本轮活跃清单）不包含它——决策 5 的核心可观察性质
     （继承 v1 判据 3）。
   - **v2 更正（原判据是假阳性）**：上一条场景里，直接查询这条记录，
     断言它的 `last_seen_at` 是 `None`——不是"等于 `first_seen_at`"
     （v1/首轮 v2 之前的写法下这个等式对任何首次插入都恒成立，跟挂载
     是否真的失败无关）。这才是 H1 真正要修的信号：一次从未被确认
     挂载成功的记录，`last_seen_at` 必须是"从未被 touch 过"这个独立
     状态，不能是任何具体时间戳。
   - `ensure_recorded` 重复调用同一个身份两次（不经过 `mark_mounted`），
     断言 `durable_for_org` 里仍然只有一行，且这一行的 `last_seen_at`
     两次调用之间都保持 `None`（证明 `ensure_recorded` 本身的语义
     修正生效，`INSERT`/`ON CONFLICT` 两个分支都不写入真实时间戳）。
   - **新增（v3：真实的时钟注入点，不再是一句没有落地的话）**：用
     §6.2 新增的 `agent24_memory::Clock` trait 的一个测试专用实现
     （固定返回值或可推进的计数器，跟 `events_emit`/
     `module_approval_broker` 测试里已有的做法同构），先
     `ensure_recorded`（`last_seen_at` 为 `None`），推进这个测试时钟，
     再用它调用 `mark_mounted`，断言 `last_seen_at` 现在是
     `Some(agent24_core::util::iso8601_from_epoch_secs(那个推进后的值))`
     ——验证的是"`None → 具体时间戳`"这个转换本身真的发生了、且这个
     时间戳真的来自注入的时钟而不是 `SystemTime::now()`，不是数值上
     凑巧满足某个恒成立的等式。

6. **`mark_mounted` 幂等判据（M2）**：对同一个 `OsMemoryPartition`
   （相同 `key`）连续调用 `mark_mounted` 两次，断言 `partitions()`
   的长度是 1 不是 2；两次调用之间构造一个不同 `key` 的 partition 并
   调用一次，断言最终长度是 2（证明去重是按 `key`，不是"整个方法
   只能调一次"这种过度保守的实现）。

### 7.2 留给 T8.5c-W-wire 补充的判据（真实资源竞争，H3 的完整解决）

**v4 更正（Codex round 3 指出这里原来的措辞有一句假话）**：本文档
**不能**证明"两个真实的、不同的 OOP 模块被 `mount_all` 真实挂载时，
确实共享同一个 admission 实例"——判据 4 第二条只是对
`build_private_memory_entitlement` 这个纯函数的单元测试，测试自己
手工构造了两次调用共享同一个 `Arc<Semaphore>` 的前提，证明的是"这个
函数正确处理共享输入"，不是"真实挂载路径真的会共享输入"。本文档只能
证明：admission `Semaphore` 的**大小**正确（判据 4 第三条）、
**给定共享输入时这个纯函数会正确保留共享关系**（判据 4 第一条）、
**ephemeral 下根本不会被构造**（判据 3）。

**以下这条是 T8.5c-W-wire 必须交付的判据，不是一个可选项**（v4 更正：
之前把它记在"待决"小节里、当作可以留到以后再拍板的开放决定，Codex
round 3 指出——对一个原本是 High 严重度的发现，"记录下来但不强制要求"
不构成解决；真正的解决方式不是给 mount 层新增测试专用捕获点，而是
直接把这条验证做成 wire 层集成测试的必交付项）：真实挂载两个不同的
OOP 模块（都请求 `memory`），让模块 A 通过真实的 `Handler::call() →
bind_to_lifecycle → remember_checked` 往返占满 4 个 admission permit
（T8.5c-P-pagination-cursor.md §6.5 第 5 点、判据 9b 的五步模型——
**这条模型必须明确让 holder 和 contender 来自两个不同的模块**，不能
像 P 原文判据 9b 目前的写法那样默认省略"跨模块"这个要求，只验证
"占满了 pool"），然后断言来自**模块 B**的第 5 个 OOP 调用确实卡在
`Semaphore::acquire_owned()` 上——这既是 H3 的完整解决，也是本文档
"跨模块共享同一个 admission"这条不变式唯一能被真正证明的地方。
`recall_page`/`recent_page` 各补一条同构测试。文末"§12 待决"不再
把这条列为可以搁置的开放项，只保留另一条真正只是加固、不影响正确性
结论的残留风险。

**v6 更正（Codex round 5 指出这几行是全文最后一处、也是最严重的一处
矛盾——刚说完"必须交付、唯一证明点"，紧接着又说 wire 可以直接假设它
成立）**：**mount 这边只保证**：admission `Semaphore` 的大小正确
（判据 4 第三条）、给定共享输入时纯函数保留共享关系（判据 4 第一条）、
只在文件后端存在（判据 3）——**"喂给 wire 层的 `Arc<Semaphore>` 在
两个真实模块之间确实是同一个"不在这个保证列表里**，wire 层**不能**
假设这一点已经成立，必须自己证明：真实挂载两个不同模块，走
`Handler::call()` 往返，确认两者确实排队等的是同一个 permit——这
既是上面"必须交付的判据"要证明的第一件事，也是"三个方法真的排队等
这一个 permit"这条断言成立的前提，两者是同一次测试要一起证明的两个
方面，不是先假设一个再验证另一个。

## 10. 自审

### 10.1 逐条核对 Codex 对 v1 的五条意见

1. **C1**——决策 2：`KERNEL_OOP_GRANTS` 明确加入 `Capability::Memory`，
   同步改写它上方矛盾的注释；§3.3 给出真实 OOP manifest 的正向判据，
   同时验证 `Grants`/`entitlement`/`Offer`/`MountReport` 四点，不是
   只改一行就当作解决了。
2. **C2**——决策 4：不再用一个全局常量套两种池的容量。ephemeral 池
   （`open_memory()`，`max_connections = 1`）结构性地不构造 admission
   `Semaphore`（`KvStore::oop_admission()` 返回 `None`），
   `MemoryLease::admission()` 方法（v4：不再是缓存字段，每次调用
   现取，见决策 4 §5.3）让 OOP mount 路径能区分"没有内存库"和"有内存
   库但没有 OOP 并发预算"，
   两者对外都表现为 `MemoryEntitlement::NONE`，但内部原因不同、
   in-process 路径完全不受影响。文件后端路径的容量公式
   （`KVSTORE_MAX_CONNECTIONS - 1 = 4`）与 T8.5c-P §12 原样一致，
   一字未改。
3. **H1**——决策 5（v3 更正）：`last_seen_at` 改为可空列（新增
   migration 0015，基于当前八列 schema 重建），`record_os_partition`
   的 `INSERT` 分支绑 `NULL`、
   `ON CONFLICT` 分支不再触碰这一列（两个分支都修，不是只改 v1 已经
   改对的那一个）；新增 `touch_os_partition_last_seen` 作为唯一能让
   这一列获得真实时间戳的入口；`mark_mounted` 只在确认挂载成功后调用
   （in-process 挪到 `app.nest(...)` 之后，见 §6.4 v2 更正），且文档
   明确写清楚"挂载成功"在这里的准确含义（supervisor slot 占用 + 任务
   spawn，不是"handshake 完成"），不再用模糊的"挂载成功"带过这条边界。
4. **H3**——v2 更正：v1 的 §3.3/§7 假设 `mount_package` 会把
   `Offer`/`memory_entitlement` 作为返回值交给判据，读代码确认它的
   真实返回类型是 `(Router, MountReport)`，两者都不在里面。v2 把判据
   拆成"单元级"（`Grants::granting`/`memory_grant_name` 纯函数，不需要
   `mount_package`）和"集成级"（`mount_all` 真实返回的 `MountReport.
   granted`/`OsMemoryCatalog`）两层，§7 拆成两半：mount 层判据（大小、
   限流器隔离、ephemeral 边界、给定共享输入时纯函数保留共享关系）本
   文档负责且给出完整设计；`Offer` 是否真的携带正确的值走完 OOP 握手，
   以及**真实跨模块共享**、真实占连接的判据（v6 更正：跨模块共享本身
   不是 mount 层能验证的部分，不能只归到"真实占连接"这一条里），
   明确移交 T8.5c-W-wire，并指出它要复用 T8.5c-P §9 判据 9b 已经设计
   好的五步模型——这是老实的验收缺口记录，不是"以后再说"，也不是
   假装 mount 层已经能验证它验证不了的东西。
5. **M2**——决策 5 §6.3：`mark_mounted` 按物理 `partition.key` 去重，
   判据 6（§7.1）验证"重复调用不增长"和"不同 key 正常增长"两个方向。

### 10.2 已确认成立部分的保留说明

- 决策 1 的 `MemoryEntitlement`/`PrivateMemoryHandle`/
  `ScopedMemoryHandle` 类型形状原样保留，唯一的调整是把"admission 恒真"
  这条不变式的证明从"admission 总是能拿到"改写为"`PrivateMemoryHandle`
  只在 `MemoryLease::admission()` 返回 `Some` 时才被构造"——不变式本身
  （三个字段非 Option、不存在半个 handle）没有被削弱。
- 决策 3 §4.2"一次 mount 调用只对应一个 `(module, partition)`，不需要
  查找表"的前提（今天不存在运行期热挂载）原样保留，未重新论证；决策 4
  的 ephemeral 分支同样只考虑这个前提下的启动期一次性挂载。

### 10.3 与 T8.5c-P §12 MUST 契约的一致性核对（v3：引用 P v5 的正式修订，不再自行解释）

§5.4 已经给出完整论证并更新：T8.5c-P 已正式修订到 **v5**（§13），由 P
自己声明这条 MUST 契约管辖的前提是"存在一个可被多个 OOP 调用方共享、
可能被占满、且可以为共享方安全预留 headroom 的连接池"。本文档的决策 4：

- 对文件后端池（`KVSTORE_MAX_CONNECTIONS = 5`）**一字不改**地遵守这
  条契约——permit 数、单例创建点（v2 挪进 `KvStore::open` 内部，比
  "与共享池同作用域"更严格）都与 P 的原文一致。**跨模块共享这一点
  本文档不声称已经证明**（v5 更正，理由跟 §5.4 一致）——判据 4 第二条
  只验证纯函数处理共享输入的正确性，真实挂载路径是否真的共享，证明
  责任在 §7.2 要求 wire 交付的真实双模块测试。
- 对 ephemeral 池，不满足 P v5 声明的适用前提——不是因为它"不是共享
  池"（round 2 评审指出的事实错误：`open_memory()` 底下确实是一个
  `SqlitePool`，多个 `KvStore` 克隆句柄共享同一个连接），而是因为这个
  共享池只有 1 个连接、进程内路径已经要用掉它，`max_connections - 1
  = 0` 没有余量能让渡给 OOP——因此不在契约管辖范围内，本文档在这个
  空白处做出决定：不发放这个能力。这不产生新的矛盾——**没有一条 P 的
  MUST 断言了"OOP memory
  在任何池配置下都必须被发放"**，P 的契约是关于"如果发放，怎么限流"，
  不是"必须发放"，P v5 §13 现在把这一点写成了 P 自己版本历史里的文字，
  不再是本文档单方面的推断。

### 10.4 与 T8.5a/T8.5b 的一致性核对（继承 v1，未改动）

- 与 T8.5a：本文档不涉及 `Handler`/`bind_to_lifecycle` 的具体调用
  形状（那是 wire 文档的事），决策 3/4 只负责把正确的
  `RateLimiter`/`Semaphore` 单例交给 wire 层用，未引入新的 lifecycle
  语义。
- 与 T8.5b：`MemoryError::QuotaExceeded` 的产生机制
  （`BEFORE INSERT` 触发器，权威计数在 `mem_owner_usage`）未改动；
  决策 3 §4.3 的论证（`RateLimiter` 与 `mem_owner_usage` 是两个不同
  层级，`RateLimiter` 在 daemon 重启时重置不违反 T8.5b/SPEC §5 的
  配额权威性要求）继承自 v1，未重新推导，因为这部分与本轮的五条问题
  无关。

## 11. 交给 T8.5c-W-wire 的接口清单

- `MemoryEntitlement::private_handle() -> Option<&PrivateMemoryHandle>`
  ——wire 层 `Handler::call()` 的 forbidden 判断唯一依据。
- `PrivateMemoryHandle { memory: Arc<OsScopedMemory>, limiter:
  Arc<RateLimiter>, admission: Arc<Semaphore> }`——三个字段都已经是
  真实、非 `Option` 的值，wire 层可以直接把它们分别交给
  `remember_checked`/`recall_page`/`recent_page`（T8.5c-P 已经给出
  这三个方法的签名），不需要再处理"某个字段可能缺失"的分支。
- `Offer.provides`/`MountReport.granted` 是否含 `memory`/
  `"_a24/memory/private/"`：唯一依据是 `memory_grant_name(&entitlement)`
  （§5.3 v2 新增，`mount_package` 已经在用同一个函数），本质上就是
  `entitlement.private_handle().is_some()`，wire 层不需要重新判断
  `granted.has(Capability::Memory)`，也不需要重新实现这条过滤逻辑——
  `_a24/memory/private/` 的挂载层已经用它过滤过 `provides`/`granted`，
  wire 只需要在 `Offer` 真的握手带出去之后确认这个值没有在传输路径上
  丢失或被篡改（这是 §3.3"验收缺口"留给 wire 的集成测试）。
- `_a24/memory/private/*` 三个方法必须**恒注册**（不管 entitlement
  是否为 `NONE`），capability 判断在 `Handler::call()` 内部——这是
  决策 1 §2.1 表格已经钉死的口径，wire 层直接照做。
- **真实资源竞争判据的起点**：wire 层实现 `remember_checked`/
  `recall_page`/`recent_page` 的 `Handler::call()` 时，三者共享的
  `Semaphore`（从各自 `PrivateMemoryHandle.admission` 拿到的同一个
  `Arc`）在 mount 层已经证明的是：大小正确（判据 4 第三条）、
  ephemeral 下不存在（判据 3）、给定共享输入时纯函数处理正确（判据 4
  第一条）。**v5 更正**：跨模块共享本身**不在**这个已证明的列表
  里——`Arc` 从 `PrivateMemoryHandle.admission` 拿到的确实是同一个
  实例这件事，第一次被真正证明就是 §7.2 要求的这条真实双模块测试，
  不是"重新验证一遍 mount 层已经证明的东西"。wire 的判据需要同时
  完成两件事：证明两个真实模块拿到的是同一个 permit，以及证明"三个
  方法确实排队等的是这一个 permit"。

## 12. 待决——已知且可接受的残留风险（不阻塞冻结判断）

**v4 更正**：原来这里记了两条"需要裁决"的开放问题。第一条（OOP 路径
缺集成级测试捕获点）round 3 评审明确指出不应该留作开放决定——已经在
§7.2 改成 T8.5c-W-wire 必须交付的判据，不再是"待决"（v5 声称已经把
全文其它暗示"可以接受间接证据"的地方——§4.1/§5.4/§10.3/§11——统一
改成跟 §7.2 一致的口径；**round 5 指出这个声明本身不完整**：§0 的
H3 总结、§7.2 自己末尾的"mount 这边只保证……wire 可以直接假设"、
§10.1 三处遗漏，其中 §7.2 那处是直接自相矛盾。v6 已经把这三处也改成
一致口径——见"v5 → v6 改动记录"）。这里保留两条真正
意义上"记录下来、经过评估后接受、不要求这一轮解决"的残留风险，跟前面
"验收缺口"（§3.3/§7.2 的 `Offer` 握手验证）性质相同：老实记录比假装
已经解决更重要，但也不是每一条老实记录的风险都必须消灭才能冻结。

**（新增，v5，Codex round 4 指出）`MemoryLease` 的 `user`/`org`/`kv`
三个字段仍然全部公开**——决策 4 v4 已经让 `admission()` 不缓存、每次
从 `self.kv` 现取，消除了"`admission` 跟 `kv` 分叉"这一种具体的绕过
方式，但没有让整个 `MemoryLease` 变成一个受构造器保护、不可被外部
拼凑出不一致状态的对象：调用方理论上仍能写
`lease.user = "someone-else".to_owned()`，构造出一个 `user` 跟
`org`/`kv` 实际代表的用户不一致的 `MemoryLease`。**采纳的判断**：
`user`/`org`/`kv` 三个字段是 F1/F8 时代就有的既有公开 API 形状，
不是本文档引入的，本文档的职责范围是"新增的 `admission` 概念要不要
可信"，不是"重新审视一个既有类型的整体封装边界"——把这个更大范围的
封装收紧列为独立的加固项，不在本文档强制要求；如果未来发现有代码
真的在依赖"改一个字段、其它字段跟着变"这种脆弱行为，那时候再做
私有化 + 访问器的改动。

**`PrivateMemoryHandle.admission`（`Arc<tokio::sync::Semaphore>`）本身
暴露 `add_permits()`/`close()` 等修改方法**——v4 已经堵住了"构造来源
错配"（`MemoryLease::admission()` 不缓存、每次从 `self.kv` 现取，见
"v2 → v3 改动记录"第 6 行），但堵不住"拿到这个 `Arc` 之后的误用"：
任何持有它的代码（今天只有 wire 层的 `Handler::call()` 实现会真正拿到）
理论上都能破坏这个 daemon 级单例的容量不变式。给它包一层只暴露
`acquire_owned()`/`Clone` 的 newtype 可以在类型层面彻底堵死这条路，
但这个类型会成为 T8.5c-P §12/§13 已经明确固定的接口契约的一部分
（P v5 的判据 9b 直接点名 `Arc<tokio::sync::Semaphore>::acquire_
owned()`）——引入 newtype 意味着需要再对 P 做一次版本修订。**采纳的
判断（不是留待下一轮，是这一轮就接受）**：不做——今天唯一会拿到这个
`Arc` 的代码是同一个 daemon 内受信任的 wire 实现，不是外部输入或
第三方模块代码，用一次额外的 P 版本修订换一个只在"内部代码写错"这种
场景下才触发的加固，成本不成比例。如果 T8.5c-W-wire 实现阶段发现
真的有代码在误用这个 `Arc`（比如某处不小心调用了 `close()`），到时候
再补 newtype 封装，不在这一轮强制要求。
