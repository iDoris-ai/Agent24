# T8.5b —— 权威事件用量计数 + 迁移/rekey（为真配额打底）

> **设计已冻结**（v1，2026-09-17）。Codex 一轮评审即**批准**：写路径覆盖完整性、幂等重放+`BEFORE INSERT`触发器的陷阱、rekey 触发器行为、`RAISE(ABORT,...)` 错误可精确匹配、真实字节计数、增量更新（非全表扫描）、WAL+序列化原子性——全部用 `sqlite3` CLI + Python `sqlite3`（模拟 sqlx/libsqlite3-sys 语义）独立复现验证，无 Critical/High。1 Medium + 4 Low 留到**实现阶段顺手处理**，不需要再送一轮设计评审：
> 1. **M1（必须处理）**：`mem_owner_quota` 配置表没有任何保护——如果 `'*'` 默认配额种子行被删除、且该 owner 没有自己的 override 行，触发器 SQL 里两层 `COALESCE` 全部落空，`WHERE ... > NULL` 在 SQLite 里为假，`RAISE` 根本不会执行——配额从"拒绝写入"静默退化成"完全不检查"，不报错不留痕。实现时二选一：给 `'*'` 行加 `BEFORE DELETE ON mem_owner_quota WHEN old.owner = '*' BEGIN RAISE(ABORT, 'cannot delete default quota') END` 保护；或至少在迁移 SQL 注释里把"这一行不可删"的运营纪律显式写清楚。
> 2. **L1**：`max_bytes` 只计 `payload` 列字节数，不是整行/整表存储占用——实现时在迁移 SQL 的列注释里显式写清楚范围，避免未来接配置的人理解成"这个 owner 总共占了多少磁盘"。
> 3. **L2**：`mem_owner_usage` 的 `row_count`/`byte_count` 递减时没有下限钳位，可以顺手加 `MAX(x-1, 0)` 式保护做纵深防御（风险很低，非必须）。
> 4. **L3**：rekey 现在每挪一行多触发 2 条 DML（旧 owner 递减 + 新 owner 递增），常数因子变大但仍是 O(N)；只在启动时、模块未挂载前跑，不影响运行时性能，可在文档/注释里诚实说明这个代价。
> 5. **L4（信息性，暂不处理）**：判据 13 的守门测试只能检测"触发器存在"，检测不了"重建顺序对不对"（先建触发器后拷贝数据会导致拷贝历史数据时被自己的配额规则拦截）。留到真的发生下一次 `mem_events` rebuild 时再补对应测试。

## 与 T8.5 的关系

T8.5 原计划一次性交付"真配额"（分区级字节/行数上限），送了 3 轮 Codex 设计评审。配额机制这部分连续两轮被判定不权威：

- 第 1 轮：查配额→判断→写入不是原子操作（TOCTOU），且字节计数用 SQLite `TEXT` 的 `length()` 数的是字符数不是字节数。
- 第 2 轮（针对"改成原子事务 + 独立计数表 `mem_owner_usage`"这个修法）：计数器不是所有写路径的权威来源——`EventLog::append`/`append_tx` 两条插入路径都不经过它；`rekey_os_partition` 改 `scope_owner` 不会同步挪动用量；把 `mem_owner_usage` 简单塞进 `OTHER_OWNER_SCOPED_TABLES`（rekey 时要求先清空）会让每个已有历史用量的 legacy 分区在 rekey 时直接失败。

T8.5a 已经把"请求生命周期信号"拆出来单独交付（`docs/design/T8.5a-request-lifecycle-signal.md`，已合并）。T8.5b 是第二个独立单元：只解决"配额计数权威、rekey 安全"这一层，不涉及配额如何被业务 RPC 消费——那是 T8.5c（或其后继任务）的事，本文档只需要保证消费者将来拿到的东西长什么样合理（见"不设计的东西"）。

## 现状复盘：`mem_events` 的写路径，以及 rekey 怎么动它

先把账算清楚，这是前两轮翻车的地方。全仓库搜索确认，`mem_events` 只有下面四条会改变其内容的路径：

**写者（INSERT）**：
- `EventLog::append`（`agent24-memory/src/event.rs:318`）——面向 `&self.pool` 的独立语句，`INSERT ... ON CONFLICT(id) DO NOTHING RETURNING seq`。这是唯一暴露给普通调用方的路径（`os_memory.rs::OsScopedMemory::remember`、各种 `kv.events().append(...)` 测试）。
- `EventLog::append_tx`（`event.rs:266`）——面向调用方持有的 `&mut SqliteConnection` 的**裸插入**（无 `ON CONFLICT`），`pub(crate)`，唯一生产调用点是 `writer.rs::WriteGate::commit_with_audit`（`writer.rs:224`），在 `BEGIN IMMEDIATE` 事务里把一条断言和它的审计事件一起提交，id 冲突时整个事务回滚（不是静默 no-op）。

**写者（UPDATE，改 `scope_owner`）**：
- `KvStore::rekey_os_partition`（`lib.rs:621`）——`UPDATE mem_events SET scope_owner = ? WHERE scope_owner = ?`（`lib.rs:674`），批量把一个分区的全部事件从旧 key 挪到新 key，跟 `mem_os_partitions`/`mem_checkpoints` 的更新在同一个事务里。

**写者（DELETE）**：
- 全仓库唯一一处：`consolidator.rs:457`，`#[cfg(test)]` 测试内部直接对 `&c.pool` 发的裸 SQL，模拟"日志被外部修过"。**没有生产路径删除 `mem_events`**——它是设计上的 append-only 日志。这条测试的价值恰恰在于：它是一条完全绕过 Rust API、直接摸库的写入，如果配额/用量机制想在"任何写路径"下都权威，连它也要覆盖到，而不能假设"只有 `EventLog` 的方法会碰这张表"。

结论（跟 T8.5a"先把读者/写者账算清楚"是同一个方法论）：**权威性要覆盖的不是"`EventLog` 暴露的两个 Rust 方法"，是"任何一条 SQL 语句"**——这正是 app 层加一层 `append_within_quota()` 包装函数治不好的病：`append_tx` 不经过它，未来某个人加一条新的写路径（哪怕只是测试用的裸 SQL）也不经过它。DB 结构性保证（触发器）跟调用路径无关，天然覆盖这四条以及未来任何新增的一条。

> **实现阶段代码评审澄清（Codex, 2026-09-18, Low，已修复）**：上一句"任何一条 SQL 语句"最初有个缺口——三个维护触发器只精确对应了 `mem_events` 上**当时设想到的三种写形状**（`INSERT`、`UPDATE OF scope_owner`、`DELETE`），漏了第四种：裸改 `payload` 列本身。没有任何生产/测试路径这么做过（append-only 日志的既有约定），但如果发生，`byte_count` 不会跟着更新、配额也不会拦截（配额检查只挂在 `BEFORE INSERT`）。已加 `mem_events_bu_payload_immutable`（`BEFORE UPDATE OF payload ... RAISE(ABORT, ...)`）把这条路直接堵死，让"任何一条 SQL 语句"这句话重新成立，而不是弱化它。

## 决策 1：两张新表——`mem_owner_usage`（权威计数，触发器维护）+ `mem_owner_quota`（配额配置，纯数据，触发器只读它）

```sql
-- migration 0014（文件名 0014_owner_usage_quota.sql，非本轮交付，供实现阶段参考）

CREATE TABLE mem_owner_usage (
    owner      TEXT PRIMARY KEY,
    row_count  INTEGER NOT NULL DEFAULT 0,
    byte_count INTEGER NOT NULL DEFAULT 0,
    updated_at TEXT NOT NULL
);

-- 配额配置本身不是本轮要交付的"真配置系统"（见决策 7），只是一张两行表：
-- '*' 是回退默认值，其余行是按 owner 的覆盖，将来任何配置层只需要
-- UPDATE/INSERT 这张表，不需要碰触发器 SQL。
CREATE TABLE mem_owner_quota (
    owner    TEXT PRIMARY KEY,
    max_rows INTEGER NOT NULL,
    max_bytes INTEGER NOT NULL
);
INSERT INTO mem_owner_quota (owner, max_rows, max_bytes)
VALUES ('*', 200000, 268435456); -- 猜的默认值，见决策 7
```

**为什么不是一张表**：`mem_owner_usage` 是**派生数据**（可以从 `mem_events` 重新 `GROUP BY` 出来，跟 MD-3b 的 FTS 投影是同一种关系——"权威 + 可重建的投影"，不是第二个真相源）；`mem_owner_quota` 是**配置**，两者的写者、写频率、谁允许改完全不同，混在一张表里会让"这一行是用量还是限额"变成靠列名猜。这也是这个仓库一贯的表设计纪律（0012/0013 把"物理 key"和"逻辑身份"拆成不同列，理由同构）。

## 决策 2：权威性怎么保证——触发器，覆盖 INSERT/UPDATE(scope_owner)/DELETE 三种路径，不依赖任何 Rust 调用点

**结论：可行，且已用真实 SQLite 验证。** 这个仓库已经有触发器维护派生表的先例（`0005_assertions_fts.sql` 的 `mem_assertions_fts_ai`，`AFTER INSERT ON mem_assertions`），`sqlx::migrate!` 对多语句 `CREATE TRIGGER ... BEGIN ... END;` 没有特殊处理问题——0005 已经在生产路径上跑了很久。

```sql
-- 覆盖 INSERT：唯一让分区变大的路径。
CREATE TRIGGER mem_events_ai_usage AFTER INSERT ON mem_events BEGIN
    INSERT INTO mem_owner_usage (owner, row_count, byte_count, updated_at)
    VALUES (new.scope_owner, 1, LENGTH(CAST(new.payload AS BLOB)), datetime('now'))
    ON CONFLICT(owner) DO UPDATE SET
        row_count = row_count + 1,
        byte_count = byte_count + LENGTH(CAST(new.payload AS BLOB)),
        updated_at = excluded.updated_at;
END;

-- 覆盖 rekey：owner 变更时把用量从旧 owner 挪到新 owner，见决策 6。
CREATE TRIGGER mem_events_au_owner_usage AFTER UPDATE OF scope_owner ON mem_events
WHEN old.scope_owner IS NOT new.scope_owner
BEGIN
    UPDATE mem_owner_usage SET
        row_count = row_count - 1,
        byte_count = byte_count - LENGTH(CAST(old.payload AS BLOB)),
        updated_at = datetime('now')
    WHERE owner = old.scope_owner;
    INSERT INTO mem_owner_usage (owner, row_count, byte_count, updated_at)
    VALUES (new.scope_owner, 1, LENGTH(CAST(new.payload AS BLOB)), datetime('now'))
    ON CONFLICT(owner) DO UPDATE SET
        row_count = row_count + 1,
        byte_count = byte_count + LENGTH(CAST(new.payload AS BLOB)),
        updated_at = excluded.updated_at;
END;

-- 覆盖 DELETE：今天没有生产路径会删 mem_events（见"现状复盘"），但唯一
-- 存在的删除——consolidator.rs 测试里那条裸 SQL——如果不覆盖，用量表就
-- 会跟真实内容脱节，"权威"这个词就不成立。防御性地做，不是补一个已知漏洞。
CREATE TRIGGER mem_events_ad_usage AFTER DELETE ON mem_events BEGIN
    UPDATE mem_owner_usage SET
        row_count = row_count - 1,
        byte_count = byte_count - LENGTH(CAST(old.payload AS BLOB)),
        updated_at = datetime('now')
    WHERE owner = old.scope_owner;
END;
```

这三个触发器附着在 `mem_events` 表本身上，跟 Rust 代码走的是哪个函数、哪个连接、有没有包在事务里**完全无关**——`append`（走 `&self.pool` 的独立语句）、`append_tx`（走调用方的 `&mut SqliteConnection`）、`rekey_os_partition` 的批量 `UPDATE`、consolidator 测试里的裸 `DELETE`，四条路径今天全部自动被覆盖，未来任何人加第五条路径也一样——这正是"权威性不依赖每个调用点记得调用某个函数"这个要求的字面意思：不是靠 code review 或者一个 lint 规则去检查"是不是每个写路径都调用了 `bump_usage()`"，是这张表根本不存在"绕过"这个动词能作用的对象。

**已验证的边界情况**（用 `sqlite3` CLI 对最小化 schema 跑的，见下面决策 4/5/6 的具体实验）：触发器在批量 `UPDATE`（rekey）时是逐行触发的（SQLite 的触发器天生是行级的，没有语句级触发器），所以一次挪 N 行的 rekey 会让 `mem_events_au_owner_usage` 精确触发 N 次，跟 `UPDATE mem_events SET scope_owner=?` 本身要触碰 N 行的开销是同一个数量级，没有引入额外的量级。

## 决策 3：真实字节计数——`LENGTH(CAST(x AS BLOB))`，不用 `octet_length()`

**已验证**：
```
sqlite> SELECT LENGTH('🎉🎉🎉🎉');                    -- 4（字符数）
sqlite> SELECT LENGTH(CAST('🎉🎉🎉🎉' AS BLOB));       -- 16（字节数，4 个 emoji × 4 字节/个）
```
`LENGTH()` 对 TEXT 参数返回的是 Unicode 字符数（这正是第 1 轮评审抓到的 bug 的字面复现）；`CAST(x AS BLOB)` 把值的类型亲和性（type affinity）改成 BLOB 后再 `LENGTH()`，返回的是真实存储字节数——这是 SQLite 类型系统的基本行为，不依赖任何版本特性。

**为什么不用 `octet_length()`**：这个仓库自己的 `0013_os_partitions_space.sql`（第 139 行注释）已经明确记录过"`octet_length()` exists but only from SQLite 3.43, a runtime version this crate does not pin"，并因此选择了别的方案。`CAST(... AS BLOB)` 是比 `octet_length()` 古老得多的 SQLite 特性（类型亲和性从 3.x 早期就有），跟这个仓库已经做出的保守选择一致，不需要重新讨论版本下限。

**为什么不在 Rust 侧序列化时拿 `payload.len()` 存成单独列**：这个方案本身没错（`event.rs` 里 `serde_json::to_string(&e.body)?` 之后立刻就有 `String::len()`），但它只能覆盖 `append`/`append_tx` 这两条 Rust 路径，覆盖不了裸 SQL（`consolidator.rs` 的测试删除路径、未来任何人手写的 SQL）——又变回"依赖每个调用点记得做对"的模式，跟决策 2 的核心论点矛盾。触发器里现算 `LENGTH(CAST(new.payload AS BLOB))` 的代价是对**这一行自己的** payload 做一次线性扫描，跟写这行数据本身的 I/O 是同一个数量级（`MAX_BODY_BYTES` 上限是 64 KiB，`os_memory.rs:141`），不是对整张表的扫描，性能上可以接受。

## 决策 4：原子性——配额检查是 `BEFORE INSERT` 触发器里的一条 `RAISE(ABORT, ...)`，不是"先查后写"

**已验证**（完整脚本见下方"自审"一节，此处摘录结论）：

```sql
CREATE TRIGGER mem_events_bi_quota BEFORE INSERT ON mem_events
WHEN NOT EXISTS (SELECT 1 FROM mem_events WHERE id = new.id)  -- 见决策 5
BEGIN
    -- COALESCE 必须包住整个子查询，不能只包列：owner 还没有 mem_owner_usage
    -- 行时，`(SELECT ... WHERE owner = ?)` 这个标量子查询本身返回 NULL（零匹配
    -- 行，不是"一行、列为 NULL"），内层 COALESCE 根本没机会跑。这是实现阶段
    -- Codex 代码评审抓到的 High：`(SELECT COALESCE(row_count, 0) FROM ...)+1`
    -- 这种写法（COALESCE 在子查询里面）会让任何全新 owner 的第一条写入完全绕过
    -- 配额。下面是修复后的正确写法。
    SELECT RAISE(ABORT, 'mem_quota:rows')
    WHERE COALESCE((SELECT row_count FROM mem_owner_usage WHERE owner = new.scope_owner), 0) + 1
          > COALESCE(
              (SELECT max_rows FROM mem_owner_quota WHERE owner = new.scope_owner),
              (SELECT max_rows FROM mem_owner_quota WHERE owner = '*'));
    SELECT RAISE(ABORT, 'mem_quota:bytes')
    WHERE COALESCE((SELECT byte_count FROM mem_owner_usage WHERE owner = new.scope_owner), 0)
          + LENGTH(CAST(new.payload AS BLOB))
          > COALESCE(
              (SELECT max_bytes FROM mem_owner_quota WHERE owner = new.scope_owner),
              (SELECT max_bytes FROM mem_owner_quota WHERE owner = '*'));
END;
```

这不是"查询-判断-写入"三步——它是**一条 INSERT 语句自身执行过程的一部分**。SQLite 对单条语句（含它触发的 BEFORE/AFTER 触发器）的执行是不可分割的：`BEFORE INSERT` 触发器在行真正落盘之前跑，跑的时候读到的 `mem_owner_usage`/`mem_owner_quota` 就是这条语句开始执行那一刻的状态，而 SQLite 本身是单写者模型（这个 crate 已经在用 `journal_mode(Wal)` + `busy_timeout(5s)`，`lib.rs:170/174`），同一时刻只有一个连接能持有写锁——所以不存在"两个并发写者都读到'还有余额'然后都写入,一起超限"的竞态窗口：第二个写者的 `BEGIN`/写语句会等第一个的写事务释放锁,而不是并发读到同一份旧状态。这跟 `KvStore::ensure_org_for_user` 已经依赖的"SQLite 写序列化"是同一个机制,不是新引入的保证。

**判据 9（见下）就是直接构造"分区已在配额上限"然后再插入一行,断言第二次插入失败且用量表数字没有被污染**——这比"用两个并发任务去赛跑"更能稳定复现,也是这个仓库测原子性时一贯的做法（`writer.rs` 的 `commit_and_audit_are_atomic_no_belief_without_record` 用的也是"预先占位造成冲突"而不是并发赛跑）。

**为什么不是"应用层一次事务里 SELECT usage FOR UPDATE 再 INSERT"**：SQLite 没有行锁,`SELECT ... FOR UPDATE` 不存在;要在应用层做到不可分割,唯一手段是要么整个数据库级别的互斥（跟触发器方案比没有任何优势,还多一次 round-trip）,要么就是第 1 轮评审已经指出过的"查-判-写"三步之间必然有窗口。触发器把这三步压缩成数据库引擎自己保证原子的一步,是唯一从根子上消除窗口的方式。

## 决策 5：幂等重放语义——`WHEN NOT EXISTS (...)` 让精确重放完全跳过配额检查

这是本轮**唯一一处需要额外小心的地方**,因为最初直接测试就证明了一个反直觉的事实：**朴素的 `BEFORE INSERT` 触发器会在一次精确重放（id 已存在,`ON CONFLICT(id) DO NOTHING` 本该让这次写入变成无操作）上错误地报出配额超限**——哪怕这次重放实际上不会新增任何一行。

**已验证**（`/tmp` 下的实验,过程见"自审"）：
1. 没有 `WHEN` 条件的朴素版本：分区用满 2/2 配额后,重放一条**已存在**的 id（`INSERT ... ON CONFLICT(id) DO NOTHING`）——**触发器仍然在 `ON CONFLICT` 决议之前跑了一次**,直接 `RAISE(ABORT, 'quota exceeded')`,整条语句失败。这精确复现了任务描述里要求解决的 Medium 级问题,而且比"配额判断顺序错了"更底层：**即使换成事务化的配额判断,如果没有这个 `WHEN` 条件,问题在触发器层面原样复现**。
2. 加上 `WHEN NOT EXISTS (SELECT 1 FROM mem_events WHERE id = new.id)` 之后：
   - 分区在配额上限（2/2）,插入一个**全新** id → 仍然正确地 `RAISE(ABORT, ...)`（配额确实该拦）。
   - 分区在配额上限,重放一条**已存在**的 id → **静默成功**,`mem_owner_usage` 数字不变,`mem_events` 行数不变——精确重放被正确识别为无操作,不占用、不检查配额。
   - 分区在配额上限,另一个 owner 试图用同一个已存在的 id 写入不同内容（跨 owner id 冲突）→ 同样不触发配额检查（`WHEN` 只看 id 存不存在,不看 owner/payload 是否匹配）,`ON CONFLICT DO NOTHING` 静默吞掉这次插入,`mem_events` 里的行保持原样——然后 `EventLog::append` 现有的"查出来发现 owner/payload 不一致,返回 `Conflict`"逻辑接管,报的是**冲突错误**,不是误导性的"配额超限"错误。这条路径完全不需要改（`event.rs:354-366` 原样保留）。

`WHEN` 子句的代价是给每次插入多一次 `id` 上的索引查找（`id` 本身已经是 `UNIQUE`,这个查找就是那条唯一索引本来就要做的查找,不是新增一次全表扫描）,可以接受。

## 决策 6：rekey 的迁移安全性——`mem_owner_usage` 不进 `OTHER_OWNER_SCOPED_TABLES`,靠触发器自动跟着 `mem_events` 的 `UPDATE` 走

`KvStore::rekey_os_partition`（`lib.rs:621`）今天的动作是：在一个事务里，① 检查 `OTHER_OWNER_SCOPED_TABLES` 里 8 张表都没有 `old_key` 的行（否则拒绝）；② `UPDATE mem_events SET scope_owner = new_key WHERE scope_owner = old_key`；③ `UPDATE mem_checkpoints SET scope_owner = new_key WHERE scope_owner = old_key`；④ `UPDATE mem_os_partitions SET owner_key = new_key ...`。

**`mem_owner_usage` 必须像 `mem_events`/`mem_checkpoints` 一样是被"移动"的表,而不是被"检查是否为空"的表**——这正是任务描述里点名的坑：如果直接把它塞进 `OTHER_OWNER_SCOPED_TABLES`,那么任何一个已经有历史事件（也就已经有 `mem_owner_usage` 行）的 legacy 分区,一旦触发 rekey 就会因为"`mem_owner_usage` 里有 `old_key` 的行"而被 ① 步拒绝——而**几乎每一个** legacy 分区都会有用量行,因为决策 2 的触发器从它诞生那一刻起就在记。

修法是**什么都不用改**：因为决策 2 里已经有一个 `AFTER UPDATE OF scope_owner ON mem_events` 触发器,它会在 rekey 的第 ② 步（`UPDATE mem_events SET scope_owner = new_key ...`）**执行过程中被自动、逐行触发**——rekey 的 Rust 代码不需要知道 `mem_owner_usage` 的存在,不需要新写一行代码去搬它,搬运是 `UPDATE mem_events` 这条语句自己的副作用。

**已验证**（完整脚本见"自审"）,模拟了任务描述里那个具体的坏序列：
1. 先在 `old_owner` 下插入 3 条事件（触发器自动把用量记到 `mem_owner_usage['old_owner'] = (3 行, 18 字节)`）——对应"`KvStore::open` 跑迁移 0014,按旧 owner key 回填用量"这一步（迁移的 `INSERT ... SELECT ... GROUP BY` 一次性重算,见决策 1 的 SQL）。
2. 模拟 `rekey_os_partition` 的批量 `UPDATE mem_events SET scope_owner = 'new_owner' WHERE scope_owner = 'old_owner'`。
3. 验证结果：`mem_owner_usage['new_owner'] = (3 行, 18 字节)`——跟 `mem_events` 里 `new_owner` 下的实际行数（3）完全一致；`mem_owner_usage['old_owner']` 变成 `(0, 0)`（孤儿行,不影响正确性,见下）。

**没有让新 owner"看起来零用量"**（任务描述里点名的第二个坏结果）：因为触发器搬的是历史用量的**加法**（`row_count = row_count + 1` 而不是覆盖）,如果 `new_owner` 在 rekey 之前已经有自己的用量（虽然今天的业务逻辑不会出现这种情况——rekey 前会先检查 `new_key` 未被占用,`lib.rs:661-673`——但触发器本身对这种情况也是安全的,`ON CONFLICT DO UPDATE` 会正确累加而不是覆盖）。

**`old_owner` 归零后的孤儿行是可接受的**,跟 `mem_os_partitions`/`mem_checkpoints` 在 rekey 后也会留下"指向已不存在分区"的痕迹是同一类无害状态——`mem_events` 本身在 `old_owner` 下已经空了,`mem_owner_usage['old_owner']` 显示 `(0,0)` 是**准确的**,不是"过时的谎言"。如果想要更干净,可以在 `AFTER UPDATE` 触发器里加一条 `DELETE FROM mem_owner_usage WHERE owner = old.scope_owner AND row_count <= 0`,但这是可选的卫生工作,不影响权威性,本轮不作为必须项（避免给触发器逻辑增加不必要的分支）。

## 决策 7：配额默认值——保守猜测 + 用一张配置表占位,不引入真正的配置系统

`mem_owner_quota` 的 `'*'` 行数值（`max_rows = 200000`,`max_bytes = 256 MiB`）**是猜的**,没有任何生产流量数据支撑——`MAX_BODY_BYTES = 64 KiB`（`os_memory.rs:141`）是单条事件的上限,`200000` 行 × 平均几百字节大概落在几十到上百 MB,数量级上"不会让一个失控模块几分钟内把 `memory.db` 撑爆",仅此而已,不是精算结果。

**将来怎么接配置**：因为限额被设计成"表里的数据",不是"触发器 SQL 里的字面量",接入配置的成本被压到最低——将来无论是 `os.json` 式的注册表、还是某种运行时管理接口,只需要在启动时（或响应配置变更时）对 `mem_owner_quota` 做 `INSERT ... ON CONFLICT DO UPDATE`,不需要 `ALTER` 任何触发器、不需要新的迁移。`owner` 列本身已经支持"按分区覆盖默认值"（比如某个已知会写很多的模块给它单独开一个更高的 `max_rows`）,不需要额外设计。这跟 T8.5a 决策 5"`budget` 从常量变成 `state.limits.total`,数据而不是常量"是同一条原则的延伸,只是这里选择"数据库里的一张表"而不是"内存里的一个 `Limits` 结构体",因为触发器只能读数据库,读不到 Rust 里的 `Arc<Limits>`。

## 判据

1. **权威性 / INSERT 路径**：分别通过 `EventLog::append`（走 `&pool`）和 `EventLog::append_tx`（走 `writer.rs::commit_with_audit` 的共享事务）各写一条事件,`mem_owner_usage` 里对应 owner 的 `row_count`/`byte_count` 都正确反映——两条路径都不需要 Rust 代码显式调用任何"更新用量"的函数。
2. **权威性 / 裸 SQL 路径**：直接对 pool 发一条不经过任何 `EventLog` 方法的裸 `INSERT INTO mem_events`（模拟"未来新增的路径"）,`mem_owner_usage` 依然正确更新——证明覆盖的是表,不是调用点。
3. **权威性 / DELETE 路径**：复刻 `consolidator.rs` 现有测试里那条裸 `DELETE FROM mem_events`,断言之后 `mem_owner_usage` 对应 owner 的计数相应减少。
4. **真实字节计数**：写入一条 `payload` 包含多个 emoji（Unicode 字符数与 UTF-8 字节数相差 4 倍以上）的事件,断言 `mem_owner_usage.byte_count` 增加的是 UTF-8 字节数而不是字符数——**正对照**：纯 ASCII payload 时两种计数法数值相同,不能用来分辨该判据。
5. **原子性 / 精确到临界值**：把某 owner 的 `mem_owner_usage.row_count` 预置为 `max_rows - 1`,插入一条新 id 的事件 → 成功,用量变成 `max_rows`；再插入一条新 id 的事件 → 必须失败（`QuotaExceeded { dimension: "rows" }`）,且失败后 `mem_owner_usage` 数字与失败前完全一致（不能一次"部分生效"）。**正对照**：换一个不同 owner 插入同样内容,不受影响。
6. **原子性 / 字节维度同上**,换成逼近 `max_bytes` 的场景。
7. **幂等重放跳过配额（核心判据）**：某 owner 的用量已在 `max_rows` 上限,重放一条**已存在**的 id（内容、owner 都与原事件一致）→ 必须成功返回原 `seq`,`mem_owner_usage` 数字不变,`mem_events` 行数不变——不因为分区已满配额而把一次本该无操作的重放误判为 `QuotaExceeded`。**正对照**：同样在配额上限,插入一条**全新** id 的事件 → 必须失败。
8. **跨 owner id 冲突不被误报为配额问题**：某 owner 在配额上限,另一 owner 尝试用同一个已存在的 id 写入不同 payload → 必须返回 `MemoryError::Conflict`（现有 `append_id_collision_across_owners_is_a_conflict_not_a_swallow` 覆盖的语义）,不能返回 `QuotaExceeded`,也不能把这次尝试计入任何一方的用量。
9. **rekey 后计数器仍然权威（核心判据）**：构造一个有 N 条历史事件的分区（先跑迁移回填得到 `mem_owner_usage[old_key] = (N, B)`）,执行 `rekey_os_partition(old_key, new_key, ...)`,断言：`mem_owner_usage[new_key] = (N, B)`,与 rekey 后 `mem_events` 里 `new_key` 下的实际行数/字节数一致；且 rekey 之后,`new_key` 分区立刻可以正确地被配额挡住（用一个刻意设得很小的 `max_rows` override 验证,插入第 N+1 条新事件必须因为超限而失败）——证明 rekey 不会让新 owner"看起来零用量"从而让配额形同虚设。
10. **rekey 失败（`OTHER_OWNER_SCOPED_TABLES` 命中）时用量表不受影响**：复刻现有测试 `a_rekey_refuses_when_another_owner_scoped_table_holds_rows`,加一条断言：拒绝发生前后 `mem_owner_usage` 数字不变。
11. **迁移回填对已有历史数据正确**：在跑 0014 之前构造若干 `mem_events` 行（模拟升级前的老库）,跑迁移后 `mem_owner_usage` 与直接对 `mem_events` 做 `GROUP BY scope_owner, COUNT(*), SUM(LENGTH(CAST(payload AS BLOB)))` 的结果逐 owner 一致。
12. **配额可配置**：把某 owner 的 `mem_owner_quota` 行改成比默认值更小的限额（不改任何触发器 SQL,只 `UPDATE` 这张表）,验证同一段插入代码在新限额下更早地被拒绝——证明"将来怎么接配置"这条路径今天就是通的,不是空话。
13. **触发器在未来的表重建中存活（守门测试）**：`KvStore::open_memory()` 跑完全部迁移后,查询 `sqlite_master` 断言 `mem_events_ai_usage`/`mem_events_au_owner_usage`/`mem_events_ad_usage`/`mem_events_bi_quota`/`mem_events_bu_payload_immutable` **五个**触发器都存在且附着在 `mem_events` 上——对应"自审"里指出的"未来 rebuild `mem_events` 会连带 drop 触发器"的风险,这条测试是防止该风险变成静默回归的护栏。

## 不设计的东西

- **配额被谁、在哪一层消费**（T8.5c 的事）。本轮只保证"如果有人在写入时想知道会不会超限、想在超限时拿到一个明确的错误",数据库层已经把这件事做对了；具体到 `_a24/memory/*` RPC 收到 `QuotaExceeded` 之后该怎么回给客户端、要不要有 soft/hard 两档、要不要给客户端一个"还剩多少"的查询接口，都不在本轮范围。`OsScopedMemory::remember`（`os_memory.rs:569`）今天完全不知道配额的存在，本轮也不改它——它调用的还是同一个 `EventLog::append`，配额检查是那次调用自动获得的副作用，不需要它自己变得"配额感知"。
- **一个真正的配置系统**。`mem_owner_quota` 只是占位——没有校验规则、没有审计、没有"谁能改"的权限模型，跟 T8.5a 决策 5 那种"从常量变成运行时状态但仍然是进程内一个 `Arc<Limits>`"不是同一量级的工程。
- **`mem_owner_usage`/`mem_owner_quota` 是否需要出现在 `OTHER_OWNER_SCOPED_TABLES` 之外的任何导出/擦除路径**。`os_partitions_for_org`/`durable_for_org` 这类查询今天回答的是"这个 org 有哪些分区"，不涉及用量数字；用量表要不要被一并导出/擦除是数据治理层面的问题，不在本轮范围，但因为它跟着 `scope_owner` 走（决策 6），任何未来的导出/擦除逻辑只要照抄"这张表跟着 `mem_events` 动"的规则就不会出错。
- **配额超限之后已经写入的历史数据要不要被清理/淘汰**。本轮是纯粹的准入控制（gate），不是垃圾回收；一个分区如果因为过去没有配额而已经超限，本轮不会主动删除任何东西——`mem_owner_usage` 会如实显示"已经超过限额"，后续新写入被拒绝，但存量不受影响。这是刻意的：批量删除历史数据是一个更危险、更需要独立设计（谁来选删哪些、按什么策略）的操作，不应该作为配额机制的副作用悄悄发生。

## 自审

逐条核对本轮要求覆盖的每一点，以及新引入的风险。

**权威性**：已在决策 2、判据 1-3 验证——触发器附着在表上而不是某个 Rust 函数上，`append`/`append_tx`/裸 SQL INSERT/裸 SQL DELETE 四条路径全部自动覆盖。

**真实字节计数**：已在决策 3、判据 4 验证，`CAST(x AS BLOB)` 对 4 个 emoji 返回 16 字节而不是 4 字符，用真实 `sqlite3` CLI 跑过，不是推断。

**rekey 迁移安全性**：已在决策 6、判据 9-10 验证——`mem_owner_usage` 不进 `OTHER_OWNER_SCOPED_TABLES`，靠 `AFTER UPDATE OF scope_owner` 触发器自动跟随 `rekey_os_partition` 现有的批量 `UPDATE mem_events`，**不需要改 `rekey_os_partition` 一行代码**。用一个模拟"先有 3 条历史事件、迁移回填、再 rekey"的完整脚本验证过，新 owner 拿到的数字跟 `mem_events` 里的真实行数完全一致。

**原子性**：已在决策 4、判据 5-6 验证——配额检查是 `BEFORE INSERT` 触发器里的 `RAISE(ABORT, ...)`，跟行的插入是同一条 SQL 语句执行过程的一部分，不存在"查询-判断-写入"之间可以被别的写者插入的窗口，因为 SQLite 本身是单写者序列化的（这个 crate 已经在依赖这个性质，`journal_mode=WAL` + `busy_timeout(5s)`）。

**幂等重放语义**：这是本轮**唯一一处最初的朴素设计被证明是错的**地方，记录下来是因为它本身就是一个值得记的教训——不是"配额判断顺序错了"这种应用层逻辑问题，是**触发器层面的一个真实陷阱**：`BEFORE INSERT` 触发器在 `ON CONFLICT` 决议**之前**运行，所以即使 Rust 代码写对了"先判断是不是精确重放再检查配额"的顺序，如果触发器本身没有对应的 `WHEN NOT EXISTS(...)` 守卫，配额检查还是会在重放路径上被触发并导致整条语句失败——**Rust 侧代码此时来不及介入**，因为 SQL 语句已经因为触发器里的 `RAISE(ABORT,...)` 而失败了，`EventLog::append` 的 `.fetch_optional().await?` 会直接拿到一个 `Err`，根本走不到后面判断"是不是精确重放"的 `SELECT` 分支。加上 `WHEN NOT EXISTS (SELECT 1 FROM mem_events WHERE id = new.id)` 之后，用完整脚本验证了三种场景都对：精确重放在满配额下静默成功、全新 id 在满配额下被正确拒绝、跨 owner id 冲突在满配额下正确地报 `Conflict` 而不是 `QuotaExceeded`。

**新的锁序检查**：这一层没有引入任何新的 Rust 级别的锁（没有新的 `Mutex`、没有跨连接通信）——所有状态变更都发生在同一个 SQLite 连接正在执行的同一条语句/同一个事务内部，靠的是这个 crate 已经依赖的 SQLite 单写者序列化（`SqlitePoolOptions::max_connections(5)` + WAL + `busy_timeout(5s)`），不是新引入的保证，因而不存在新的死锁风险。与 T8.5a 决策 4"`send_replace` 在锁外调用避免两把锁嵌套"是同一种检查方法，只是这里连"两把锁"都没有——只有 SQLite 自己的写锁,一把。

**新的死锁/正确性风险——未来 `mem_events` 再次被 rebuild 时触发器会被静默丢弃**：这是本轮自审找到的、原始任务描述没有点名但值得记录的一条真实风险。SQLite 的 `DROP TABLE` 会级联删除附着在该表上的触发器；`0011_events_owner_trim.sql`、`0013_os_partitions_space.sql` 都已经用过"建 `_new` 表、拷贝数据、`DROP`、`RENAME`"这种 rebuild 手法（原因是 SQLite 不能直接 `ALTER` 一个 `CHECK` 约束或加 `NOT NULL` 列），而且 0011 的注释已经明确写过"a rebuild drops them with the table"这条教训——但那次说的是索引,不是触发器。**如果未来某次迁移出于别的原因需要再 rebuild 一次 `mem_events`（比如再加一条 CHECK 约束），而作者不知道/忘记这个事实，`mem_owner_usage` 就会在那次迁移之后悄悄停止被维护——不会报错，只会从此不再权威，而"不再权威"恰好是这整个设计存在的理由要反对的那件事。** 缓解：① 判据 13 的守门测试，在每次迁移跑完后断言五个触发器都还在 `sqlite_master` 里，任何未来的 rebuild 一旦忘记重建触发器，这条测试立刻红；② 本文档"具体改动清单"里已经把这条写成需要在未来 rebuild 迁移的注释里显式提醒的规则，跟 0011 对索引做的事是同一个纪律。这条风险不影响本轮设计本身的正确性（因为 0014 之后到今天为止没有任何计划中的 `mem_events` rebuild），但值得现在就记录,避免它变成两年后一次不相关的迁移里悄悄引入的回归。

**批量导入/迁移路径的性能与正确性**：今天唯一会对 `mem_events`做批量写的是 0011/0013 式的 rebuild（`INSERT INTO mem_events_new SELECT ... FROM mem_events`），而 0014 排在它们之后——rebuild 发生时触发器还不存在，不受影响。**给未来的 rebuild 作者的具体提醒**（写进了"具体改动清单"）：如果未来确实需要在触发器存在之后再 rebuild `mem_events`，正确做法是照抄 0011/0013 对索引的处理顺序——先完成"建新表、拷贝、drop 旧表、rename"，**最后**才在新表上重建这五个触发器，而不是先建触发器再拷贝——否则拷贝过程中的每一行 `INSERT INTO mem_events_new SELECT ...` 都会被 `mem_events_bi_quota` 当成"新增长"而不是"历史数据原样搬家"来检查，一个早已超过当前配额的合法历史分区会在自己的数据被拷贝回来的过程中被自己的配额拒绝，导致 rebuild 失败或数据丢失。这条同时也解释了为什么 `mem_owner_usage` 的初始回填（决策 1/6）是用一次性的 `GROUP BY` 重新计算,而不是指望搬迁过程中的触发器增量——批量搬迁场景下,重新计算比信任增量更简单也更不容易踩上面这个坑。

**内存/存储无界性检查**：`mem_owner_usage`/`mem_owner_quota` 都是 owner 基数的表（一行对应一个 `scope_owner`），基数上界等于历史上出现过的 owner 数量——这个数量原本就受 `mem_os_partitions` 隐含约束（每个 owner 对应一个已记录的分区，或者是某个真实用户的 bare user id），不会无界增长。两张表都是普通 SQLite 表，没有引入新的内存驻留结构。
