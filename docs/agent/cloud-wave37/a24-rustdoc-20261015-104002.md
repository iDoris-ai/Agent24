# a24-rustdoc-20261015-104002：rustdoc E0463 独立根因研究（Linux 云端）

> **声明**：这是 Linux x86_64 云端的 test-only 研究，**不是 macOS 验收，也不是产品批准**。云端只用了公开 baseline a9b（canonical `iDoris-ai/Agent24`，`ls-remote` 核对 `ab/preview-hw-23-probe-disk` = a9b36ce），**没有复制本机那 25 个私有组合**。本次没有跑 Agent24 全 workspace，也没有跑任何 hardware/SystemProbe。**本机真实根因仍为 unknown**。下文的通用复现只说明“这种机制足以产生同类症状”，不能证明本机就是这个原因。

## 1. 环境
- 云 VM：Linux 6.18 x86_64；rustup 装了 `1.95.0 (59807616e 2026-04-14)`，commit 和本机 Homebrew 1.95.0 一致（但这是 rustup 构建，不是 Homebrew 构建）。对照组用 1.97.0 (2d8144b78)。
- baseline 布局：`agent24-agent` 依赖 `async-trait 0.1.91`（proc-macro）、`agent24-store` 等路径 crate。在 a9b 上，`agent24-agent/src` 里 **0 个 doctest 代码块**，但 cargo 仍会对它执行 `rustdoc --test`。这一步需要加载全部 `--extern` 和传递依赖，并 dlopen async_trait 的 dylib，所以“没产生任何 doc 结果就 E0463”这个现象与“没有 doctest”并不矛盾。

## 2. 实验结果（1.95.0 与 1.97.0 完全一致；原始输出见同目录 `*.linux-1.95.0.out` / `*.linux-1.97.0.out`）

| # | 场景 | exit | 关键输出 |
|---|---|---|---|
| E1 | ws_a `test --doc -vv` | 0 | 正控制 |
| E2 | ws_a 完整 `test` | 0 | 正控制 |
| E3 | ws_b（另一个 source 路径）共享同一 target | 0 | **workspace 成员的 `-C metadata`/文件名与 ws_a 完全相同**（`libfx_store-<同一哈希>.rlib`），ws_b 直接被判为 Fresh |
| E4 | ws_a 完整 test 进入 8s 慢测试窗口时，ws_b 跑 `cargo build` | 0 | 0.04s 完成，**没有出现 “Blocking waiting for file lock”**，说明 cargo 在执行测试/doctest 阶段**不持有** build-dir 锁 |
| E5 | 窗口内 ws_b 用不同 RUSTFLAGS 构建 | 0 | 生成了另一个哈希的文件，原文件 inode 不变，不会造成干扰（反证：“RUSTFLAGS 不同导致覆写”这条不成立） |
| E6 | 窗口内 ws_b 修改共享 proc-macro 源码后全量重建 | 0 | 同名 `.so` 的 inode 变了；由于下游也一起一致地重建，doctest 仍然通过 |
| E7 | 窗口内移走 store rlib | 1 | `error: extern location for fx_store does not exist`（**不是 E0463**） |
| E9 | 窗口内 ws_b 只重建 `-p fx_store`，且源码不同（模拟另一个 worktree 处在不同 commit） | 101 | `error[E0460]: found possibly newer version of crate fx_store which fx_agent depends on`：单元测试和集成测试全绿，**唯独 doctest 失败** |
| E10 | 窗口内只重建共享 proc-macro（SVH 不同，下游不重建） | 0 | Linux 上不失败：单独换掉 proc-macro dylib 不足以触发错误 |
| E11 | 同 E10 的写者，但写完之后才跑 `test --doc` | 0 | cargo 重新做指纹检查后重建，所以是绿的。这解释了为什么 `--doc` 单独跑能通过 |
| E12 | 窗口内移走传递依赖 fx_core 的 rlib（rmeta 还在） | 101 | `crate fx_core required to be available in rlib format` |
| E12b | 窗口内 fx_core 的 rlib 和 rmeta 都缺席 | 1 | **`error[E0463]: can't find crate for fx_store`**：报错点名的是直接依赖 store，真正缺的却是它的传递依赖 |
| E13 | 重建期间以约 30 次采样探测 | — | 同名 proc-macro `.so` 出现了多个 inode（被替换）；采样太粗，没有捕捉到缺席瞬间 |
| E8 | 慢窗口，无写者（反控制） | 0 | — |

## 3. 假设评估
- **H1：另一个 source 路径/worktree 和本 runner 共用 target，在测试窗口内写入同名单元**。机制上有支持：E3 说明不同路径会产生**同名**产物，E4 说明测试阶段不持锁，E9/E12b 说明这样就能产生“只有 doctest 失败、E0460/E0463”的症状，而 `--doc` 单独跑（E11）是绿的。这与本机“`--doc` 绿、完整 test 跑了 3154 个之后第一个 doctest 失败”在形态上一致。**但本机是否真有这样一个写者，没有得到证明**。
- **H2：只是 proc-macro dylib 被换了 inode**：在 Linux 上不足以触发（E10）。macOS 上 dylib 的加载/代码签名行为不同，**未验证**。
- **H3：RUSTFLAGS 不同的写者**：已被推翻（E5，哈希不同，不会覆写）。
- **H4：编译器错配**：本工装里没有出现。云端 1.95.0 与 1.97.0 结果一致，**无法证明也无法排除**本机 Homebrew 构建的特有问题。
- **E0463 的文案**：只有 rlib 和 rmeta 都缺席时才会出现 E0463，而且报错点名的可能是直接依赖（E12b）。直接 `--extern` 缺失时报的是 “extern location does not exist”（E7）；SVH 偏斜时报的是 E0460（E9）。因此**本机完整的 stderr 文本（点名哪个 crate、有没有 “extern location”/E0460 伴随）有很强的区分力**。

## 4. 下一条 macOS 诊断命令（不改 target，也不是“清 target/拆命令”式的绕过）
本机仍然原样跑门禁命令，同时旁挂只读监视器：
```bash
tools/qa/rustdoc-repro/target-window-watch.sh rust/target /tmp/a24-watch.log \
  agent24_store agent24_agent agent24_core agent24_tools agent24_models agent24_memory agent24_protocol agent24_workspace async_trait &
(cd rust && cargo test --workspace --offline --locked -vv) 2>&1 | tee /tmp/a24-full.log; echo "exit=${PIPESTATUS[0]}"
touch /tmp/a24-watch.log.stop
grep -nE 'error\[E04(60|63)\]|extern location|Doc-tests agent24_agent' /tmp/a24-full.log
```
判读方法：runner 在编译结束（日志里 `Finished`）之后，按理不会再写这些文件。
- 如果窗口内 `/tmp/a24-watch.log` 出现了 `CHANGE`（rlib/rmeta/.d/fingerprint 的 inode 或 mtime 变化），就**支持 H1**，而且能直接看到被改的是哪个单元。
- 如果完全没有 CHANGE 却仍然 E0463，那么 **H1 被推翻**，应该转查 macOS 的 dylib 加载问题或编译器问题。下一步是从 `-vv` 日志里取出 agent24_agent 那条 rustdoc argv 原样重跑，看是否稳定复现。

失败后，再对报错点名的 crate 及其 `.d` 文件执行 `ls -li rust/target/debug/deps/lib<name>-*`，核对文件是否存在、有没有生成新的 inode。
