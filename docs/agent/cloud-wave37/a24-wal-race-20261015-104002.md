# a24-wal-race-20261015-104002：测试库复制中的 WAL TOCTOU

- 仓库：iDoris-ai/Agent24
- 基线：`ab/preview-hw-23-probe-disk` @ `a9b36ceee8a74f0c477b37836506933b09aafcf5`（含 main 622be5d / #964）
- 分支：`baton/grokbot-a24-20261015-104002-wal-race-r2`（仅推送，无 PR、无合并）
- 包：`agent24-documents`（`rust/apps/agent24-documents`）
- 改动范围：仅 `rust/apps/agent24-documents/src/state/tests.rs`（测试代码）；生产 DB / 快照 / 迁移逻辑未改。

## 1. 现象

`a_read_only_database_file_is_not_writable` 原测试为了得到新 inode，先
`Db::open(made).pool().close().await`，再对 `documents.db` 与 `documents.db-wal`
逐个执行 `if exists() { fs::copy().unwrap() }`。CI 偶发
`Os { code: 2, kind: NotFound }`，位置在 `fs::copy`（原第 171 行）。

## 2. 机制（竞态，不是生产数据损坏）

依赖版本（Cargo.lock）：sqlx-core / sqlx-sqlite 0.8.6，libsqlite3-sys 0.30.1。

1. `PoolConnection` 被 drop 时，sqlx 用 `rt::spawn` 异步把连接还回池（`return_to_pool`，
   中间有一次跨 worker 线程的 `ping`）。
2. `PoolInner::close` 的循环在第 `max_connections` 轮拿到全部 permit 后直接结束，
   不再弹出 idle 队列；`release()` 也不检查池是否已关闭。于是一条在 `mark_closed`
   之前已过 `is_closed` 检查、随后 `release()` 回 idle 的连接，会在 `close().await`
   返回后仍然打开。
3. 这条连接随 `Db` 临时值 drop 时只是丢掉 `command_tx`；sqlx-sqlite 的 worker 线程
   随后在**自己的线程上**结束并 `sqlite3_close`。作为最后一条连接，SQLite 会检查点并
   删除 `-wal`。这一步与测试线程的 `exists()`→`fs::copy` 没有任何先后约束。

实测（Linux，本分支临时探针，未提交）：300 次 `Db::open(..).pool().close().await` 之后，
`-wal` 仍存在 241 次，其中 215 次在随后 20 ms 内自行消失——即 close 返回后仍有连接在
异步关闭。WAL 由 SQLite 正常检查点后删除，数据完整；失败只在测试的复制辅助里。

## 3. RED（确定性复现）

提交 `2f3c225`：把原循环原样抽成 `copy_database(from, to, closing)`，语义不变，只在
看到 `-wal` 之后、复制之前关闭一条传入的连接（替身：池遗留的最后连接）。新增：

- `a_wal_closed_away_during_the_copy_still_gives_a_complete_database`：源库用单条原生
  连接建表并写一行（`wal_autocheckpoint=0`，提交只在 WAL 中）；该连接作为最后连接在
  竞态点关闭 → SQLite 删除 WAL → 旧辅助 `fs::copy` 返回 `Os code 2 NotFound`。
  连续 20 次运行 20/20 失败，错误一致。
- `copying_a_database_that_is_not_there_is_an_error`：旧辅助对缺失主库静默返回 `Ok`（吞错），失败。
- `copying_into_a_missing_directory_is_an_error`：目标目录不存在的真实 I/O 错误必须上报；新旧都通过。

`cargo test -p agent24-documents --locked --lib state::tests` → exit 101（2 个新测试失败，符合预期）。

## 4. GREEN（修复）

提交 `408d414`：`copy_database` 不再按文件复制，而由 SQLite 自己做一致快照：
用 `create_if_missing(false)` 打开源库（缺失即报错）→ 在竞态点关闭传入连接（此时它已
不是最后连接）→ `VACUUM INTO ?` 写出单个新 inode 文件 → 由于 `VACUUM INTO` 产物头部为
回滚日志模式（实测 header 18/19 = 1/1），再用该副本唯一连接设 `journal_mode=WAL` 并校验为
`wal` 后关闭，保持与原测试相同的 WAL 数据库形态，不留 sidecar。所有错误均原样返回；
不特判、不忽略 `NotFound`。原断言（`NotWritable`）、chmod 与特权检测逻辑全部保留。

额外验证（临时探针，未提交）：300 次“真实 `Pool::close` 后立即复制”，`-wal` 存在 261 次，
复制 300/300 成功且副本含迁移记录。
