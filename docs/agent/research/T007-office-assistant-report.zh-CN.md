# T007 OfficeAssistant 能力与交互研究

状态：v0.2 全量研究稿，整合原页面规划；未实施或验收。更新日期：2026-10-16（UTC）。[English full report](report.md)

**阅读基线**：本稿保留 v0.1 的能力、交互、技术、权限和验收研究。实现状态仍来自 2026-10-04 的固定源码快照（Agent24 `54cec44`、Components `667809a`），不是 2026-10-16 的最新代码审计。下文涉及“已有”“尚未接线”“默认”“当前 run”等实现描述均按该历史基线理解；实施前须复核。此次新增的是作者提供的页面规划、产品边界澄清、授权模型与演示验收细化，并提供内容对应的完整英文版，不宣称功能已上线。

## 结论

OfficeAssistant 建议作为 Agent24 基础办公套装中的助理能力层：把用户意图转换为可检查的计划、草稿、动作与回执，复用 Agent24 的运行、工具、审批、审计及记忆体系。优先研究“会议转写 → 纪要 → 行动项 → 确认 → 交付”一条完整链路，再复用其骨架到邮件、文档和知识检索。

2026-10-04 基线显示，最需要补齐的是可观察的任务闭环。Components 已有普通用户入口、五类流程说明和五份 Skill；本轮检查的 workspace server 尚无这些 Assistant 流程的执行端点。Agent24 已有 run、工具审批、取消和状态事件等底座，但当前产品路径的资源授权、workspace 绑定与出站治理仍有缺口。不能将说明页面或接口基础设施合并成“办公助理已可自主执行”的交付结论。[S01][S02][S08]

本稿只形成能力边界、交互方案、技术取舍和验证路线，不调整开发优先级。2026-10-04 的 Agent24 来源已明确记忆 M1/P0 为主线、P1 紧随其后；Open Design 在 M10 已集成，后续 OD-M11/TPI-W/OC 线暂停。OpenCreator 按作者方向是计划接入项，本题不重新展开这两个工具的独立调研。[S09]

### 原页面规划如何融入本研究

作者提供的页面主张是：“把重复的活儿交出去。每一件事做完之前，都会先等你点头。”这适合作为面向用户的信任承诺，但需要落实为可检验的交互与权限合同。建议研究中的精确定义是：**助理先准备可审阅的结果；涉及外部发送、远端修改或扩大访问范围时，按本次确认或已明确授予且仍有效的范围执行，超出范围再询问。** 用户已经要求的读取、整理、草稿生成，不必每个内部步骤重复打断；读取本身仍受资料访问权和处理目的地约束。原页面中的概括句可保留为历史规划，但正式发布时应配合这段解释，避免暗示每个低风险步骤必定弹窗或已授予的范围失效。

五类流程在 v0.1 已有覆盖。这次整合的增量不是再造一套功能清单，而是把“能做什么”对应到输入、可审阅产物、授权边界、回执和验证顺序。邮件出站、社区群发、Notion 读写和 LINE 明确列为需要配置/授权的能力；介绍页、Skill 文件或连接成功都不能替代实际授权，也不能证明生产可用。[S21]

会议流程作为**优先演示**：使用合成转写或已获授权、去标识的样本，无需客户真实数据即可验证“理解 → 草稿 → 人工修改 → 确认边界 → 交付/回执”的骨架。这是降低首次验证门槛的选择，不是声称其他四类不能演示。没有接真实服务时，界面须标明模拟交付，不能把本地演示说成 Notion/邮箱闭环已完成。

## 一 产品位置与概念边界

### 作者已经确认的结构

- Agent24 本身是基础 Office Suite，日常办公能力属于其基础定位。
- Sin90、Cos72 是按个人或组织场景加载的 OS。
- 邮件、Notion 等能力可以由自研或组合的基础模块提供。
- Workspace 的早期表述强调多动作工作流程；T004 后续澄清为已有应用的独立 UI 加完整工作流程，通过菜单嵌入套装，可选或推荐接入。基础模块是宿主可调用的工具动作，不要求先打开这个应用界面。[S22]
- Open Design 已集成，OpenCreator 计划接入；创作范围可以重叠。[S17][S18]

OfficeAssistant 是否最终成为菜单名、模块名或独立目录仍可调整；它的责任先定义为“理解任务、组织步骤、呈现确认、汇总结果”。默认无需加载 Sin90 或 Cos72 才能起草邮件或处理文档。组织共享资料、成员分工等专属语义再由 Cos72 提供；个人场景上下文可由 Sin90 提供。这是基于已确认产品结构的建议，不表示这两条接线已完成。

### 需要分开的 Workspace

报告中的“办公工作流程”是任务组织概念；产品 Workspace 是承载独立应用 UI 与流程的入口；Agent24 的 L2 workspace 则是文件系统根、租约和生命周期边界。此外还有 Cos72 社区工作台和组织记忆作用域的历史命名。几者可以关联，但不能因名称相同就共享权限、生命周期或状态机。[S09][S22]

建议助理任务界面用“任务/工作流程”，文件位置设置用“文件工作区”，独立应用入口保留具体应用名；不把一次后台工具调用包装成需要打开 Workspace 的流程。后端使用不同 ID，例如 workflow_id、run_id、workspace_id、artifact_id，明确关联而不合并。以上字段是建议的数据契约，不是已有 wire 的声明。

### 系统关系

| 部分 | 对 OfficeAssistant 的责任 | 当前应保留的边界 |
|---|---|---|
| Agent24 | 唯一执行控制面，持有 run、工具、审批、审计及工作区权限 | 助理不能另起绕过内核的执行通道 |
| 基础能力模块/连接器 | 读邮件、取资料、写页面等有界动作 | 安装、连接、读取、写入、持续授权分别披露 |
| Documenting | 读取、定向编辑、审阅、版本及导出服务，供助理与原生文档界面复用 | 只承担已约定的部分办公操作；产品级 Office 导入/导出与回流须单独验收，不追求完整 Office 替代 |
| Knowledge Base / Media Base | 在授权范围提供检索、来源、版本与资料处理服务 | 不替代文档原件/修订权威；默认上下文或索引成功不等于取得访问或发布权限 |
| 应用 Workspace | 提供独立应用 UI 与完整流程，可消费助理生成的产物 | 不成为基础工具调用的必选前置，也不拥有第二套审批权威 |
| Skill | 输入输出规则、步骤、质量约束与适用条件 | 文本指令本身不授予权限，也不证明连接器可用 |
| Sin90/Cos72 | 个人/组织场景语义及相关数据 | 基础办公不强制依赖 OS；跨作用域访问需授权 |
| iDoris | 目标模型网关与出站隐私执行者 | Agent24 的 iDoris provider 尚未接线；不能宣称已有统一隐私保证 |
| AgentEar | 可选语音入口及转写材料 | 第一轮可直接输入转写，避免把语音闭环作为前置 |
| Open Design/OpenCreator | 需要创作交付时的工作流程消费者或步骤 | 只定义任务与产物交接；不在本题扩展其开发 |
| Hyphae/Web3 | 后续可能的协作、通信或身份能力 | 本 MVP 不依赖、不启动、不据此承诺已集成 |

架构历史基线依据 Agent24 原仓库；Components 是导航和跨组件背景。[S08][S09] Documenting/KB 与应用 Workspace 的职责按 T004/T005/T006 的后续研究对齐。[S22][S23][S24] “默认内置、宿主可调用”描述用户体验，不预先裁决 Documenting 的进程内/外或 domain OS 实现归属；相关工程契约仍须在其主题内冻结。

## 二 能力范围

### 第一版建议交付什么

1. 会议材料转纪要和行动项。优先输入现成转写，输出纪要与结构化任务；每项保留 source_quote/材料位置，缺少负责人或日期时标“待确认”。来源未表达的承诺不能自动补全。
2. 邮件或消息转回复草稿。显示针对哪条来信、拟用哪个账号、哪些收件人、附件及具体正文；发送作为另一个动作。
3. 文档转行动项。对给定材料提取要求、期限和下一步，显示证据；不把文档中的第三方命令当作授权。
4. 研究资料转结构化摘要。限定来源范围，保留链接、日期和不确定性；不能把摘要成功当作外部事实已验证。
5. LINE 咨询转建议回复。第一阶段人工复制；连接渠道和业务系统是后续授权下的扩展。

前四类加 LINE 与已有五流程说明一致；具体交互、成功标准是本稿提议。现有五份 Skill 与五流程并非逐一对应：Skill 目录为 meeting-to-tasks、mail-draft、line-reply、notion-write、kb-ingest，不应声称每个流程已有独立执行实现。[S02][S03][S04][S05][S06][S07]

### 五类流程的输入、产物与外部动作

| 页面流程 | 可先完成的准备工作 | 需要明确授权的后续动作 | 可检查结果 |
|---|---|---|---|
| 会议 → 纪要 → 任务 | 合成/授权转写，纪要、决策和带出处的候选任务；缺负责人/日期则待确认 | 写入指定任务系统/Notion，或把纪要发给指定人员 | 本地产物版本；真实写入后另有目标链接、外部 ID 与结果状态 |
| 邮件 / 消息 → 起草回复 | 读取获授权的指定线程，形成回复草稿，列出引用与附件 | 在邮箱服务保存草稿、发送/回复、增加收件人或附加新资料分别按范围判定 | 草稿和发送回执分开；服务商接受不等于收件人已收到 |
| 文档 → 行动项 | 提取约定资料的要求、期限、负责人和来源位置 | 修改原件、提交新修订、同步远端任务、分享文件 | 来源版本、待确认字段、修改差异及相应提交回执 |
| 研究 → 结构化摘要 | 在选定公开/授权来源内形成问题、证据、结论、不确定性与下一步 | 用新私有资料查询第三方、共享/发布、写入目标库 | 来源链接和日期、事实/推断区分、缺失证据；摘要完成与发布完成分开 |
| LINE 咨询 → 建议回复 | 用户提供或已授权读取的咨询，加获授权知识资料，输出可人工复制的建议 | 连接指定 Official Account、读取 webhook、reply/push/broadcast 各自按范围授权 | 建议文本与依据；启用真实发送后记录目标、消息 ID/服务端结果及未知送达状态 |

“可先完成”仍以用户请求和已获资料/处理权限为前提，不表示自动读取整箱邮件、所有 Notion 页面或全部 LINE 会话。外部平台中的草稿也是一次远端写入，不能与本地预览混为一谈。四类授权敏感能力的具体合同见第五节。

LINE 在泰国的渠道价值可以作为场景选择理由，但不应把用户量直接当可触达客户数。LINE Thailand 于 2025-03-04 的官方公告披露 **截至 2024 年 6 月为 5,600 万 MAU**；LY Corporation 于 2025-05-30 的另一篇官方文章记载截至 2024 年 12 月为 5,400 万用户，两者未解释差异。因此本稿只引用带日期与口径的历史数值，不把“泰国 5,600 万用户”作为 2026 年实时规模或产品市场规模结论。[S25][S26]

### 首轮不承担什么

不新造邮箱、Notion 协作编辑器、CRM 或完整项目管理产品；尽量把产物交回既有工具。首轮不启用默认群发、无人值守外发、跨组织资料共享、自动付费或高风险决策。周期性任务与持续授权要作为单独功能设计，不能由一次“同意”隐含开启。

KB 作为读取和交付材料的位置需要明确访问范围。现有原型的 visibility 固定 public、分类的 embedding/LLM 分支未接实，不能直接用作多用户权限感知知识底座。public 字段不等于已公开发布，但同样不构成隔离保证。[S02][S07]

## 三 界面与交互期望

### 已有明确要求

Components 记录的用户原话要求普通用户首页解释“能做什么、怎么开始”，技术信息单独放到另一页。T004 也要求从用户任务出发，区分可用、试用与规划。Notion Skill 明确要求用户看见助理能访问哪些页面。上述方向可直接继承。[S01][S05][S17]

当前材料不能证明用户已经选择了聊天式、卡片式或三栏布局。下面是可用于评审的交互方案，不能写成作者已确认 UI。

### 建议的三个主视图

- 发起任务：一句话输入，添加材料或选已有资料，选交付去向；显示本次资料范围和“仅起草/确认后交付”。
- 任务详情：顶部一句话目标，中间步骤与当前状态，旁边或下方产物预览；随时能取消、改要求、查看需要确认的动作。
- 连接与权限：按账号/服务显示连接状态、允许访问的资源、允许动作、到期/撤销入口。技术页另放模型、成本、日志等排障信息。

普通界面使用“待你确认”“正在读取资料”“已保存草稿”“发送结果待核实”等任务语言，不要求用户理解 provider、token、MCP 或状态机。

### 七个必须可观察的语义

| 语义 | 用户看到什么 | 后端应保证什么 |
|---|---|---|
| 计划 plan | 将读取哪些材料、生成什么、哪些步骤会写入或发出 | 计划版本固定；新范围、新目标或实质内容变化需重新判断授权 |
| 动作 action | 一个动作的账号、目标、输入/差异、影响范围 | 每步有独立 action_id、尝试记录和关联 run；不把一段自然语言当执行凭据 |
| 审批 approval | 批准此步、修改、拒绝、停止；可选项由服务端提供 | 审批绑定具体动作与最终载荷版本；过期、拒绝、断线不得默认放行 |
| 取消 cancel | 已请求停止、已停止；同时列出已完成动作 | 取消停止未来工作，不声称撤销已发邮件或已写远端页面 |
| 重试 retry | 失败步骤、可安全重试的范围、已成功的步骤 | 不整条盲重放；有幂等键或先查询远端结果，结果未知时先核对 |
| 状态 status | 执行中、待确认、部分完成、受阻、结束 | UI 投影跟随内核权威状态；断线后重新查询，不靠本地动画判断成功 |
| 回执 receipt | 产物链接/版本、已执行步骤、失败或未知步骤、后续动作 | 批准、工具返回、服务商接受、实际送达分别记录 |

Agent24 已有计划审批接口、工具门禁、取消和 run 迁移，但上表完整业务语义仍需补齐和验收。[S12][S13][S14][S15]

特别注意三点：

- 批准计划不是无限授权。即使 plan 模式解锁了工具集合，外部动作仍应按风险、目标和实际载荷走各自门禁。
- 不混用 gate 与 advise。模块“已批准”只描述决策维度；初次 required 事件不含 executed_at，执行结果要另查。不能凭审批事件给用户显示“已发送”。[S14]
- 当前 run 终态只有 completed、failed、cancelled 等既有枚举，并且终态没有出边。“部分完成/结果未知/正在停止”可以是工作流程/连接器层的投影或新增契约；重试创建关联的新尝试，不原地复活已结束 run。[S13]

### 一个可评审的用户流程

用户上传一段转写：“整理纪要和待办，先给我看。”

助理展示计划：“读取这一份材料，生成纪要和行动项，暂不发给其他人。”随后逐项列出处，不明确的负责人和期限留空。

用户改正一项任务后要求写入某个 Notion 页面。界面显示账号、精确页面、实际变更内容、会离开本机的内容及访问范围。确认的是这次写入，不因此授予任意页面访问或长期同步权限。

写入后展示页面链接和版本/回执。若超时但远端可能已创建页面，状态为“结果待核实”，先查询去重；若其他步骤已成功，只重试未完成步骤。这是建议验收剧本，本轮没有连接账号或执行写入。

## 四 后端技术栈与选项

### 现有可复用基础

Agent24 实际实现是 Rust daemon；依赖含 Tokio、Axum，暴露 REST/WebSocket；store 使用 SQLite 并承载审计。桌面壳为 TypeScript、Electron、React、Vite。工具、MCP、policy、model router、memory 等属于已有内核服务。[S08][S10][S11]

Components workspace 是 Python 标准库 HTTP 原型；它适合说明产品、展示本地 KB 和技术实验，不能从 assistant_status 返回的 LangGraph/Postgres 字符串推导这些依赖已部署。[S01][S02]

### 推荐取舍

| 选项 | 适用场景 | 本稿判断 |
|---|---|---|
| Agent24 内核加薄工作流层 | 基础办公、单机、现有桌面整合 | 首选研究路线，复用权限与执行权威；业务步骤和 UI 投影需清晰分层 |
| 受监督的进程外模块 | OS 专属业务、希望单独发布的流程服务 | 可选；通过 os-proto/callback 接内核，不另建模型/工具绕过路径 |
| LangGraph 加独立状态存储 | 经验证确需图式编排、长等待恢复的复杂业务 | 仅作候选；先证明 Agent24 无法满足的缺口，避免双审批、双 run、双审计 |
| 另引入通用 Agent 框架替代内核 | 全栈重做 | 本题无此需要；与唯一控制面的既定关系不符 |

因此不建议仅因历史原型写了 Postgres 就增加数据库。若工作流先落 SQLite，可增加业务状态表或投影，但 schema、迁移、重启恢复与主 store 的边界需通过 ADR 决定，不能在前端另存一套权威审批结果。

模型侧沿用 Agent24 provider/router 接口。MiniCPM 是历史 Assistant 默认方向，但不在本题凭旧榜单锁定具体模型版本或能力；用实际会议抽取和多步工具评测决定是否需升级档位。本地模型不可用且用户选“仅本地”时应明确失败，不自动回落云端。[S08][S19]

这里还有一个真实接线差距：现有 LocalOnly 路由机制会拒绝远端，但主对话、子 agent、REST 聊天目前仍传默认 TaskProfile；不能只加一个“仅本地”开关而不贯穿到实际调用。Guardian 默认关闭，也不能拿“有 Guardian 代码”表示产品默认已经自动审查。[S08]

连接器选原生 API/MCP 或受控适配器均可，关键是权限、目标、幂等与回执契约。历史 resend-cli 不自动等于个人邮箱阅读/回复能力；账号身份、线程回复、草稿、发送权限和服务商 API 都需单独验证。Notion 也需核验最终工具的目标资源与写入行为，不能以“官方 MCP”四字代替集成验收。[S04][S05]

### 建议最小数据契约

工作流记录：目标、来源引用、计划版本、步骤依赖、关联 run、用户可见状态。
动作记录：工具/连接器、账号引用、精确目标、有效输入摘要、审批绑定、幂等键、尝试次数。
产物记录：类型、位置、版本/hash、来源证据、读写范围。
回执记录：业务结果、外部 ID/链接、确认时间、可否补偿、验证状态。
敏感正文保留在受控产物存储，常规事件和审计只记录必要元数据；对载荷作哈希绑定不意味着应该把完整正文写入日志。

这些是待冻结的 OfficeAssistant 契约字段，尚非 Agent24 已提供的 API。

## 五 权限和可靠性边界

### 四类需要明确授权的能力

以下是拟议产品合同，不是本次研究对任何实际账号的连接或发送授权。平台凭据只证明技术身份，不能替代用户业务授权。

| 能力 | 最小授权范围与用户需要看见的内容 | 准备与执行边界 |
|---|---|---|
| 邮件出站 | 发件账号、具体收件人/有界收件人集合、用途、最终正文与附件；持续授权另列期限、频率/数量边界与撤销方式 | 本地生成草稿、远端保存草稿、发送分别标识；改账号/受众/实质内容重新判定 |
| 社区群发 | 渠道、具体社区/群及名单快照、人数、内容版本、时机、频次/费用上限、取消截止点 | 预览/测试发送与全量发送分开；不能由“回复一个人”推导群发权限；首轮保留逐批确认和去重回执 |
| Notion 读写 | 选定连接类型、页面/数据库及继承子页面范围，读取/插入/更新能力分列，明确写入目标与差异 | 已授权读取无需每次重新确认；新范围先授权；写入按本次或有效范围授权，不能因已连接就写任意页面 |
| LINE | 指定 Official Account/channel、可读会话事件、reply/push/broadcast 动作、目标用户/群范围、有效期与额度 | 建议回复默认可人工复制；连接收信不等于允许发送；自动回复、主动推送和广播需要分别配置业务授权 |

Notion 官方文档分别定义 read/update/insert 等能力；连接共享父页面会包含相应子资源。必须显示有效范围，而非只显示父页面名称。内部连接需显式共享页面；公共 OAuth 连接有页面选择流程。个人 access token 的范围与用户工作区权限相关，不能把所有凭据都宣传为天然页面级最小授权。最终接入方式仍待选定与验收。[S29][S30]

LINE Messaging API 的 reply 使用 webhook 中的短时、单次 reply token；人工审阅或长时间生成后不能假设 token 仍可用。push 也有可发送对象限制；broadcast 面向该 Official Account 的好友，不是全体 LINE 用户。延迟后若 reply 不可用，应显示无法原路发送，只有在 push 资格与授权同时成立时才可另行执行。push/broadcast 涉及套餐配额；HTTP 200 不代表最终送达。不要把用户的“同意发送”扩大成替换渠道、扩大受众或不受限重试。[S27][S28]

### 便利与安全由可见的授权档位平衡

建议默认“仅准备 / 关键动作逐次确认”，可在验证后增加“有界委托”：用户明确选工具、账号、目标/受众、动作类别、资料/处理范围、有效期与用量边界，并随时可暂停/撤销。界面应说明现在用的是哪份授权、这次为何无需再次询问、结果在哪里。授权到期、撤销、超范围或最终载荷发生实质变化时应暂停，不能暗中改用另一渠道。

不必把“每个动作都点一次”当作永久产品限制，也不能把“更方便”当成无范围全权代理。第一轮 MVP 仍用逐次确认验证外部动作的门禁；持续授权是后续独立设计和验收项。增加权限、敏感资料外传、不可逆/高风险动作还须遵守适用平台政策与实际部署的安全要求，普通“自动”档位不能覆盖这些限制。此处提出选择机制，不宣称已经实现。

### 继承的安全与可靠性要求

1. 唯一权威。前端、Skill、MCP 描述和外部文档不能给自己扩大权限。内核仍裁决每次工具调用；安装器不能隐式获得风险豁免。[S12][S16]
2. 当前产品授权限制。默认 legacy bearer 全权；capability 令牌基础设施存在，但路由资源鉴权、事件过滤等未完成。桌面通用代理也有待隔离项。因此首轮可做可信本地材料与 mock connector 的验证，不开放不可信插件或组织共享执行面。[S08]
3. 文件安全。workspace-bound 的路径约束仅在对应路径下生效，当前默认产品路径尚有缺口；shell_exec 固定 cwd 不等于 OS 沙箱。连接器执行不能偷换成任意 shell 来绕过模型与权限边界。[S08][S09]
4. 出站分开治理。发往 LLM 的负载与邮件、Notion、HTTP、MCP 的直接出站是不同出口。本地推理不保证资料不外传；iDoris 尚未接线、非 LLM egress guard 尚有待实现项目时，不应承诺全链路脱敏已生效。[S09]
5. 审批最后有效载荷。先做必要隐私处理，再让用户看最终要发送的内容；批准后若收件人、页面、附件或正文实质变化，旧批准不能悄悄复用。脱敏不能擅自损坏业务含义，无法兼顾时阻塞并解释。
6. 最小目标授权。首次 MVP 逐次确认外部写入。若以后支持持续授权，按工具、具体目标、动作类别、有效期和撤销范围建模；不得把一次同意转成整段会话任意外发。2026-10-04 基线的 Agent24 已有 external 定向授权规则，但部分法律约束仍需机械化验证。[S16]
7. 可恢复不等于可撤回。保存草稿和带版本写入优先；发送、群发和不可逆操作保留单独门禁。取消与补偿是两件事，补偿本身也可能需要授权。
8. 事件不是交付证据。WebSocket 可掉线；客户端在重连后读取权威快照。当前 seq 是每连接单调，不应自行当作跨重连可靠全局游标。[S14]

## 六 研究 MVP 与验收

### R0 冻结体验和契约

用合成会议转写、模拟连接器和现有 Agent24 契约绘制任务详情、审批、断线、取消及回执。演示包应明确样本为合成数据，不包含客户真实资料、真实凭据或未经授权的账号；模拟动作和真实动作在界面上区分。产出状态映射和需要新增字段的清单。成功标准是评审者可以指出“将做什么、何时发生外部影响、现在停下会留下什么”。

### R1 本地材料完整链路

输入一份转写，完成纪要、行动项、来源引用、用户修改和本地交付。禁止捏造负责人/日期；缺证据项明确标待确认。至少保留一份可重复输入、期望纪要/任务、来源定位与实际输出；逐项核对任务遗漏、无依据承诺和人工修订保留情况，不用漂亮页面替代结果正确性。测试取消发生在读取、模型等待、审批等待和写入边界时的表现，以及重启后的状态恢复。

### R2 单个获授权连接器

由作者选一个邮箱或一个 Notion 测试目标，先只读或草稿，再在明确授权下做一次写入。首个连接器的选择暂不替用户决定。验收需实际账户范围、可控测试资料、结果查询及去重证据；研究报告不代替连接授权。

### R3 复用到第二条流程

复用同一动作/审批/回执骨架，再接邮件草稿或文档行动项。若第二个流程仍需重写审批和恢复机制，说明抽象尚未成立。其后再评估语音、OS 共享资料和多人协作。

### 最小反例验收表

| 情形 | 必须观察到的结果 |
|---|---|
| 用户拒绝、审批过期、无审批通道 | 外部动作未发生，状态明确且可解释 |
| 批准后修改目标或最终载荷 | 旧批准不放行新动作 |
| 外部服务成功后本地超时 | 先查询/对账，无重复邮件或重复页面 |
| 第一步成功、第二步失败 | 保留成功回执，仅重试必要步骤 |
| 执行中取消 | 后续步骤停止；已发生外部影响如实列出 |
| 重启或 WS 断线 | 恢复权威状态，不靠旧卡片再次发送 |
| 资料含越权指令 | 只作为材料处理，不扩大读取或发送范围 |
| 本地模型不可用 | 仅本地任务失败/等待，不偷切外部服务 |
| 试图访问未授权页面或路径 | 拒绝；不能从同名 workspace 推导权限 |
| 跨连接器出站绕过隐私层 | 测试失败并阻止启用该执行路径 |
| 撤销/过期的有界委托，或群发名单发生变化 | 暂停相关动作，重新检查授权；不以旧计划继续发送 |
| LINE 审阅后 reply token 已不可用 | 不盲重试或擅自转 push；说明限制并核对替代动作资格与授权 |
| Notion 父页面授权导致子页面可见 | 展示并核对实际继承范围；撤权后检索/写入也失效 |
| 模拟连接器返回成功 | 清楚标为演示结果，不报告真实远端写入或送达 |

建议按场景记录通过/失败、证据和复现步骤，安全反例不得以平均成功率掩盖。2026-10-04 进行的是静态源码核对；2026-10-16 进行的是文档整合及官方连接器资料核验，两轮都没有执行以上验收。

## 七 需要作者拍板的少量问题

- 第一版用户是谁：个人使用，还是 4seas 内部协作？两者直接影响共享权限范围。
- 会议流程优先做无客户数据的骨架演示；第一条实际外部闭环选邮件还是 Notion？用哪个账号和精确测试目标？
- “Assistant”准备作为基础首页入口，还是在统一输入框中按任务路由？可先用同一交互契约做两个视图评审。

- 默认逐次确认与后续有界委托的体验如何取舍？社区群发及 LINE 自动发送是否属于首发范围，还是先保持草稿/人工复制？

这些决定不阻止继续完善纯本地研究稿，但应在连接账号或启动开发前明确。MVP 研究顺序不表示重新排期；历史记忆主线与暂停安排仍须由相应项目的最新决议确认，本稿不擅自恢复。
