# REPRO #1020：内核 `kill -9` 后 documents 模块孤儿与 blob 锁

日期：2026-10-16。范围：只复现、只写本文件。没有改生产代码。

复现成功。默认启动方式下，issue 描述的现象在当前 main 的 debug 构建上仍然成立。

## 结论

Q1. 内核被 `kill -9` 后，按默认方式启动的 documents 模块**不退出**。第一次采样（`kill` 返回后约 0ms）PPID 已经是 1，15.044s 内 242 次采样全部存活，约 48s 时 `etime` 仍是 `00:48`，直到本复现主动 `kill -9` 它。issue 里「没有任何信号让它退出」对这条默认路径没有过时。

同一二进制在 stderr 改写到普通文件时，会在约 55ms 内打出 SDK 的 `callback connection lost` 并退出。默认路径不退出，是因为 stderr 是内核的管道，不是因为钩子根本不存在。

Q2. 孤儿活着时，它仍独占 `blobs/.lock`。新内核起来后 `GET /api/v1/documents/documents` 三次都是 HTTP **503**，响应体为：

```json
{"error":{"code":"storage_unavailable","details":{"cause":"locked","retryable":true},"message":"document storage is unavailable (locked)"}}
```

只杀掉这个孤儿、等 3 秒（超过 `REOPEN_INTERVAL` 的 2 秒），同一请求回到 **200** `{"documents":[],"next_cursor":null}`，锁改由新模块持有。

Q3. 两处：

- 内核侧收尾在 `rust/apps/agent24d/src/server.rs:1361-1397`（只登记 SIGTERM / SIGINT）和同文件 `1907-1915`（优雅停机时停模块进程组，并指望模块在回调 EOF 上自己退出）。`kill -9` 不可捕获，这两处都不会跑。`1364-1365` 的注释已经写明：信号的默认动作会留下模块。
- SDK 侧本该收尾的是回调 socket 读到 EOF 之后的默认钩子：`rust/crates/agent24-os-proto/src/rpc.rs:908-909`（空缓冲即 `FrameError::Eof`）→ 调用点 `rust/crates/agent24-os-proto/src/module.rs:544-556` → `declare_dead` `311-323` → `rust/crates/agent24-os-sdk/src/module.rs:53-57` 的 `warn!` 然后 `process::exit(70)`。documents 没有覆盖钩子（`rust/apps/agent24-documents/src/main.rs:28-30`）。设计决策在 `docs/design/ME4-S3-os-sdk.md:868-872`（Q10）。默认启动下这条 `exit(70)` 没有完成：钩子里的 `tracing::warn!` 写到已断的 stderr 管道，Rust 1.95 的 `eprintln!` 在 `stdio.rs:1165` panic，panic 发生在 tokio 任务里，`exit(70)` 被跳过，HTTP 服务继续占着锁。这个 panic 文本来自同编译器的微基准，不是从孤儿进程里抓到的。

「模块 stdin 是内核管道、内核一死就能读到 EOF」这个前提不成立。stdin 在 `rust/crates/agent24-os-proto/src/launch.rs:568` 写成 `Stdio::null()`，注释在 `483-485`。运行时 `lsof` 的 fd 0 在 kill 前后都是 `/dev/null`。用户消息里的路径 `rust/apps/agent24-os-proto/` 不存在，crate 在 `rust/crates/agent24-os-proto/`。`read_frame_async` 定义在 `rpc.rs:892`，不在 `module.rs`。

## 对照：stderr 改到文件时，钩子会在约 55ms 内退出

主复现之后，隔离包里的 `bin/agent24-documents` 被换成一个只存在于 `/tmp` 的 shell 包装（生产树没有改）。包装把真正的 debug 二进制挪到 `agent24-documents.real`，并用 `2>>` 把 stderr 追加到 `/tmp/a24-1020-repro/logs/module-stderr.log`。这是为了看见钩子日志。它不是 issue 的默认启动方式。

这次 daemon pid `7281`，port `62033`，token `46a7476bf86e079369a65a7c4a5faa7531fa38172fb34262317bec92a0c3ae4c`。基线 `GET` 为 200。模块 pid `7283`，PPID `7281`，命令行是 `agent24-documents.real`。

`kill -9 7281` 后，`gone_at=0.055s`。stderr 多出一行（时间戳 `2026-10-16T11:57:01.148237Z`，与包装启动 `18:57:01` 同一秒）：

```text
WARN agent24_os_sdk::module: callback connection lost; exiting so the supervisor restarts this module
```

这行就是 `agent24-os-sdk/src/module.rs:55` 的原文。默认管道上这行写不出去，所以主复现里看不到它，进程也不走完 `exit(70)`。

另有一次诊断（daemon `46045`）被记下来以免和主证据混在一起：驱动脚本和 `daemon.json` 的 pid 更新赛跑，等了 60 秒后杀掉的是 `script` 的进程组。daemon 是 pty 前台进程，`script` 退出时它收到的是 SIGHUP，不是 SIGKILL。那次模块同样打出了上述 WARN 并退出。它说明「stderr 可写时钩子能走完」，不能当作 `kill -9` 的计时。

## 微基准（解释为什么 `exit(70)` 没执行）

`/tmp/pipepanic`，edition 2021，依赖 tokio 1 与 tracing-subscriber 0.3，`rustc` 与上面相同，`--offline` 编到 `/tmp/pipepanic-target`。不进仓库。

形状：`tracing_subscriber::fmt()` 写到 stderr；tokio 任务里睡 200ms，然后按参数做 `tracing::warn!` 和/或 `eprintln!`，接着 `process::exit(70)`；主任务睡 3 秒后 `eprintln!("STILL_RUNNING")`。stderr 是管道，读端在 warn 之前关掉。panic hook 把信息追加到 `/tmp/pipepanic-panic.txt`。

三次结果：

```text
mode=warn     exited 101 in 3.708s
mode=eprintln exited 101 in 3.049s
mode=both     exited 101 in 3.051s
```

panic 文件（每种模式各两条，任务里一次、主任务的 `STILL_RUNNING` 再一次）：

```text
panicked at /rustc/59807616e1fa2540724bfbac14d7976d7e4a3860/library/std/src/io/stdio.rs:1165:9:
failed printing to stderr: Broken pipe (os error 32)
```

退出码是 101，不是 70。tokio 接住了任务里的 panic，`process::exit(70)` 没有跑到；进程一直活到主任务自己再打印、同样 panic。

对应源码：

- `tracing-subscriber` 0.3.23 `fmt()` 在 `fmt/mod.rs:473` 把 `log_internal_errors` 设为 `true`。
- 写失败时 `fmt/fmt_layer.rs:1051-1053` 用 `eprintln!` 打 fallback。
- Rust 1.95 `std::io::stdio::print_to` 在写失败时 panic（panic 文本指向 `stdio.rs:1165`）。Rust 忽略 SIGPIPE，所以断管道是 EPIPE 而不是直接被信号杀死。

documents 的对应关系：`main.rs:21-26` 把 tracing 打到 stderr，默认 info；`launch.rs:570` 把 stderr 接成内核排空的管道；`kill -9` 关掉读端。回调读任务在 `module.rs:532` `tokio::spawn`，EOF 后 `declare_dead` 调用钩子。钩子先 `warn!` 再 `exit(70)`。推断：这条 `warn!` 在断管道上 panic，任务 panic 被 tokio 接住，`exit(70)` 不执行，`main` 停在 `module.serve(...).await`（`main.rs:67`）。

支持这条推断、但不是孤儿自己的 backtrace 的观察：

- 另一次默认启动（daemon `64739`，模块 `64759`）在 `kill -9` 后 0.4s：进程仍在，PPID 1，回调 fd 10 已消失，`blobs/.lock` 仍被它持有。`sample` 显示父进程是 launchd `[1]`，主线程停在 `agent24_documents::main` `main.rs:67` → `tokio::runtime::block_on` → `kevent`，不在 `process::exit` 里。
- 上面的 55ms 对照证明钩子函数在 stderr 可写时确实跑到了 `warn!` 并且进程随后消失。
- 微基准证明同编译器上，tokio 任务里的 `warn!` / `eprintln!` 在断 stderr 上会在 `exit(70)` 之前 panic，进程以 101 继续活着。

没有从主复现的 pid `32506` 抓到 panic 文本：它的 stderr 就是那条已经断开的管道。也没有用 lldb 停在那个进程里。`Connection` 的 `Drop`（`module.rs:705-709`）会 abort 读写任务且不调用钩子；55ms 对照里 WARN 已经打出来，所以主路径不是「连接被静默 drop、钩子从未运行」。

## 排除掉的解释

- 模块没装上或没挂上：`/api/v1/os` 是 mounted，列表接口先返回过 200。
- 503 是死掉的代理或损坏状态：响应体 `cause` 是 `locked`；只杀孤儿、不重启第二轮 daemon，3 秒后同一 URL 回到 200，锁换到新模块。
- 锁被别的进程拿着：重启后 `lsof` 只有孤儿 pid。
- stdin EOF 能当退出信号：源码是 `Stdio::null()`，`lsof` fd 0 是 `/dev/null`。
- 钩子没编进这份二进制：stderr 改到文件时打出了钩子的那句 WARN，进程在 55ms 内消失。

## 没做到的

- 没有测 release 构建。panic 在预编译的 std 里，链接同一 rustc 的 release 二进制很可能同样行为。没有实测。
- 密集采样只覆盖 kill 后 15.044 秒。进程在约 48 秒（`etime 00:48`）时仍在，然后被本复现杀掉。没有观察分钟或小时级。退出不是「晚一点」，在观察窗口里它一直活着。
- 没有抓到孤儿进程自己的 panic 文本，也没有 lldb。Q3 里「`warn!` 在断管道上 panic、tokio 吃掉任务 panic」是源码加对照加微基准的推断。
- 现场没有从 stdout 读到 ready line；用的是 `daemon.json`。ready line 事后在 typescript 里。
- `~/.agent24` 目录 mtime 有变化。db、`os/`、`packages/` 的 mtime 没有变，`os.json` 不存在。
- 没有反汇编安装后的二进制。

## 给后续修复的建议（本次没有改代码）

默认启动下，回调 EOF → `exit(70)` 这条退路会被钩子里的 `tracing::warn!` 挡住：写失败的 `eprintln!` 在 `exit` 之前 panic。修的时候要让退出不依赖这次日志写成功（先 `exit`，或日志路径不要走会 panic 的 print 宏，或关掉 `log_internal_errors`，或在钩子里 `catch_unwind` 之后再 `exit`）。内核的 SIGTERM 处理帮不上 `kill -9`。stdin 不是可用的死亡信号。release 构建再跑一遍可以把「std 的 panic 在 release 用户 crate 里同样发生」从推断变成实测。
