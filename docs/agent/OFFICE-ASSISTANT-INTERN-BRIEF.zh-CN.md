## 1. 一页说清：做什么、M1、你的角色、你的边界

**我们在做什么。** Agent24 是一个本地优先（local-first）的 AI 代理平台。OfficeAssistant 是 Agent24 基础办公套件里的一层薄助手。它把一个请求（"把这次会议整理成纪要和待办，先给我看"）变成用户可以检查的计划、草稿、动作（action）和回执（receipt）。Agent24 的内核（kernel）仍然是唯一负责运行工具、请求批准（approval）、写审计日志的地方。我们**不是**在做一个新的邮件客户端、Notion 替代品、CRM 或项目管理工具。

**我们的承诺，精确化之后。** 面向用户的说法是：*"把重复的工作交出去。每件事完成前，都会等你批准。"* 可测试的版本是：助手先把结果准备好供审阅；任何向外发送数据、远端修改内容或扩大访问范围的操作，只在用户对**该具体动作**的确认之下执行（或在用户明确授予、且仍然有效的范围之内执行）。超出该范围就要重新询问。

**里程碑 1（OA-M1）：本地闭环。** 完全不接真实账号。我们使用合成的会议转录稿和一个 mock connector（模拟连接器）：

1. 输入转录稿 → 输出会议纪要 + 行动项。
2. 每一项都指向原文中确切的出处引文。
3. 缺少负责人或截止日期 → 标记为"待确认"。**绝不编造**会上没有说过的承诺。
4. 用户的编辑会被保留；重新生成不得覆盖它们。
5. 本地交付或模拟交付，回执上清楚标注 **"模拟"（simulated）**。
6. 取消、重试、断开连接和重启都要安全：不会重复发送，界面也绝不显示它无法证明的"成功"。

**你在 M1 负责的内容：**
- 合成的会议转录稿与"金标准"（gold standard）预期输出（泰语、英语以及混合语言会议）。
- 一个评测脚本，逐项比较实际输出与预期输出。
- 负例测试用例：拒绝、过期、批准后 payload 被改动、取消、重启、"藏在转录稿里的指令"。
- 演示脚本与验收记录（每个场景的通过/失败、证据、复现步骤）。
- 泰语界面文案审校。
- 你的反馈（第 3 节）。这和代码同样重要。

**你绝对不能做的事（硬性规则）：**
- 不做任何真实的对外操作：不发邮件、不写入 Notion、不在 LINE 上发消息，**哪怕只是"测试一下"也不行**。
- 不碰凭据：不创建、不存储、不复制、不转发 API key、token、OAuth 授权或密码。
- 不用生产数据：不用任何真实客户材料；也不用真实的会议录音或转录稿，**除非 jason 以书面形式提供了已去标识化的样本**。
- 不合并、不打 tag、不发布、不修改分支保护。
- 不得自行修改 `docs/laws/`、ADR，或内核的批准/审计/授权代码。你可以提 issue，也可以写涉及这些部分的测试。
- 不在 Mac mini 上运行任何东西。

**拿不准时：先问，不要猜。**

## 2. 协作约定

| 事项 | 约定 |
|---|---|
| 语言 | 所有书面工作、PR 和提问都用英语。测试数据和界面文案里欢迎使用泰语。 |
| 节奏 | 每周一次同步会（时间待商定），加上随时可以发的异步提问。预计一个工作日内回复。泰国与团队其他成员可能不在同一时区，所以凡是阻塞你的问题，请写明截止时间和时区。 |
| 分支 | 你在名为 `ab/office-assistant-NN-<short-name>` 的任务分支上工作（集成分支尚待批准）。永远不要以 `main` 为目标。 |
| PR 大小 | 默认 ≤ 300 行改动。如果无法拆分，请在 PR 描述中说明原因。 |
| 提 PR 前 | 运行 `AGENTS.md` 中的本地检查（Rust：`cargo fmt --check`、`clippy`、`test`；TypeScript：如果改动了 `apps/`，运行 `pnpm typecheck && pnpm lint && pnpm test`）。然后运行 `pre-pr-check.sh`，并在 PR 描述中按编号逐条回应每个命中项。 |
| 评审 | 每个 PR 都由 PR-Daemon（自动评审器）和一位人工评审。低风险 PR（测试数据、脚本、文档）在 CI 通过且检查项都已回应后即可合并。安全、权限、存储迁移和协议类 PR 需要 PR-Daemon 明确给出 APPROVE。合并由维护者操作，不由你操作。 |
| 提交 | 用你自己的身份提交。PR 被批准之后，未经询问不要再推送新提交，因为这可能使已有的批准失效。 |
| 测试数据 | 每个合成文件的第一行都是 `SYNTHETIC — not real people or companies`。使用虚构的人名和公司名。 |
| 提问 | 如果需求有歧义，写下你看到的两种理解，问清楚指的是哪一种。不要默默选一种。 |

## 3. 我们希望你反馈的问题

请用第 4 节的模板作答。简短回答就可以。"我不知道"也是有效且有用的回答。

### (a) 优先级
- **A1.** M1 的功能顺序如下：(1) 合成数据 + 金标准 → (2) 带出处引文的抽取 → (3) "待确认"标记 → (4) 编辑保留 → (5) 批准卡片 + 模拟交付 → (6) 取消/重试/重启 → (7) 任务详情界面。你会把哪些提前或推后？为什么？
- **A2.** M1 是否缺少某个泰国办公用户第一天就会期待的功能？
- **A3.** M1 里有没有哪项在现阶段不值得做？
- **A4.** 第一个真实连接器（M2）在邮件和 Notion 之间二选一。由 jason 决定，但对你认识的人来说哪个更重要？为什么？

### (b) 泰国职场与沟通习惯
- **B1.** LINE 在泰国职场中扮演什么角色（团队群聊、客户联系、审批、分享文件）？用的是个人 LINE、LINE Official Account、LINE WORKS，还是混用？
- **B2.** 会议纪要通常怎么写、怎么分享（格式、谁来写、会后多久、通过什么渠道）？一个"正常"的行动项是什么样的：是否总有负责人和日期？
- **B3.** 在泰语会议中，负责人和截止日期通常如何表达？例如：间接指派、敬称或昵称（ชื่อเล่น）、佛历年份（พ.ศ.）、相对日期。其中哪些会让抽取模型困惑？
- **B4.** 当任务是以含蓄或客气的方式指派时，助手应该标记为"待确认"还是视为已指派？怎样会让人感觉得体而不是尴尬？
- **B5.** 混合语言会议（泰语/英语，或有说中文的人）：我们的测试数据应该包含哪些模式？
- **B6.** 跨时区、跨语言协作：通常会出什么问题？
- **B7.** 界面措辞："等待你的确认"、"结果需要核实"、"模拟"在泰语里应该怎么写，才能既清楚又礼貌？请给出建议措辞。
- **B8.** 这些习惯会如何改变我们的功能优先级（例如，LINE 建议回复是否应该提前）？

### (c) 流程改进
- **C1.** 每周一次同步加异步提问，这个评审节奏适合你吗？什么方式会更好？
- **C2.** 只有英文的文档是否构成障碍？关键决策的泰语摘要会有帮助吗？
- **C3.** 你希望验收怎么进行：现场演示、录屏、书面证据，还是组合？
- **C4.** 你希望以什么方式收到对你工作的反馈（PR 评论、通话、书面总结）？
- **C5.** 本简报中有没有不清楚或自相矛盾的地方？

### (d) 在泰国做这件事的坑
- **D1.** 你所知道的法律或合规问题（例如 PDPA 与会议转录稿中的个人数据、职场录音的同意）。
- **D2.** 语言与文本处理的坑（泰语词与词之间没有空格、泰文数字、日期格式、人名）。
- **D3.** 平台方面的坑（LINE 账号类型、企业认证、消息配额或费用、职场工具限制）。
- **D4.** 自动消息中可能让用户难堪的文化坑（语气、层级、正式程度）。
- **D5.** 其他你认为我们会做错的地方。

## 5. 术语表

| 术语 | 在本文中的含义 |
|---|---|
| Kernel（内核） | Agent24 的 Rust 守护进程。运行、批准、审计和权限的唯一权威。 |
| Run（运行） | 内核中的一次执行。已结束的 run 永不重启；重试会创建一个新的 run。 |
| Action（动作） | 一个会产生效果的步骤（例如"发送这封邮件"）。每个 action 有自己独立的批准。 |
| Receipt（回执） | 实际发生了什么：已批准 / 已派发 / 已被服务方受理 / 已核实。这些是不同的事情。 |
| Mock connector（模拟连接器） | 一个假的邮件/Notion/LINE，永远不会联系真实服务。它的结果总是标注为"模拟"。 |
| LocalOnly（仅本地） | 不得离开本机的数据，包括不得发往云端 AI 模型。会议内容默认是 LocalOnly。 |
| Gold standard（金标准） | 针对某个测试输入、由人写出的预期正确输出。 |
