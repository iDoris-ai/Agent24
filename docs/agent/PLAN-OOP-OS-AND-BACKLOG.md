## 一、这个目标必须等 ME-3 —— 这是实测，不是推断

【实测】磁盘上的包只要写 `impl_kind: out_of_process`，**今天在挂载时被硬拒**：

- `rust/apps/agent24d/src/domain.rs:727` → `if !manifest.is_mountable_in_process()` 直接拒绝
- `rust/crates/agent24-domain/src/lib.rs:705` → `is_mountable_in_process()` 只对 `InProcessCrate` 返回 true，注释原文：*"ME-3's transport does not exist yet, so the in-process mounter MUST refuse it rather than half-mount a config it cannot honor"*

而 ME-3a（已合）交付的是**发现 + 安装**：`agent24 os install <目录>` 能把包放进 `~/.agent24/packages/`，daemon 下次启动会扫到它。**扫到 ≠ 装得上** —— 扫到的进程内包必须是编译进内核的 crate，扫到的进程外包会被拒。所以今天磁盘安装这条路对第三方是空的。

### Sin90 需要哪几刀 —— 比整个 ME-3 少一刀

【实测】`rust/crates/agent24-sin90-os/domain-os.yml`：

```yaml
kernel_capabilities: [events]      # 只有 events
data_dir: ~/.agent24/os/sin90/     # 自己管数据,不用内核记忆
```

**所以 Sin90 进程外化不需要 ME-3d（记忆回调）。** 这一刀是全 ME-3 里否定用例最多、最难的一刀（租约、配额、分区键、`private/*` 拒绝租约字段……）。

## 四、两个决策的上下文

### 决策一：hyphae 的那行 SQL

【实测】机制：`agent.go:208-238` 先 `relay.Publish` 后 `StoreOutgoingMessage`。若 daemon 恰在 3s 订阅窗口内收到自己发的消息并写成 `is_incoming=1`，发送方随后的 `INSERT OR REPLACE` 会把它**覆盖回 0**，而 daemon 的 `seen` 已记下该 id 不会再处理 → 这条消息在本地库里永远是「出站」。

【实测】本地 minirelay：`sent=105 confirmed=2 lost=94`（≈2%）；`messages.db` 里含 canary 的行 `is_incoming=0` 有 130 条、`=1` 有 11 条。后果：`degraded_transitions` 持续增长，**F5 判据 6（入站通路活性）不可能通过**。

修法本身：让 upsert 的 `is_incoming` 单调（`ON CONFLICT(id) DO UPDATE SET is_incoming = messages.is_incoming OR excluded.is_incoming`），或发布前先落库。**注意「一行」是低估** —— `INSERT OR REPLACE` 是 delete-then-insert，其他列也会一起丢。

| 选项 | 做什么 | 代价 |
|---|---|---|
| **A** | 本地打补丁 + 重编 + 验证，不提交上游 | F5 立刻能跑；修复只活在我们机器上，上游仍坏，别人复现不了我们的结果 |
| **B** | 打补丁 + 给上游开 PR | 做对了；F5 要等另一个仓库的评审来回 |
| **C** | 不打补丁，换公共 relay + 拉长 canary 间隔 | **⚠️ 我此前把 C 说得可行，那是没有依据的**（见下） |

**对 C 的更正【判断】**：我之前建议「用公共 relay + canary 间隔拉到 15 分钟」，理由是远端 relay 往返慢、竞态窗口小。**这条从来没有被测过。** 而且按现有数字算：单次确认率 2%，`staleAfterMs = 3×间隔` 意味着要三次里至少中一次，`1-0.98³ ≈ 6%` —— **拉长间隔并不改变单次赢面，C 按我原来的说法站不住。** 若要保留 C，先做一次实验：在公共 relay 上发 100 条 canary 量确认率（约 10 分钟），**确认率高才谈 C**。

【判断】我的建议是 **A**，理由是它把「F5 能不能跑」和「上游什么时候接受补丁」解耦；随后再走 B，把补丁和那条契约测试一起提上去（FU-33 里已经写明：那条契约上游没有任何测试守着，一次重构就能静默作废 Agent24 的活性判据）。

### 决策二：Mac mini 什么时候起

- 它做什么：F5 是 **7 天泡测**，两台机器同时跑能把「只在这台机器上成立」的结论排除掉。runbook 已在 `docs/SOAK-F5.md`，本机那套准备（二进制、LaunchAgent、无密码 identity、oMLX、两条 schedule、端到端 `agent24 chat` 2.4s）已经跑通过一遍。

## 六、能装 Node.js 写的 OS 吗 —— 设计上可以，但今天缺一个字段

【判断】边界是**一个进程 + 一份 wire 协议**，没有任何一处是 Rust 特有的：内核 spawn 一个子进程、按 `/api/v1/<ns>/*` 把 HTTP 原样代理给它、用 NDJSON over UDS 走回调。模块用什么语言写，内核看不见也不该看见。

【实测，2026-09-10；此后已由 manifest 的 `spawn` 字段解决 —— 探针会告诉你它在不在】**当时没有任何地方能说出"怎么启动它"。** `RawManifest` 的 13 个字段（`rust/crates/agent24-domain/src/lib.rs`）里没有 spawn 命令：

```
name / version / route_namespace / event_module / data_dir /
requires_models / requires_apis / requires_deps / kernel_capabilities /
ui_entry / impl_kind / manifest_version / min_daemon_protocol
```

SPEC 的 ME-3a 那行写了「manifest 支持 `impl_kind: out-of-process` **+ spawn 命令**」，**后半没实现** —— ME-3a 交付的是发现、安装与门 6。

**所以 T3（3b-3 spawn + 监督）的第一件事是给 manifest 加这个字段**（**已做**，见探针 `3b-3 manifest spawn 字段` 一行；该字段落地时还带了一条**超出 SPEC 的规则**，见下），而它的形状直接决定 Node.js 能不能装：

- 只允许一个可执行文件路径 → Node 模块要自带一个 wrapper 脚本
- 允许 `command + args`（如 `node`, `["server.js"]`）→ Node/Python/任何语言直接可写

【判断】**取后者**，理由不是灵活性，是前者会把「用什么语言写」变成一件需要绕过去的事，而绕法（wrapper 脚本）比字段本身更难审。

### 这个字段是执行边界，所以 FU-41 必须在它之前闭

manifest 里一旦能指名一个要执行的程序，**谁能写这个 manifest 就等于谁能让 daemon 执行任意命令**。FU-41（ephemeral packages root 没有所有权/权限校验）今天的代价只是「污染拒绝列表」，加上这个字段之后就是执行边界 —— 台账里已经写明「不要用『路径不可猜』当作已修」。

## 七、「领域 OS」还是「角色场景 OS」—— 一个比 ME-3 更重要、且与它正交的决定

用户 2026-09-10 提出：OS 不只是一个领域数据模型，**它是业务场景 / 特定角色的 OS** —— 面向普通打工人的、面向个体的、面向设计师的，是不一样的 OS。

**这个说法和今天的架构在一件事上不一致：谁拥有名词。**

### 【实测】今天内核拥有什么

```
agent24-agent    agent-loop        agent24-models    模型路由
agent24-memory   记忆底座          agent24-scheduler 调度
agent24-policy   审批/风险         agent24-tools     工具
agent24-store    存储              agent24-worker    执行
```

**全是运行时能力，没有一个领域名词。** 没有 task、没有 calendar、没有 contact、没有 project。Sin90 的 direction / rhythm / task 是**它自己的**，存在它自己的 `data_dir` 里。

### 于是有一个具体症状

一个人同时装了「打工人 OS」和「设计师 OS」：

- 【实测】`mount_all` 遍历整个 catalogue，**两个都会被挂载、都在服务路由、都在发事件**。没有任何字段能表达「这两个是同一个人的两副镜片，一次只激活一副」。
- 两个 OS 各有自己的 `data_dir` → **两份任务列表、两份日程**。那不是「一个人的两个角色」，那是两个 App。

`kernel_capabilities` 说的是模块**能做什么**，不是它**为谁而做**；manifest 里也没有任何字段说得出受众、角色或场景。

### 三种架构，是三个不同的产品

| | 谁拥有领域名词 | 两个角色 OS 共存时 | 代价 |
|---|---|---|---|
| **A. OS = 垂直栈**（今天的形状） | 每个 OS 自己 | 各有各的数据，互不相干 | 适合互不相交的领域（Sin90 个人 / Cos72 社区）；**不适合一个人的多个角色** |
| **B. OS = 编排层** | **内核**拥有 task/calendar/memory 等名词，OS 定义流程、提示词、策略、界面 | 天然共存：两副镜片看同一批任务 | 内核要长出领域名词（大改），且必须先有 Models + Scheduler 句柄 |
| **C. 垂直栈 + 共享总线** | 各自拥有，靠显式授权/事件互读 | 能共存，但要两两对接 | 从今天出发最便宜；风险是 N² 集成 |

**用户描述的那个 OS 指向 B。** 而今天的实现是 A。

### 为什么这件事现在就要定，尽管它不在 ME-3 的链上

ME-3 决定「能不能装」，**不决定「谁拥有名词」** —— 走完 ME-3，A/B/C 三种都还能选。所以它不挡 v0.5.0。

**但它挡 Sin90 的存储 schema。** 如果方向是 B，Sin90 就**不该拥有 task** —— 它该拥有 direction / rhythm 这些它独有的概念，task 从内核读。而数据所有权是最贵的那种迁移：等 Sin90 的表结构定型、有了真实数据再改，成本比现在高一个量级。

### 【判断】我的建议

**先做 C，把 B 当方向。** 理由：

1. **B 的前提今天不存在。** 内核要长出领域名词，而它连 Models / Scheduler 的句柄都还没有（`KernelCtx` 只有 `events()` 和 `memory()`）。直接上 B = 在没有编排能力的内核里先塞进领域名词，顺序反了。
2. **A 走不到 B。** 每个 OS 各存各的，数据越攒越多，迁移成本单调上升。
3. **C 是唯一一条不用现在下注的路**：OS 仍拥有自己的数据，但**跨 OS 的读取必须显式授权、走内核**。哪些名词被反复跨 OS 读取，会自己浮出来 —— 那批就是 B 里该由内核拥有的名词。**让证据决定，而不是让我现在猜。**

**需要立刻做的一件小事**：manifest 加一个**受众/场景**字段（如 `audience: [worker, designer]`），并明确 `mount_all` 今天把所有已装模块同时挂起 —— **「这两个是替代关系」这件事今天说不出来**。这是 B 和 C 都需要的第一块砖，且不依赖任何 ME-3 的刀。

### 用户已裁决（2026-09-10）

**取 B（延后）**：`Models` + `Scheduler` 的回调**不进 ME-3**，留到 v0.6。v0.5.0 只保证「能装、能代理、能发事件、能用记忆」。

> 注意这里有两个不同的 B：上一段的「B 架构」（内核拥有名词）和这条裁决里的「选项 B」（编排能力延后）。裁决说的是后者。**两者不冲突** —— 编排能力延后，正好给「哪些名词该由内核拥有」留出用证据回答的时间。
