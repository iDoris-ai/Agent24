## 1. สรุปในหนึ่งหน้า: เราสร้างอะไร, M1, บทบาทของคุณ และขอบเขตของคุณ

**เรากำลังสร้างอะไร** Agent24 เป็นแพลตฟอร์ม AI agent ที่ทำงานบนเครื่องของผู้ใช้เป็นหลัก (local-first) ส่วน OfficeAssistant คือระบบผู้ช่วย (thin assistant layer) ที่ฝังอยู่ในชุดโปรแกรมออฟฟิศพื้นฐานของ Agent24 ทำหน้าที่เปลี่ยนคำขอ (เช่น "ช่วยทำรายงานการประชุมและรายการสิ่งที่ต้องทำจากการประชุมนี้ ให้ฉันดูก่อน") ให้เป็นแผนงาน ร่างข้อมูล รวมทั้ง action (ขั้นตอนการทำงาน) และ receipt (หลักฐานการทำรายการ) ที่ผู้ใช้ตรวจสอบได้ โดย kernel (แกนกลางของระบบ) ของ Agent24 ยังคงเป็นที่เดียวที่รันเครื่องมือ ขอ approval (การอนุมัติ) และเขียนบันทึกการตรวจสอบ (audit log) เรา**ไม่ได้**สร้างโปรแกรมอีเมลใหม่ ไม่ได้สร้างสิ่งที่มาแทน Notion ไม่ได้สร้าง CRM และไม่ได้สร้างเครื่องมือบริหารโครงการ

**คำมั่นสัญญาของเรา ที่ชัดเจนและเที่ยงตรง** ข้อความที่สื่อสารกับผู้ใช้คือ: *"ปล่อยให้งานซ้ำ ๆ เป็นหน้าที่ของเรา คุณเพียงแค่ตรวจสอบและอนุมัติในขั้นตอนสุดท้ายของแต่ละงาน"* ส่วนฉบับที่ทดสอบได้คือ: ผู้ช่วยจะเตรียมผลลัพธ์ไว้ให้ตรวจทานก่อน การกระทำใดก็ตามที่ส่งข้อมูลออกไปภายนอก แก้ไขสิ่งใดในระบบปลายทาง (remote) หรือขยายสิทธิ์การเข้าถึง จะเกิดขึ้นได้ก็ต่อเมื่อผู้ใช้ยืนยัน action นั้นโดยเฉพาะเท่านั้น (หรือตามขอบเขตการเข้าถึง (scope) ที่ผู้ใช้ยินยอมอย่างชัดเจนและยังมีผลบังคับใช้) สิ่งใดที่อยู่นอกขอบเขตนั้นต้องถามผู้ใช้ใหม่อีกครั้ง

**Milestone 1 (OA-M1): วงจรการทำงานภายในเครื่อง (local loop)** ไม่ใช้บัญชีจริงใด ๆ เลย เราใช้บทถอดความการประชุม (transcript) ที่จำลองขึ้นมา (synthetic) และ mock connector (ตัวเชื่อมต่อจำลองที่ไม่ติดต่อบริการจริง):

1. ป้อน transcript เข้าไป → ได้รายงานการประชุม (meeting minutes) + รายการสิ่งที่ต้องทำ (action items) ออกมา
2. ทุกรายการต้องชี้กลับไปยังข้อความต้นฉบับที่ตรงกันทุกคำ (exact source quote)
3. หากไม่มีผู้รับผิดชอบหรือวันครบกำหนด → ทำเครื่องหมายว่า "รอการยืนยัน" (needs confirmation) **ห้ามคิดข้อผูกมัดขึ้นมาเองโดยเด็ดขาด** ถ้าในที่ประชุมไม่มีใครพูดหรือรับปากไว้จริง
4. การแก้ไขของผู้ใช้จะถูกเก็บรักษาไว้ การสร้างผลลัพธ์ใหม่ (regenerate) ต้องไม่เขียนทับการแก้ไขเหล่านั้น
5. การส่งภายในเครื่องหรือการส่งแบบจำลอง โดยมี receipt ที่ระบุอย่างชัดเจนว่า **"simulated" (โหมดทดลอง ไม่ได้ส่งจริง)**
6. การยกเลิก การลองใหม่ (retry) การตัดการเชื่อมต่อ และการรีสตาร์ต ต้องทำงานอย่างปลอดภัย: จะไม่มีการส่งข้อมูลซ้ำสองครั้งอย่างแน่นอน และหน้าจอต้องไม่แสดงว่าสำเร็จหากพิสูจน์ไม่ได้

**สิ่งที่คุณรับผิดชอบใน M1:**
- transcript การประชุมจำลอง และผลลัพธ์ที่คาดหวังแบบ "gold standard" (คำตอบมาตรฐานที่มนุษย์เขียน) สำหรับการประชุมภาษาไทย ภาษาอังกฤษ และหลายภาษาปนกัน
- สคริปต์ประเมินผล (evaluation script) ที่เปรียบเทียบผลลัพธ์จริงกับผลลัพธ์ที่คาดหวังทีละรายการ
- กรณีทดสอบเชิงลบ (negative test cases): การปฏิเสธ การหมดอายุ การเปลี่ยน payload (ข้อมูลที่จะถูกส่ง) หลังได้รับ approval แล้ว การยกเลิก การรีสตาร์ต และ "คำสั่งที่ซ่อนอยู่ใน transcript"
- สคริปต์การสาธิต (demo script) และบันทึกการตรวจรับ (acceptance record) ได้แก่ ผ่าน/ไม่ผ่าน หลักฐาน และขั้นตอนการทำซ้ำสำหรับแต่ละสถานการณ์
- การตรวจทานข้อความภาษาไทยบนหน้าจอ (Thai UI copy)
- ความคิดเห็นของคุณ (หัวข้อที่ 3) ซึ่งสำคัญพอ ๆ กับโค้ด

**สิ่งที่คุณห้ามทำ (กฎเด็ดขาด):**
- ห้ามดำเนินการใด ๆ ที่ส่งออกไปภายนอกจริง: ห้ามส่งอีเมล ห้ามเขียนข้อมูลลง Notion และห้ามโพสต์บน LINE **แม้จะเป็น "แค่ทดสอบ" ก็ตาม**
- ห้ามเกี่ยวข้องกับข้อมูลรับรองตัวตน (credentials): ห้ามสร้าง ห้ามจัดเก็บ ห้ามคัดลอก และห้ามส่งต่อ API key, token, การอนุญาต OAuth (OAuth grant) หรือรหัสผ่าน
- ห้ามใช้ข้อมูลจริงจากระบบที่ใช้งานอยู่ (production data): ห้ามใช้เอกสารของลูกค้าจริง และห้ามใช้ไฟล์บันทึกเสียงหรือ transcript การประชุมจริง **เว้นแต่ jason จะให้ตัวอย่างที่ลบข้อมูลระบุตัวตนแล้ว (de-identified) เป็นลายลักษณ์อักษร**
- ห้าม merge ห้าม tag ห้าม release และห้ามเปลี่ยน branch protection ใด ๆ
- ห้ามแก้ไข `docs/laws/`, ADR หรือโค้ดส่วน approval/audit/การอนุญาตสิทธิ์ (authorization) ของ kernel ด้วยตนเอง คุณสามารถเปิด issue และเขียนการทดสอบที่เกี่ยวข้องกับส่วนเหล่านี้ได้
- ห้ามรันสิ่งใดบน Mac mini

**เมื่อไม่แน่ใจ: ให้ถามก่อน อย่าเดา**

## 2. ข้อตกลงในการทำงานร่วมกัน

| หัวข้อ | ข้อตกลง |
|---|---|
| ภาษา | ใช้ภาษาอังกฤษสำหรับงานเขียนทั้งหมด PR และคำถาม ยินดีให้ใช้ภาษาไทยในข้อมูลทดสอบและข้อความบนหน้าจอ (UI copy) |
| จังหวะการทำงาน | ประชุมซิงก์ (sync) สัปดาห์ละหนึ่งครั้ง (เวลาจะตกลงกันอีกครั้ง) และคุณสามารถฝากคำถามแบบ async ได้ตลอดเวลา โดยปกติจะได้รับคำตอบภายใน 1 วันทำการ เนื่องจากไทยกับสมาชิกคนอื่นในทีมอาจอยู่คนละเขตเวลา หากมีคำถามใดที่ทำให้งานของคุณติดขัด (blocking) โปรดระบุกำหนดเวลา (deadline) และเขตเวลา (time zone) ให้ชัดเจนเสมอ |
| Branch | คุณทำงานบน task branch ที่ตั้งชื่อว่า `ab/office-assistant-NN-<short-name>` (อยู่ระหว่างรอการอนุมัติ integration branch) ห้ามตั้ง `main` เป็น branch ปลายทาง (target) ของ PR โดยเด็ดขาด |
| ขนาดของ PR | โดยปกติไม่เกิน 300 บรรทัดที่เปลี่ยนแปลง หากแยกย่อยไม่ได้ โปรดอธิบายเหตุผลในคำอธิบาย PR (PR body) |
| ก่อนเปิด PR | รันการตรวจสอบภายในเครื่องตามที่ระบุใน `AGENTS.md` (Rust: `cargo fmt --check`, `clippy`, `test`; TypeScript: `pnpm typecheck && pnpm lint && pnpm test` หากคุณแก้ไขไฟล์ใน `apps/`) จากนั้นรัน `pre-pr-check.sh` และตอบทุกประเด็นที่พบในคำอธิบาย PR โดยอ้างหมายเลขของแต่ละประเด็น |
| การรีวิว | ทุก PR จะได้รับการรีวิวโดย PR-Daemon (ระบบรีวิวอัตโนมัติ) และโดยมนุษย์ PR ที่มีความเสี่ยงต่ำ (ข้อมูลทดสอบ สคริปต์ เอกสาร) สามารถ merge ได้หลังจาก CI ผ่าน (เป็นสีเขียว) และตอบประเด็นการตรวจสอบครบแล้ว ส่วน PR ด้านความปลอดภัย สิทธิ์การเข้าถึง การย้ายข้อมูลในที่จัดเก็บ (storage migration) และโปรโตคอล ต้องได้รับ APPROVE อย่างชัดแจ้งจาก PR-Daemon ผู้ดูแล (maintainer) เป็นผู้ merge ไม่ใช่คุณ |
| Commit | ทำ commit ด้วยตัวตน (identity) ของคุณเอง หลังจาก PR ได้รับการอนุมัติแล้ว ห้าม push commit ใหม่โดยไม่ถามก่อน เพราะอาจทำให้การอนุมัตินั้นเป็นโมฆะ |
| ข้อมูลทดสอบ | ไฟล์จำลองทุกไฟล์ต้องขึ้นต้นด้วยบรรทัดหัว `SYNTHETIC — not real people or companies` และใช้ชื่อบุคคลและบริษัทที่แต่งขึ้น |
| การถามคำถาม | หากข้อกำหนดกำกวม ให้เขียนการตีความสองแบบที่คุณเห็น แล้วถามว่าหมายถึงแบบใด อย่าเลือกแบบใดแบบหนึ่งเองโดยไม่แจ้ง |

## 3. คำถามที่เราอยากได้ความคิดเห็นจากคุณ

โปรดตอบโดยใช้แบบฟอร์มในหัวข้อที่ 4 ตอบสั้น ๆ ได้ คำตอบว่า "ไม่ทราบ" ก็เป็นคำตอบที่ใช้ได้และมีประโยชน์

### (a) ลำดับความสำคัญ
- **A1.** ลำดับฟีเจอร์ของ M1 มีดังนี้: (1) ข้อมูลจำลอง + gold standard → (2) การสกัดข้อมูล (extraction) พร้อมข้อความอ้างอิงจากต้นฉบับ → (3) การทำเครื่องหมาย "รอการยืนยัน" → (4) การเก็บรักษาการแก้ไขของผู้ใช้ → (5) การ์ดขอ approval + การส่งแบบจำลอง → (6) ยกเลิก/ลองใหม่/รีสตาร์ต → (7) หน้าจอรายละเอียดงาน (task-detail UI) คุณจะย้ายข้อใดให้เร็วขึ้นหรือช้าลง และเพราะเหตุใด
- **A2.** M1 ยังขาดฟีเจอร์ใดบ้าง (ถ้ามี) ที่คนทำงานออฟฟิศในไทยคาดว่าต้องมีตั้งแต่วันแรก
- **A3.** มีสิ่งใดใน M1 ที่ยังไม่คุ้มที่จะทำในขั้นนี้หรือไม่
- **A4.** สำหรับ connector (ตัวเชื่อมต่อกับบริการภายนอก) ตัวแรกที่จะใช้จริง (M2) ตัวเลือกคืออีเมลหรือ Notion แม้ว่า jason จะเป็นคนตัดสินใจ แต่สำหรับคนที่คุณรู้จัก คิดว่าตัวเลือกไหนน่าจะสำคัญหรือตอบโจทย์พวกเขามากกว่ากัน และเพราะอะไร

### (b) วัฒนธรรมการทำงานและการสื่อสารในที่ทำงานของไทย
- **B1.** LINE มีบทบาทอย่างไรในการทำงานในประเทศไทย (แชทกลุ่มของทีม การติดต่อลูกค้า การอนุมัติ การแชร์ไฟล์) ใช้ LINE ส่วนตัว, LINE Official Account, LINE WORKS หรือใช้ผสมกัน
- **B2.** โดยทั่วไปมีการเขียนและแชร์รายงานการประชุมอย่างไร (รูปแบบ ใครเป็นผู้เขียน เขียนหลังประชุมเร็วแค่ไหน ผ่านช่องทางใด) action item ที่ "ปกติ" มีลักษณะอย่างไร: มีผู้รับผิดชอบและวันที่เสมอหรือไม่
- **B3.** ในการประชุมภาษาไทย มักระบุผู้รับผิดชอบและวันครบกำหนดอย่างไร ตัวอย่างเช่น: การมอบหมายงานแบบอ้อม ๆ คำนำหน้าแสดงความเคารพหรือชื่อเล่น ปีพุทธศักราช (พ.ศ.) และวันที่แบบสัมพัทธ์ (relative dates) สิ่งใดบ้างที่จะทำให้โมเดลสกัดข้อมูล (extraction model) สับสน
- **B4.** เมื่องานถูกมอบหมายโดยนัยหรือด้วยถ้อยคำสุภาพ ผู้ช่วยควรทำเครื่องหมายว่า "รอการยืนยัน" หรือถือว่ามอบหมายแล้ว แบบใดดูให้เกียรติกันมากกว่า และไม่ทำให้อึดอัด
- **B5.** การประชุมหลายภาษา (ไทย/อังกฤษ หรือมีผู้พูดภาษาจีนร่วมด้วย): ข้อมูลทดสอบของเราควรมีรูปแบบใดบ้าง
- **B6.** การทำงานร่วมกันข้ามเขตเวลาและข้ามภาษา: โดยทั่วไปมักเกิดปัญหาอะไร
- **B7.** ถ้อยคำบนหน้าจอ: ข้อความ "waiting for your confirmation", "result needs verification" และ "simulated" ควรเขียนเป็นภาษาไทยอย่างไรให้ชัดเจนและสุภาพ โปรดเสนอถ้อยคำ (หมายเหตุผู้แปล: ฉบับนี้จงใจคงข้อความทั้งสามไว้เป็นภาษาอังกฤษ เพื่อไม่ให้ชี้นำคำตอบของคุณ)
- **B8.** วัฒนธรรมเหล่านี้ส่งผลต่อลำดับความสำคัญของฟีเจอร์อย่างไร (เช่น ควรทำฟีเจอร์แนะนำข้อความตอบกลับใน LINE ให้เร็วขึ้นหรือไม่)

### (c) การปรับปรุงกระบวนการทำงาน
- **C1.** การประชุมซิงก์สัปดาห์ละครั้งร่วมกับการถามคำถามแบบ async เป็นจังหวะการรีวิวที่เหมาะกับคุณหรือไม่ แบบใดจะดีกว่า
- **C2.** การที่เอกสารเป็นภาษาอังกฤษเท่านั้นเป็นอุปสรรคหรือไม่ บทสรุปภาษาไทยของการตัดสินใจสำคัญจะช่วยได้หรือไม่
- **C3.** คุณต้องการให้การตรวจรับงาน (acceptance) เป็นแบบใด: สาธิตสด วิดีโอที่บันทึกไว้ หลักฐานเป็นลายลักษณ์อักษร หรือผสมกัน
- **C4.** คุณต้องการได้รับความคิดเห็นต่องานของคุณในรูปแบบใด (ความคิดเห็นใน PR การโทรคุย หรือบทสรุปเป็นลายลักษณ์อักษร)
- **C5.** มีส่วนใดในเอกสารนี้ที่ไม่ชัดเจนหรือขัดแย้งกันเองหรือไม่

### (d) ข้อควรระวังเมื่อพัฒนาระบบนี้ในไทย
- **D1.** ข้อกังวลด้านกฎหมายหรือการปฏิบัติตามข้อกำหนด (compliance) ที่คุณทราบ (เช่น PDPA และข้อมูลส่วนบุคคลใน transcript การประชุม หรือความยินยอมในการบันทึกเสียงในที่ทำงาน)
- **D2.** ข้อควรระวังด้านภาษาและการประมวลผลข้อความ (ภาษาไทยไม่มีการเว้นวรรคระหว่างคำ ตัวเลขไทย รูปแบบวันที่ ชื่อบุคคล)
- **D3.** ข้อควรระวังด้านแพลตฟอร์ม (ประเภทบัญชี LINE การยืนยันตัวตนทางธุรกิจ โควตาหรือค่าใช้จ่ายในการส่งข้อความ ข้อจำกัดของเครื่องมือในที่ทำงาน)
- **D4.** ข้อควรระวังด้านวัฒนธรรมในข้อความอัตโนมัติ (น้ำเสียง ลำดับชั้น ความเป็นทางการ) ที่อาจทำให้ผู้ใช้อับอายหรือเสียหน้า
- **D5.** เรื่องอื่น ๆ ที่คุณคิดว่าเราอาจทำผิดพลาด

## 5. อภิธานศัพท์ (Glossary)

| คำศัพท์ | ความหมายในเอกสารนี้ |
|---|---|
| Kernel (แกนกลางของระบบ) | บริการเบื้องหลัง (daemon) ที่เขียนด้วย Rust ของ Agent24 ซึ่งเป็นส่วนเดียวที่มีสิทธิ์ขาดในการควบคุม run, approval, การตรวจสอบ (audit) และสิทธิ์การเข้าถึงทั้งหมด |
| Run (การรันหนึ่งครั้ง) | การประมวลผลหนึ่งครั้งใน kernel — run เดิมที่เสร็จสิ้นแล้วจะไม่ถูกรันซ้ำ การลองใหม่ (retry) จะสร้าง run ใหม่ขึ้นมา |
| Action (ขั้นตอนการทำงาน) | ขั้นตอนหนึ่งที่ก่อให้เกิดผลจริง (เช่น "ส่งอีเมลฉบับนี้") แต่ละ action มี approval ของตัวเองแยกกัน |
| Receipt (หลักฐานการทำรายการ) | สิ่งที่เกิดขึ้นจริง: อนุมัติแล้ว / ส่งออกไปแล้ว (dispatched) / ผู้ให้บริการรับเรื่องแล้ว / ตรวจยืนยันแล้ว (verified) ซึ่งเป็นคนละสถานะกัน |
| Mock connector (ตัวเชื่อมต่อจำลอง) | อีเมล/Notion/LINE ปลอมที่ไม่ติดต่อบริการจริงเลย ผลลัพธ์จะถูกระบุว่า "simulated" (โหมดทดลอง ไม่ได้ส่งจริง) เสมอ |
| LocalOnly (เฉพาะในเครื่องเท่านั้น) | ข้อมูลที่ต้องไม่ออกจากเครื่อง รวมถึงห้ามส่งไปยังโมเดล AI บนคลาวด์ เนื้อหาการประชุมเป็น LocalOnly โดยค่าเริ่มต้น |
| Gold standard (คำตอบมาตรฐาน) | ผลลัพธ์ที่ถูกต้องตามที่คาดหวังสำหรับข้อมูลทดสอบหนึ่งชุด ซึ่งเขียนโดยมนุษย์ |
