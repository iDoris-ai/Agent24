## 0. 现在是什么情况

- Agent24 现在是**单人本机产品**。多用户要等权限基础设施：资源级授权和会话/运行归属（PLAN-OD-NEXT F11.0 / OD-M11）处于 **PAUSED**，组织身份（SPEC-ORG-SPACE F9/F10）没有排期（`docs/documenting/README.md:666`）。在那之前多用户门槛不对外宣称（`README.md:705-709`）。
- 路线图把组织化（F9/F10）留到「第二个真实用户」出现再做，不排期（`docs/agent/COMPONENT-ROADMAP.md:180`，`docs/agent/roadmap.md:75,134`）。
- 知识库这边：远端用户级凭据要由一个可信的签发服务发，这个服务部署在哪、谁来运营**没定**（`CONTRACT-READONLY-v1.md:58`，#992）。同一租户里的每个人有没有不同权限也**没定**（`CONTRACT-READONLY-v1.md:95,370`，#993）。上游 WeKnora 同一租户内没有按人区分的 ACL（`CONTRACT-READONLY-v1.md:95`，矩阵 #10）。

## 1. 第一版可能的三种形态

| 形态 | 做什么 | 前提 | 大致工作量 | 谁拍板 |
|---|---|---|---|---|
| **A. 远端同租户、多人共享一个只读组织库** | 同一组织的几个人，各用自己的 Agent24 连同一台远端 WeKnora，只读搜索和引用同一个组织库 | ① 身份服务有人做、有人运营（§2 Q1）；② 定为全员同权（§2 Q2）；③ 完成 KB-C1-03（按 D2 重写授权，L，`PLAN-KNOWLEDGE-TASKS.md:66`）、KB-C2-01（身份交换，M，`:78`）、KB-ORG-01（组织身份契约，M，`:115`）、KB-ORG-02a（两用户与跨组织测试，M，`:116`）；④ 放量过 KB-ORG-03（L，`:118`） | 大：Agent24 和 WeKnora 合计 3 个 M + 2 个 L（含放量门），再加一个外部身份服务；Agent24 宿主要能取用户绑定的凭据（`CONTRACT-READONLY-v1.md:58`） | 身份服务谁做、谁运营：**David 和 jason**（§5.3，`PLAN:148`）；全员同权还是按人设权限：**David 和 jason**（§5.4，`:149`）；放量：**jason**（`:118`） |
| **B. 本机多个 OS 用户** | 同一台 Mac 上几个系统账号共用一个 Agent24 / 一个本机知识库 | 先要改契约：local-managed 现在规定实例只服务**本机唯一用户**，principal 就是这个用户（`CONTRACT-READONLY-v1.md:59`，R1.4，David 10-17 定）；还要 F11.0/OD-M11 恢复并完成（`README.md:666`） | 不确定，至少要改契约，加上一整套 Agent24 权限基础设施 | 改契约：**David**（R1.4 是他 10-17 定的）；恢复 OD-M11 并排期：**David 和 jason** |
| **C. 不做** | 维持单人本机，多用户门槛不宣称（`README.md:709`） | 无 | 0 | **David** |

**B 和契约冲突**：R1.4 明确 local-managed 是「本机单用户实例」，本实例的秘密只给本实例用（`CONTRACT-READONLY-v1.md:59`）。几个 OS 用户共用一个实例，就违背了这个前提。如果每个 OS 用户各装各的、互不共享，那只是多份单人副本，不算「多人使用」（这种用法本文没有验证过）。所以不建议选 B。

**本文建议**：没有具体的第二个用户之前选 C。出现了第二个真实用户就走 A，按 §3 的清单先做试点。这和计划里的建议一致（`loop-8-draft.md:91`）。

## 2. 开工前必须先回答的问题

1. **身份由谁验证，签发服务谁来运营**（PLAN §5.3，`PLAN-KNOWLEDGE-TASKS.md:148`；#992）。不能把租户的签名密钥（HMAC）放进 Desktop 来绕开这个问题：拿到它的人能冒充任何用户签名（D2，`PLAN:28`；`CONTRACT-READONLY-v1.md:56`）。这个问题没答之前，只能做单用户样本和 Mock（`CONTRACT-READONLY-v1.md:58`）。
2. **资料是全员同权，还是按人设权限**（PLAN §5.4，`PLAN:149`；#993）。全员同权可以直接用「组织 = 租户」的共享集合；按人设权限要先做 D2 的权威授权（D3，`PLAN:29`）。
3. **放量由 jason 定**（KB-ORG-03，`PLAN:118`）。放量门按实际开放的功能列证据：身份、出口、容量、备份恢复、上游升级回归。
4. **Mock 激活码不是身份**，只能用来演示，不能当作多人功能交付：
   - 激活码只对应「一个演示租户 + 模板库 + 配置版本」，没有用户这个字段（WeKnora `internal/application/service/agent24_mock_activation.go:21-26`）；
   - 激活路由注释写明：没有身份服务，owner 就是租户本身（`api_tenant:<id>`），激活码就是凭据，不走 Auth（`internal/handler/agent24_knowledge_init.go:3-7`，owner 在 `:163` 这样算）；
   - 所以两个人如果拿同一租户的激活码，服务端会把他们当成**同一个 owner**，共用一个默认库（每个 owner 只有一个默认库，`internal/types/agent24_default_kb.go:4-5,21-22`）。用 Mock「两个人各自开通」，只能靠给两人各配不同的租户，这时演示的是两个单人租户，不是同一组织里的两个人；
   - PLAN §5.6 也写明 Mock 不算商业闭环（`PLAN:151`）。对外最多只能写「Mock 身份演示」。

## 3. 「第二个真实用户」出现时的最小试点清单

前提：§2 的 Q1、Q2 已有答复，KB-C1-03 和 KB-ORG-01 已完成（KB-ORG-02a 依赖 KB-ORG-01，`PLAN:116`）。

**KB-ORG-02a 两用户测试**（`PLAN:116`）——同一组织的用户甲、乙，对共享只读组织库：
- [ ] 甲、乙各自用**自己的**用户绑定凭据，搜索、计数、read、预览、下载、引用的结果都只在授权范围内；
- [ ] 缓存和后台作业不会把甲的结果交给乙（如果是按人设权限）；
- [ ] 撤掉乙的权限后，乙已经在跑的任务结果不再交付、不再发布；
- [ ] 审计和访问日志里记的是甲、乙各自的 principal，不是租户（`PLAN:66`）；
- [ ] 授权范围取交集，交集为空就拒绝，绝不回写空数组（D2，`PLAN:28`）。

**跨组织隔离测试**（D3 `PLAN:29`、KB-ORG-02a `PLAN:116`）——另一组织的用户丙：
- [ ] 丙对甲乙组织的库，上面每一项都拒绝，计数也不泄露；
- [ ] 集成模式下，不能沿用已有的跨租户或 Agent 共享授权（D3 `PLAN:29`）；
- [ ] 凭据里的 tenant_id 和 key 所属租户对不上时一律拒绝（`CONTRACT-READONLY-v1.md:57`）。

试点期间，对外口径是「单组织只读试点」。多用户门槛（中途撤权、用户之间的权限分隔、按人隔离，`README.md:705-708`）要等 Agent24 权限基础设施完成后才算达到。
