# KB-C3-EVAL 深度检索评估记录（2026-11-24）

> Loop 7 第 3 项。本 Loop 只做评估，不实现（David 11-24 确认）。依据：`knowledge-materials/plan/loop-7-draft.md` 第 3 项；`docs/knowledge/PLAN-KNOWLEDGE-TASKS.md` WS8 的 KB-C3-EVAL；`docs/agent/tasks.md` 中 KB-C3 的说明：不能强制限制时只用检索，不阻塞基础问答。
> 代码基线：Agent24 `origin/ab/ui` 25576352；WeKnora fork `iDoris-ai/WeKnora` `a24/develop` 2d61d6420。
> **结论：等条件**（理由见 §5）。评估通过也不等于授权实施；David 已在 §6 确认结论（11-24，经 General 转达）。

## 1. 摘要

- 在演示库上用本地 Qwen3-8B-4bit 跑了 12 个复杂问题，比较三种做法：A 简单检索；B 改写 + 多步检索 + 证据整理（计划里说的「深度检索」）；C 改写 + 多步检索，但不做证据整理。
- **B 不如 A**：质量更差（好 3 题、差 5 题；A 是好 5、差 3），错误陈述 9 处，A 是 6 处。B 的延迟约为 A 的 1.9 倍，token 约为 1.8 倍。问题出在整理那一步：8B 模型在逐步摘事实时会丢事实、编事实，也会把标记搞反。
- **C 小幅好于 A**：多步检索把证据覆盖从 15/19 提高到 18/19，好答案从 5 题增加到 6 题，差答案从 3 题降到 1 题。但错误陈述从 6 处增加到 8 处：证据多了，模型也编得多了。延迟约为 A 的 1.45 倍，单轮 prompt 最多 3320 token，贴近平衡档 3.5k 的上限。
- **强制限制只有一部分。** 服务端（WeKnora）只提供单次检索和读取，每次请求的 deadline、条数、取消是强制的。「多步子任务」的步数、token、总时限和费用，WeKnora 不管；agent24d 有 run 级的步数上限和取消，但没有 run 级墙钟时限，也没有 token 和费用预算。这正是计划里所说「拿不到证据就保持只读检索」的情况。

## 2. 方法

| 项 | 做法 |
|---|---|
| 在哪跑 | 全程在 mini 本机，没有动 David 的 Mac（General 11-24 同意）。 |
| 检索 | 本机演示栈 18282 的 `POST /api/v1/agent24/knowledge/search`，与 App 用同一个接口、同一把演示 key。范围是演示库 ffec8cdb（7 份 s01 PDF，bge-m3）加 K2 439127c1（1 份合成 md）。两库评分空间不同：第一次请求被拒，返回 `mixed_score_space`，按返回的分组逐组检索，再按名次轮流合并、去重，与 #2058 的做法一致。所以每次检索实际发 3 个请求。 |
| 模型 | 外挂盘上已有的 `mlx-community/Qwen3-8B-4bit`，与 David Mac 上是同一份权重。用 mlx_lm.server 临时起在 127.0.0.1:18095，跑完已经停掉，没有下载模型。设置为 temperature 0，关闭思考（`/no_think`）。机器是 Apple M4、16 GB；延迟只能看相对值，绝对值和 David 的 Mac 不同。 |
| 问题集 | 按演示库里实际的 7 份文档自拟 12 题（多文档对比、跨语言、跨库、需要整理证据），每题先对照原文写好要点，见 `kb-c3-eval/questions.json`。演示库里没有合同，「综合各份合同」这类原话改用收费目录、通知类文档代替。 |
| A 简单检索 | 原问题检索 1 次，取前 5 段（每段截到 600 字），模型调用 1 次，直接回答。 |
| B 改写 + 多步 + 整理 | 模型把问题拆成最多 3 个子查询（硬上限写在脚本里）；每个子查询检索前 4 段并去重；每步调一次模型，摘出带编号的事实；最后用整理好的事实回答。模型调用最多 5 次。 |
| C 改写 + 多步，不整理 | 拆子查询（1 次模型调用）；原问题和各子查询各检索前 4 段，轮流合并、去重，最多 8 段；1 次模型调用回答。共 2 次。 |
| 计量 | 端到端墙钟时间；prompt/completion token 取 mlx_lm 的 usage；检索请求数和耗时；证据覆盖 = 题目需要的文档出现在证据里的个数。 |
| 打分 | 先按要点关键词自动匹配（`gold_hit`，只作参考），再逐题人工核对原文，给出好 / 中 / 差，并数出错误陈述：与原文不符或资料里没有的说法。**以人工结果为准**：自动匹配会把「没找到」「数值对但结论错」算成命中，例如 Q05 B。 |

脚本与原始结果见 `docs/knowledge/kb-c3-eval/`（`run_eval.py`、`search.py`、`questions.json`、`results.jsonl`）。凭据只从本机 600 权限的文件读取，不在脚本和输出里出现。复跑：先用 mlx_lm.server 在 127.0.0.1:18095 起模型，然后在该目录下运行 `python3 -s run_eval.py`（A、B 两组）和 `MODES=C python3 -s run_eval.py`；结果追加写入 `results.jsonl`。

### 3.3 观察

1. **多步检索主要补的是证据覆盖，而不是推理。** 补上的三题都是检索漏了：Q02 漏了英国的截止日，Q06、Q09 是中文问题检索英文文档，前 5 段里没有。原问题检索一次就能补上的那部分，用「多查几个改写」比「多步执行器」便宜得多。
2. **8B 模型做「证据整理」得不偿失。** 每一步摘事实都会丢东西（Q05、Q10），也会编东西（Q06、Q09）。把原始证据直接交给最后一步（C），质量反而比 B 好。
3. **证据越多，编得越多。** C 的错误陈述多于 A：模型看到相关文档就倾向于补全细节（Q06 的通知方式）。A 检索不到时会如实说「没找到」，这一点更安全。
4. **成本可控，但会顶到预算。** C 单轮 prompt 最多 3320 token，平衡档的目标是 ≤3.5k，没有余量再加历史对话。B 每轮的 prompt 小，但调用次数多，延迟接近 A 的 2 倍。

## 4. 强制限制的证据（服务端与 agent24d）

按「步骤 / token / deadline / 出口 / 取消 / 工具限制」逐项核对。「强制」指代码确实会截断或拒绝，而不是写在提示词里。

### 4.1 WeKnora fork（a24/develop 2d61d6420）

| 限制 | 有没有 | 证据 |
|---|---|---|
| 单次请求 deadline | **有，强制** | `internal/handler/agent24_knowledge_search.go:228` 用 `context.WithTimeout(budget.deadline_ms)`；上限 30000 ms（`agent24_knowledge_capabilities.go:26`），超出的值被压到上限（`agent24_knowledge_search_plan.go:81`）。超时返回 `timeout`（`agent24_knowledge_search.go:194`）。测试：`TestAgent24KnowledgeSearchDeadlineAndLimits`、`TestAgent24KnowledgeSearchEndedByDeadline` |
| 单次结果条数 | **有，强制** | `max_results` 上限 50（`capabilities.go:24`、`search_plan.go:82`），在 `agent24_knowledge_search_hits.go:243` 截断。测试同上 |
| 并发 | **只校验，不执行** | `max_concurrency` 上限 4，经过解析和压值（`search_plan.go:83`），但 handler 里没有任何地方用它控制并发；单次检索本来就只调用一次检索器 |
| 取消 | **有，强制** | 调用方断开时什么都不写（R7.1，`agent24_knowledge_search.go:192`）。测试：`TestAgent24KnowledgeSearchClientGone` |
| 工具限制（出口） | **有，强制** | 集成模式只开放白名单路由（ready/search/read、UI、候选、嵌入页），其他路由一律返回 404（`internal/router/agent24_integration_gate.go:22-41`）。WeKnora 自带的 Agent 和对话（ReAct 循环，`internal/agent/engine.go` 的 `MaxIterations`，可以设成 -1 表示不限）在集成模式下访问不到。测试：`TestAgent24IntegrationGate` |
| 多步子任务的步数 / token / 总时限 / 费用 | **没有** | 服务端没有「多步任务」这个概念：每次请求独立，不累计步数，不计 token（search 只做检索，不调对话模型），没有费用计量 |

| 限制 | 有没有 | 证据 |
|---|---|---|
| 步数 | **有，强制（run 级，不分子任务）** | `MAX_ITERATIONS = 10`（`rust/crates/agent24-agent/src/source_policy.rs:17`），循环在 `run_manager/execute.rs:809`，超出时以 `max_iterations` 失败（:1112）。测试：`tests/lifecycle.rs` 的 `endless_tool_requests_hit_max_iterations` |

| 知识库调用预算 | **有，强制（单次调用）** | 一次调用总时限 15 s、最多 8 个请求（含分组和重试）（`rust/crates/agent24-knowledge/src/provider/budget.rs:16,18`），每个 binding 主通道最多 4 个并发（:20）。测试：`provider/budget/tests.rs` 的 `a_call_budget_counts_every_request_and_shares_one_deadline`、`a_call_past_its_deadline_sends_nothing_and_takes_nothing`。工具超时 60 s（`rust/apps/agent24d/src/knowledge_tools.rs:29`） |

| run 级墙钟时限 | **没有** | `rust/apps/agent24d/src/inbound/service.rs:17` 写明「没有 run 级墙钟超时」：卡在模型请求上的 run 不会自己结束。只读子代理 `explore` 有 120 s 的墙钟上限（`subagent.rs`），但它没有知识库工具 |

### 4.3 小结

单次检索这一层的限制（deadline、条数、取消、出口白名单）已经齐全，而且都有测试。「有界知识子任务」需要的子任务步数、累计 token、总墙钟时限、费用，以及部分结果的出口，WeKnora 不提供（也不该由它提供），agent24d 目前也没有强制实现。按 PLAN 的口径，这几项属于实施的前置条件，现在都还没满足。

## 5. 结论：等条件

不选「做」：在当前默认模型（Qwen3-8B）上，计划里的「改写 + 多步 + 证据整理」比简单检索更差、更慢、更贵（§3.1 B 列）。另外，有界执行要求的 token、总时限和费用三项限制，现在都没有强制实现（§4）。

不选「不做」：多步检索确实补上了证据覆盖（15/19 → 18/19，C 列），这对跨文档、跨语言的问题是实打实的收益。如果换更强的模型，整理那一步的损失可能消失。

**要满足以下三条，才重新评估（用同一套脚本和问题集复跑，作为反面对照）：**

1. **模型**：默认问答模型换成更强的（本地更大的模型，或允许用云端模型），并且用本记录的脚本复跑：B 或 C 的「好」比 A 至少多 2 题，错误陈述不多于 A。
2. **强制限制**：agent24d 先补齐知识子任务的强制限制，每项都要有测试——子任务步数、累计 token 上限、总墙钟时限、取消后返回 partial（附已有来源），以及只含 `knowledge_search`/`knowledge_read` 的工具白名单（参照 `explore` 的做法）。这属于实施本身的安全前置，走 APPROVE@head。
3. **前置事项先落地**：Loop 7 第 0、1 项（检索稳定、跨库引用）验收通过，并且 FU-226 有结论。如果跨语言漏检靠检索侧就能解决，深度检索的收益会进一步变小，那时应考虑改选「不做」。

在此之前保持只读检索（`tasks.md`：不能强制限制时只用检索，不阻塞基础问答）。
