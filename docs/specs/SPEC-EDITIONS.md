## 0. 为什么现在写

`MISSION.md` 已经定了模型：MushroomDAO 研发数字公共物品、HyperCapital 是唯一授权商业伙伴、
商业收入 40% 回流社区国库、个人与 ≤50 人小社区永久免费。

**但「哪些能力属于开源侧、哪些属于商业侧」今天没有任何工程边界，也没有一张表。**

这件事**必须在 Cos72 商业化之前定**，而不是之后再拆。理由很实际：
一旦某个能力先在商业侧长出来，再把它挪回开源侧就变成了「收回承诺」的反向操作 ——
而反过来（先开源、后加托管）从来不难。**先划线，再写代码。**

## 1. 划线的原则（这一条比表本身重要）

Proma 的三档表值得学的不是条目，是**它划线的方式**：

> **开源版拿到的是完整的产品。商业版卖的是托管、额度、分发、合规 —— 这些天然属于组织的东西。**

具体到我们，我把它写成四条：

### P1 · 不阉割功能

**任何一项「agent 能做什么」的能力，MUST 在开源版完整可用。**

不存在「开源版只能建 3 个 schedule」「开源版没有审批门」这种线。
一个人在自己的机器上、用自己的 API key，应该能得到与付费用户**完全相同**的 Agent24。

> 与 `MISSION.md` 的一致性：数字公共物品「不会因为使用人数增加而降低每个人享受到的福祉」。
> 功能配额直接违反这句话。

### P2 · 商业侧卖的是「我们替你承担的东西」

托管、代付、额度、可靠性保障、组织级管理、合规 —— 这些的成本随用户数**线性增长**，
所以按用量收费是诚实的。功能的边际成本是零，所以按功能收费不是。

### P3 · 数据主权不作为商品

**MUST NOT** 出现「开源版数据留本地、商业版数据上云」这种线，
更**不得**有「用你的数据换免费额度」的安排。

> `MISSION.md`：「我们拒绝以提取个人隐私数据为基础的商业模式。」
> 商业版可以**提供**云同步作为一项服务，但**本地优先必须在所有版本中都是默认且完整可用的**。

### P4 · 退出成本必须为零

**用户 MUST 能在任何时候停止付费，把数据留在自己机器上继续用开源版。**
数据格式（SQLite + 迁移）在所有版本中相同；商业版不得引入只有它能读的存储。

## 3. 裁决记录（2026-09-02，用户已拍板）

### ① 审批的组织化 — **已裁决：算功能 → 判定与授权机制全部开源**

> 用户：「判定机制开源、管理界面与合规报表商业化，可以；审批的组织化算不算功能，应该算吧」

**定稿的线**：

| 归属 | 内容 |
|---|---|
| **开源版（完整）** | `Authorizer` 判定 · grants · groups · 交集判定 · 审计**事件** · `SpaceId` / org 模型 —— 即 M3 的 F3.1/F3.2/F3.3 全部 |
| **企业版** | 管理这些东西的**界面**、跨成员的**合规报表**、与企业身份系统（SSO/LDAP）的**对接** |

**分界的判据**：**能不能安全地多人使用，是功能；管起来省不省事，是服务。**
判定机制若不开源，开源版的多人使用就是不安全的 —— 那等于拿安全做收费杠杆，
违反原则 1 也违反 `MISSION.md`。而管理界面与报表的成本确实随组织规模增长，属原则 2。

**这条同时是 M3 的排期依据**：M3 的内容全部落在开源侧，所以它的优先级由**产品需要**决定，
不受商业化节奏影响。（M3 今天仍标「等第二个真实用户，不排期」，理由不变。）

### ② 托管同步与本地优先 — **已裁决，表述如下**

> **L-ED-3（拟）· 本地优先在所有版本中都是默认且完整的。**
>
> Agent24 在**任何**版本中 **MUST NOT** 要求数据离开用户的机器才能工作。
> 托管同步 **MUST** 是可选的、端到端加密的，且**关闭后全部功能照常**。
>
> 商业版提供的是**同步的运输，不是数据的归属**：密钥在用户手里，我们看不到明文；
> 停止订阅后本地数据完整可用 —— 不降级、不锁定、不需要导出。

**为什么要写成这个形状**：「商业版才能多设备」会慢慢滑成「商业版才好用」，
而这个滑坡没有单一时刻是错的。把「关掉之后一切照常」写成硬条款，
每一个新功能都要先回答「不同步的人还能用吗」，滑坡才有地方被卡住。

### ③ 「≤50 人」这条线 — **出处存疑，待你确认是否仍作数**

**这个数字不是用户在对话中提出的**，来自
[`Brood/protocol/MISSION.md:87`](../../../Brood/protocol/MISSION.md)：
> 「开源组织（MushroomDAO）: 研发数字公共物品，免费提供给所有人（个人/小社区 ≤50人 永久免费）」

用户 2026-09-02 指出未曾说过该数字。**在确认它是否仍是协议层的有效约定之前，本节的建议不生效。**

**若它仍作数**，工程上的建议不变：Agent24 是本地优先的，我们**没有也不应该有**统计社区人数的遥测。
所以 —— **开源自建永不设限也不计数；50 人是购买托管服务的门槛线，不是使用开源软件的许可条件。**
这样既守住数字公共物品的承诺，也不需要任何遥测。

**若它不作数**：删除本节，`§2` 表中「适用」一行的「≤50 人社区」改为「个人 · 社区」。

## 3bis. 原始讨论（留档）

### ① 审批的组织化算不算「功能」？（最难的一条）

`docs/agent/roadmap.md` 的 **M3 组织化**（grants + groups + 交集判定 + 审计事件）
今天标着「等第二个真实用户，不排期」。

**它落在 P1 和 P2 的边界上**：
- 按 P1（不阉割功能），「多人协作的授权模型」是内核能力，应该开源；
- 按 P2（商业侧卖组织级的东西），「谁能批谁的、审计追溯、合规报表」正是典型的组织需求。

**我的建议：判定机制开源，管理界面与合规报表商业化。**
即：`Authorizer` / grants / groups / 审计事件**全部在开源版**，
企业版加的是**管理它们的 UI、跨成员的报表、与企业身份系统的对接**。

理由：判定机制若不开源，开源版的多人使用就是不安全的 —— 那等于用安全性做收费杠杆，
违反 P1 的精神也违反 `MISSION.md`。而管理界面的成本确实随组织规模增长。

### ② 托管同步与「本地优先」怎么并存？

表里标 ❓ 的「跨设备同步」是 P3 的边缘：提供同步服务没问题，
但必须保证**同步是可选的、端到端加密的、且关掉之后一切照常**。
需要一条明确的表述，否则「商业版才能多设备」会慢慢滑成「商业版才好用」。

### ③ 50 人怎么数、谁来数？

`MISSION.md` 写「个人/小社区 ≤50 人永久免费」。
**但 Agent24 是本地优先的，我们没有、也不应该有**统计一个社区有多少人的遥测。

三个选项：
- **(a) 荣誉制** —— 写进 LICENSE 附加条款，不做技术限制。**我倾向这个。**
- (b) 由 Cos72 的成员表自报 —— 但那是用户自己的数据库，我们读不到也不该读。
- (c) 只在使用托管服务时才计数 —— 即「50 人」这条线只对商业版有意义，纯开源自建**不设限**。

**(a) 与 (c) 可以合并**：开源自建永远不设限也不计数；50 人是**购买托管服务的门槛线**，
不是使用开源软件的许可条件。这样既守住了数字公共物品的承诺，也不需要任何遥测。

## 4. 明确不做的

- **不做功能配额。**（P1）
- **不做「社区版 / 专业版」双代码库。** 一个仓库、一个构建，差异只经 `distro/` 缝叠加
  （`SPEC-SKILL-DISTRIBUTION.md` §2）。双代码库会在三个月内漂移成两个产品。
- **不做「开源版有广告 / 遥测」。**（P3）
- **不把安全能力放进付费档。** 审批门、隔离、签名验证全部开源 ——
  拿安全做收费杠杆是这个行业最恶劣的做法之一，也直接违反 `MISSION.md`。
