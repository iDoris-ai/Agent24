## 0. 为什么是两半

一个 Skill 分发机制要回答两个**互不相同**的问题：

| 问题 | 谁的机制 | 没有它会怎样 |
|---|---|---|
| **私有物怎么叠加进公开构建？** | Berd 的 `distro/` 分发缝 | 商业/企业定制只能 fork 主仓，或者把私有内容塞进公开源码树 |
| **已经分发出去的怎么升级？** | Proma 的 frontmatter `version` 比对 | 修好的 Skill 永远到不了老用户手里，或者覆盖掉用户自己的改动 |

**两个都要。** 只有前者 = 装得进去但更新不了；只有后者 = 能更新但只能更新我们自己写死在二进制里的那些。

## 1. 三个来源，三种所有权

Skill 有三种来源，**所有权与升级规则各不相同，不得混为一谈**
（Berd 把这三类分在 `skills/` · `distro/skills/` · `.agents/skills/`，我们照办）：

| 来源 | 位置 | 所有权 | 升级规则 |
|---|---|---|---|
| **内置（bundled）** | 二进制内嵌 / `<安装目录>/skills/` | **我们的** | 随版本走，用户不改就跟随升级（§3） |
| **分发（distro）** | `$AGENT24_DISTRO_DIR` 或 `<资源目录>/distro/skills/` | **分发方的**（HyperCapital / 某社区） | 同 §3，但版本空间独立 |
| **用户（user）** | `~/.agent24/skills/` | **用户的** | **我们永不写入**（§4） |

**这三者的优先级是：用户 > 分发 > 内置。**
同名时高优先级完整取代低优先级，**不做字段级合并** —— 合并出来的 Skill 谁也没写过，出了问题无人可问。

## 2. 分发缝：公开构建必须自足

**L-DIST-1（拟）**：**公开构建 MUST 自足** —— 不依赖任何私有仓库、私有 registry 或企业凭据即可完整构建与运行。
私有内容 MUST 只经下列缝叠加，MUST NOT 进入公开源码树。

缝的形状（照 Berd，但换成我们的命名）：

```
distro/
  distro.toml     分发级默认值（分发方名称、Skill 市场 URL 模板、可选的默认 relay）
  skills/         种进用户全局 skills 目录的 Skill
  os/             随分发预装的领域 OS（对接 ME-2 的 `agent24 os` 注册表）
```

解析顺序：`AGENT24_DISTRO_DIR` 环境变量 → 安装目录下的 `distro/` → 无（纯公开构建）。

**`distro.toml` 的每个字段都要校验，不是「读到什么算什么」。**
Berd 对一个 URL 模板写了六条校验（必须 HTTPS、必须含且只含一个 `{skillId}`、
占位符不得出现在 authority 部分、不得带凭据或 fragment）—— 那是对的：
**分发方是我们信任但不控制的一方，它的配置是输入，不是权威。**

> 与 `MISSION.md` 的关系：这条缝是「开源组织研发数字公共物品 / 商业实体提供 Pro 服务」
> 在工程上的落点。**没有它，开源侧与商业侧只能靠纪律区分，而纪律会在赶工期时失效。**
> 详见 [`SPEC-EDITIONS.md`](SPEC-EDITIONS.md)。

## 3. 升级：版本号驱动，且只升不覆盖

### 3.1 契约

每个 Skill 的 `SKILL.md` frontmatter **MUST** 带 `version`（semver）。

```yaml
---
name: myvote-tally
version: 1.2.0
description: …
---
```

**播种规则**（内置与分发 Skill 在启动时种进 `~/.agent24/skills/`）：

| 目标状态 | 动作 |
|---|---|
| 不存在 | 写入 |
| 存在，来源版本 **更高** | **覆盖**，并记一条事件 |
| 存在，来源版本 **相等或更低** | **不动** |
| 存在，但用户改过（§4） | **不动**，并提示有新版本可用 |

**只比版本号。不比内容，不比 mtime。**
比内容会让用户的任何一处改动都变成「冲突」；比 mtime 会因为 checkout / rsync / 时钟漂移而误判。
版本号是一个作者必须**显式**递增的数字 —— 它编码的是意图，而 hash 与时间戳编码的是意外。

### 3.2 配套的工程纪律（必须同时立，否则 §3.1 是死的）

**改动任何内置 / 分发 Skill 的任何内容，MUST 同步递增其 `SKILL.md` 的 `version`。**

这条**必须有 CI 检查**，不能靠自觉：
> 若本次 diff 触及 `skills/<name>/**` 中任一文件，而 `skills/<name>/SKILL.md` 的 `version` 未变高 → CI 红。

**理由与 A6 的零漂移门完全一致**：一个「作者必须记得做」的步骤，如果忘了不会立刻出错、
只会让**老用户**收不到升级，那它一定会被忘掉 —— 而且没人会发现，因为开发机上永远是全新安装。

这条同时治了 `SPEC-ME-FOLLOWUPS.md` **F4a** 记下的那个病的第三个病灶
（前两个：OpenAPI 少写端点、`os list` 输出形状漂移）。

## 4. 用户所有权是不可动摇的

**L-DIST-2（拟）**：一旦一个 Skill 被写进 `~/.agent24/skills/`，**它就是用户的**。
系统 MUST NOT 覆盖用户修改过的 Skill；MUST NOT 删除用户的 Skill；
MUST NOT 因为升级而丢弃用户的本地改动。

**怎么判定「用户改过」**：播种时记下所写内容的哈希（记在 `~/.agent24/skills/.seeded.json`，
不写进 Skill 目录本身，免得污染用户的东西）。升级时若磁盘上的哈希 ≠ 播种时记录的哈希 → 用户改过 → 不动。

**这与 §3.1「只比版本号」不矛盾**：版本号决定**要不要升**，哈希决定**能不能升**。
两个判断，两个来源，缺一个都会做错事。

> 这条与 H2 的 inviolable 是同一族：**override store 是 user-local，永不由模块清单或 persona 写入。**
> 模块可以*声明*它想要什么，是否信任由用户决定 —— Skill 亦然。

## 5. 与既有机制的接线

| 既有 | 接法 |
|---|---|
| **ME-2 `agent24 os` 注册表** | `distro/os/` 里的领域 OS 走已有的 install/activate 流水，**不新建第二条安装路径** |
| **H10 模块安装知情同意** | 分发来的 Skill 与模块同权：**安装后默认 disabled，pending consent**，展示它声明的权限。分发方的身份不是豁免 |
| **MD-7 知识层** | Skill 与 MD-7 的 `Instruction` **不是同一个东西**：Skill 是**能力**（可触发的流程），Instruction 是**指令**（注入的规则）。不要合并二者的存储 |
| **L-CTX-1/2**（[`../laws/CONTEXT.md`](../laws/CONTEXT.md)） | Skill 目录的发现同样**不得向上遍历祖先目录**；每个被加载的 Skill 都要能点名其规范化路径 |
