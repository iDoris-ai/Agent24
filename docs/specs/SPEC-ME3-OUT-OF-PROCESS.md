# SPEC-ME3 — 进程外领域 OS（Out-of-Process Provider）

> 立于 2026-09-02。裁决依据：[ADR-031](../decision.md)（协议按「缝」分别裁决）。
>
> 前置：ME-1（`DomainModule` + `KernelCtx`）、ME-2（配置驱动注册表 + `agent24 os` CLI）均已交付；`ImplKind::OutOfProcessProvider` 这个枚举值 ME-2 时就留好了，本文档负责让它有实现。
>
> 关联：[`SPEC-MD-ME.md`](SPEC-MD-ME.md) §5 ME-3 行、[`SPEC-ME-FOLLOWUPS.md`](SPEC-ME-FOLLOWUPS.md) §「留给 ME-3 的（进程外模块）」、[`SPEC-ORG-SPACE.md`](SPEC-ORG-SPACE.md)（所有权模型）。

## 这份文档的范围，先说死

**这是「让一个第三方进程成为领域 OS」的机制，不是「沙箱」，也不是「插件市场」。**

它覆盖：怎么把进程外模块挂上来、路由怎么到它、它怎么回调内核要记忆/事件/审批、它崩了怎么办、它不可信这件事怎么在机制上体现。

它**不**覆盖：进程隔离的强度（不做 seccomp/沙箱，§8）、模块签名与信任根（ME-6，P4 门后）、跨机分发（单机本地进程）、模块间通信（模块之间不互相看见，只经内核）。这些在 §8 逐条列明，不是遗漏。

**一句话形状**：内核 spawn 一个子进程，把 `/api/v1/<ns>/*` **反向代理**给它；它经一条**窄的 JSON-RPC 回调通道**向内核要记忆、发事件、请审批。入站是代理，不是协议；**只有出站方向需要定义协议**。

---

## 1. 为什么入站不需要协议

`DomainModule::routes()` 在进程内返回一个 `axum::Router`。这个形状过不了进程边界——但**它的效果**过得去：模块在本地端口上提供 HTTP，内核把自己命名空间下的请求原样转发过去。

内核已经有 axum，反向代理是几十行。为「模块贡献路由」发明协议，是把一个已解决的问题重新问一遍。

**内核在代理路径上仍然是权威**，这几条不下放：

- **鉴权在内核**。ME-1b 已经钉死挂载顺序（模块先 nest，内核 auth layer 最后），代理路由走同一条路——模块**永远看不到未鉴权的请求**，也拿不到内核 token。
- **命名空间不可越界**。模块声明 `route_namespace`，代理只转发该前缀下的路径；模块无法通过返回重定向或路径穿越跳出去。
- **模块不认识内核的其它路由**。它只知道自己那一段。

## 2. 出站：回调通道

模块要的四件事，对应 `Capability`：`Memory`、`Events`、`Models`、`Scheduler`/`Policy`（后两者本轮不做，见 §8）。

**通道形状**：JSON-RPC 2.0 over Unix domain socket（本地、无端口、文件权限即访问控制）。内核 spawn 时创建 socket 并把路径与一次性令牌通过环境变量交给子进程。

**方法集刻意小**，且与进程内 trait 一一对应：

| 方法 | 对应进程内 | 说明 |
|---|---|---|
| `initialize` | 挂载握手 | 模块报自己的 manifest 摘要与协议版本；内核回**授予的能力集**（不是模块请求的，是内核批准的） |
| `_a24/memory/write` | `ScopedMemory::write` | 有大小上限，见 §4 |
| `_a24/memory/recall` | `ScopedMemory::recall` | **有界分页 + 可取消** |
| `_a24/memory/recent` | `ScopedMemory::recent` | 同上 |
| `_a24/events/emit` | `EventSink` | 只能发自己 `event_module` 的事件 |
| `_a24/approval/request` | 审批门 | 语义对齐 ACP 的 `session/request_permission`（ADR-031） |

`_` 前缀与 `_meta` 是 ADR-031 定的 ACP 对齐惯例：线格式将来能复用，词汇表本来就该不同。

### 身份不由模块提供

**这是本文档最重要的一条。** `SPEC-ME-FOLLOWUPS` 已经写过：

> 远端模块**永远不发**自己的 owner/分区 key，身份来自已认证的连接或不可伪造的租约。

所以每个模块有**自己的** socket 与令牌，内核**按连接**查出它是哪个模块，再自己推导 `(org, space, module)` 分区键（ADR-030）。协议里**没有**让模块说「我是谁」的字段——不是「不该填」，是**填不了**。

一个模块若能声明分区键，F1/F8 的物理隔离就被绕过了；这正是 ADR-029 复审当年指出的那个洞的进程外版本。

## 3. 生命周期

```
os install <name>   →  校验 manifest（impl_kind: out-of-process）+ 记录 spawn 命令
os activate <name>  →  内核 spawn 子进程 → 等它连上回调 socket 并 initialize
                       → 健康探测通过 → 挂代理路由
（运行中）           →  子进程崩溃 → 代理路由换成内核的 503 → 按退避重启
os deactivate       →  发停止信号 → 宽限期 → 强制 kill → 摘路由
```

**一个模块挂了不能带走内核。** ME-1 已经为进程内定了这条规矩（`open_store` 返回 `Err` 时挂 503 而不是崩溃）；进程外只是把「返回 Err」换成「进程没了」，结论不变。

**目录条目独立于模块是否在线而持久。** migration 0012 已经做到，`SPEC-ME-FOLLOWUPS` 明确要求 ME-3 不要退回内存态：模块离线时，它的记忆分区、目录条目、事件历史都还在——**离线不等于卸载**。

## 4. 信任降级：进程外模块比进程内更不可信

进程内模块是编进内核的 crate，供应链风险在编译期。进程外模块是**别人的二进制**。三条机制随之收紧：

**（1）配额从「地板」升级成真配额。**
`SPEC-ME-FOLLOWUPS` F7 说得很直白：单条记忆的大小上限**不是配额**，模块可以用任意多次合法的小写入把共享库撑大。进程内这条被降级为 F7 待办；**进程外它是必须项**——按分区的字节/行数上限 + 写入限流，超限返回明确错误而不是静默截断。

**（2）请求与响应都要有硬上限。**
不只是请求。一次 `recall` 可以合法地要求返回很多东西；响应侧没有上限，内核就会替一个不可信模块把自己撑爆。

**（3）`recall`/`recent` 有界分页 + 可取消。**
连接断开即取消——否则一个走掉的模块会留下一个还在扫分区的查询。

## 5. 审批门与代理的交汇（本轮最难的一处）

模块处理一个被代理的请求时，可能需要审批（比如 Cos72 要动一笔社区资金）。链路是：

```
用户 → 内核（已鉴权）→ 代理 → 模块 → 回调 _a24/approval/request → 内核 → 用户批准 → 模块继续
```

难点是**归因**：内核收到审批请求时，必须知道它属于**哪一次用户请求**，否则审批弹窗上写不出「谁、为什么」。

**做法**：内核在代理时注入一个不可伪造的 `X-A24-Request-Id`（内核生成、不接受模块伪造），模块回调审批时原样带回。内核用它把审批归因到那次请求与那个用户。模块**不能**凭空发起一次无归因的审批——没有 request id 的审批请求直接拒绝。

> 这条与 ACP 的 `session/request_permission` 是同一件事的两个语境：那边归因到 session，这边归因到 request。ADR-031 只核到语义层对齐，**字段级契合度仍未验证**（§9）。

## 6. F4e：`os enable` 会从「今天不可达」变成现实问题

`SPEC-ME-FOLLOWUPS` F4e 记着一条：`PATCH` 放行 `Refused` 条目——`os enable <会被准入拒绝的模块>` 返回成功并落盘，但不存在任何能让它生效的路径。当时的判断是「今天不可达（生产 catalogue 只有 sin90 且可准入），**ME-3 会让它变成现实问题**」。

它现在到期了。进程外模块的准入会因为缺依赖、版本不符、清单非法而被拒，而 `enable` 仍会写下一个永远不会生效的启用位。**ME-3 必须在 PATCH 路径上做准入校验**：拒绝的模块 `enable` 返回错误，而不是返回成功再把矛盾落盘。

## 7. 交付 / 测试 / 验收

| ID | 交付 | 依赖 | 测试 | 验收 |
|---|---|---|---|---|
| **ME-3a** | manifest 支持 `impl_kind: out-of-process` + spawn 命令；进程监督（起/停/崩溃退避重启） | ME-2 | 子进程被 kill 后自动重启；重启期间该命名空间返回 503 而非 500/挂起；内核不受影响 | 一个模块挂掉不带走内核 |
| **ME-3b** | 反向代理：`/api/v1/<ns>/*` → 子进程；鉴权在内核、命名空间不可越界 | ME-3a | 无 token 访问模块路由 401；模块试图响应命名空间外的重定向不被跟随；路径穿越被拒 | 模块永远看不到未鉴权请求 |
| **ME-3c** | 回调通道：Unix socket + JSON-RPC + `initialize` 能力协商；**身份由连接决定** | ME-3a | 模块伪造 owner/分区字段无效（协议里没有该字段，且伪造 `_meta` 不影响分区）；未授予 `Memory` 的模块调 memory 方法被拒 | 分区键不可被模块影响 |
| **ME-3d** | 记忆回调 + 真配额 + 请求/响应双向上限 + 有界分页可取消 | ME-3c | 超配额写入返回明确错误；超大响应被截断为分页而非撑爆；断连即取消进行中的 recall | 不可信模块撑不爆内核 |
| **ME-3e** | 事件回调（只能发自己 `event_module`）+ 审批回调（必须带内核注入的 request id） | ME-3c | 模块发别人模块的事件被拒；无 request id 的审批请求被拒；审批能正确归因到发起用户 | 越权发事件/无归因审批都不可能 |
| **ME-3f** | mock Provider OS（本仓，仅测试用）走完整条链路 | ME-3a–e | 挂载 → 路由代理 → 事件转发 → 记忆读写 → 审批 往返全绿 | **装第三方 OS 零改内核** |
| **ME-3g** | F4e：`PATCH` 启用路径做准入校验 | ME-3a | 准入被拒的模块 `enable` 返回错误且**不落盘** | 不再有「启用了但永不生效」的条目 |

**验收总条件**（对应 SPEC-MD-ME §5 ME-3 行）：一个 mock Provider OS 挂载 + 路由代理 + 事件转发，**内核不重编**。

## 8. 做不到什么（逐条，不是遗漏）

- **不是沙箱。** 子进程以当前用户身份运行，能读写用户的文件、发网络请求。ME-3 的隔离是**内核资源**（记忆分区、事件、路由）层面的，不是操作系统层面的。要 OS 级隔离需要另一次立项（seccomp/容器/VM），且与「单机个人 agent」的定位是否匹配需要先想清楚。
- **不做模块签名与信任根。** 那是 ME-6（ADR-016 阶段 3，P4 门后）。在此之前，装一个进程外模块 = 信任它的作者，与 `curl | sh` 同级。**文档必须这么写，不能含糊。**
- **不做 `Scheduler` / `Policy` 能力的回调。** 本轮只做 `Memory` / `Events` / 审批。这两个进程内都还没有稳定消费者，先有消费者再有提供者。
- **不做跨机。** Unix socket，本地进程。远程 Provider 要重新想身份与传输，不在本轮。
- **不做模块间通信。** 模块之间不互相可见，一切经内核。这是有意的：模块直连会把内核的所有权模型架空。
- **不做热更新。** 换版本 = deactivate + activate。

## 9. 公开问题

1. **审批门的字段级契合度**：ADR-031 只核到语义层。真要与 ACP 的 `session/request_permission` 对齐字段，得逐字段比一遍——留到 ME-3e 实现时做，或裁定「只对齐语义，不追字段」。
2. **崩溃重启的退避参数**：需要一个真实的第三方模块才知道合理值。先用与 F2 一致的策略，不另立。
3. **代理的流式响应**：SSE / chunked 走代理是否需要特殊处理，等有需要流式的模块再定；mock 模块不覆盖。
4. **配额的默认值**：§4 说必须有真配额，但**具体数值需要一张用量表**（F7 也卡在这）。ME-3d 实现时先给一个保守默认 + 可配置，并把「值是猜的」写进注释。

---

> **给复审者的一句话**：本文档最该被挑战的是 §2「身份不由模块提供」和 §4「配额从地板升级成真配额」。前者若有任何一条路径让模块影响分区键，ADR-030 的所有权模型就被绕过了；后者若做成和进程内一样的「地板」，那 §4 的标题就是假的。
