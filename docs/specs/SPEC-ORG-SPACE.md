# SPEC-ORG-SPACE — 组织、空间、授权与工作上下文

> 立于 2026-08-23。起因是一句判断：**个人 Agent 不要按「个人产品」架构，底层从第一天就该假定将来存在多人，否则第二阶段会重写。**
>
> F8（PR #140）已经做掉了最不可逆的一层：记忆的所有者从「用户」变成「组织里的空间」。这份文档定义它之上的部分，**以及同等篇幅的「做不到什么」**。
>
> 关联：[`SPEC-ME-FOLLOWUPS.md`](SPEC-ME-FOLLOWUPS.md)、`rust/apps/agent24d/src/os_memory.rs`（F8 内核侧契约）。

## 这份文档的范围，先说死

**这是一个「组织记忆访问模型」，不是一个完整的「组织 Agent 模型」。**

第一版的标题和用例让它读起来像后者，复审判定这是本仓库那个老毛病的又一次发作（契约声称的比机制交付的多）。所以：它覆盖**谁能碰到哪些记忆、此刻哪些在作用域内、以及这两件事怎么被审计**。它**不**覆盖外部系统凭据、非人主体、数据驻留、法务封存、破窗访问、委托链 —— 这些在 §8 逐条列明，不是遗漏。

每一节标了状态：**【已建】** F8 已交付 ｜ **【设计】** 本文档定义、尚未实现 ｜ **【不做】**。

## 0. 要解决的问题

一个 Agent 进入组织，立刻会被问到六个问题。它们看着像一类，其实是四类，混在一起设计一定重写：

| 问题 | 真正属于 | 本文档 |
|---|---|---|
| A 能看这条记忆吗？ | 授权 | §3 §4【设计】 |
| B 能让 Agent 去调用它吗？ | 授权（**两个主体**） | §4【设计】 |
| 财务的东西不能漏进客户对话 | **作用域**，不是授权 | §5【设计】 |
| 这是员工观点还是公司事实？ | 溯源 | 【不做】F11 |
| 两个人给出冲突信息怎么办？ | 断言层 | 【不做】F11 |
| 谁改了这条规则？ | 审计 | §6【设计】 |

**「财务的东西不能漏进客户对话」不是权限问题** —— 顾问对两个客户的资料都有权限。它是「此刻什么在作用域内」的问题。当权限做，会得到一个每天都要改授权的系统；当作用域做，是一次选择。见 §5。

## 1. 主线：**按变更频率分层**

F8 的教训一句话：**写进存储 key 的东西，改不动。** 所以每个概念只问一件事 —— 多久变一次：

| 概念 | 是什么 | **在 key 里？** | 多久变 | 状态 |
|---|---|---|---|---|
| **Org** | 租户边界，拥有空间 | ✅ | 几乎不变 | 【已建】 |
| **Space** | 记忆容器，所有权单位 | ✅ **（只有不可变 ID）** | 很少 | 【已建】仅 module 私有 |
| **Member** | 我默认在哪个 org 做事 | ❌ | 很少 | 【已建】单成员 |
| **Group**（部门/团队） | 有名字的一组人，授权主体 | ❌ | **经常** | 【设计】 |
| **Grant** | 谁能对哪个空间做什么 | ❌ | **经常** | 【设计】 |
| **Workspace** | 此刻哪些空间在作用域内 | ❌ | **每天** | 【设计】 |

### 部门的准确说法

**部门标识不进 key。** 组织重组是企业里最频繁的结构变更，把 `finance` 编进 owner key 等于每次重组重写全部记忆行。

但要说准：**部门完全可以拥有一个隔离空间** —— 只是进 key 的是那个空间**稳定的不可变 ID**，不是 `finance` 这个部门标识。第一版写成「部门永远不能对应隔离边界」，过头了。部门在授权上是一个 **Group**；它拥有的空间是 **Space**。

## 2. 模型

```
Org ─────────────────────────────────────────────┐
 ├─ Member    (org, user)                        │  我的 home org
 ├─ Group     (org, id, name)                    │  部门 / 团队
 │    └─ GroupMember (group, user, since)        │
 └─ Space     (id, org, kind, display_name, class)
      id:    不可变、生成的、永不复用  ◄── 唯一进 key 的部分
      kind:  personal | module | shared
      class: internal | confidential

Grant  (space_id, principal, capability, lifecycle)
   principal:  User(id) | Group(id) | Module(name)
   capability: read < write < admin
   lifecycle:  granted_by, granted_at, expires_at?, revoked_at?

Workspace (active scope)                  ← 视图，不拥有任何东西
   └─ 一组 space id（有序）
```

### ⚠️ Space 的 ID 必须不可变 —— 这是一道硬门槛

**F8 的 `partition_key` 把整个 space 字符串编进 owner key。** 所以：

- **`Space.id` 是生成的、不可变的、永不复用的**（如 `spc_<ULID>`）。
- **`display_name` 可以随便改**，它不进 key。
- 今天唯一存在的 space 是 `os:<module>`，由模块名派生 —— 这是 F8 明确接受的债：**改模块名会产生一个新分区，老数据留在老名字下**。shared space 绝不能重复这个形状。

**这条不能等第二个用户。** 一旦第一个 shared space 用名字做了 ID，改名就等于弃数据 —— 跟 F8 修的是同一类错误。见 §9 硬门槛。

### `classification` 的准确说法

只有两级：`internal | confidential`。它 gate **一件事**：**`confidential` 的空间不把句柄发给带网络出口能力的模块。**

**这是一条出口约束，不是一套企业密级体系。** 它不管间接调用、不管数据被复制到低密级空间、不管已缓存的内容。叫它 classification 容易让人以为有比机制更强的保护 —— 所以这里写明它是什么。

### 为什么没有 `OrgMembers` 主体

第一版有一个 `OrgMembers` 主体（「org 全员」）。复审指出它让 §3 自相矛盾：如果全员是可授权主体，那**加入成员就等于立刻获得一批权限**，而 §3 恰恰声称 membership ≠ access。

删掉它。要「全员可读」就建一个 group 并显式加人 —— 多一步，换来 membership 这个词只有一个意思，以及不存在「我不知道自己被授了什么」的隐式广播。

## 3. 关键分离：**成员资格 ≠ 访问权**

- **Member 回答「我默认在哪个 org 做事」。** 只用来解析一个默认值。**一人一个 home org。**【已建：F8 拒绝一人两 org，因为那会让 org 解析不出来、所有模块失去记忆】
- **Grant 回答「我能碰什么」。** 可以指向**非成员**。

分开之后：跨组织协作**不需要把人塞进两个 org**；顾问/外部审计/客户对接人都是「非成员 + 有 grant」；离职是一次授权清理，不是一次数据迁移（**但不是「一次撤销」**，见 UC7）。

---

## 4. 判定：**两个主体的交集**【设计】

Agent 系统跟普通权限系统真正不同的地方：一次交互式访问有**两个**主体 —— **谁在问**（user）和**什么在执行**（module）。

```
allow(user U, module M, space S, op) =
      effective(U, S) ⊇ op          // U 自己 + 所属 Group
  AND effective(M, S) ⊇ op          // M 这个模块
  AND (S.class ≠ confidential  或  M 无网络出口能力)
```

**模块不能超出用户的授权；用户也不能借模块去够模块没被授权的东西。** 没有这条，装一个第三方模块就成了越权的路径。

**「一次交互式访问」是准确的措辞，第一版写的「每一次访问」不是。** 定时任务、后台 agent、服务账号没有「谁在问」—— 这个模型**表达不了**它们，见 §8。本仓库已经有 `agent24-scheduler`，所以这不是假想问题，是一个已知缺口。

### capability 是一条格，不是一个集合

```
read < write < admin
admin ⊇ write ⊇ read
```
`admin` 额外意味着：管理该空间的 grant、改 `display_name`、归档该空间。**`admin` 不意味着删除空间**（见 §8 保留治理）。

`effective(P, S)` = 所有命中 P 的、未撤销、未过期的 grant 的 capability 上确界。

**只做并集，不做否定。** 没有 deny 规则 —— 有 deny 就有优先级，有优先级就有「为什么我看不到」查不清的那天。要收紧就撤销。

### 执行点是**句柄发放**，不是每次查询

F8 的形状已经如此：模块拿到的句柄**绑死一个分区**，没有参数能让它换一个。所以判定发生在**内核决定把哪些空间的句柄交给这个 (user, module) 组合**的时候。

这样 `confidential` 的约束才是构造性的：会联网的模块**根本拿不到**那个空间的句柄，而不是每次查询被拒。第一版在公式里写运行时 allow、在用例里写「结构上拿不到句柄」，两处不一致 —— 以句柄发放为准。

## 5. Workspace：作用域，不是权限【设计】

**权限说「我可以碰什么」，作用域说「此刻什么在里面」。两者都要允许。**

```
in_scope(S) = allow(U, M, S, op)  AND  S ∈ active_scope
```

顾问 Alice 对客户 A 和 B 的资料都有**合法权限**。做 A 的事时 B 不该出现 —— 不是靠 prompt 叮嘱模型别提，是**结构上不在检索范围内**。

**这一层是必要的**（复审同意：一个表示合法可达集合，一个表示本次检索集合，是实质区别）。但**持久化的、有名字的 Workspace 对象可以延后** —— 早期由**请求级的 active scope** 承载同样的安全语义就够了。

Workspace 不拥有任何东西，不进 key，删掉它不会删掉任何记忆。

## 6. 审计【设计】

`EventLog`（M-D 的情节权威）已在。**要写事件的不止 grant：**

- grant 的创建、撤销 —— 带 `granted_by`
- **group 成员的加入与移除** —— 第一版漏了这条。group 成员变化**会改变 effective access**，只审计 grant 的话，「某人在某日为何能访问」根本重建不出来
- space 的创建、归档、`display_name` 变更

撤销是**软撤销**（写 `revoked_at`，保留行）—— 硬删会让审计记录随权限一起消失。

**过期不产生事件。** `expires_at` 让访问**惰性失效**（判定时比较时间），但时间流逝本身不执行写操作。要在到期那一刻留下事件，需要一个 sweeper —— 本期不做。第一版把「可记录」和「自动产生到期事件」混为一谈。

## 7. 用例

> 每个用例都写全**两个主体**。第一版只写用户一侧，等于在用例里违反了自己最核心的规则。

### UC1 · 个人用户（org of 1）
一个 org、一个 member、一个 personal space、每模块一个 module space。

**空间创建时自动铸一条 `admin` grant 给创建者** —— 没有「隐式 admin」这种规则。第一版写「不需要任何 grant，自己的空间隐含 admin」，跟 §4 的公式直接冲突（`effective` 只由 grant 产生，无 grant 必须拒绝）。用一条真实的初始 grant 代替一条隐式规则，公式就不用开特例。

模块要读用户的 personal space，仍需要一条给 `Module(M)` 的 grant —— 装模块时由用户授予。**界面上感觉不到「组织」，但底下没有特例代码。**

### UC2 · 一个人加入公司
Jason 的 home org 仍是他自己的，Acme 给他发 grant。

**准确的说法**：模型让「个人」和「Acme」成为**两个不同的空间**，默认在**两个不同的 workspace** 里，所以**默认不会混**。

**模型不保证「不流进」。** 只要 Jason 对两边都有 grant，把两个空间放进同一个 active scope，检索就会同时命中 —— **没有任何信息流控制**。第一版说「这只有在成员资格≠访问权之下才成立」，是错的：那条分离决定**可达性**，不决定**流向**。默认隔离是一次配置选择，不是一条不变量。

### UC3 · 部门
Finance 五个人 → `Group(finance)`。空间 `spc_7QK…`（display_name「Finance Private」）授予 `Group(finance)` read+write。
**同时**，能读它的模块各需一条 `Module(...)` grant —— 只给人授权，`allow` 仍然不通过。

- **新人入职**：加进 group。不碰空间，不碰 key。
- **组织重组**：改 group 成员。**key 一行不动。**
- **改名**：改 `display_name`。**key 一行不动**，因为进 key 的是 `spc_7QK…`。

### UC4 · 客户隔离（顾问）
同一 org 下两个 shared space。Alice 对两者都有 grant，相关模块也有。
她的 active scope 只含客户 A → **B 的内容不在检索范围内**。权限没变，作用域变了。

### UC5 · 临时授权
外部审计师 30 天访问某财务空间 → grant with `expires_at`。
→ **到期后判定不再通过**（惰性）。**到期本身不产生事件**（§6）。

### UC6 · Agent 代表用户行动（交集）
Bob 对某空间有读权限，第三方模块 X 没有 → Bob 通过 X **拿不到**。
X 有而 Bob 没有 → **也拿不到**。

### UC7 · 离职（**不是一次撤销**）
第一版说「一次授权撤销」，是错的。闭环至少要三步：
1. 撤销 Alice 的**直接** grant（软撤销，保留行）；
2. 把她移出**所有 group** —— 否则她仍从 group 那侧拿到访问；
3. 终止她在该 org 的 **Member** 状态（如果她是成员）。

三步都要写审计事件。她写进共享空间的记忆**留在 org** —— 那些记忆属于空间，不属于她。她的 personal space 跟她走。

**模型没有 engagement 生命周期**：一个外包有多条直接 grant 时，离场要靠**发现并撤销全部**，单条 `expires_at` 不构成整体闭环。见 §8。

### UC8 · 「导出属于 Bob 的一切」
**这个问题在共享空间里没有答案**，合规场合一定会问：
- Bob 的 personal space → 全部，可导出可删除
- Bob **创建**的分区 → 溯源可查（`logical_user`）【已建】
- Bob **断言**的条目 → 需要 `asserted_by`【不做，F11】
- Bob 写进共享空间的内容 → **属于 org**，不随他走。返回整个空间是超采，返回空是漏采

### UC9 · 密级
`confidential` 空间的句柄**不发给**带网络出口能力的模块（§4 执行点）。
**前提**：模块的网络能力必须有一份内核可信的登记 —— **今天没有**，见 §8。

## 8. 明确不做 / 做不到

这一节和上面同等重要。本仓库过去二十余轮复审抓到的，几乎全是「契约声称的比机制交付的多」。

### 边界
1. **不是沙箱。** 进程内模块是受信代码。约束的是**内核交出什么**。
2. **不做加密隔离。** 同一 SQLite 文件、同一进程 —— 能读文件的人能读全部。
3. **不做字段级/行级权限。** 粒度是**空间**。要更细就再开一个空间。
4. **不做 deny 规则。**
5. **不做配额**（F7 仍欠）。单条大小上限是地板不是配额。
6. **ID 是数据库全局的** —— 两个空间铸同一 id 会互相拒绝写入（可用性通道，不是泄漏）。
7. **一人一个 home org。** 跨组织靠 grant。

### 表达不了（复审逐条点出，这里逐条承认）
8. **外部系统凭据（credentials）。** API key、OAuth token 这类东西**不在本模型内**。它们的形状跟 Space 很像（属于某个空间、授予某些主体、有生命周期、要轮换），**将来应作为一种新的受管资源接进同一套 Grant**，但本期完全没有。这是相对于「组织 Agent」这个目标最大的缺口，明说。
9. **非人主体**：服务账号、定时任务、后台 agent、workload identity。`Module(name)` 是全局的，分不出同一模块的不同部署/实例/用途。
10. **委托与破窗。** 临时 grant 能表达「结果」，不能表达「过程」：谁有权代表谁委托、委托是否受原边界限制、破窗的理由/审批/通知/事后复核、源授权撤销后派生 grant 是否级联失效 —— 全都没有。
11. **子公司 / 控股结构。** Org 是**扁平**的，没有父子、没有继承边界。表达不了「集团可审计子公司，子公司互不可读」。
12. **数据驻留与法务封存。** Space 没有 region、没有 retention、没有 hold 状态；capability 里没有 delete/retain 语义。
13. **空间的 stewardship。** 团队解散后空间不会消失（好事），但没有 steward、没有生命周期状态、没有接管规则、没有孤儿检测 —— **存得住，治理不了**。
14. **嵌套 group。** 复杂矩阵组织会摊成大量平铺成员关系。
15. **模块网络能力的登记**（UC9 的前提）。
16. **权限不管内容对错。**「这条该不该存在」「两人说法矛盾」属于断言层（F11）。

## 9. 硬门槛：**不能等第二个用户的三件事**

其余都能等真实需求。这三件一旦有数据就重演 F8 修的那个错误 —— 维度定错、事后才发现：

1. **shared / personal space 的稳定不可变 ID**（§2）。F8 把整个 space 字符串编进 owner key。**必须在第一个 shared space 建立之前定死。**
2. **org/space 是否可能跨物理数据库或地区。** 今天明确是单 SQLite 文件。数据驻留后补，可能要搬迁全部 owner-keyed 数据。**必须在写入多地区数据之前决定。**
3. **agent loop 的 personal 记忆归属**（今天用裸 user id，游离在模型外）。**必须在它跟空间模型产生任何交互之前定下迁移规则。**

### F8b 的接缝签名（**这才是 F8b 的价值所在**）

复审说得对：光有一个叫 `Authorizer` 的 trait 和「两百行」不能证明形状是对的。**签名必须现在就容得下将来要问的东西**，否则调用点还要再铺一次：

```rust
struct AccessRequest<'a> {
    actor:     Actor<'a>,        // 今天只有 User；Service 是已知缺口(§8.9)
    module:    &'a str,          // 第二个主体
    space:     &'a SpaceId,      // 不可变 ID
    op:        Op,               // read | write | admin
    scope:     Option<&'a ActiveScope<'a>>,  // 请求级作用域(§5)
}
struct Decision { allow: bool, reason: &'static str }  // reason 供审计
```

默认实现：只对该模块自己的私有空间返回 allow，其余 deny —— **跟今天完全等价，行为零变化**。

**F8b 不冒充 access control。** 它只是让「能不能」这件事第一次有一个被问到的地方。

## 11. 会被问到、但本文档不回答

- **角色（Role）。** 没有角色，只有 group + capability。角色是两者的预设组合，等真实需求 —— 提前造角色体系是这类系统最典型的过度设计。
- **授权 UI / 审批流。** 属于产品。
- **模块自己声明需要哪些空间。** 需要模块可表达、内核可校验的清单，ME-3 之后。
- **联邦 / 多实例。** 本文档假定单 daemon、单数据库文件。
