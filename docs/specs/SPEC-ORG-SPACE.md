# SPEC-ORG-SPACE — 组织、空间、授权与工作上下文

> 立于 2026-08-23。起因是一句话的判断：**个人 Agent 不要按「个人产品」架构，底层从第一天就该假定将来存在多人，否则第二阶段会重写。**
>
> F8（PR #140）已经把最不可逆的那一层做掉了：记忆的所有者从「用户」变成「组织里的空间」。这份文档定义它之上的部分 —— 部门、授权、工作上下文 —— 以及**明确不做什么**。
>
> 关联：[`SPEC-ME-FOLLOWUPS.md`](SPEC-ME-FOLLOWUPS.md)（F1–F7 台账）、`rust/apps/agent24d/src/os_memory.rs`（F8 的内核侧契约）。

---

## 0. 这份文档要解决的问题

一个 Agent 一旦进入组织，立刻会被问到六个问题。它们看着像一类，其实是四类，混在一起设计就一定会重写：

| 问题 | 真正属于 | 本文档 |
|---|---|---|
| A 能看这条记忆吗？ | 授权 | §3 §4 |
| B 能让 Agent 去调用它吗？ | 授权（**两个主体**） | §4 |
| 财务的东西不能漏进客户对话 | **作用域**，不是授权 | §5 |
| 这是员工观点还是公司事实？ | 溯源 | §8，不在本期 |
| 两个人给出冲突信息怎么办？ | 断言层 | §8，不在本期 |
| 谁改了这条规则？ | 审计 | §6 |

**「财务的东西不能漏进客户对话」不是权限问题** —— 顾问对两个客户的资料都有权限。它是「此刻什么在作用域内」的问题。把它当权限做，会得到一个每天都要改授权的系统；把它当作用域做，是一次选择。这条区分是本文档的核心，见 §5。

---

## 1. 一条主线：**按变更频率分层**

F8 的教训用一句话讲完：**写进存储 key 的东西，改不动。**

所以整个模型只按一个标准分层 —— 这个概念多久变一次：

| 概念 | 是什么 | **在 key 里？** | 多久变一次 |
|---|---|---|---|
| **Org** | 租户边界，拥有空间 | ✅ **是** | 几乎不变 |
| **Space** | 记忆的容器，所有权单位 | ✅ **是** | 很少 |
| **Member** | 我默认在哪个 org 里做事 | ❌ | 很少 |
| **Group**（部门/团队） | 有名字的一组人，授权主体 | ❌ | **经常** |
| **Grant** | 谁能对哪个空间做什么，带生命周期 | ❌ | **经常** |
| **Workspace** | 此刻哪些空间在作用域内 | ❌ | **每天** |

**部门绝不能进 key。** 组织重组是所有企业里最频繁的结构变更之一 —— 把 `finance` 编进 owner key，等于每次重组都要重写全部记忆行。部门在本模型里是一个 **Group**：一组人的名字，用来发授权。重组改的是 group 的成员，key 一行不动。

这也回答了「不同部门算不算不同 workspace」：**部门是 Group（谁），空间是 Space（什么），工作上下文是 Workspace（此刻）。** 三个不同的东西，混成一个就是重写的起点。

## 2. 模型

```
Org ─────────────────────────────────────────────┐
 │                                               │
 ├─ Member    (org, user)                        │  我的 home org
 │                                               │
 ├─ Group     (org, name)                        │  部门 / 团队
 │    └─ GroupMember (group, user)               │
 │                                               │
 └─ Space     (id, org, kind, name, class)  ◄────┘  拥有记忆
      kind:  personal | module | shared
      class: public | internal | confidential

Grant  (space, principal, capability, lifecycle)
   principal:  User(id) | Group(id) | Module(name) | OrgMembers
   capability: read | write | admin
   lifecycle:  granted_by, granted_at, expires_at?, revoked_at?

Workspace (id, owner_user, name)          ← 视图，不拥有任何东西
   └─ 一组 space 引用（有序）
```

### Space 的三种 kind

- **`personal`** —— 一个人自己的。今天 agent loop 的记忆用裸 user id 做 key，游离在模型外，F8c 把它搬进来。
- **`module`** —— 一个领域 OS 的私有空间（F8 已交付的唯一一种）。
- **`shared`** —— org 内多人可达。

`Customer A` **不需要新 kind**，它就是一个叫这个名字的 `shared`。少一种 kind 就少一处将来要分叉的判断。

### `classification` 的存在条件

`public / internal / confidential` **只有在它 gate 住了什么的时候才配存在**。本设计里它 gate 一件事：**`confidential` 的空间不授予带网络出口能力的模块。** 如果哪天这条不执行了，这一列就该删掉 —— 一个没人查的密级字段比没有密级更危险，因为它让人以为有保护。

## 3. 关键分离：**成员资格 ≠ 访问权**

这是整个设计里最省事的一条，也是 F8 五轮复审逼出来的：

- **Member 回答「我默认在哪个 org 里做事」。** 它只用来解析一个默认值。**一个人只有一个 home org。**
- **Grant 回答「我能碰到什么」。** 它可以指向任何 user，**不要求对方是 member**。

两者一分开，三个难题当场消解：

1. **跨组织协作不需要把人塞进两个 org。** F8 现在正是拒绝这个 —— 一个人在两个 org 里，他的 org 就解析不出来，所有模块失去记忆。正确做法是给对方的人发一条 grant。
2. **顾问 / 外部审计 / 客户方对接人**，都是「非成员 + 有 grant」，不是「成员」。
3. **离职**变成一次授权撤销，不是一次数据迁移。

---

## 4. 判定规则：**两个主体的交集**

这是 Agent 系统跟普通权限系统真正不同的地方。每一次访问都有**两个**主体：**谁在问**（user）和**什么在执行**（module）。

```
allow(user U, module M, space S, op) =
      effective(U, S) ⊇ op        // U 自己的授权（含所属 Group、OrgMembers）
  AND effective(M, S) ⊇ op        // M 这个模块的授权
  AND S.class ≠ confidential  或  M 无网络出口能力
```

**模块不能超出用户的授权；用户也不能借模块去够模块没被授权的东西。**

没有这条交集，装了某个第三方模块的人，就能通过那个模块读到他自己本来读不到的东西 —— 这是这类系统最常见的越权形状，而且极难在事后加上，因为要给每一条读路径补调用点。

**所以 F8b 只做一件事：把这个判定点铺进所有读路径，默认实现等价于今天的行为**（模块只能碰自己的私有空间）。判定逻辑将来随时能换，调用点事后补不起。

### `effective` 的算法

```
effective(principal P, space S) =
    ⋃ { g.capability | g ∈ Grant(S),
                       g.principal 命中 P,
                       g.revoked_at is null,
                       g.expires_at is null 或 > now }
```

「命中」：`User(P)` 直接命中；`Group(G)` 当 P ∈ G；`OrgMembers` 当 P 是 S.org 的 member。

**授权只做并集，不做否定。** 没有 deny 规则 —— 有 deny 就有优先级，有优先级就有「为什么我看不到」查不清的一天。要收紧就撤销，不是叠加一条否定。

## 5. Workspace：作用域，不是权限

**权限说「我可以碰什么」，工作上下文说「此刻什么在作用域内」。两者都要允许。**

```
in_scope(S) = allow(U, M, S, op)  AND  S ∈ active_workspace.spaces
```

为什么值得单独一层：顾问 Alice 对客户 A 和客户 B 的资料都有合法权限。她在做 A 的事时，B 的东西**不该出现** —— 这不是靠 prompt 叮嘱模型别提，是**结构上查不到**。

Workspace **不拥有任何东西**，它只是一个有序的 space 引用集合。所以：

- 它不进 key，随便改。
- 它可以跨 org 引用空间（前提是每个空间都有合法 grant），这正是「一个人在不同组织里开不同 workspace」的形态。
- 删掉一个 workspace 不会删掉任何记忆。

---

## 6. 审计：授权变更是事件

`EventLog`（M-D 的情节权威）已经在了。**每一次 grant 的创建、撤销、到期，都写一条事件**，带 `granted_by`。「谁改了这条规则」因此是一次查询，不是一个需要新机制的问题。

撤销是**软撤销**（写 `revoked_at`，保留行）—— 硬删会让审计记录随权限一起消失。

## 7. 用例

### UC1 · 个人用户（org of 1）
一个 org、一个 member、一个 personal space、每模块一个 module space。**不需要任何 grant**（自己的空间隐含 admin），界面上完全感觉不到「组织」的存在。这就是 `Organization size = 1`，**没有任何特例代码**。

### UC2 · 一个人加入公司
Jason 的 home org 仍是他自己的。Acme 给他发 grant。
→ **他的个人记忆不会流进 Acme，Acme 的不会流进他的个人 workspace。** 这只有在「成员资格 ≠ 访问权」之下才成立。

### UC3 · 部门
Finance 有 5 个人 → `Group(finance)`。`Finance Private` 空间授予 `Group(finance)` read+write。
- **新人入职**：加进 group。不碰空间，不碰 key。
- **组织重组**：改 group 成员。**key 一行不动。**

### UC4 · 客户隔离（顾问场景）
同一个 org 下 `Customer A` / `Customer B` 两个 shared space。Alice 对两者都有 grant。
她的 workspace「Acme 项目」只包含 Customer A。
→ 她问 agent 时，**B 的内容不在作用域内，查不到**。权限没变，作用域变了。

### UC5 · 临时授权
外部审计师需要 30 天访问某个财务空间 → grant with `expires_at = now + 30d`。
→ **到期自动失效，不依赖任何人记得收回。** 这是 grant 带生命周期的真实理由。

### UC6 · Agent 代表用户行动（交集规则）
Bob 对 `Team Shared` 有读权限。他装了第三方模块 X，X 没有该空间的 grant。
→ Bob 通过 X 提问，**拿不到** Team Shared 的内容。
→ 反过来 X 有 grant 而 Bob 没有，**也拿不到**。

### UC7 · 离职
撤销 Alice 在 Acme 的全部 grant（保留行以供审计）。
→ 她写进 `Team Shared` 的记忆**留在 Acme** —— 那些记忆属于空间，不属于她。
→ 她的 personal space 跟她走。

### UC8 · 「导出属于 Bob 的一切」
**这个问题在共享空间里没有答案，文档必须说清楚**，因为合规场合一定会问：
- Bob 的 personal space → 全部，可导出可删除。
- Bob **创建**的分区 → 溯源可查（`logical_user`）。
- Bob **断言**的条目 → 需要 `asserted_by`（F11，未做）。
- Bob 在共享空间里写下的内容 → **属于 org**，不随他走。返回整个空间是超采（带走了别人的），返回空是漏采。

### UC9 · 密级
`Confidential` 的 `Finance Private` 空间，不授予带网络出口的模块。
→ 一个会联网的模块，**结构上拿不到**这个空间的句柄。

## 8. 明确不做 / 做不到

这一节和上面同等重要。这个仓库过去二十轮复审抓到的，几乎全是「契约声称的比机制交付的多」。

1. **不是沙箱。** 进程内模块是受信代码。本设计约束的是**内核交出什么**，不是一个确定要越界的模块最终能碰到什么。
2. **不做跨 org 的空间共享。** 一个空间属于且只属于一个 org。跨组织协作 = 给对方的人发 grant，**不是**让空间属于两个 org，**更不是**让人成为两个 org 的成员。真正的组织间信任关系是另一个量级的问题，本期不碰。
3. **不做字段级 / 行级权限。** 授权粒度是**空间**。要更细就再开一个空间。
4. **不做加密隔离。** 同一个 SQLite 文件、同一个进程。隔离是**内核强制**的，不是密码学强制的 —— 能读到文件的人能读到全部。
5. **不做配额**（F7 仍欠着）。一个模块仍能用大量小的、合法的写入挤占共享数据库。单条大小上限是地板，不是配额。
6. **ID 是数据库全局的。** 两个空间铸出同一个 id 会互相拒绝写入。这不是泄漏，是一条可用性通道。
7. **不做 deny 规则**（见 §4）。
8. **部门不是隔离边界。** 它是一组人。隔离边界永远是空间。
9. **一个人只有一个 home org。** 不支持「同时是两个组织的成员」—— 跨组织靠 grant。
10. **权限不管内容对错。** 「这条记忆该不该存在」「两个人说法矛盾」是断言层的问题（F11），不是授权问题。

## 9. 分期

| 阶段 | 内容 | 何时 | 为什么是这个时候 |
|---|---|---|---|
| **F8** ✅ | 所有权维度 = (org, space)；org 为一等实体 | PR #140 | key 改不动，必须趁零数据 |
| **F8b** | **判定接缝**：内核持有的 `Authorizer`，默认实现等价于今天的行为 | **紧接着** | 贵的是**调用点**，不是策略逻辑 |
| **F8c** | agent loop 自己的记忆搬进 `personal` space | 之后 | 它是今天唯一游离在模型外的分区 |
| **F9** | `spaces` + `grants`（带生命周期）+ `groups` + 交集判定 + 审计事件 | **等第二个真实用户** | 形状要被真实需求定，不是被想象定 |
| **F10** | Workspace（作用域视图） | F9 之后 | 依赖多个空间存在才有意义 |
| **F11** | `asserted_by` + 冲突断言并存 | 跟 F2 一起 | 属于断言层 |

**现在只做 F8b。** 约两百行，不引入任何存储，**不改变任何行为** —— 它只是让「能不能」这件事第一次有一个被问到的地方。

**F9 明确不现在做。** 没有第二个真实用户时做授权 UX、角色层级、委托，会把形状全部猜错。

## 10. 会被问到、但本文档不回答

- **角色（Role）**。本设计里没有角色，只有 group + capability。角色是 group 与 capability 的一种预设组合，等真实需求出现再说 —— 提前造角色体系是这类系统最典型的过度设计。
- **授权的 UI / 审批流。** 属于产品，不属于内核。
- **模块自己声明它需要哪些空间。** 需要一个模块能表达、内核能校验的清单，属于 ME-3 之后。
- **联邦 / 多实例。** 本文档假定单个 daemon、单个数据库文件。
