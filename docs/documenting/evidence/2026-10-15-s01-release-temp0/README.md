## J9：温度确实是 0，结果可以复现

ME4-S2b 设计 §7 J9 要求经内核实测。

1. **温度**：本次验收的 19 次模型请求，Ollama 默认日志级别下打印的采样参数都是 `temp = 0.000`。
2. **重放**：验收结束后，在同一个 `HOME` 里，对 `s01-07` 用同样的 schema 以 `rerun` 重新抽取 3 次。这 3 次请求在 Ollama 日志里也都是 `temp = 0.000`。
   - **3 次结果逐字节相同**：20 个字段的取值、`normalized` 和锚点都一样。
   - **但与验收时那一次有 12 个字段不同**。多数只是 `normalized` 用了中文还是英文，例如「无需」与「no」。也有 3 个取值不同，例如「B座 0302-2208 单元」与「0302-2208 单元」，「物业前台」与「FM front desk」。
   - **原因**：Ollama（llama-server）的 prompt cache。
     - 验收时 `s01-07` 是在别的文档之后算的，缓存里的前缀只部分命中；
     - 3 次重放时缓存里已有完全相同的提示词，日志写着 `prompt is already in the cache`。

     温度 0 时是贪心解码，缓存状态不同，计算路径就不同，浮点误差会让个别位置选中不同的词。
   - 这**不是**设计 §8 的 R-a。R-a 说的是不同硬件、不同后端版本之间不能逐字节一致；这次是同一台机器、同一个后端，只是缓存命中情况不同。这是一条新的残余风险，在设计 §8 补为 R-f。
   - 上一份基线 README 说温度 0 的两次全量运行「结果完全相同」。那是在当时条件下观察到的事实，不是保证：本次说明，缓存状态不同时，结果可以不同。
   - 对抽取的含义：`extractor_version` 和业务键保证同样的请求重放同一个结果，不会重新抽取。要比较两次运行，应该看分数，不要逐字节比对。

## 还没解决的

- **答案质量受 7B 所限**：常把值改写成规范形式，或只答一部分；认不出日期矛盾（`conflict` 0/2）。
- **大模型的实验（不入库）**：另一个会话在 Modal 上的 GPU（L40S）上用同样的温度 0、v3 跑过。材料不在本仓库：
  - `qwen2.5:32b`：必答 75/115；
  - `qwen3.8:27b` 关思考：75/115，严重错误 4；
  - `qwen3.8:27b` 开思考 + 「两遍法」：84/115，严重错误 2。

  它们指出了下一步的方向：Ollama 上的思考模型在加了 schema 约束时会「想对写错」。要不要在内核的 Ollama 路径上关思考、或者做两遍法，另写设计请 David 定。
