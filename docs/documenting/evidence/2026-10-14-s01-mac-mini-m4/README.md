# 2026-10-14 S01 验收：本机基线（Mac mini M4，`qwen2.5:7b`）

这是 DOC-1-09 第 9 步第一次用真实内核和本地模型跑的验收（设计文档 `docs/documenting/acceptance/README.md` §5）。
**结论：不通过。** 这份报告作为基线入库，供后面的修改对照。还没有人工复核，字段正确率是下限。

`report.json` 和 `report.md` 由验收 harness（`packages/documents-accept`）写出，没有手工改动。

- 复核前的机械打分：
  - 必答字段正确率 21/115（18.3%），背景字段正确率 12/35（34.3%）；

## 不通过的原因（已查明的部分）

1. **内核在 120 秒时断开模型调用。** 抽取一次最多输出 4096 token，这台机器约 21 token/s，写满要 195 秒；而 provider、内核 RPC、SDK 三层都是固定的约 120 秒。
   Ollama 日志里有 4 次恰好 `2m0s` 的 500，`s01-08` 因此失败。修订设计见 `docs/design/ME4-S2a-model-call-progress-timeout.md`（#948，待 jason 审）。
2. **模型的答案质量。** `qwen2.5:7b` 常把值改写成规范形式（如 `2026年10月8日` → `2026-10-08`），或只答一部分。同样的样本，用 `qwen2.5:14b` 在临时放宽超时的实验构建上跑，必答字段正确率是 49/115（42.6%）。那次运行用的不是本 commit 的构建，所以不作为证据入库。
3. **锚点大多丢失**：有值的候选值里，88/128 个被记为没有出处，其中 73 个的原因是“引文不在所指的块里”。
   - **全有或全无**：抽取器只要发现一个值的某一条引文对不上它所指的块，就把这个值的锚点全部丢掉（`extract/ground.rs` 的 `ground()`）。
   - **没有设温度**：抽取时没有设采样温度，Ollama 用的是默认的 1.0，模型每次给出的引文差别很大。
   - **重放对比**：把 s01-07 的抽取请求原样重放，默认温度 3 次、温度 0 三次。默认温度下，写错的引文是 5/17、4/19、17/35，能落地的值是 12/17、14/18、9/19。温度 0 下三次完全相同，写错的引文 3/19，能落地的值 15/18。
   - **剩下的 3 条**：温度 0 下仍对不上的 3 条引文，在哪个块里都找不到，是模型改写了原文。所以在 s01-07 这一个请求里，把块编号只当提示、由 OS 按原文定位帮不上忙。
     但 8 份样本全量就不同了（见下面的「后续实验」）。

## 后续实验（2026-10-15，不入库）

用只在本机构建、不提交的实验构建测量：四处时限放宽到 30 分钟；需要温度 0 时，内核发给 Ollama 的请求写死 `temperature: 0`（日志核实为 `temp = 0.000`）。数字都是复核前的机械打分。

| 配置 | 必答字段正确 | 有值的候选值里带锚点的 | 金标锚点命中 |
|---|---|---|---|
| 本基线：温度 1.0，抽取器 v2 | 21/115 | 40/128（31.3%） | 28/185 |
| 温度 1.0，v2 | 30/115 | 55/135（40.7%） | 28/195 |
| 温度 1.0，v3（引文按原文定位） | 32/115 | 73/134（54.5%） | 41/183 |
| 温度 0，v2 | 44/115 | 68/138（49.3%） | 41/206 |
| 温度 0，v3 | 44/115 | 88/138（63.8%） | 59/206 |

- 温度 0 让正确率从 18%–28% 升到 38%，两次结果完全相同。
- 引文按原文定位（v3）不改变答案，只让锚点落地更多。
- 第 2、3 行是两次不同的运行，答案本身也有差别。只看定位规则的效果：把同一批回答（7b、温度 1.0、16 个请求、133 个带引文的值）分别按 v2 和 v3 的规则核对，能落地的值从 68 个增加到 82 个（PR-Daemon 在 #959 的意见）。
- 曾有一次用派生模型名（Modelfile `PARAMETER temperature 0`）跑的「温度 0」全量，其实仍是 1.0：Ollama 的 OpenAI 兼容层在请求不带温度时写入 1.0，并优先于 Modelfile。上表里那次运行是第二行，不是温度 0。
