## 0. 范围

harness 把 S01 的样本经**已注册的操作**跑一遍，对照金标打分，并按追溯链记录证据。

- **走产品路径**：只调真实内核转发的 REST 路由 `/api/v1/documents/*`，documents 模块按正常方式安装。不读 `data_dir`，不直接调引擎，不经任何演示界面。
- **第 1 片只有 REST 这一条通道**。对话入口（模块声明的工具）等 #735 落地后，作为第二条通道接入，跑同一批检查。
- **不替代单元测试**。cargo 和 vitest 的测试证明代码按契约工作；harness 证明装好的产品在真实样本上给出了什么结果。
- **第 2 片**（编辑、提交、导出）的检查项另写，沿用本文的证据格式。

## 1. 形态

| 项 | 决定 |
|---|---|
| 位置 | `packages/documents-accept`，TypeScript，用 `tsx` 运行，`vitest` 测试 |
| 类型 | 请求和响应的类型取自 `@agent24/api-client`（由 `protocol/openapi.yaml` 生成），不手写第二份 |
| 连接 | 读内核写的状态文件 `~/.agent24/daemon.json` 里的端口和 token；路径可以用 harness 的 `--daemon-json` 参数另指 |
| 输入 | `docs/documenting/samples/s01/<id>/` 下的 `source.*`、`meta.yaml`、`gold.json`，加上本文新增的 `ask.json`（§2） |
| 输出 | `docs/documenting/evidence/<日期>-s01-<机器标签>/` 下的 `report.json` 和 `report.md`（§5）。机器标签由运行的人给，写硬件（例如 `m4-16g`），不用主机名 |

选 TypeScript 的理由：打分和报告的单元测试进 CI 现有的 Typecheck + Test；类型来自 OpenAPI 的生成物，契约一变，类型检查先失败；不需要新的工具链。`eval/decide/bench` 用 Python 是因为它要加载模型库，这里用不到。

- **未核对的金标不进入统计**（样本规范 §5 第 3 步）：`gold.json` 的 `verified_by` 不是 `david` 的样本，harness 跳过并在报告里列出。
- **每次运行都重新导入样本**，得到新的文档（同一份字节导入两次是两个文档，ADR-DOC-02 §3），所以不会重放上一次运行的抽取结果。DOC-1 不提供删除，这些文档会留在 `data_dir` 里。
- **可重试的 503 要重试**。例如第一次读文本时文本层还在解析，会回 `engine_unavailable`（`details.retryable: true`）。harness 按间隔重试，到上限仍不成才记失败。

## 2. `ask.json`：向抽取提的问题

金标只有答案，没有问题。每个样本新增一份 `ask.json`，内容就是抽取请求的 `schema`：

```json
{ "fields": [
  { "key": "shutoff_date", "description": "停水日期", "type": "date" },
  { "key": "contact_phone", "description": "物业联系电话", "type": "identifier" }
] }
```

- `key` 与 `gold.json` 的字段一一对应，必答项和背景项（`role: context`）都问。harness 启动时校验两边的 `key` 集合相同，不同就不跑。
- `description` 用读者的话写要找什么，**不得带出答案**。harness 启动时机械检查：每个字段的 `description` 里，不得出现这个字段金标的 `value`、`normalized`，或任一候选的 `value`、`normalized`（两边都先做 §4.1 的 L2，再不分大小写、去掉全部空格）。
- `type` 取 OpenAPI 的枚举（`text`、`date`、`datetime`、`amount`、`number`、`identifier`、`boolean`）。
- 由 Claude 起草，随 PR 评审。改 `ask.json` 等于换了一组问题，之前的抽取结果不能再和新的比；报告记录每份 `ask.json` 的 sha256。

| `ACC-IDEM-2` | 带 `rerun: true` 和 `Idempotency-Key` 请求头发两次，是同一个新 job；同一个键换一个仍然合法的请求体（最后一个字段换一种类型提示），是 422 `idempotency_key_reused` | README §14 幂等 | §5.7 第 2 条 | 通过 / 失败 |
| `ACC-IDEM-3` | 抽取在运行时取消，等 job 到 `cancelled`；再发同一请求：200，同一个 `job_id`，状态仍是 `cancelled`，`attempt` 不变；`POST …/retry` 之后回到 `queued`，`attempt` 加 1 | README §14 幂等 | §5.7 第 3 条、§7 | 通过 / 失败 / 未执行 |

- **覆盖点 C1–C10**（样本规范 §2）经 `meta.yaml` 的 `covers` 落到具体字段：一个覆盖点下的字段全部判对，这个覆盖点才算通过；有字段还在待复核，覆盖点就记“待复核”。
- **`ACC-IDEM-1`、`ACC-IDEM-2` 用 1 页的 s01-07 做。** 打分用的是第一次（不带 `rerun`）的抽取。rerun 出来的那个 job 核对完就取消，不等它跑完，也不打分。
  - `ACC-IDEM-1` 等 job 结束之后再重放，这样重放之外没有别的东西在动。已成功或已取消的 job 原样返回（200，状态、`attempt`、`extraction_id` 都不变）；失败或中断的 job 按 §5.4 重新排队（202，`queued`，`attempt` 加 1），这同样算通过，报告里注明是哪一种。
  - 抽取路由的每一次应答都按路由自己的约定核对：200 只配已成功或已取消的 job，202 只配还在排队、运行或正在取消的 job；应答里的 job 必须是这份文档第 1 版的抽取。新的 rerun 必须是 202 加一个排队或运行中的 job。
  - rerun 的请求起出来的每一个 job（包括本不该被接受的那一次）核对完都取消；取消和 `retry` 的应答必须是 200 加被问的那个 job，取消之后 job 只能是正在取消、已取消或早已成功：还在排队或运行说明取消没生效，停在失败或中断则下一次同键请求会把它重新跑起来（§7）。
- **`ACC-IDEM-3` 用 33 页的 s01-01 做。** 它的文本超过一个窗口、字段超过一批，至少要调 4 次模型。
  - 取消正在运行的 job，它先进入 `cancelling`，worker 到下一次调用模型之前才停下。所以要轮询到 `cancelled`（有时限）再核对；`cancelling` 期间的重放是 202 加同一个 job，不作为判定。
  - 取消到达之前 job 已经成功，这一项记“未执行”，不算失败。
  - 核对之后 `retry`，跑完的结果用于 `ACC-EXTRACT`。
- **成功应答的状态码按契约核对，不是只看 2xx。** 读 JSON 的路由一律要 200；新建上传是 201（每次运行都用新的键，不会是重放的 200）；新的导入是 202 加一个排队或运行中的 `import` job；抽取路由见上。上传的应答必须是所报的字节数和 sha256，分块的应答必须是同一个上传。
- §5.7 第 1 条的原文是“不同的 `tool_call_id`、相同的业务参数”。REST 通道没有 `tool_call_id`，这里验的是它的等价物：同一个业务请求重发。工具通道接入后再验原文。

## 4. 抽取结果怎么打分

### 4.1 比较文本用的两种规范化

沿用样本规范 §4.3 的定义，两边做同样的处理：

- **L1**：NFKC，并把连续空白（含换行）折叠成一个空格，去掉首尾空白。
- **L2**：在 L1 的基础上，再删掉至少一侧是 CJK 字符的空白。

### 4.2 状态

| 金标 \ 结果 | `present` | `missing` | `conflict` | 没有回答 |
|---|---|---|---|---|
| `present` | 看值（§4.3） | **漏掉** | **误报冲突** | **漏掉** |
| `missing` | **编造** | 判对 | **编造** | 未回答 |
| `conflict` | **擅自取舍** | **漏掉** | 看候选（§4.3） | **漏掉** |

- 金标是 `missing` 而结果给了值，不管给的是什么，都是编造（README §11.1：缺失就是缺失）。
- 金标是 `conflict` 而结果只给了一个值，是擅自取舍（样本规范 C10），即使那个值是候选之一。
- “没有回答”指结果里没有这个 `key`，或者它的 `status` 不是契约里的三种之一（这时不看它带的值）。契约保证每个字段都有回答，harness 不依赖这一点：缺了就按上表记，金标是 `missing` 时也不算判对。结果里多出的 `key` 列在报告里，不打分。
- `missing_reason` 只记录是否一致，不影响判定。文本层有未读出区域时，结果用 `unread` 代替 `not_in_document` 或 `referenced_but_absent` 算一致（ADR-DOC-02 §3.2）。

### 4.3 值

模型被要求给出“能回答问题的最短片段”，而金标的 `value` 常带着上下文（例如 “2月14日（周六）、2月28日（周六）上班”）。所以机械比较只下三种结论，拿不准的一律交人：

| 结论 | 条件 |
|---|---|
| **相同** | 两边的 `value` 经 L2 后相等；或者两边的 `normalized` 都不为空且相等，**并且**两边的 `value` 经 L2 后一方包含另一方 |
| **待复核** | 不满足上一条，但两边的 `value` 经 L2 后一方包含另一方，或者两边的 `normalized` 都不为空且相等 |
| **不符** | 以上都不满足 |

- `normalized` 是模型自己写的，OS 不核验它与 `value` 是否对应，所以单凭 `normalized` 相等不能自动判对：另一句话里的同一个日期，`normalized` 也一样。
- 128 个有值的金标字段里，带 `normalized` 的只有 51 个。多数字段靠 `value` 的比较，“待复核”不会少。

冲突字段按 `normalized` 比候选：金标的候选和结果的候选各自按 `normalized` 分组。金标的一组在结果里**对上**，要求结果有同一个 `normalized` 的组，并且两组里各有一个候选，它们的 `value` 经 L2 后一方包含另一方；只有 `normalized` 相同的，同样不能自动算对上。

- 金标的每一组都对上、结果也没有多出的组：判对。
- 只对上一部分，记“候选不全”；结果里有金标没有的组，记“多出候选”；有组只是 `normalized` 相同，记“待复核”。这三种都交人。
- 一组也没对上（包括结果没有给出候选）同样是“候选不全”，交人，不记成“不符”：结果毕竟认出了冲突。

### 4.4 锚点

锚点比的是位置，不是字符串：

1. `ACC-FIND` 把金标每条锚点的引文定位成文本层里的 `(block_id, text_range)`，同一页上可能不止一处。只有 `find` 的命中与结果的锚点出自同一个文本层（`text_layer_sha256` 相同）时，才比位置；不同就直接走第 3 步。
2. 结果里这个值（或这个候选）的某个锚点，与其中一处落在同一个块里，而且范围有重叠，这条金标锚点就算**被覆盖**。
3. 金标锚点用 `find` 定位不到时，退而比较引文：同一页上，两条引文经 L2 后一方包含另一方，也算被覆盖。
4. 仍然对不上的，一律算**未覆盖**，并标上“`find` 定位不到”，在报告里逐条列出，人可以按 §4.7 改判。

`find` 定位不到的情况确实存在：`find` 只在单个块内匹配，不做 NFKC，也不会跳过原文里多出的空格。金标 277 条引文里至少有 4 条是这样（都在 s01-01，例如金标写 “沪财税〔2025〕145号”，文本层是 “145 号”），跨块的引文还会更多。把这些从分母里拿掉，会让恰好不给这几处证据的结果占便宜，所以不拿掉。

每个值的锚点结论：金标锚点**全部被覆盖**、**部分被覆盖**、**都没有**，或者结果本身就是 `anchors: []`（**无来源**，附它给的 `unsourced_reason`）。值相同但无来源，值仍算对，它的金标锚点全部算未覆盖（README §8：无来源的值照实标出，不悄悄采信）。

图片样本 s01-06 的 13 条金标锚点按样本规范属于 L3（待目视）：OCR 的文字与金标对不上时，它们会落进“`find` 定位不到”，要靠 §4.7 的人工改判，读第一份报告的锚点命中率时要记得这一点。

`ACC-FIND` 自己另出一个数：金标锚点在所标页上的**可达率**。它与模型无关，量的是读取引擎和查找规则。不设通过线，对不上的逐条列出原因。

### 4.5 严重错误

`severity: critical` 的必答字段，判定是编造、擅自取舍、漏掉、误报冲突、值不符或未回答的，每个字段记一条严重错误，并标明是哪一种。

- 还在“待复核”的严重字段，复核之前不计入，单独列为“待复核（严重）”，让人先看这些。
- 背景字段（`role: context`）的同类错误单独列，不计入。

### 4.6 `must_not_assert`

这些命题不能靠字符串判定（样本规范 §4.2）。harness 把每条命题和这份样本的抽取结果并排列在报告里，状态为“未评审”，由人按 §4.7 的方式填结论。

### 4.7 人工复核

机械结论不够的地方，由人写进报告目录下的 `review.json`，harness 重新生成报告时合并进去：

```json
{ "reviewer": "david", "items": [
  { "sample": "s01-03-zh-holiday-2026", "extraction_id": "ext_…", "field": "makeup_workdays_spring", "verdict": "correct", "note": "…" },
  { "sample": "s01-07-mixed-building-notice", "extraction_id": "ext_…", "must_not_assert": 3, "verdict": "not_violated" }
] }
```

- 复核只针对**这一次**的抽取结果，所以每条都带 `extraction_id`，换了结果就失效。
- 一条复核针对三样东西之一：
  - 一个字段的结论：`field` 加 `verdict`（不能再写成“待复核”）。能用的词按金标的状态来，就是 §4.2 那张表里这一行有的：金标 `present` 用 `correct`、`mismatch`、`missed`、`false_conflict`；金标 `missing` 用 `correct`、`fabricated`、`unanswered`；金标 `conflict` 用 `correct`、`mismatch`、`missed`、`chose_one`；
  - 一条金标锚点是否被覆盖（§4.4 第 4 步的改判）：`field` 加 `anchor` 加 `verdict`，取 `covered` 或 `uncovered`。`anchor` 是这条锚点在 `report.json` 里这个字段的 `anchors.anchors` 中排第几（从 1 起）；`report.md` 的“未覆盖的金标锚点”清单里每条都标着这个编号。冲突字段的锚点是按候选组排的，顺序和 `gold.json` 里不一样，以报告为准；
  - 一条 `must_not_assert`：`must_not_assert`（第几条，从 1 起）加 `verdict`，取 `violated` 或 `not_violated`。
- 对不上的条目（样本或字段不存在、`extraction_id` 不是报告里的那一次、结论不是上面的词、同一样东西判了两次时的后一条——即使前一条本身没生效）不生效，在报告里逐条列出原因。条目里不能有上面没提到的成员。
- 人改判的锚点，覆盖了就算覆盖，也不再算“`find` 定位不到”。覆盖点（§3）按人的结论再算一遍，和机械结论并列。
- 合并复核时，读回的 `report.json` 里已有的复核（各处的人的结论和复核后的汇总）一律不采信：每次都从机械结论出发，按 `review.json` 重新合并、重新计数。读回时还核对汇总数字和覆盖点仍能从各字段推出来，推不出来就拒绝。
- 人可以推翻任何机械结论，报告同时保留机械结论、人的结论和复核人。

### 4.8 汇总

样本规范 §5 第 5 步要的五个数，分母都只算必答字段，背景字段另起一行。

一个字段**判对**，指下面三种之一：金标 `present`，结果 `present` 且值“相同”；金标 `missing`，结果 `missing`；金标 `conflict`，结果 `conflict` 且候选判对。

| 指标 | 算法 |
|---|---|
| 字段正确率 | 判对的字段数 ÷ 字段数。“待复核”的字段留在分母里，复核之前不进分子，所以这个数在复核前是下限；报告同时给出待复核的个数和复核后的数 |
| `missing` / `conflict` 判对率 | 金标为 `missing`（或 `conflict`）的字段里判对的比例，两类分开。S01 里 `conflict` 字段只有 2 个，这个比例只能当计数看 |
| 锚点命中率 | 被覆盖的金标锚点数 ÷ 金标锚点数，只算金标和结果都有值的字段（含结果无来源的），冲突字段按对上的候选组算。同时给出其中“`find` 定位不到”的条数 |
| 严重错误数 | §4.5，逐条列出，另列“待复核（严重）” |
| `must_not_assert` 违规数 | §4.6，同时给出未评审的条数 |

## 5. 证据

每次用于验收结论的运行，报告入库到 `docs/documenting/evidence/<日期>-s01-<机器标签>/`：

- `report.json`：
  - 这次运行的环境：仓库 commit、`os_version`、各引擎的 id 和版本、`extractor_version`、实际使用的 `model_id`、机器型号和系统版本；
  - 每份样本的 `content_sha256`、`ask.json` 和 `gold.json` 的 sha256；
  - 每个检查项的结果和耗时，每个字段的金标、结果、机械结论、人的结论；
  - 追溯链：一行一条 `场景 / 能力 ID → 契约 → 检查 ID → 负责人 / 阶段 → 结论`。
- `report.md`：§4.8 的汇总表、严重错误清单、待复核清单，供人读。
- `review.json`：有人工复核时才有（§4.7）。

报告不含 token、主机名、本机路径和用户数据。样本都是公开文件，结果里的引文可以入库。

跑证据的内核用一个空的数据目录（单独的 `HOME`），里面只有这次导入的样本。应答不合契约时，报告会摘录应答正文的开头（最多 200 个字符），所以内核里不能有日常使用的文档。

写文件之前，harness 还会再查一遍：

- token 和用户主目录，在两份文件里都不能出现；
- 本机路径不能出现；
- 主机名（带域名和不带域名的）按整词查，范围是内核和复核人用自己的话说出来的文字：抽取结果里模型写的值和引文、引擎的 id 和版本、问题描述、复核人写的内容等。harness 自己写的样本 id、字段名、金标、检查编号、契约里的固定词（如 `present`、`ready`）和读到的机器型号都不查。
  - 抽取结果是文档原文，引擎 id 是内核给的名字。所以主机名恰好是样本里的某个词（如 `tax`），或者是引擎 id 的一段（如 `apple-pdfkit` 里的 `apple`）时，报告写不出来，报错会指出是哪个字段。

写到一半崩溃时，证据目录里可能留下 `.report.json.<随机串>.tmp` 这样的临时文件。harness 不会把它们当成证据读取；提交证据前删掉即可。

## 7. 实施顺序

每个 PR 不超过 300 行（不计测试），都以 `ab/documenting` 为目标：

1. 本文。
2. 包的骨架，读取并校验 `gold.json`、`meta.yaml`、`ask.json`；把新包加进根 `package.json` 的 `typecheck` 和 `test`，CI 才会跑它。
3. 8 份样本的 `ask.json`。
4. 打分：状态与值（§4.2、§4.3）。
5. 打分：锚点（§4.4）与汇总（§4.5、§4.8）。
6. REST 客户端与 `ACC-CAP`、`ACC-IMPORT`、`ACC-GET`、`ACC-TEXT`、`ACC-RENDER`、`ACC-FIND`。
7. `ACC-EXTRACT` 与 `ACC-IDEM-1..3`。
8. 报告与人工复核的合并（§4.7、§5），命令行入口。
9. 第一次入库的运行证据（需要一台有本地模型的机器）。
