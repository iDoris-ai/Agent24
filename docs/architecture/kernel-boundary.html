二、理想：内核画死，外面随便换

同一个栈形，差别只在两件事：内核有了明确边界，边界上有四个受控接口；领域 OS 从内核里搬出去，站到边界之上，只能通过接口向下调用。

三、你问的四件事

memory 应该在内核里，对不对？

对，而且它已经在了。agent24-memory 是内核 crate，被 agent24-agent 依赖。理由不是"重要所以放内核"，而是：上下文预算、压缩、崩溃恢复这三件事每个 OS 都需要，且与 agent loop 的热路径耦合 —— 放外面等于每个 OS 各写一遍，还各错一遍。

但要认账：M-D 那 12 个模块目前一个都没接进 loop。内核里躺着一套完整的记忆底座，loop 却还在用它之前的老 session 层。这是"建好了没通电"。

Sin90 / Cos72 在哪一层？和 memory 是上下层还是调用关系？

两者都是，而且必须同时是。领域 OS 在内核之上（层级），只能向下调用内核（方向）—— 单向，永不反过来。

判据在代码里，不在图里：agent24d/Cargo.toml 中不允许出现任何 OS crate。今天它出现了两个（sin90 + sin90-store），所以今天这条不成立 —— ME-1 修的就是这个。

Agent 最核心的是什么？

你说的是对的：prompt 组装 + 工具调用 + loop。代码印证 —— run_loop（lib.rs:986）每一轮做四件事：按模式重算可用工具集 → 调模型 → 先把 assistant turn 落盘再执行工具 → 过审批门后 dispatch。第三步的顺序是崩溃恢复的全部基础：磁盘上"尾部 tool_call 没有应答"这个形状，就是"死在等审批"的判据。

新能力（压缩 / 恢复 / 轨迹 / 评测 / 回滚 / 自进化）放哪一层？

一条判据："换一个 OS 之后还需不需要它"—— 需要就进内核，不需要就出去。

能力归属为什么现状
上下文管理 / 压缩内核 · memory与 token 预算和 loop 热路径耦合，每个 OS 都要已建未接
权限 / 审批内核 · policy必须不可绕过；OS 能自己实现就等于没有已通
崩溃恢复内核 · agent + memory恢复靠 thread 形状 + 事件重放，都是内核物resume 已通
跨机 / 跨会话迁移内核 · memory 重放事件日志是权威，迁移＝在别处重放已建未接
trajectory 轨迹内核 · memory · trace自进化的输入，必须全量可回溯不截断已建未接
evaluation 评测内核旁挂，不进热路径评测是门禁不是运行时；进 loop 会拖慢每一轮harness 已建 · CI 门未建
评测不过自动回滚内核 · policy ← eval回滚是权限决策，归审批引擎而非评测器未建
自进化OS 层或其上与领域强绑（Sin90 进化的是"节律"，Cos72 不是）未建

四、"个人操作系统"到底是什么

你问 Sin90 究竟包含哪些东西、怎么标准化。答案：一份 manifest 声明七件事，内核只认 manifest 不认名字。

所以"底座 + 不同 OS = 不同 agent"这个模型准不准？

方向准，但今天还差一层没兑现。缺的不是概念，是三样具体的东西：

  • 内核仍按名字认识 Sin90（依赖 + 硬编码路由 + AppState 字段）→ ME-1b 在修
  • KernelCtx::memory(scope, grants) 不存在 → 两个 OS 之间的记忆隔离目前靠调用方自觉，不靠机制
  • Scope 有 owner/agent/session/run 四维，但存储层只强制 owner 一维，agent 维全仓零使用 —— 同一 owner 挂两个 OS，记忆是相通的

换句话说：换 OS 今天能换，但"换了不互相污染"还没有机制保证。这三条已经进了 improvement/ 台账的 TODO-A。
