## 1. 现有鉴权与令牌

### 1.1 存储：纯内存，不持久化
- `cap/store.rs:26-31` `CapabilityStore` 文档写明 "In-memory capability authority. It stores only token digests and claims."；`State { records: HashMap<[u8;32], Record>, ids: HashMap<String,[u8;32]>, epoch: u64 }`（`store.rs:15-19`），`Record { claims, revoked }`（`store.rs:10-13`）。
- 键是令牌的 SHA-256（`cap/token.rs:74-77` `digest`）。令牌是 32 字节 CSPRNG，64 位小写 hex 作 bearer（`token.rs:5-23`，`parse_bearer` 同时接受大写，`token.rs:25-34`）。`CapabilityToken` 没有 Debug/Display/序列化。
- 没有任何落盘。daemon 重启后所有令牌作废（`daemon_generation` 也换了）。`validate_record` 另外检查 `claims.daemon_generation == store.daemon_generation`，否则 `StaleGeneration`（`cap/validate.rs:84-86`）。
- 撤销：`revoked` 置位，`epoch` 自增，经 `watch::Sender` 广播（`cap/revoke.rs:12-87`）。提供 `revoke(token)`、`revoke_by_id`、`revoke_by_generation / daemon_generation / host_generation / sidecar_generation`。**生产代码里只有 `revoke_by_id` 被 HTTP 调用**（`d/server.rs:925`）；`CapabilityWatch`（`cap/watch.rs`）和 `revoke_by_*_generation` 在 server 里没有调用点（grep `revoke_by|\.watch()|CapabilityWatch` 无命中），`events.rs` 的 WS 不会因吊销而断开（对应 ADR 的 G-API-4）。`d/main.rs:15-21` 因此给 `mod capabilities` 加了 `#[allow(dead_code, unused_imports)]`，注释写 "staged beyond route policy"。

### 1.2 `Audience`（`cap/types.rs:13-17`）
只有两个：`ProductHost`、`CreativeRuntime`。没有「一方外壳」「开发者应用」「远程设备」这些区分。

### 1.3 `CapabilityClaims`（`cap/types.rs:93-106`）
`capability_id: String`（16 字节随机 hex，`token.rs:79-88`）、`audience`、`workspace_id/attachment_id/principal_id: Option<String>`、`daemon_generation: String`、`host_generation: Option<String>`、`sidecar_generation: Option<String>`、`created_at/expires_at: u64`（unix 秒）、`allowed_operations: BTreeSet<Operation>`。
- `Authorization { claims, epoch }`（`types.rs:108-112`）：`auth` 中间件验证通过后塞进 `req.extensions`（`d/server.rs:~992`），**只有 `mint_creative_capability` 读它**（`server.rs:806`，`Option<Extension<Authorization>>`）。
- `Resource { workspace_id, attachment_id, principal_id, session_id, run_id }`（`types.rs:19-26`），但 `validate_record` 的精确匹配只比 workspace/attachment/principal 三个（`validate.rs:96-104`）；session/run 字段目前没人比。
- `CapabilityError`（`types.rs:114-124`）：`Unauthorized, Expired, Revoked, StaleGeneration, OperationDenied, ResourceDenied, HostRequired, InvalidTtl`；`Display` 一律输出 "unauthorized"（不泄漏原因）。
- Creative TTL 上限 `MAX_CREATIVE_TTL_SECONDS = 3600`（`types.rs:5`）；mint 请求默认 300 秒（`server.rs` `default_creative_ttl`）。

### 1.4 ProductHost 的关键特性（对设计最要紧）
- `mint_product_host(host_generation, ttl, created_at)`（`cap/mint.rs:54-73`）：`allowed_operations: BTreeSet::new()`（空），`workspace/attachment/principal = None`。
- **ProductHost 不检查 allowed_operations 也不检查资源**：`validate_record` 里两个 `if audience == CreativeRuntime` 分支才检查操作和资源（`validate.rs:90-108`）。所以 ProductHost = 全权，`Operation` 对它不起作用。
- 启动时只铸一枚，TTL = `Duration::from_secs(u64::MAX)`（`d/server.rs:1483-1487`），`expires_at` 用 `saturating_add`（`mint.rs:70`），等于永不过期；没有续期、没有轮换 API；`host_generation` 是 `generate_token()` 的随机串，**只在 claims 里，不对外暴露**。
- 「按进程、短期、可续期、进程退出即失效」的令牌：**现有代码没有对应能力**（没有 TTL 续期方法、没有按进程绑定的字段、没有主体/来源字段）。需要新增（例如 `Audience::FirstPartyShell`、claims 里加 pid/peer 身份、`renew`）。
- `mint_creative` / `mint_creative_authorized`（`mint.rs:75-144`）：要求持有者是 ProductHost、同 daemon generation、未过期、未撤销；`allowed_operations` 与 `Operation::creative_allowlist()` 求交集（`mint.rs:123-127`）。
- 路由：`POST /api/v1/capabilities/creative`（`server.rs:1066-1069`）铸 Creative；`POST /api/v1/capabilities/{id}/revoke`（`1070-1073`）撤销，幂等，不泄漏 id 是否存在（`server.rs:924-930`）。**没有「签发开发者令牌」路由**，也没有列表/最后使用时间/hash 之外的元数据存储。

### 1.6 `server.rs` 的 `auth` 中间件（`d/server.rs:949-1006`）
- 唯一放行：`GET /api/v1/health`（`server.rs:950-952`，方法也卡死）。
- 取 `Authorization: Bearer ...`。按 `state.auth_mode` 分两路：
  - `LegacySingleToken`：`constant_time_eq(presented, state.token)`，对就放行任意路由（`server.rs:959-971`）。
  - `Capabilities`：`state.capabilities` 为 None → 503 `host_authority_unavailable`；无 bearer → 401；否则 `required_operation(method, path)` → `store.validate_bearer(bearer, operation, &Resource::global(), unix_now())`。`OperationDenied/ResourceDenied/HostRequired` → 403 `forbidden`；其余 → 401（`server.rs:972-1005`）。资源**永远是 `Resource::global()`**，没有从路径/请求提取 workspace/session/run（G-API-1 缺口）。
- 中间件挂在 `kernel.merge(modules).layer(auth)`（`server.rs:~1218-1222`），注释强调模块路由必须在 auth 之前合并。
- `required_operation`（`server.rs:1016-1031`）：`GET /api/v1/models`→ModelsRead；`POST /api/v1/capabilities/creative`→CapabilityMint；`POST /api/v1/capabilities/*/revoke`→CapabilityRevoke；**其他一律→ModelsAdmin**。因此 Creative 令牌（白名单里没有 ModelsAdmin）只能读 models，其余全 403；ProductHost 全过。
- `AppState`：`auth_mode`、`capabilities: Option<CapabilityStore>`、`token`（`server.rs:38-42`）；`enable_capability_auth` 把 `token` 置空串、`auth_mode=Capabilities`（`server.rs:701-705`）。

### 1.7 legacy token 流程
- `serve` 里 `AuthMode::LegacySingleToken => (generate_token(), None, None)`（`server.rs:1479`）：一枚 32 字节随机 hex，进 `AppState.token`。
- 写进 `daemon.json`（`DaemonState::new_legacy(port, token, pid, version, generation)`，`server.rs:2446-2452`），并同时打印到 stdout 的 ready 行（`server.rs:2484-2490`，`println!("{ready}")`）。
- **所有现有客户端都用 legacy**：桌面 `backend-manager.ts:175` 以 `spawn(bin, ['serve','--port','0'])` 起 daemon，stdio `['ignore','pipe','pipe']`，从 ready 行读 token（`backend-manager.ts:344-347`）；CLI `spawn_daemon` 也是 `serve --port 0 [--ephemeral]`（`agent24-cli/src/main.rs:604-642`）；LaunchAgent plist 的 ProgramArguments 是 `serve --port 0`（`agent24-cli/src/service.rs:88-95`）。**全仓只有集成测试 `rust/apps/agent24d/tests/capability_startup.rs:24-33` 用 `--auth-mode capabilities`**，且用的是 `--ephemeral`；非 ephemeral 的 capability 路径（单例锁 + 写 capability 版 daemon.json）有代码（`server.rs:2453-2459`）但没有端到端测试。
- 桌面复用外部 daemon：`tryReuseExternal` 读 `daemon.json` 的 `token` 与 `port` 并健康检查（`backend-manager.ts:233-249`、`115-126`），capability 版 daemon.json 里没有 token，所以会得到空串。
- 桌面 `backendProxy`：`ipcMain.handle(IpcChannels.BackendProxy, ...)` 校验 `isBackendProxyRequest`（只要求 method + 绝对路径）后 `proxyToBackend(req)`（`apps/desktop/src/main/ipc/index.ts:316-325`，校验函数在 `ipc/index.ts:119`），代 renderer 带全权 token 转发任意路径。

### 1.8 `validate_auth_startup`（`d/server.rs:2571-2589`）
纯函数，四种组合：`(Capabilities,true)` OK；`(Capabilities,false)` → `PermissionDenied "capability mode requires trusted host bootstrap stdio"`；`(Legacy,true)` → `InvalidInput`；`(Legacy,false)` OK。`serve()` 开头第一件事调它（`server.rs:1323`），之后的 `match (auth_mode, host_bootstrap_stdio)` 里 `(Capabilities,false)` 又重复报错一次（`1329-1334`）。单测 `server.rs:3658-3663`。**新增 `--enroll-endpoint` 要改这里**（让 `(Capabilities, false)` 在 enroll_endpoint=true 时通过，并决定 `(Legacy, enroll)` 是否拒绝）。

## 2. host_bootstrap

### 2.1 CLI 参数
`d/main.rs:108-128`：`serve --port <u16, 默认0> [--ephemeral] [--auth-mode legacy-single-token|capabilities] [--host-bootstrap-stdio(hide)]`。`AuthModeArg` → `agent24_protocol::state_file::AuthMode`（`main.rs:88-102`）。`run_serve` 把 4 个参数传给 `server::serve`（`main.rs:157-176`）。
**当前没有 `--enroll-endpoint`。**

### 2.2 完整流程（capability + `--host-bootstrap-stdio`）
1. `validate_auth_startup`（`server.rs:1323`）。
2. `crate::host_bootstrap::open_stdio()`（`server.rs:1326`；`d/host_bootstrap.rs:19-26`）：对 stdin、stdout 各 `rustix::io::fcntl_dupfd_cloexec(fd, 3)` 复制到 ≥3 的 fd 且 CLOEXEC，再 `fstat`，**只接受 FIFO 或 Socket**（`is_ipc_channel`，`host_bootstrap.rs:28-45`），终端/普通文件→`PermissionDenied "capability bootstrap requires FIFO or socket stdin and stdout"`。模块文档明说：fstat 证明不了管道是私有的，那是启动者的放置契约（`host_bootstrap.rs:1-8`）。返回 `ReadyWriter`（stdout dup）与 `ParentLiveness`（stdin dup）。
3. 父管道存活监控：`tokio::spawn`，`parent_liveness.closed().await`（读 stdin 直到 EOF 或错误，`host_bootstrap.rs:62-70`），然后 `parent_shutdown.request()` 并记 "trusted host bootstrap closed; shutting down capability daemon"（`server.rs:1354-1361`）。这就是「父管道 EOF → 关机」。
4. 单例锁（非 ephemeral）、`daemon_generation = generate_token()`、铸 ProductHost 令牌（见 1.4，`server.rs:1477-1491`）。
5. 启动完成后（stores、模块、路由都就绪）写 `daemon.json`（capability 版，不含 token，`server.rs:2444-2467`），再 `shutdown.commit_ready()`（与关机请求竞争同一个原子位，`server.rs:2470`；输了就 `remove_if_owner` 且不打印 ready）。
6. 构造 ready JSON：`{"type":"ready","port","product_host_token","auth_mode":"capabilities","generation","version"}`（`server.rs:2492-2510`），注释写「此秘密只经继承的 ready 管道交给拉起它的可信宿主，不写 daemon.json」；`host_ready.send(&ready).await?`（一行 JSON + `\n` + flush，`host_bootstrap.rs:47-54`）；随后 `drop(ready)`，库里只留 digest（`server.rs:2521-2525`）。
7. legacy 模式 ready 行是 `println!` 到 stdout，含 `token`。
- tracing 日志一律走 stderr（`main.rs:~120` `with_writer(std::io::stderr)`），stdout 专给 ready 行。

### 2.3 `cfg(unix)` 与非 Unix 桩
`d/main.rs:29-70`：
- `#[cfg(unix)] mod host_bootstrap;`（真实实现，依赖 `rustix::stdio`、`fcntl_dupfd_cloexec`、`fstat`）。
- `#[cfg(not(unix))] mod host_bootstrap { ... }`：内联桩，`ReadyWriter(Infallible)`、`ParentLiveness(Infallible)`；`open_stdio()` 直接返回 `io::ErrorKind::Unsupported "capability bootstrap requires Unix IPC descriptor validation"`；`send`/`closed` 用 `match self.0 {}`（不可达）。含义：**Windows 上 capability 模式根本起不来**（`open_stdio` 返回 Err，serve 直接失败）。ADR 说的「这个通道只有 Unix 实现」属实。
- 另外 `server.rs:1369-1393` 的信号处理与 `1723-1732`（workspace_service）也按 `cfg(unix)/cfg(not(unix))` 分开；`state_file.rs:259-284` 的 `pid_alive` 在非 Unix 恒为 true。

### 2.4 ADR-035 的 iDoris Admin FD 交付（`apps/desktop/src/main/idoris-admin.ts`）——「一次性登记权经 FD 交付」的参照
- 启动者在 argv 里给**非秘密的 FD 编号选择器** `--idoris-admin-token-fd <n>`（`idoris-admin.ts:11,29-38`）：`=` 写法或重复→`invalid`；fd 必须 3..0x7fffffff 的整数。
- 秘密是**恰好 65 字节**：64 位小写 hex + `\n`（`TOKEN_FRAME_BYTES=65`，`parseTokenFrame`，`idoris-admin.ts:12,71-77`）。
- `readAdminTokenFromFd(fd, timeout=5s)`（`idoris-admin.ts:79-104`）：`createReadStream('', {fd, autoClose:false})` 读到 EOF；超过 65 字节→null；超时/错误→null；**无论成败都 `close(fd)`**。
- 选择器非法时 `closeClaimedAdminTokenFds`：把 argv 声明过的所有可识别 FD 全关掉，免得后续 spawn 的子进程继承（`idoris-admin.ts:40-57,264-269`）。
- token 只留在 Electron main 内存，通过闭包 `() => fetchIdorisOverview(token, port)` 使用，renderer 只得到零参数的 `idorisStatus()`（`idoris-admin.ts:258-277`；调用点 `main.ts:21,27`）。
- ADR-035 原文（`docs/decision.md:1424-`）：两条匿名一次性管道，一条给 iDoris stdin，一条给 Agent24 main；用完写端立即关；token 不进 argv/env/文件/stdout/stderr/日志；Windows 用显式 allowlist 的 inherited HANDLE。
- **与 CORE-2 的差别**：ADR-035 是「启动者生成 token → 交给消费者」，消费者 Electron 读后关；CORE-2 要的是「启动者交一次性**登记权**→ 子进程拿它去 daemon 换自己的令牌」。可复用：选择器格式/固定长度帧/超时/读后关/无效选择器时关闭候选 FD 的这套模式。agent24d 一侧的对应实现（读继承 FD、一次性、绑定具体连接）**仓库里没有**。

## 3. UDS 与对端凭据

### 3.1 现有 UDS 监听
- **attach 监听**：`d/attach_listener.rs`。路径 `<state_dir>/attach/agent24d.sock`（`d/attached.rs:195-197` `socket_path()`；ADR 的 `state_dir` 即 `AGENT24_DATA_DIR` 或 `~/.agent24`）。`ensure_private_dir`（`attach_listener.rs:~40-75`）要求父目录是真目录（symlink_metadata）、属主=euid、模式**恰好 0700**，不合格就拒绝而不是修正；`bind()`（`attach_listener.rs:~80-110`）处理陈旧 socket（能 connect 则判定另一 daemon 在跑并禁用自己的 attach；connect 不上则 unlink 重 bind）、`ENAMETOOLONG`（macOS 104 字节限制）。**注意：socket 节点本身没有显式 chmod 0600**，靠 0700 父目录保护。持久监听、可多次 accept；握手超时 `HANDSHAKE_DEADLINE=5s`；daemon 用 `tokio::spawn(attach_listener::run(...))` 启动，仅非 ephemeral（`server.rs:2388-2408`）。绑定失败只降级，不拖垮 daemon。
- **模块回调 socket（accept-once）**：`rust/crates/agent24-os-proto/src/endpoint.rs`：`CallbackListener::accept_one`（`endpoint.rs:~560-575`）；各目录强制 0700（`endpoint.rs:310,361,424-431,511`）。
- **os-fd**：`rust/crates/agent24-os-fd/src/lib.rs`，唯一把继承 fd 变成 socket 的 crate（`LISTEN_FD=3`，`ENV_LISTEN_FD="A24_LISTEN_FD"`，`TAKEN` 原子位只许取一次，校验是 socket/UNIX/STREAM/listening 且**没有 FD_CLOEXEC**才算「内核 dup2 过来的」，`lib.rs:9-40`）。这是仓库里「继承 FD 一次性领取」的现成模式；`unsafe_code="deny"` 仅此 crate 例外（其余 workspace 为 forbid）。用的是 rustix **1.1**（"0.38.44 getsockname 在 macOS 上 panic"，`os-fd/Cargo.toml`）。

### 3.2 是否已经取对端凭据：取了，但只比 uid，没用 pid
- `attach_listener.rs:162-175` `stream.peer_cred()`（tokio `UnixStream::peer_cred`）→ `cred.uid()`，与 `rustix::process::geteuid().as_raw()` 比较，不等就关闭连接。`endpoint.rs:570` 同样只 `peer_cred()?.uid()`。
- tokio 1.53.1 的 `UCred` 有 `uid()/gid()/pid()`（`tokio-1.53.1/src/net/unix/ucred.rs:~15-35`）：Linux 走 `SO_PEERCRED`（`ucred.rs:92,129`），macOS 走 `getpeereid` + `getsockopt(SOL_LOCAL, LOCAL_PEEREPID)`（`ucred.rs:297-337`，注意是 **EPID，即 effective pid**，在 connect 时刻取得；macOS 拿 pid 无需额外依赖）。**所以拿到对端 PID 不需要新依赖，`stream.peer_cred()?.pid()` 即可**，仓库目前没调用 `.pid()`。
- rustix：0.38.44 有 `rustix::net::sockopt::get_socket_peercred`（`rustix-0.38.44/src/net/sockopt.rs:1385-1388`），1.1.4 有 `socket_peercred`（`rustix-1.1.4/src/net/sockopt.rs:1689-1692`），**都只在 `cfg(linux_kernel)`**，macOS 上没有；rustix 没有 `getpeereid` 封装。agent24d 的 rustix 是 0.38，features `["fs","process","stdio"]`，没开 `net`（`agent24d/Cargo.toml:71`）。结论：跨平台取凭据用 tokio 的 `peer_cred()`，不用 rustix。
- 找不到：`SO_PEERCRED` / `LOCAL_PEERCRED` / `getpeereid` / `proc_pidpath` 在 `rust/` 源码里 **0 处直接调用**（grep 仅命中 tokio 内部和注释）。

### 3.3 「按 PID 解析可执行文件路径」：未找到现成代码
- 仓库 `rust/` 内没有 `proc_pidpath`、`/proc/<pid>/exe`、`readlink` 之类。能找到的相邻代码：
  - `state_file.rs:272-284` `unsafe_free_kill`：Linux 看 `/proc/<pid>` 是否存在，macOS 回退到 `ps -p <pid> -o pid=`。
  - `agent24-comm/src/daemon.rs:85-99,181`：用 `ps -o lstart= -p <pid>` 做 pid 复用判别，文档明说**因为 workspace 禁用 unsafe_code**所以不用 `proc_pidinfo` 系统调用（`daemon.rs:91-95`）。
  - `agent24-os-proto/src/launch.rs:329` 读 `/proc/self/fd`（Linux 专用）。
- 实现路径与约束：`libc 0.2.191` 里有 `proc_pidpath(pid, buffer, size)`（`libc-0.2.191/src/unix/bsd/apple/mod.rs:5501`），agent24d 已依赖 `libc = "0.2"`（`agent24d/Cargo.toml:~75`），但调用是 `unsafe`，而 **workspace lint 是 `unsafe_code = "forbid"`**（`rust/Cargo.toml:42-43`），需要像 `agent24-os-fd` 那样开一个独立的、`deny` + 单点 `allow` 的小 crate。Linux 可用 `std::fs::read_link("/proc/<pid>/exe")`（safe）。备选 safe 办法是 shell out `ps -p <pid> -o comm=`（会截断/不可靠，且与 TOCTOU 一并存在）。

### 3.4 PID 竞态提示（对设计相关）
对端 PID 是 connect 时刻的快照；peer 进程可以 exec 成别的程序，或 PID 被回收。macOS 上 tokio 不提供 audit token，只给 pid。`security-framework` 的 `GuestAttributes::set_audit_token(CFDataRef)` 需要 audit token（`LOCAL_PEERTOKEN`），tokio 拿不到，需自行 `getsockopt`（需要 unsafe）。

  - **`daemon.singleton.lock`**：`try_acquire_singleton()`（`state_file.rs:209-224`），`fs2::try_lock_exclusive` 非阻塞；拿到返回 `File` 守卫，**daemon 整个生命周期持有**（`let _singleton = ...`，`server.rs:1427-1439`），拿不到→`Err("another agent24d is already running (singleton lock held)")`。`--ephemeral` 跳过。
  - **`daemon.lock`**：短时 `hold_lock()`（`state_file.rs:159-168`），只在 `write()` 与 `remove_if_owner()` 里临时持有，保护 daemon.json 的读-改-删竞态。
- 目录权限：`write()` 里 `create_dir_all` 后 `set_permissions(dir, 0o700)`（`state_file.rs:175-180`，仅 Unix）；临时文件 `daemon.json.tmp.<pid>` 以 `mode(0o600)` 创建，写 + `sync_all`，再 `rename` 覆盖（`state_file.rs:186-200`）。

### 8.2 `daemon.json` 内容（`DaemonState`，`state_file.rs:31-48`）
字段：`port: u16`、`token: String`（capability 模式缺省且 `skip_serializing_if empty`）、`pid: u32`、`version: String`、`generation: String`（缺省为空，仅 legacy 旧文件允许为空）、`auth_mode`（缺省 legacy）。`validate()`：legacy 必须有 token；capabilities 必须**无** token 且 **有** generation（`state_file.rs:89-109`）。**目前不含**：协议版本、迁移水位、登记端点路径、socket 路径、`status`。ADR 要的「登记端点路径」「版本协商字段」都要新加（`GET /health` 也要加字段，现 `Health` 只有 `status/version/backend`，`d/server.rs:~718-724`）。

### 8.3 写入时机（`d/server.rs`）
顺序（非 ephemeral）：拿单例锁（`1427-1439`）→ 写 shutdown marker（`1449-1470`）→ `daemon_generation = generate_token()`（`1477`）→ 铸 ProductHost（`1479-1491`）→ 打开 `agent24.db`/`memory.db`（含 sqlx 迁移，`1493-1519`）→ 启动模块/路由/attach listener（`~1536-2425`）→ **构建 `DaemonState` 并 `state_file::write`（`2444-2467`；失败仅 `warn`，不致命）** → `shutdown.commit_ready()`（`2470`；输给关机则 `remove_if_owner` 且不打 ready）→ ready 行（`2480-2520`）。
即：daemon.json 在迁移**之后**、就绪**之前**写入，与 ADR「全部库迁移成功后才写 `daemon.json` 并发布就绪」顺序一致（现状已满足，只缺失败回滚与停靠态）。`write` 失败只告警意味着「daemon 在跑但不可发现」，对登记端点要决定是否致命。

### 8.4 `generation`
`generate_token()`（`server.rs:1225-1229`）：32 字节 `rand::rng().fill_bytes` → 64 位 hex。**每次进程启动生成一枚**，既写入 daemon.json 与 ready 行，也作为 `CapabilityStore::new(daemon_generation)` 的 `daemon_generation`（`server.rs:1481`）。含义是「daemon 进程实例标识」，不是单调递增整数，也不是持久化的。`validate_record` 比较它实现「换代即全部令牌作废」（`validate.rs:84-86`）。因此「daemon 换代时旧登记全部作废」天然成立（令牌随进程消失，且 generation 不匹配），但**登记端点自身的 UDS 路径**如果固定，就需要像 attach socket 那样处理陈旧节点（`attach_listener::bind`）。

### 8.5 `remove_if_owner(pid)`（`state_file.rs:241-257`）
持 `daemon.lock`，读 daemon.json，解析并 `validate()` 通过且 `state.pid == pid` 才 `remove_file`。调用点：优雅退出末尾（`server.rs:2566`）、输给关机竞态时（`2472`）、以及某个线程里用于关机清理（`server.rs:1971`，`std::thread … remove_if_owner(pid)`）。注意是**按 pid 而不是 generation 判属主**；pid 复用理论上存在窗口，但 daemon 持有单例锁、旧进程已死，实际安全。若要「按 generation 判」需要改。
- `read_live()`（`state_file.rs:226-239`）：存在 + 可解析 + `validate()` + `pid_alive`。`pid_alive` 在 Linux 看 `/proc/<pid>`，macOS 靠 `ps -p`（`state_file.rs:272-284`），非 Unix 恒 true。

## 对设计最关键的 8 条事实

1. **ProductHost 是全权且永不过期**：它不查 `allowed_operations` 与资源（`validate.rs:90-108`），TTL=`u64::MAX`（`server.rs:1483-1487`），启动时只铸一枚；现有 `Audience` 只有 `ProductHost/CreativeRuntime`，没有短期、按进程、可续期的一方外壳令牌，需要新增 Audience 与 claims（pid/身份/续期）。
2. **`Operation` 几乎没接线**：`required_operation` 只认 models/mint/revoke 三类，其余一律 ModelsAdmin（`server.rs:1016-1031`）；`ApprovalDecision/GrantManage/OverrideManage/ModuleAdmin/Shutdown` 等都存在于枚举但无路由用到；改记忆设置、读记忆、聊天、Hyphae 等**没有对应枚举项**。提升级/日常级的划分必须先补这张映射表（第 6 节）并改 `auth` 中间件使其按方法+路径区分。
3. **capability 模式目前没有任何生产使用者**：桌面、CLI、LaunchAgent 全是 legacy（`serve --port 0`）；只有 `tests/capability_startup.rs` 用 `--auth-mode capabilities --ephemeral --host-bootstrap-stdio`。非 ephemeral 的 capability 路径（单例锁 + capability 版 daemon.json）有代码但无端到端测试；CLI 对 capability daemon 一律 `host authority unavailable`（`main.rs:644-662`）。
4. **`validate_auth_startup` 是 `--enroll-endpoint` 的卡口**：现在 `(Capabilities,false)` 硬报错（`server.rs:2571-2589` 且 `1329-1334` 重复）；`host_bootstrap` 在非 Unix 是桩（`main.rs:31-69`，返回 `Unsupported`），所以服务模式只要不走 stdio 才可能在 Windows 上起得来；父管道 EOF→关机的 `tokio::spawn` 在 `server.rs:1354-1361`，服务模式需整体跳过它。
5. **对端凭据现成可取 pid，不需新依赖，但仓库没用**：`stream.peer_cred()` 已在 `attach_listener.rs:164` 和 `endpoint.rs:570` 使用，只比 uid；tokio 1.53.1 的 `UCred::pid()` 在 Linux（SO_PEERCRED）和 macOS（`LOCAL_PEEREPID`）都可用。rustix 的 peercred 仅 Linux。**没有任何「PID→可执行路径」代码**；`workspace` 是 `unsafe_code="forbid"`，`proc_pidpath` 需要像 `agent24-os-fd` 那样的 deny+单点 allow 的小 crate，或改用 `security-framework` 的 `SecCode::path`。
6. **macOS 签名校验已有可用的安全封装，免 unsafe**：`security-framework 3.7.0` 已在 macOS 依赖树里（经 `keyring`→`agent24-comm`→`agent24d`），提供 `SecCode::copy_guest_with_attribues(set_pid)`、`SecRequirement::from_str`（requirement 串）、`check_validity`、`SecCode::path`（`os/macos/code_signing.rs:138-311`），只需在 `agent24d/Cargo.toml` 直接声明。但 tokio 不给 audit token，只能按 PID 校验，有 PID 复用/exec 竞态。
7. **Team ID 与签名流水线不在仓库里**：Team ID `HYAP444FN9`（`Developer ID Application: Huifeng Jiao`）只出现在 Release `v0.5.1-preview.20261016.2` 的说明里；`package.json` 的 electron-builder、两个 workflow、全仓都没有 identity/hardenedRuntime/entitlements/notarize 配置，TASKS.md 的 DEP-B* 仍 BLOCKED，与 ADR-037 决策 5「流程已跑通」不符。内嵌 `agent24d` 的独立签名状态、CLI（tar.gz，不签）都**未能确认/未签**，且开发构建无 Team ID——身份校验必须定义「未签名/ad-hoc」时的降级路径（这正是 ADR 的「开发构建首次登记」）。
8. **「一次性登记权经 FD 交付」有两个现成参照，但 daemon 侧缺实现**：ADR-035 的 Electron 侧（`idoris-admin.ts`：argv 只放 FD 编号选择器、65 字节固定帧、5s 超时、读后必关、非法时关闭候选 FD）和 Rust 侧 `agent24-os-fd`（`LISTEN_FD=3`、`TAKEN` 原子位只许领一次、必须无 CLOEXEC 才算内核传入）。另外 `host_bootstrap.rs` 只做「stdin/stdout 必须是 FIFO/Socket」的 fstat 校验。把这些组合成「daemon 开 UDS 0600 + 启动者经继承 FD 交一次性登记码 + 绑定连接用一次即失效」需要新实现。
- 补充（也很关键，列为第 9 条不占「8 条」名额）：**`daemon.json` 无登记端点/协议版本/迁移水位字段，`/health` 只有 `status/version/backend`**；`generation` 是每次启动随机 64-hex（非单调），已同时用作 `CapabilityStore.daemon_generation`，所以「换代作废旧登记」天然成立，但 UDS 路径若固定则需处理陈旧节点（可复用 `attach_listener::bind` 的做法）；`remove_if_owner` 按 pid 判属主而非 generation。
