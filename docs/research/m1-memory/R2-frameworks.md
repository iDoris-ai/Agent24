# R2：开源 agent 记忆框架调研

## ① 一句话结论

**Agent24 M1 应保留「EventLog 原文权威 + AssertionLedger/WriteGate + personal scope + 可撤回 FTS 投影」，优先吸收来源追踪、作用域过滤、检索观测与评测方法；图谱、模型自主改写及文件式长期记忆留待后续，不能用它们替换本轮可验证的记住—召回—撤回契约。**（研究判断；依据：[M1 冻结计划](../../agent/M1-PLAN-v2.md)、下文逐项源码与比较。）

核查日期：2026-10-02。方法：通过 `curl -L` 读取一手 README、LICENSE、关键实现及论文/官方文档；GitHub 代码尽量固定到 commit，在线文档反映抓取时内容。没有安装或运行被调研框架，没有复现模型 benchmark；“论文/项目报告”不等于本地实测，“未核实”也不等于功能不存在。各节“优缺点”“与 M1 关系”属于基于所引证据的工程判断。

本报告先通读了 [M1-PLAN-v2.md](../../agent/M1-PLAN-v2.md)：T06b/T07b 是笔记本本地模型的可选项；编辑、同义 supersede、物理擦除、导出、多用户和 instruction store 明确不在冻结交付内。因此本报告的改法是供后续决策的建议，未修改计划或实现。[M1 §0、§2、§4](../../agent/M1-PLAN-v2.md)

## ② 逐项核查

### 1. Letta / MemGPT：分层记忆与自编辑

**版本边界。** 当前 Letta 主仓 README 将旧 V1 API server 标为退休，活动源码迁至 `letta-code`；下述 core/archival/recall 以历史服务端快照核查，并单列当前实现，不能把旧 Python schema 当作新 runtime。[迁移说明](https://github.com/letta-ai/letta/blob/5bcdd177d70fa2b31a754cfcd801e77b2e1ab16a/README.md)

**当前实现补充。** 当前 Letta Code 已采用文件式 MemFS：README 称包括 memory blocks 在内的 agent context 由 Git 跟踪，并可同步到自定义 GitHub 仓库；源码按 agent ID 放在 `~/.letta/agents/<agentId>/memory`，本地 backend 有独立根目录，故默认作用域是 agent 级文件树。它保留标准 agent 的 `.mdx` memory blocks，同时增加可浏览、可由 agent 修改的文件树与 Git 版本历史；和历史 Python 服务端以数据库 Block 为主的实现相比，是 block + Git-backed filesystem 的双层形态。frontmatter 校验区分 legacy 与 v2：legacy 保护 read_only，v2 普通笔记要求 name/description，而 MEMORY.md 不带 frontmatter。Git 同步提供文件版本迁移途径，但本次未验证用户级完整导出和彻底删除历史的工作流；仓库 LICENSE 为 Apache-2.0。[README](https://github.com/letta-ai/letta-code/blob/37c2ab0fc80b58bff0fc2ccdbe838a2d72d45bf7/README.md) [memory filesystem](https://github.com/letta-ai/letta-code/blob/37c2ab0fc80b58bff0fc2ccdbe838a2d72d45bf7/src/agent/memory-filesystem.ts) [memory blocks](https://github.com/letta-ai/letta-code/blob/37c2ab0fc80b58bff0fc2ccdbe838a2d72d45bf7/src/agent/memory.ts) [frontmatter policy](https://github.com/letta-ai/letta-code/blob/37c2ab0fc80b58bff0fc2ccdbe838a2d72d45bf7/src/memory-frontmatter.ts) [LICENSE](https://github.com/letta-ai/letta-code/blob/37c2ab0fc80b58bff0fc2ccdbe838a2d72d45bf7/LICENSE)。

**是什么、模型。** MemGPT 论文把长对话代理类比为带层级存储管理的操作系统：有限上下文为主存，外部存储通过代理工具调用读写；论文摘要和正文描述 archival storage 与 conversation/recent context 的分页式管理。[论文 HTML](https://arxiv.org/html/2310.08560) [摘要](https://arxiv.org/abs/2310.08560)。Letta 历史服务端把 agent in-context 的 core memory 表示为带 label 的 `Block` 列表，并提供 block 编辑工具；Block 字段含 `value`、字符 `limit`、`label`、`read_only`、`description`、`metadata`、模板相关 ID 等。[Memory schema](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/memory.py) [Block schema](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/block.py)。该代码还将 archival、recall 计数与 core memory 分开报告，说明它们是不同外部/上下文面向的记忆类别。[ContextWindowOverview schema](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/memory.py)

**写入、冲突与检索。** Core block 是 agent 可调用 `core_memory_append` / `core_memory_replace` 自编辑的工作记忆；replace 要求旧文本匹配，空新文本可删除该段，Unicode 明确支持，但这是直接修改 block 内容，不是带 provenance 的不可变断言账本。[memory tools implementation](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/functions/function_sets/base.py)。Block 有长度上限和只读属性；`update_memory_if_changed` 只在 memory 有变化时应用更新，具体并发冲突/版本 CAS 语义在所读文件中未核实。[Block schema](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/block.py) [Agent update path](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/agent.py)。Archival memory 提供 agent 调用的 `archival_memory_insert` / `archival_memory_search`：工具契约称其语义相似度检索、可按 tags（any/all）和时间范围筛选、返回 id/timestamp/content；函数本身是 dispatcher stub，底层检索实现与排序细节未从该历史快照核实。Recall memory 是 agent 消息历史；`conversation_search` 源码实际调用 `message_manager.list_messages_for_agent(query_text, roles, limit)`，工具说明为 text + semantic hybrid search，支持 role 与时间筛选。应区分 recall 查询（源码调用可见）与 archival 后端（工具契约可见、存储排序后端未核实）。[base tools](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/functions/function_sets/base.py) [memory schemas](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/memory.py) [MemGPT paper](https://arxiv.org/html/2310.08560)。

**作用域与用户控制。** Block schema 带 block id、创建/更新者、project/template 等上下文；多 agent 可共享 block 的所有权/绑定模型，适合显式可编辑空间，但个人空间与组织隔离的完整授权规则需结合其已退休服务端 API，M1 不应照搬。[Block schema](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/block.py) [Letta archived README](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/README.md)。当前 Letta README 指向独立新项目；新代码行为不由旧 Python schema 代表。[当前 README](https://github.com/letta-ai/letta/blob/5bcdd177d70fa2b31a754cfcd801e77b2e1ab16a/README.md)。该历史实现的查看/修改路径明显（Block API 与 agent tool），但此处未核实一键导出、用户级彻底删除与审计事件的端到端语义。中文方面，Block 工具文档明确支持 Unicode；中文 tokenizer/检索质量与评测未核实。[Block tools](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/memory.py)。许可证：历史服务端仓库 LICENSE 为 Apache-2.0。[LICENSE](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/LICENSE)。

**评测、优缺点及 M1 关联。** MemGPT 论文 Table 2 的 DMR 中，GPT-4 Turbo 基线为 35.3%，加 MemGPT 为 93.4%，ROUGE-L recall 从 0.359 到 0.827；这是该论文的有限上下文基线设定，不等于今天全文上下文模型的成绩，也不是 Agent24 的复现结果；当前 Letta README 未提供同一配置下可直接比较的本地 Rust 基线。[论文](https://arxiv.org/html/2310.08560) [当前 README](https://github.com/letta-ai/letta/blob/5bcdd177d70fa2b31a754cfcd801e77b2e1ab16a/README.md)。优点是把“始终在上下文的少量核心内容”和“按需访问的长记忆”分开，并让 agent 能自我维护核心区；缺点是自编辑使事实来源、撤回历史与冲突裁决容易变成 mutable text，且实现迁移让当前可复用性需谨慎判断。[paper](https://arxiv.org/html/2310.08560) [Block tools](https://github.com/letta-ai/letta/blob/56ba9c25552605eec89de8ed3dc6394b625c1993/letta/schemas/memory.py) [current repository notice](https://github.com/letta-ai/letta/blob/5bcdd177d70fa2b31a754cfcd801e77b2e1ab16a/README.md)。对 M1：可借其概念区分稳定核心信息与可搜索长记忆，但 M1 当前 assertion + FTS + 会话 EventLog 已有更清晰的来源与撤回模型；core blocks 自编辑不适配 T06/T09 的明确记住与撤回语义。可将“记忆容量/每块限制”转为检索注入预算与界面展示约束（T07/T11），不必引入 agent 自编辑工具。[M1 T06/T07/T09/T11](../../agent/M1-PLAN-v2.md)

### 2. Mem0：历史四动作、当前 ADD-only 与混合检索

**是什么、模型。** Mem0 是提供 SDK 和托管平台的记忆层；当前 README 将 OSS v3 写入描述为 single-pass、ADD-only extraction，并明确其无 UPDATE/DELETE 自动抽取、历史记忆不会被该流水线覆盖。[README](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/README.md) [核心实现 `Memory.add`](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py)。实现字段包括 UUID `id`、`data` 文本、`text_lemmatized`、内容 `hash`、`created_at`/`updated_at`、可选 `attributed_to` 与调用方 metadata；scope 入口为 `user_id`、`agent_id`、`run_id`，至少一个必须给出，并被加入向量过滤条件。[实现：add/scope](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py)。可供 Rust 设计参考的最小列为 `(id, owner_type, owner_id, content, normalized_text, content_hash, created_at, updated_at, metadata)`，但 Mem0 hash 是 MD5 去重实作，不建议直接照用作安全标识。[实现：hash/dedup](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py)

**历史版本边界。** 另对 GitHub tag `v0.1.118` 做了固定版本核查：tag 对应 commit `ed5a1e9fc68fcd7671a70c33a540d24573755449`，下列结论只指该版本，不能外推到当前 Add-only 主线。[v0.1.118 tag](https://github.com/mem0ai/mem0/releases/tag/v0.1.118) [固定 commit](https://github.com/mem0ai/mem0/tree/ed5a1e9fc68fcd7671a70c33a540d24573755449)。

**历史向量记忆流程确有两段 LLM 阶段。** `_add_to_vector_store(..., infer=True)` 第一阶段调用 fact extraction prompt，输出 `facts`；对每条新 fact 做 embedding，再向 vector store 搜 top-5 旧记忆并去重；第二阶段调用 `get_update_memory_messages(old_memories, new_facts, ...)` 生成 `memory` action 列表，然后以 `ADD` 新建、`UPDATE` 覆盖指定旧 id、`DELETE` 删除指定旧 id、`NONE` 不改（源码日志把 `NONE` 称作 “NOOP”）。也就是说动作协议值是 `NONE`，NOOP 是日志/概念称呼，并非另一个 JSON event 名称。[v0.1.118 `main.py` extraction/action code](https://github.com/mem0ai/mem0/blob/ed5a1e9fc68fcd7671a70c33a540d24573755449/mem0/memory/main.py)。此版本通过把候选 UUID 暂时映射为小整数交给 LLM，再映回真实 UUID，降低模型胡写 id 的风险；仍由 LLM 决定冲突动作，异常/空响应会变为空 actions 并继续保存消息，故不是确定性冲突裁决。[same source](https://github.com/mem0ai/mem0/blob/ed5a1e9fc68fcd7671a70c33a540d24573755449/mem0/memory/main.py)。历史 `NONE`/`UPDATE`/`DELETE` 证据由源码确证，避免将其混同当前的 ADD-only 路径。

**历史 Graph Memory 是外接 Neo4j 的独立图更新管线。** 同一版本 `MemoryGraph.add` 依次从文本抽实体、抽实体关系、按实体 embedding 查相似节点/关系、用 LLM 选择需删除的旧关系，再删除旧关系并写入新节点/关系；Graph 实体有 `name`、`type`、`embedding`，节点和关系带 user_id（并可附 agent_id/run_id）作用域。图检索将实体向量相似度阈值匹配得到的边转成 `source / relationship / destination` 三元组，再用 BM25 取 top-5；源码 `query.split(" ")` 的 tokenization 对中文分词很可能不理想，但中文效果没有测试证据，因此需标为风险推断。[v0.1.118 `graph_memory.py`](https://github.com/mem0ai/mem0/blob/ed5a1e9fc68fcd7671a70c33a540d24573755449/mem0/memory/graph_memory.py) [Graph prompts/utilities](https://github.com/mem0ai/mem0/blob/ed5a1e9fc68fcd7671a70c33a540d24573755449/mem0/graphs/utils.py) [Graph tool schemas](https://github.com/mem0ai/mem0/blob/ed5a1e9fc68fcd7671a70c33a540d24573755449/mem0/graphs/tools.py)。Graph 源码的旧关系更新机制并非 bi-temporal：更新提示指导删除过时/矛盾边，图关系还设置 `updated_at`，但有效时间区间 / transaction time 双时态字段未核实。[`graph_memory.py`](https://github.com/mem0ai/mem0/blob/ed5a1e9fc68fcd7671a70c33a540d24573755449/mem0/memory/graph_memory.py) [prompts](https://github.com/mem0ai/mem0/blob/ed5a1e9fc68fcd7671a70c33a540d24573755449/mem0/graphs/utils.py)。

**论文评测与版本边界。** Mem0 论文 arXiv:2504.19413 的摘要报告在 LOCOMO 上涵盖 single-hop、temporal、multi-hop、open-domain 类别，作者声称 Mem0 相对论文称作 OpenAI 的基线，LLM-as-a-Judge 指标有 26% relative improvement（不据此比较 Agents SDK），Mem0 + graph 比 base overall 高约 2%；这些是论文作者摘要所述结果，须按论文 setup 解读，不能作为当前 SDK 或本地 Agent24 的实测。[arXiv abstract](https://arxiv.org/abs/2504.19413)。当前主线 README 的 LongMemEval 指标口径则是 managed platform 的生产代表模型栈，并明确专有优化不可用 OSS，因此与论文的 LOCOMO 评测也不可直接横比。[current README benchmark note](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/README.md)。


**当前写入、重复与更新/删除。** 当前 OSS `add` 先按 scope 取最近消息与已有向量候选，再进行一次 LLM extraction；空抽取仍保存消息。新文本批量 embedding，按内容 hash 去重（也在当前 batch 去重），然后批量写向量库，失败后逐条 fallback；仅成功持久化的项写 `ADD` history。**在这条当前默认 OSS 路径中没有自动 UPDATE/DELETE/NOOP 的四类冲突分类器**，README 也特意称 Add-only。[实现完整路径](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py) [README](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/README.md)。然而 SDK 仍有显式 `update(memory_id, text)` 与 `delete(memory_id)` 管理 API，history 中可产生 UPDATE/DELETE；这是调用方主动操作，不是 add 流程中的 LLM 冲突动作。[显式 update/delete 实现](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py) [history storage](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/storage.py)。在这份当前 SHA 源码里没有 NOOP/ NONE 动作；写“Mem0 ADD/UPDATE/DELETE/NOOP 自动流程”会把旧版或其他记忆系统的行为错误套给当前版本，必须以版本为界。[实现](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py)。

**召回、scope、图、多语言。** 当前 OSS `search()` 默认排序是混合分数：先取语义向量候选（over-fetch `max(top_k*4,60)`），并调用 vector store `keyword_search`；无 keyword 能力的 backend 会退化为语义检索。BM25 sigmoid 归一化、语义分数阈值过滤、实体 boost（权重 0.5）共同按加权归一化和降序排列。keyword 分数只为语义候选加分，没有 keyword-only 候选并入结果集。可选 reranker 需显式 `rerank=True` 且配置 reranker，默认关闭。`expiration_date` 过期项默认隐藏（可 `show_expired`），不是时间衰减排序；`reference_date` 明确是 Platform-only、OSS 不支持。评分函数没有时间权重/decay 项。[OSS search implementation](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py) [scoring implementation](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/utils/scoring.py) [README retrieval note](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/README.md)。多 scope filter 可帮助隔离 user、agent、run；交集语义和组织级授权需由调用方配置，不能等同 Agent24 的 `SpaceId` 授权边界。[scope validation/filter](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py)。Graph Memory 官方文档描述平台内抽实体为节点、共享实体连接记忆，抽取和检索两阶段参与；文档区分实体节点与用于 scope 的 user/agent/app/run IDs，并说明当前图是平台功能，早期外部图数据库接入已被其平台原生实现替代。[Graph Memory 文档](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/docs/platform/features/graph-memory.mdx)。因此当前平台原生图不能列为 OSS 本地能力；前述历史版外接 Neo4j 源码则可核查。中文/多语言：检索质量依赖 embedding、NLP 预处理和后端；未找到中文检索专项 benchmark 或中文 tokenizer 保证。[README](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/README.md)。

**查看、导出、评测与许可。** SDK 有 get/get_all/search/update/delete 和 memory history 等程序接口，便于应用做列表与维护；用户可视化界面、端到端导出格式与单条撤销是否恢复旧值需按具体部署核实。[Memory API](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py) [storage history](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/storage.py)。README 当前表列 LongMemEval 67.8 对 94.4，且说明是在相同 production-representative model stack、single-pass、top_200 retrieval budget 下比较；同时明确数字来自 managed platform，含专有优化，OSS SDK 只能期待方向接近、不能期待相同数字。[README benchmark caveat/table](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/README.md)。这些是项目报告数字，独立复现/中文评测未核实；不能当作 OSS 可重现性能保证。许可证为 Apache-2.0。[LICENSE](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/LICENSE)。

**优缺点及 M1 关联。** 优点：scope 字段明确、内容 hash 去重、写入阶段区分提取/向量化/持久化/history，并在批写失败后逐项回退；显式 history 可支持追踪操作。[实现](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py) [storage](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/storage.py)。缺点：自动抽取依赖 LLM，当前主线不做语义冲突更新；向量库和 history 存储的跨库原子性在所读代码中未见保证；平台 benchmark 含闭源优化，graph 功能也不能视作本地 OSS 能力。[实现](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py) [README](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/README.md) [graph doc](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/docs/platform/features/graph-memory.mdx)。M1 的 T06 明确推迟自动提取与同义 supersede，因此 Mem0 的 extraction prompt、批 embedding 及重复 hash 可留作 T06b/T07b 之后研究；T07/T08 可借鉴“给固定 top-k 预算并报告检索评测”，但必须在本地模型和中文样本上重跑，不能引用平台 LongMemEval 数字作为门禁。M1 的 `owner` 应只允许个人空间，不采用多个 user/agent/run ID 的任意组合，避免绕过 T07/T10 的 personal-only 策略。[M1 计划 T06/T07/T08/T10](../../agent/M1-PLAN-v2.md) [Mem0 scope](https://github.com/mem0ai/mem0/blob/abb81c88e1f738a8117d8293530fbc31a5ef8fd9/mem0/memory/main.py)。

### 3. Zep / Graphiti：时态图与来源关系

**是什么与边界。** Graphiti 是开源 Python 框架，用可增量更新的 temporal knowledge graph 表达 agent 交互、结构化数据和来源 episode；图包含 Entity 节点、EntityEdge 事实边、Episodic 原始片段及 Community。官方 README 明确 Graphiti 是 Zep 上下文基础设施的 OSS 核心，而 Zep 托管服务采用 proprietary Context Graph Engine，提供用户/线程管理、治理、dashboard 等；两者不能混为一谈。Graphiti 要自带 Neo4j、FalkorDB 等图数据库；其 README 标明 Kuzu deprecated。[Graphiti README（固定 commit `3c427640`）](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/README.md) [Graphiti EntityEdge 源码](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/edges.py#L263) [Graphiti Node 源码](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/nodes.py#L93)

**机制与可借鉴数据模型。** `Node` 的公共字段包括 `uuid`、`name`、`group_id`、`created_at`；`EntityNode` 有 `name_embedding`、`summary`、`attributes`；`EntityEdge` 有 `source_node_uuid`、`target_node_uuid`、`name`、`fact`、`fact_embedding`、关联 `episodes`，及 `expired_at`、`valid_at`、`invalid_at`、`reference_time`。[Node 源码](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/nodes.py#L93) [EntityNode 源码](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/nodes.py#L499) [EntityEdge 源码](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/edges.py#L263) `valid_at`/`invalid_at` 描述事实在现实世界何时生效/失效；`created_at` 是系统记录时间，`expired_at` 表示边被系统过期处理的时间，`reference_time` 来自 episode。M1 若未来做 supersede，可加 `valid_from/valid_to` 与 `recorded_at/retracted_at` 两组时钟；当前断言本来就是显式用户声明，应把 provenance `EventId`、trust/modality 与时间字段分开，不能把自然语言日期误当系统写入时间。论文称 episode 是原始输入、语义图是派生结构并保留 source trace。[Graphiti 论文 §2](https://arxiv.org/html/2501.13956)

**写入、去重、冲突。** 当前 `add_episode` 按 group 取旧 episodes，抽实体并调用 `resolve_extracted_nodes`，再抽关系、解析重复和矛盾边，最终持久化 episode 与派生图。实体先用语义/全文候选匹配，再让 LLM 判同一实体；关系解析比较端点及相关事实，对矛盾旧边填 invalidation 时间。此类模型判定不是确定性真值仲裁，实体误合并须另测。README 强调结构化输出能力，弱模型可能抽取失败。[add_episode](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/graphiti.py) · [node resolution](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/utils/maintenance/node_operations.py) · [edge resolution](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/utils/maintenance/edge_operations.py) · [README](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/README.md)

**召回、时间排序与观察。** `search_config.py` 将 edge/node 搜索配置为 BM25、cosine similarity、BFS，可选 RRF、node distance、episode mentions、MMR、cross-encoder reranker；Graphiti search 实现并行执行启用的方法，`group_ids` 贯穿过滤。[Search 配置源码](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/search/search_config.py#L32) [edge search 源码](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/search/search.py#L253) 时间主要体现在事实有效区间和查询过滤；在核对的 Graphiti 配置/代码中**未核实到通用 recency decay**。论文解释 rerank 有 episode mention、图距离及 cross-encoder，后者计算代价更高。[论文 §3](https://arxiv.org/html/2501.13956) 源码用 tracing span 暴露搜索方法、候选数、reranker 等字段；托管 Zep 宣称可用 dashboard 查看图、debug/API logs，这属于其产品能力，不能假定 OSS 自带同等运维界面。[search tracing](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/search/search.py#L98) [Zep/Graphiti 对照](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/README.md#zep-vs-graphiti)

**作用域、用户控制、多语言与许可证。** `group_id` 标为 graph partition，模型节点/边查询支持 group ID；删除 API 可按 group 批量删，故它可作为租户/用户隔离的实现构件，但数据访问控制与授权仍由集成方完成。[Graphiti node partitions/delete](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/graphiti_core/nodes.py#L178) 有节点/边的直接 delete 和按 group 删除；核对的 OSS README/source 未核实统一用户导出、带审计的编辑 UI、撤回工作流。中文专项检索/评测支持未核实；README 的默认模型/embedding 提供商是 OpenAI，并未承诺中文指标。[README](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/README.md) OSS LICENSE 是 Apache-2.0。[LICENSE](https://github.com/getzep/graphiti/blob/3c427640abf909f12f71f963fce15eb514a3c493/LICENSE) Zep 托管服务的服务条款/价格/许可证不在本次开源仓库许可证结论内。

**评测与局限。** 论文 Table 1 的 DMR：Zep 94.8%、MemGPT 93.4%，回答模型为 gpt-4-turbo；MemGPT 数字引用既有结果，同表 full-context 已达 94.4%。DMR 每个会话组最多约 60 条消息，不足以检验超长记忆。LongMemEval_s Table 2：gpt-4o-mini 下 full-context 55.4% → Zep 63.8%；gpt-4o 下 60.2% → 71.2%（+11.0 个百分点，按表值计算相对约 +18.3%；论文正文写约 18.5%，不是 +18.5 个百分点）。评判器 GPT-4o；图构建用 gpt-4o-mini，检索采用 BGE 系模型。论文未成功完成 LongMemEval 上的 MemGPT 对照，因此这组不能称“胜过 MemGPT”。gpt-4o 延迟 28.9s → 2.58s 是作者的全文上下文对照实验；Zep 走托管网络路径，且输入上下文量不同，不能用作本地 Graphiti SLA。以上均未独立复现。[论文模型/DMR §4.1–4.2](https://arxiv.org/html/2501.13956#S4.SS2) · [LongMemEval §4.3 与表格](https://arxiv.org/html/2501.13956#S4.SS3)

**与 M1 关系。** Graphiti 的 provenance episode→派生事实、时态字段、按作用域查询和多路检索值得参考；但 M1 已冻结为显式「记住」规则、personal space、SQLite AssertionLedger、FTS OR 候选、forget 撤回，不能把自主图抽取或图数据库加入 M1。适合当后续 FU-M1-2（同义更新/supersede）及 T07b 向量召回设计参考；其实体归并/LLM 冲突裁决需放到笔记本本地模型路线评估。[M1 T06/T07/T09 与 FU-M1-2](../../agent/M1-PLAN-v2.md)

### 4. LangMem / LangGraph Store：记忆策略与存储协议分离

**是什么与组件边界。** LangMem 是 MIT 许可的记忆管理库，提供 agent 在当前交互中调用的 memory tools（hot path），以及可在后台抽取、整合、更新记忆的 manager；LangGraph Store 是可持久化的跨 thread key/value store，记忆策略由 LangMem 提供，向量索引由 Store 配置决定。三类概念是 semantic（事实/偏好）、episodic（经历及其结果/策略）、procedural（指令/行为规则）；它们是组织记忆的类别，具体 schema 可由应用定义。[LangMem README（固定 commit `9d033b4`）](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/README.md) [LangMem episodic guide](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/docs/docs/guides/extract_episodic_memories.md) [LangMem semantic guide](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/docs/docs/guides/extract_semantic_memories.md)

**数据模型与写入/更新。** LangGraph `Item(namespace: tuple, key: str, value: dict, created_at, updated_at)` 由 namespace+key 定位；`SearchItem` 加可空 score，search 的 namespace 是前缀匹配，可能覆盖后代空间。LangMem `create_memory_manager` 默认允许 insert/update、关闭 delete，模型通过结构化调用给出新条目、保留 id 的更新或 `RemoveDoc(json_doc_id)`。`MemoryStoreManager` 搜索已有条目、按 `(namespace,key)` 去重，再将模型决定映射为 `put/aput` 与 `delete/adelete`；异步路径用 `asyncio.gather` 提交，不能据此假定整批原子提交。[Store 字段与 SearchOp](https://github.com/langchain-ai/langgraph/blob/157a06dda988d85afeb8751ff27b35ab3f4f8bf4/libs/checkpoint/langgraph/store/base/__init__.py) · [extraction.py](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/src/langmem/knowledge/extraction.py)

**直接工具的控制边界。** `create_manage_memory_tool(actions_permitted=...)` 限定可调用动作并再次检查，update/delete 需要 id；update 对同 key 做 put/upsert，没有先检查旧版本的 CAS。namespace 从模板/运行 config 计算，工具本身不验证传入 user_id 的所属关系。因此“有 namespace”不能替代服务端身份绑定，且 mutable store 不等价于不可变 AssertionLedger。[tools.py](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/src/langmem/knowledge/tools.py)

**Hot path 与 background。** Hot path 允许当前 agent 显式调用 `create_manage_memory_tool`、`create_search_memory_tool` 来决定何时写和查；background quickstart 将 memory manager 放在独立流程异步处理对话，semantic guide 也给出后台处理、分次管理复杂更新的示例。[LangMem README](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/README.md) [semantic guide background 示例](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/docs/docs/guides/extract_semantic_memories.md#background-processing) 该机制让用户响应不必等待复杂 consolidation，但这是应用编排方式，不代表有内建 exactly-once、失败重试或事务保证；在 M1 显式 retain 写入路径中不能用异步抽取替代原子 evidence 写入。

**召回、隔离与遗忘。** Store 在 namespace 前缀下搜索，可配置向量索引，manager 多查询结果按 score 排序；本次未核实统一 BM25 混合、cross-encoder rerank 或 recency decay。`delete(namespace,key)` 构造 `PutOp(value=None)`，内存 backend 直接移除 item；它不是 M1 的 tombstone+撤回事件。BaseStore 有可选 TTL 接口，按访问时间过期、可刷新并由 best-effort sweep 清理，但 `supports_ttl` 默认 false，不能推断每个 backend 支持；核对的 InMemoryStore 没有 TTL sweep。TTL 到期删除也不同于相关性时间衰减。[BaseStore 删除与 TTL](https://github.com/langchain-ai/langgraph/blob/157a06dda988d85afeb8751ff27b35ab3f4f8bf4/libs/checkpoint/langgraph/store/base/__init__.py) · [内存 backend](https://github.com/langchain-ai/langgraph/blob/157a06dda988d85afeb8751ff27b35ab3f4f8bf4/libs/checkpoint/langgraph/store/memory/__init__.py) · [MemoryStoreManager](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/src/langmem/knowledge/extraction.py)

**用户控制与可观测性。** Store 提供 get/put/search/delete，适合应用构建列表、编辑和撤回适配层；本次未核实 LangMem 自带通用用户管理 UI、完整导出流程、逐事实审计日志。后端持久化与应用 tracing 需另行接入；不能将 LangGraph checkpointer 的 thread 状态历史等同跨 thread 的 Store 事实版本。[Store 源码](https://github.com/langchain-ai/langgraph/blob/157a06dda988d85afeb8751ff27b35ab3f4f8bf4/libs/checkpoint/langgraph/store/base/__init__.py) · [官方 persistence 文档](https://docs.langchain.com/oss/python/langgraph/persistence#memory-store)

**多语言、许可与评测。** LangMem 与 LangGraph 文档示例以英文对话/schema 为主，未核实官方中文检索质量基准；底层模型、embedding 与 Store 后端可以配置，但不等于框架已证明中文召回效果。[LangMem README](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/README.md) LangMem/LICENSE 为 MIT。[LICENSE](https://github.com/langchain-ai/langmem/blob/9d033b47d9ce53e37e92c92241b0496c0278932e/LICENSE) 核对的 LangGraph 根 LICENSE 也是 MIT；具体托管产品不在该结论内。[LangGraph LICENSE](https://github.com/langchain-ai/langgraph/blob/157a06dda988d85afeb8751ff27b35ab3f4f8bf4/LICENSE) 本轮官方资料未找到 LangMem 自身可复现的记忆 benchmark 结果；效果取决于提示词、模型、存储和索引，应视作组件/工作流而非性能保证。

**与 M1 关系。** 可借鉴的是 `namespace=(app,user_id,...)` 的 scope 组织、事实结构 schema、后台 consolidation 与检索/管理职责分离。M1 的权限是 T02 personal key + T07 只查 personal owner；调用方需将 owner 参数绑定授权主体，不能照搬“namespace 即隔离”的安全假设。M1 T06 只允许显式规则匹配写入；`T06b` 是唯一适合本地模型实验的后台抽取扩展点。M1 T09 的撤回需要账本 UPDATE 与撤回事件同事务，语义应保持在存储层，而非依赖 LLM 输出 `RemoveDoc`。[M1 T02/T06/T06b/T09](../../agent/M1-PLAN-v2.md)

### 5. Cognee：资料摄入、知识图与检索管线

**是什么。** Cognee 是把原始资料转成可检索知识图谱的 agent memory / knowledge engine；当前 README 将流程表述为 `remember` 存储、`recall` 查询、`improve` 反馈/跨阶段改进、`forget` 删除。本文源码固定在仓库 commit [`b32d8afc`](https://github.com/topoteretes/cognee/commit/b32d8afc59e1064d9291b9828a8a147be9cc8bab)，README 强调可选择本地模型和图、向量检索。[README](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/README.md)

**模型与管线。** API 有意拆开 `add`（接收文件/文本并登记，不在 add 本身调用 LLM）和 `cognify`（执行后续 pipeline）；`Data` 表的可借鉴字段包括 `id, name, extension, mime_type, owner_id, tenant_id, dataset_id, legacy_id, content_hash, raw_content_hash, external_metadata, system_metadata, node_set, pipeline_status, token_count, data_size, created_at, updated_at, last_accessed, importance_weight`。同一 `(dataset_id, owner_id, content_hash)` 有 lookup index 供去重；更新需显式 `update(data_id, ...)` 保持 identity，add 不承担更新。注意这只是内容/摄取实体字段；知识图谱节点边由 pipeline 的 DataPoint 类型继续建模，不能把 Data 表误当断言账本。[Data model](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/modules/data/models/Data.py) [add 源码](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/api/v1/add/add.py) [cognify 源码](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/api/v1/cognify/cognify.py)

**图数据模型（源码核对）。** `DataPoint` 是图节点基类：`id(UUID), created_at/updated_at(ms), ontology_valid, ontology_uri, version, topological_rank, valid_to(ms), metadata{type,index_fields,identity_fields,transparent}, type, belongs_to_set, source_pipeline, source_task, source_node_set, source_user, source_content_hash, feedback_weight, importance_weight`。业务子类的标量字段成为 node properties；嵌套 DataPoint 字段形成关系边。`identity_fields` 经 UUID5 派生稳定 ID，供同一实体跨导入合并；没有 identity field 就随机 ID，不会自动 dedup。向量索引字段由 `metadata.index_fields` 声明。通用 `Edge` 值字段为 `source, target, relationship_type, weight, weights, properties, edge_text`；通常由类型化子类/模型声明边，而非一张 assertion 表。它提供关系图与实体归一化能力，但没有天然等价于 Agent24 的 trust/modality/assertion 状态账本。[DataPoint 模型](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/infrastructure/engine/models/DataPoint.py) [Edge 模型](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/infrastructure/engine/models/Edge.py)

**召回、更新与遗忘。** 搜索先按用户的 `read` ACL 解析可访问 datasets，再按 `query_type` 路由检索器；支持多种搜索类型/graph 与 vector lane 的 hybrid 路径、`top_k`、节点类型/名称过滤和邻域参数。README 所述 memory graph/vector retrieval 也可部署在 Postgres demo 后端，但其 README 明确标 demo 功能。`forget(data_id, dataset_id)` 删除数据项及其图/向量记忆；`memory_only=true` 会保留原始 data row/file、删除该来源节点边与向量、清理关联 edge evidence/session cache，并重置 cognify pipeline status；全量 dataset 删除则走 empty_dataset。删除前解析 dataset 且校验 delete 权限，按 dataset lock 与数据库 scope 执行。它是实际硬删除，和 M1 的撤回事件语义不同。更新 ingestion 的源码强调 replacement 成功后再删除旧项。未在已读源码中核实通用时间衰减排序，也未核实一种统一的事实冲突裁决/断言 supersede 规则，不能把 `importance_weight` 字段当作已证实的衰减实现。搜索可 `only_context` 取回上下文，内部 search history 记录 query/completion 等，但这不等于用户友好的记忆审计 UI。[search 源码](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/api/v1/search/search.py) [forget 调用/权限和删除逻辑](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/api/v1/forget/forget.py) [add 更新/替换逻辑](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/api/v1/add/add.py) [官方权限文档](https://docs.cognee.ai/setup-configuration/permissions) [README graph/Postgres 与 forget](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/README.md)

**scope、控制面与多语言。** `owner_id`/可选 `tenant_id` + dataset `owner_id`/`tenant_id` 及 ACL（read/write/delete/share）形成 user→dataset scope；默认后端访问控制配置影响 single-user/local 与 multi-tenant 形态。能查看图（UI/visualization）及搜索上下文；API 有 update/delete 能力；批量导出/个人数据完整导出语义未核实。中文支持：README 有中文社区入口/多语言资料证据，但没有找到针对 CJK tokenizer、中文检索效果或中文 benchmark 的实现/结果证据，故中文召回质量未核实。[Dataset model](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/modules/data/models/Dataset.py) [权限配置文档](https://docs.cognee.ai/setup-configuration/permissions) [README](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/README.md)

**评测与边界。** README 报告 BEAM 100K-token 设定得分 0.79（0–1）：固定 hybrid retrieval、来自一个 held-out conversation 的 20 个问题、四轮；10M-token 探索得分 0.67，但用了另一 conversation、同一问题集选择/打分 routing，且报告说明仍有分布式 ingestion 复现缺口。两项适合作为项目内研究信号，不足以外推中文个人事实记忆准确率。框架较完整、图关系可解释且 ACL/异步 ingestion 有产品化思路；代价是 pipeline/数据库/模型栈明显大于 Agent24 M1 的本地 SQLite 账本，事实写入有 LLM pipeline 的不确定性，需谨慎做成显式记忆的权威写入源。Cognee 仓库 LICENSE 为 Apache-2.0。[BEAM 说明与结果](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/README.md) [BEAM 方法与复现限制](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/cognee/eval_framework/beam/REPORT.md) [LICENSE](https://github.com/topoteretes/cognee/blob/b32d8afc59e1064d9291b9828a8a147be9cc8bab/LICENSE)

**对 Agent24 M1。** 有价值：Data 的 `owner/dataset/content_hash/timestamps` 适合作为来源文档/索引的辅助字段；add 与 cognify 分层启发 T06b（可选本地抽取）将摄入和抽取拆开；ACL 说明 personal space 的 scope 必须进所有检索条件；搜索观测应记录使用了哪些结果。M1 直接采用其图构建、自动抽取、multi-tenant ACL、vector DB、异步 scheduler 不合适：M1 冻结为 personal-only、显式「记住」、原文事件不可删、T07 首版 FTS，向量仅 T07b 可选。`forget` 的硬删除含义与 M1-T09 的“撤回=断言失效+撤回事件、EventLog 原文保留”不一致。[M1 计划 T06/T07/T07b/T09](../../agent/M1-PLAN-v2.md)

### 6. MemOS：可组合记忆容器与文本生命周期

**是什么，注意版本边界。** MemOS 是 memory OS 研究路线：论文把 memory 区分为 plaintext/textual、inference activation state、模型参数/adapter 三种生命周期不同的资源，以 MemCube 统一封装；仓库提供可加载/导出不同 memory backend 的软件接口。论文里的跨层“蒸馏/调度/参数化”理念不能直接推断为本地已实现的自动能力。[论文 arXiv](https://arxiv.org/abs/2507.03724) [论文 HTML](https://arxiv.org/html/2507.03724) [README](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/README.md)

**模型与可运行机制。** MemCube 是容器，`BaseMemCube` 暴露 text/activation/parametric（代码另有 preference text）memory 后端及 `load(dir)`/`dump(dir)`；GeneralMemCube 通过 config + factory 构造后端。文档给出导出文件 `config.json`, `textual_memory.json`, `activation_memory.pickle`, `parametric_memory.adapter`，并提醒 embedding 模型/维度需匹配。textual item 的源代码有 `TextualMemoryItem`/metadata、来源 `SourceMessage(type, role, chat_time, message_id, content, doc_path, file_info, image_info, extra provenance)`；metadata 可含 `user_id, session_id, status(activated/resolving/archived/deleted), is_fast, evolve_to`；归档版本记录 `version, memory, update_type(conflict/duplicate/extract/unrelated/feedback), archived_memory_id, created_at, timespec, memory_form(state/event)`。字段组合对 Agent24 的 evidence/provenance 与撤回历史有启发，但其设计保存了可编辑的旧 node，而 M1 是 append-only EventLog + assertion ledger。[MemCube base](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/mem_cube/base.py) [TextualMemoryItem 源码](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/memories/textual/item.py) [MemCube 文档](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/docs/en/open_source/modules/mem_cube.md)

**具体文本更新/删除及 scope。** Tree memory 的组织器在 hard conflict update 中比较两个候选的 `metadata.updated_at`，保留较新节点并调用 `graph_store.delete_node(older.id, user_name=...)` 物理删除旧节点；在合并冲突路径则先创建 merged node、迁移边，再把两个旧 node 标成 `status=archived`，加 `MERGED_TO` lineage edges。检索默认 `status="activated"`，因此 archived 不会作为普通 active memory 命中。这里不是 EventLog 式完整不可变审计：hard-update 是删除，merge 才保留归档节点。Searcher 的所核对的检索路径传 `user_name` 到 graph store；向量过滤条件可附加 `search_filter`（含 `user_id` 等 metadata 条件），要求调用侧传入。MemCube API 的 `readable_cube_ids`/`writable_cube_ids` 决定跨 cube 搜索/写入集合，结果带 `cube_id`；这证明视图层可限定 cubes，不自动证明每个后端强制隔离正确，具体后端 ACL 仍需部署验证。[hard-update 与归档/merge handler](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/memories/textual/tree_text_memory/organize/handler.py) [检索 active status 与 user_name/filter](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/memories/textual/tree_text_memory/retrieve/recall.py) [MemCube Views](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/multi_mem_cube/views.py) [cube API scope](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/docs/en/open_source/modules/mem_cube.md)

**写入/去重/更新与检索。** MemOS 多数完整功能需结合指定 View、Reader、Scheduler、Searcher 和 graph/vector DB 配置；所核对的 preference text adder 的 pipeline 涉及候选新记忆、duplicate/conflict 判定、归档旧版本/关联新节点及向 vector DB 写入，状态包含 resolving/archived。Tree textual search 源码接 BM25 与 graph retriever，Searcher 包含 query/task parsing、graph retrieval、rerank；实现中能找到基于 query/context 的相关度加权，但未核实通用 timestamp 时间衰减公式。当前源码中用户过滤路径以 `user_id` 作 vector payload filter；View 文档以可读/可写 cube id 作 scope，复合视图返回来源 `cube_id`。遗忘的软删除/物理删除完整事务与跨索引一致性策略未从已读的 adder/search 源码核实；不要把 README 的统一 add/retrieve/edit/delete 产品承诺当作所有后端行为都已验证。[adder](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/memories/textual/prefer_text_memory/adder.py) [Searcher](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/memories/textual/tree_text_memory/retrieve/searcher.py) [reranker](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/src/memos/memories/textual/tree_text_memory/retrieve/reranker.py) [View scope 文档](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/docs/en/open_source/modules/mem_cube.md)

**用户控制、多语言、评测、许可证。** MemCube 可 dump/load，本地配置与文本记忆可浏览文件；图化设计和 README 声称支持 edit/delete，但当前源码核查不足以确认完整 viewer/API 的所有权验证与导出删除语义。官方 README 有中文 README 链接、中文文档可见，证明文档本地化，不证明中文检索 benchmark。README 自报 LoCoMo **88.83**、LongMemEval **89.20**，并引用 OmniMemEval，但需注意具体模型、版本、prompt、测试集与 judge 对比口径应到 OmniMemEval 原始报告复核；此轮未从 README 单独取得可复现的评测脚本参数，视为项目自报数据而非独立验证。许可证 Apache-2.0。[中文 README](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/README_ZH.md) [README 性能表](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/README.md) [OmniMemEval](https://github.com/MemTensor/OmniMemEval) [LICENSE](https://github.com/MemTensor/MemOS/blob/a7367d07e55db61099f7b4e2c1108bc5831a24f3/LICENSE)

**对 Agent24 M1。** 可以借其 provenance 形状（`source type/role/message_id/time/content`）补强 M1-T06 evidence 旁的来源显示/审计视图；保留 `recorded_at/valid-time`、原始来源引用和状态历史，UI 可解释 assertion 从哪里来。MemCube scope 机制提醒个人空间的空间 ID 必须随读写请求显式传递，可帮助审查 T02/T07/T10。可借但 M1 不做：树状 graph/semantic memory、background scheduler、activation cache、adapter/parameter memory、自动 preference/conflict resolution，适合 M2+。不适合 M1 当 authoritative store：它将文本、activation、参数混在 OS 生命周期，且更新/归档会重组节点；Agent24 冻结要求 EventLog 原文永存、Trust/Modality/provenance 的 WriteGate、明确记住才入账、忘记追加事件。特定 Cognee/MemOS 内部图和向量 DB 不是 Agent24 Rust M1 的部署目标。[M1 计划 T02/T06/T07/T09/T10](../../agent/M1-PLAN-v2.md)

### 7. OpenAI Agents SDK / Assistants：会话存储与长期记忆须分层判断

- **是什么。** Python Agents SDK 的基础 `Session` 是跨 run 的消息历史接口，公开 `get_items/add_items/pop_item/clear_session`；当前源码另外提供 sandbox 文件式长期记忆，不能再笼统写“SDK 只有短期记忆”。Assistants 是托管 API，不是开源记忆框架；其官方迁移页写明已于 **2026-08-26 sunset、不可用**，这里只作历史参照，不建议新接入。[Session 源码](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/src/agents/memory/session.py) · [sandbox memory](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/docs/sandbox/memory.md) · [官方迁移页](https://developers.openai.com/api/docs/assistants/overview)
- **数据模型与写入。** `SQLiteSession` 的 `agent_sessions(session_id PK, created_at, updated_at)` 与 `agent_messages(id INTEGER PK, session_id FK, message_data JSON文本, created_at)`，有 `(session_id,id)` 索引；`add_items` 批量追加并提交，底层不是事实级 ADD/UPDATE 判决器，也没有消息内容唯一约束。sandbox 则先将会话提取为 `rollout_slug/rollout_summary/raw_memory`，再由第二阶段 agent 整理 `MEMORY.md` 与 `memory_summary.md`；元信息含 `rollout_id/rollout_path/updated_at/terminal_state`，可追到原 rollout，但不是逐条 assertion 的 evidence 外键。[SQLite 实现](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/src/agents/memory/sqlite_session.py) · [提取结构](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/src/agents/sandbox/memory/interface.py) · [生成调度与元信息](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/src/agents/sandbox/memory/manager.py)
- **召回、更新、遗忘。** 普通 Session 取最新 N 项后按时间顺序返回，不做 BM25/vector/rerank。sandbox 启动时注入短摘要，agent 按关键词搜索 `MEMORY.md`，再按需读 rollout summaries；可在 run 中修订过期记忆，session 关闭时做提取和 consolidation。第二阶段按 `updated_at` 选择最近的 raw memories，并向整理 agent 提供移除清单；这是整理输入的 recency 策略，不是经过校准的召回时间衰减公式，也不证明完整物理擦除。普通 Session 的 `pop_item/clear_session` 和 compaction 的后缀替换会 DELETE 行，因此不能把它直接当 M1 永久 EventLog。[SQLite 删除/检索路径](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/src/agents/memory/sqlite_session.py) · [sandbox 检索说明](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/docs/sandbox/memory.md) · [选择逻辑](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/src/agents/sandbox/memory/storage.py)
- **作用域、可控性、中文、许可。** SQLite 查询按 `session_id` 隔离，表内没有 Agent24 的 `(org,user,space)` 授权模型；sandbox 隔离键是 layout 路径，而不是 agent name，共享 layout 的 agent 可共享整理后的记忆——应用仍需配置文件访问权限。Session 可读/清空，文件可查看、编辑、复制导出；这不等于统一的记忆管理 REST/UI。SDK README 提供运行 tracing，中文目录存在，但中文记忆质量基准**未核实**；SDK 本身 MIT，调用的托管服务不因此变成开源服务。[SQLite schema](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/src/agents/memory/sqlite_session.py) · [layout 与读写模式](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/docs/sandbox/memory.md) · [README](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/README.md) · [中文文档](https://github.com/openai/openai-agents-python/tree/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/docs/zh) · [MIT](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/LICENSE)
- **评测与取舍。** 所读 README/实现/指南没有提供可用于本报告横向排名的统一长期记忆分数；质量、中文命中率与本地 oMLX 的可替代性**未核实**。工程优点是存储协议小、源数据与整理文件分层、按需读取；缺点是摘要/整理由模型决定，文件层没有 Agent24 的 Trust/Modality 门禁。**对 M1 的判断：**借鉴 Session 协议的清晰边界和摘要失败的观测方式，保留 T03/T04 的 append-only 权威日志；两阶段提取只作为 T06b 以后参考，不能取代 T06 的用户显式授权。[实现依据](https://github.com/openai/openai-agents-python/blob/730deb419c0a2e9e5ebd739499744e4a6bf89ed1/src/agents/sandbox/memory/manager.py) · [M1 T03–T06b](../../agent/M1-PLAN-v2.md)
