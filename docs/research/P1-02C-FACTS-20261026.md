## 1. 写入路径 × 撞到 QuotaExceeded 时用户看到什么

### W1 会话轮次（最重要，每轮都写）
- 错误传递：`append_turn` 返回 `Err(QuotaExceeded)`（`?` 提前返回，事务丢弃回滚）→ `SessionMemory::remember`（session_memory.rs:307-）里 `append_result?` → `RunManager::remember_exchange`（`C/agent24-agent/src/lib.rs:723-750`）把 Err 转成 `EventBody::MemoryWriteFailed{session_id, reason: err.to_string()}` 并返回 `MemoryWriteOutcome::Failed`。
- reason 文本是 `MemoryError::Display`：`quota exceeded for owner "<含 NUL 的分区键>": rows limit reached`（lib.rs:82-85），**原样进事件，含内部分区键**。
- **run 路径**（`lib.rs:2023` 在 `run.completed` 之前调用 `remember_exchange`，结果被 `_ =` 丢弃）：run 仍以 `completed` 结束，答案正常返回；唯一信号是 `memory.write_failed` 事件（WS）。模型输出可能已经说"好的，我记住了"，没有任何改正。仓库内没有桌面端消费 `memory.write_failed`/`memory.write_skipped`（git grep apps/ 无命中，只有 Rust 事件定义与测试）。
- **/api/v1/chat 路径**（`A/agent24d/src/routes.rs:632-655`）：HTTP **200**，响应体照常；`memory_receipt` 仅当提示是显式「记住」时存在（`explicit_remember_state.and(...)`，:636），Failed → `"failed"`，桌面端 `Chat.tsx:94-161` 显示 `memory.failed` 文案。**非显式记住的普通轮次写失败时：receipt 为 None，用户界面零提示**（只有 WS 事件 `memory.write_failed`）。
- 无 `memory.write_skipped{reason:"quota"}`：`write_skipped` 只有 `reason:"paused"`（lib.rs:1727-1733、`chat_memory_prelude`）。
- 后续副作用：会话上下文来自 `SessionLog::load_view`（`session_memory.rs:context`），失败的轮次不在日志里，下一次 run 的上下文看不到它（测试 `C/agent24-agent/src/session_failure_tests.rs:73-186` 钉住：quota=0/1 时 run completed、`memory.write_failed` 每次一条、日志无半写、下一轮上下文无泄漏）。满额后会话历史**冻结在最后一次成功写入处**，模型对此无感知。
- 部分成功组合：`append_turn` 成功但 W4（`retain::persist`）失败 → `retain_result` 为 Err → 仍报 Failed；此时该轮消息已落盘而断言没有（两个事务，不跨事务原子）。反例：W4 在同一 `remember` 内才发生，append_turn 先占 2 行。

### W2 压实摘要
- `compact` 的 `append_summary` 若撞配额：`session_memory.rs` 里 `Ok(Err(err)) => tracing::error!("session {sid} compaction failed; originals retained")`（约 :424-430），**不发事件、不影响返回值**。压实**增加**行数（+1 `session.summary`，上限 `max_summary_chars=4000` 字符），不删原文。
- 副作用：摘要写不进去 → 未折叠的 tail 继续变长；`context()` 在 tail 超过 `max_recent*RECENT_HARD_CEILING_FACTOR`（`4*40=160`，session_memory.rs:17/283）时只在视图里丢最老消息并 `tracing::error!`，日志仍完整。

### W3 旧会话导入
- `ensure_imported`（session_memory.rs:~250-270）里 `import_legacy(...).await?` 失败直接传出：`context()` 返回 Err → run 路径 `session_context`（lib.rs:694-708）捕获为 warn 并**返回空上下文**；`remember()` 的准备阶段则 `result?` → Failed。用户看不到。

### W4 显式记住断言
- 同 W1 的 Failed 路径（`retain::persist` 的 `?`）。注意顺序：W1 先写，通常 W1 就先撞满；W4 单独撞配额只在 W1 刚好用完最后一行余量时出现。
- `propose()` 是逐候选循环（writer.rs:729-），`?` 使整个调用返回 Err，**已提交的前面候选的 decisions 丢失**（当前只传 1 个候选，实际无影响）。reject 审计在配额满时变成 `Err`，而不是 `WriteDecision::Rejected`。

### W5 撤回（违反 ADR 的关键）
- 满额时 `forget` 返回 `Err(QuotaExceeded)`，整笔回滚，**断言保持 active**（测试 `C/agent24-memory/src/lib.rs:2544 forget_quota_failure_keeps_assertion_live_and_can_retry`）。
- HTTP：`A/agent24d/src/memory_routes.rs:212-231`：非 Forgotten/AlreadyForgotten/NotFound 的 Err 一律 **500** `{"code":"internal","message":"could not retract the assertion"}`，不区分配额与其他故障；日志 `tracing::error!`。桌面端 Memory 页对失败的 retract 显示错误并保留条目（`Memory.test.tsx:132`）。
- 撤回本身**增加**一行（`assertion.retracted`），所以满额后"用户想删除这条记忆"做不到，且用户看到的只是通用 500。

### W6 模块 remember（进程内）
- `os_memory.rs:831-845`：`.map_err(|e| DomainError::Store(e.to_string()))` —— 类型信息丢失，`Display` 含分区键（`module store: quota exceeded for owner "...": rows limit reached`）。模块（进程内域 OS）拿到的是 `DomainError::Store(String)`，无法与普通 IO 错误区分。是否经过某条渗漏到 UI 的路径：**未能确认**（未追到 domain.rs 对 DomainError::Store 的最终呈现）。

### W7 模块 remember（OOP）
- `map_memory_error`（`os_memory_page.rs:192-215`）：`QuotaExceeded` → `ErrorKind::QuotaExceeded`（wire `quota_exceeded`，`agent24-os-proto/src/rpc.rs:130/202`），消息固定 `"memory {rows|bytes} quota exceeded for this module"`，owner 只进 `tracing::warn!`（正确脱敏）。其他错误统一 `-32603`/`"an internal memory storage error occurred"`。
- SDK 侧 `ClientError::QuotaExceeded` 被分类为 **permanent、非 retryable**（`agent24-os-sdk/src/error.rs:112,430`）——而当前没有任何释放路径，所以对模块而言确实是永久失败。
- HTTP 返回码：模块走 JSON-RPC over OOP，没有 HTTP 码。

## 2. 审计、撤回与配额

- **审计在 mem_events 里，且计入配额**：`mem.write_decision`（`writer.rs:222-250 audit_event`）、`assertion.reasserted`（:708）、`assertion.retracted`（assertion.rs:~95）都是 `MemEvent`，经 `append_tx`，被 `mem_events_bi_quota` 触发器同口径计行/字节。没有任何 kind 白名单豁免。
- **记忆写入失败 → 审计也一起失败（且必须）**：断言行与审计行在同一 `BEGIN IMMEDIATE` 事务，审计 INSERT 被触发器 ABORT → `?` 返回 → 事务丢弃 → 断言也回滚。反过来，满额时**没有"写入失败但留下拒绝审计"的能力**：失败本身不留 mem_events 记录（只有 tracing 与 `memory.write_failed` 事件，后者是 WS 广播，不持久化）。
- **撤回在满额时失败**：见 W5。`forget` 的事件是 `append_tx` 普通 INSERT，吃同一配额门，无豁免。
- **暂停开关不受影响**：`PUT /api/v1/memory/settings` 写 `kv` 表（`KvStore::set_memory_enabled`，lib.rs:416-423），不碰 `mem_events`，满额后仍可暂停。
- **没有任何不受配额约束的保留空间**：触发器对所有 `scope_owner`、所有 kind 一视同仁；`mem_owner_quota` 只能按 owner 设 override，无"控制记录保留额度"概念；无 `kind` 维度。只有 `WHEN NOT EXISTS(id)`（0014:180）让**完全相同 id 的重放**绕过配额（幂等，不是保留空间）。
- 断言本身（`mem_assertions`）、FTS、`mem_consolidations`、embeddings、`kv` 都**不计配额**（0014 只统计 `mem_events.payload`）；断言的增长只通过"每条必配一个审计事件"间接受限。

## 3. 原子性

- `commit_with_audit_using_clock`（writer.rs:520-725）：`pool.begin_with("BEGIN IMMEDIATE")` → 断言 `insert_tx`（:720）→ 审计 `append_tx`（:721）→ `commit`。审计撞配额时 `?` 提前返回，`sqlx::Transaction` 在 drop 时回滚，**整笔回滚，不会只写一半**。
- 触发器是 `RAISE(ABORT)`：SQLite 语义下只回滚**当前语句**，同事务里之前的语句保持未提交状态；回滚完全依赖调用方丢弃事务（此处 `?` 保证）。这是代码约定，不是 SQL 保证——将来若有人 catch 错误后继续 `commit`，会写出半笔。
- 证据：`C/agent24-agent/src/session_failure_tests.rs`（quota=1 时 append_turn 第二行失败，第一行回滚，`view.tail.is_empty()`）；`writer.rs:1104 h02_failed_reassert_append_is_atomic`（注入 ABORT，事件数与 `mem_owner_usage` 均不变）；`C/agent24-memory/tests/reassert_audit.rs:126 rejected_reassert_proof_rolls_back_the_entire_transition`；`lib.rs:2544`（forget 回滚）。
- 跨事务不原子：W1(append_turn) 与 W4(persist) 是两个事务（session_memory.rs:339-381），W1 成功而 W4 失败会留下消息而无断言（见 §1）。
- reassert 分支（writer.rs:667/708）在一个事务里最多追加 2 行（audit + reassert），同样整笔回滚。

## 4. 磁盘满

- **没有 SQLITE_FULL / IO 错误的专门映射**：`MemoryError::Sqlx(#[from] sqlx::Error)`（lib.rs:35-36）透明包装；`MemoryError::Io(String)` 只用于 mkdir 与"owner 未配置"。grep（memory/store/agent/agent24d）无 `SQLITE_FULL`/`StorageFull`/`DiskFull`/`ENOSPC` 处理。
- 用户看到：W1/W4 → 同 §1（`memory.write_failed`，reason 为 sqlx 原文如 `database or disk is full`；chat 的 receipt=failed 仅对显式记住）；W5 → 500 internal（同配额）；W7 → `-32603` "an internal memory storage error occurred"；W6 → `DomainError::Store(原文)`。无法区分"配额满"与"盘满"以外的 HTTP/receipt 维度（receipt 只有 saved/paused_not_saved/failed）。
- **没有任何写入前剩余空间检查**：`agent24-hw` 的磁盘探测（`probe.rs:85/104`、`disks.rs:70 free_bytes_for_path`、`legacy_disk.rs:21 legacy_cwd_free_bytes`）只被 `agent24-decide`（`tier.rs:19 MIN_FREE_DISK_BYTES=2GB`，决定模型档位）、`A/agent24d/src/hardware.rs`、`decide_routes.rs:68` 使用；记忆写入路径不依赖 agent24-hw。注意 `legacy_cwd_free_bytes` 按 **cwd** 取盘，不是 `memory.db` 所在卷。
- 参照物：`A/agent24-documents/src/state.rs:322 io_cause` / :401 `Some(13) => StorageCause::DiskFull` 已有 SQLite code 13(FULL) → `disk_full` 映射，并有写探针 `probe_write`（:~330）区分满盘与不可写（SQLite 满盘可能表现为 SHMSIZE/IOERR）。这是文档子系统的现成做法，记忆层可借鉴，但目前未复用。
- memory.db 位置：`state_dir()/memory.db`（`A/agent24d/src/server.rs:487`），与 Run DB（`agent24-store`）是不同文件。
- 配额与盘的关系：配额只计 payload，不含索引/WAL/FTS/页；`mem_events` 有 `mem_events_owner_seq`、`mem_events_session_seq` 等索引，所以磁盘占用 > 256MiB payload 是常态，配额不能保证盘不满。

## 5. 压实与清理现状

- 全仓库生产代码 grep：**无 `VACUUM`、无 `incremental_vacuum`、无 `auto_vacuum`、无 `wal_checkpoint`**（唯一的 `wal_checkpoint(TRUNCATE)` 在 `C/agent24-memory/tests/p1_capacity_probe.rs:37`，测试）。`KvStore::open`（lib.rs:288-300）设 WAL + `foreign_keys` + `busy_timeout=5s` + `row_buffer_size`；`synchronous` 未显式设置（用 sqlx 默认，未能确认其值）；无 `wal_autocheckpoint` 调整（SQLite 默认 1000 页自动 checkpoint）。
- **mem_events 没有任何生产删除路径**。DELETE 命中：`consolidator.rs:154/157`（删 `mem_consolidations`，派生数据）、`retriever.rs`（重建 FTS，派生）、`lib.rs:1092`（`kv` 表一条）、`knowledge.rs:281`（`mem_instructions`）。`DELETE FROM mem_events` 只出现在测试（`consolidator.rs:457`、`event.rs:1307`）。0014 的 `mem_events_ad_usage` 触发器是"防御性"，注释明说"no production path deletes"。
- 会话压实 `CompactionPolicy`（`C/agent24-memory/src/session.rs:31-49`，默认 max_recent=40/keep_recent=20/summary≤4000 字符）：**只追加摘要行，不删原文**（`compact` 里"originals retained"），所以压实在存储上是**净增**，仅减少 prompt 体积。
- M3 `delete_run_message_range`（`C/agent24-store/src/repo.rs:1128`）：删的是 **Run DB 的 `run_messages`**（run 内 prior_context 的复制，`lib.rs:1764-1782`，best-effort，且在 `unproven_source_failure` 时跳过），**不碰 memory.db / mem_events**，是派生副本。
- `agent24-store` 里的 `allocation_retention_writer.rs` 属 Run DB 的另一类数据，未核对其语义，与 mem_events 无关（未能确认更多）。
- 结论：当前**没有压实、没有保留、没有回收**。满额后没有任何机制能让 `row_count` 下降，对 personal 与 module 均是死路。PLAN-M2.md:52 与 jason 的 C3 P1 登记已承认此点。

## 6. per-owner override

- `mem_owner_quota`（0014）：`owner PK, max_rows, max_bytes`；仅 `'*'` 行由迁移种下（200000 / 268435456）；该行受 BEFORE DELETE 与 BEFORE UPDATE OF owner 触发器保护（0014:40-58），**但 `UPDATE ... SET max_rows` 不受保护**，可把默认调成任意值（包括 0）。
- **生产代码里没有任何写入者**：grep `mem_owner_quota` / `mem_owner_usage` 在非测试 Rust、desktop、cli 中**零命中**（仅迁移、`event.rs`/`lib.rs`/`writer.rs`/`session_failure_tests.rs` 的测试、`tests/p1_capacity*.rs`）。设计文档称"任何未来配置层只需 INSERT ... ON CONFLICT"（0014 注释），未实现。
- 没有 API、没有 CLI、没有 daemon 路由。改限额的唯一办法是对 `memory.db` 直接跑 SQL（需文件系统权限，等同本机用户，无应用层权限模型）。测试通过直接对池执行 SQL 来设置（`p1_capacity.rs:22 set_quota`）。
- 触发器按 `scope_owner` 精确匹配 owner 键（含 NUL 分隔的 `partition_key`），写 override 必须用完整分区键（`os_memory.rs:252`），人手拼写易错且无校验。

## 7. 用量可读性

- `mem_owner_usage`（row_count、byte_count、updated_at）由 `AFTER INSERT/UPDATE OF scope_owner/DELETE` 触发器维护，数据是**权威且现成**的。
- **没有任何 API/UI/CLI 读取它**：生产代码零命中（同 §6 grep）。`/api/v1/memory/*` 只有 3 个路由（server.rs:1115-1125）：`GET assertions`、`DELETE assertions/{id}`、`GET|PUT settings`，响应无用量字段。`/health` 里是否有记忆用量字段：未发现（未能确认完整 health 结构，grep 无 memory usage 命中）。
- 读取的现成基础：`mem_owner_usage` 单行主键查询，成本 O(1)；`memory_routes::memory_ctx` 已能拿到 `(KvStore, owner)`，新增只读端点无需新依赖。需要注意 `byte_count` 仅 payload，UI 文案不能写成"占用磁盘"（0014:25-31 已声明）。
- P1-03 告警需要的阈值比较、百分比、`updated_at` 新鲜度都没有实现。

## 8. personal 与 module 共用配额

- **owner 值不同**，各自一行 `mem_owner_usage`、各自受限：
  - personal：`partition_key(org, SpaceId::personal("local"))`，`SpaceId::personal(user) = "usr:{user}"`（`os_memory.rs:222`），`LOCAL_USER = "local"`（server.rs:472），在 `server.rs:508-529 session_memory` 里 `ensure_personal_recorded` 后 `.with_owner(owner)`；`memory_routes` 用同一 owner（`AppState.memory_owner`，server.rs:580）。
  - module：`partition_key(org, SpaceId::module_private(module))`，`"os:{module}"`（os_memory.rs:~210），`OsScopedMemory.key`，写入时 `Scope{owner: self.key, agent: Some(module)}`（os_memory.rs:796-802，module 不能选 owner）。
  - 测试 `os_memory.rs:1587 personal_spaces_are_disjoint_from_module_spaces` 钉住个人与模块键互不相同。
- 因此**模块写满不会挤占个人记忆的配额**（触发器按 scope_owner 精确计）。反过来个人写满也不影响模块。
- 但：(a) 所有 owner 默认同为 `'*'` = 200000 行 / 256MiB，**没有全局总量上限**——N 个模块 + personal 理论上可占 (N+1)×256MiB payload，磁盘风险由此叠加；(b) personal 一个 owner 同时承载会话消息、摘要、断言审计、撤回事件，会话轮次是主要消耗者（每轮 2 行，每 20 轮左右 +1 摘要行）；(c) 同一个 `memory.db` 文件、同一个池，模块写入大量时会争抢写锁（单写者 + `busy_timeout=5s`），但不争抢配额。
- 模块自身另有 `MAX_BODY_BYTES = 64KiB`（os_memory.rs:156）与限流（OOP 令牌桶），不是配额。

| 不静默删原文 | 无任何删除/压实删原文路径 | 满足（代价：无法回收） |

| 用户可撤回/遗忘 | 满额时 `DELETE assertions/{id}` 500，断言保持 active | **违反** |
