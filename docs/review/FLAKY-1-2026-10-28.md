## 模块卡片：产品路径错误，不是身份写入/读取竞态

调用链与证据：

- `rust/apps/agent24d/src/server.rs:2874` 的 `callback_root` 原先用传入路径估算最大 socket 长度。
- `rust/crates/agent24-os-proto/src/endpoint.rs:179` 的 `CallbackDir::create` 随后对 `run` 目录 canonicalize。macOS 上 `/var` 变成 `/private/var`，多 8 字节；`/tmp` 也会扩成 `/private/tmp`。
- 首轮 CPU 压力测试中，50 组卡片测试失败 12 组，每组两个需模块运行的测试均失败。保留 stderr 后，`/tmp/flaky1/before-load/card-12.log` 明确记录：规范化后的最大 socket 路径为 111 字节，超过 103 字节，整个进程模块 host 无法启动。最终卡片返回 `no_package_identity`，原有 `running_card` 条件轮询到 30 秒后报错。
- 此问题依赖 PID 位数：规范化前路径在阈值内时会漏选 fallback；PID 多一位，反而可能选中 fallback 并成功。并发和循环推进 PID，表现看似与负载有关；单纯延长等待不能修复一个从未启动的模块。

修法：估算路径前先 canonicalize 已存在的 root，再决定是否使用原有安全检查保护的短路径。fallback 的命名算法与安全检查保留。不存在的 root 保持原有后续创建/报错行为。

确定性反面对照：`server::tests::callback_root_accounts_for_symlink_expansion_before_choosing_a_socket_path`（`server.rs:6172`）建立短别名，指向真实长目录，经真实 `process_host` 创建目录并绑定 socket。修复前必败，错误为 160 字节超过 103 字节；修复后通过。测试不依赖特定 PID 或运行速度。原有“不安全 fallback 必须拒绝”测试同时通过。

身份专项核查：

- `rust/crates/agent24-os-proto/src/launch.rs:525` 在 spawn 子进程前计算 artifact，`:620` 在构造 generation 时传入。
- `rust/crates/agent24-os-proto/src/drain.rs:324` 的 artifact 是 generation 的不可变字段，`:394` 直接读取。
- `rust/crates/agent24-os-proto/src/supervisor.rs:860` 先安装 generation，`:916` 后转入 Running。
- `rust/apps/agent24d/src/module_tool_runtime.rs:192` 读取前还要求 enable epoch 已观察、generation 处于 Running。

没有发现“先发布 Running，再写 artifact”的竞态。本次复现的 `no_package_identity` 来自模块 host 未启动；历史 #1433 的具体失败是否完全同源，缺少当次 daemon stderr，不能反推为已证实。

## WAL：测试把合法 Busy 当成失败，并把调度延迟当成写入阻塞

首轮 50 次中 4 次失败，均为 `got Busy { wal_before: ... }`，例如 `/tmp/flaky1/before-load/wal-08.log` 的 `wal_before: 44990456`。

`rust/crates/agent24-memory/src/wal_maintenance.rs:236` 和 `:271` 均允许 checkpoint 的锁竞争返回 Busy 并退避；maintainer 连接的 `busy_timeout` 在 `:132` 被设为 0。原测试同时发起 50 次写入，却只接受 Done/Partial。并发写锁或自动 checkpoint 竞争时 Busy 是产品设计的合法结果。另一个 `worst < 1s` 断言包括 CPU 调度与 SQLx worker 调度时间，不能证明延迟来自 SQLite 锁；D7 设计没有这项墙钟延迟规格。

测试修法：

- `wal_maintenance.rs:573` 复用现有 `after_passive` hook 和两个 oneshot 事件。大 WAL 完成 PASSIVE 后才放行写入；checkpoint 仍在途时，等待 50 个写入实际完成，然后继续。核对 Partial、未发出 TRUNCATE、50 个值均可读。移除原先 2ms sleep 和 1 秒单写耗时断言。
- `wal_maintenance.rs:608` 新测试显式持有 `BEGIN IMMEDIATE` 写锁，要求 checkpoint 在 COMMIT 前返回 Busy，且记录一次 TRUNCATE 尝试；COMMIT 后下个空闲窗口必须 Done 且 WAL 为零。这样锁竞争路径不靠调度碰运气。
- 30 秒仅为检测事件无法完成的死锁看门狗；成功判据是事件顺序、结果、计数及持久化数据，不是放宽单次写入耗时。

产品 WAL 逻辑未改。已有 `data_version` 重读到 TRUNCATE 之间的最佳努力窗口（`:254`）仍存在；本次没有把测试通过解释成严格的写入延迟保证。
