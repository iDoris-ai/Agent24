# ADR-039：概念模型——本体、能力、技能

索引：[架构总入口](../architecture/README.md)・[ADR 索引](README.md)

- 状态：**已接受（r2，Fable 评审后修订）**（2026-11-01，jason 认可；r2 落实评审项 H1、H2、H3、M8、M9、M12，见各节）
- 地位：总纲。之后所有关于扩展、组件、技能的 ADR，都要用本文的概念和名词。
- 相关：[ADR-038 组件契约 v1](ADR-038-component-contract-v1.md)、[ADR-K1-01 模块工具契约](ADR-K1-01-module-tool-contract.md)、[可进化性评估](../architecture/EVOLVABILITY-ASSESSMENT-2026-11-01.md)

## 1. 背景

Agent24 先后出现过这些扩展名词：进程内 DomainModule、领域 OS、附着模块、sidecar、MCP server、workspace、组件安装器，还有将来要加的 Skill。

每个名词都有自己的生命周期、授权和协议。对外讲不清楚，对内也没法判断一个新东西该归哪一类。

## 2. 决策：一个本体，两个概念

```
        技能  ← 帮用户把一件事办成（可安装，可进化）
          ↓ 调用
        能力  ← 能做什么（可安装，可卸载）
          ↓ 运行在
     Agent24 本体  ← 不用装，也不能卸
```

### 2.1 本体

本体就是 Agent24 daemon，负责思考（agent 循环、模型路由）、记忆、审批与审计、调度、权限令牌、能力管理。本体不算一个「概念」，它就是产品本身。

### 2.2 能力

**能力回答「能做什么」**，是手段。能力可大可小，判断标准不是大小：
- 原子能力，例如 OCR、文档转换、图片处理、CAD 转换；
- 服务能力，例如本地模型（iDoris）、通信（Hyphae）、语音（AgentEar）、知识库；
- 完整系统，例如 Open Design、Open Creator。它们自带界面，但仍然是能力；它们的工作区仍是本体管理的资源（§4）——每个项目绑定到本体的一个 scratch workspace（ADR-004 的目标形态），不是组件自己的私有工作区。
- 领域包，例如 Sin90、Cos72。一个领域包是**一个组件**，里面既可以有能力（领域模型、工具、记忆分区），也可以有技能（面向该领域用户目标的步骤）。归类的对象是包里的每一项，不是整个包；所以「Sin90 是能力还是技能」这个问题本身不成立，要问的是「Sin90 里的这一项是什么」。

**工具与能力的关系**：一项能力至少暴露一个工具（ADR-K1-01）；原子能力通常只有一个工具，服务能力有多个。单个工具不是独立的能力——「知识库检索」是「知识库」能力的一个工具，不单列。

### 2.3 技能

**技能回答「帮用户把什么事办成」**，从用户的目标出发，按步骤组合多项能力。

例如「把扫描的合同整理成摘要并发给同事」，就要用到 OCR、文档、通信三项能力。

技能里有这些内容：说明、步骤、依赖哪些能力（按 ADR-038 D9 的能力 id 声明）、评测用例、版本。技能本身不持有权限，用到的每一项能力都按能力的规则审批。

用户可见的一步式 prompt 模板（例如「把这段话改成正式邮件」）是**零依赖技能**：只有说明和步骤，不依赖任何能力，同样走 ADR-040 的版本、评测、审批、回滚。本体内部的 system prompt 不是技能，属于本体。

## 3. 三条规则

1. **调用只能单向：技能 → 能力 → 本体提供的服务。** 具体有三条边界：
   - **能力之间不直接调用。** 一项能力需要另一项能力时（例如 Open Design 需要 OCR），走本体的工具调用路径（ADR-K1-01），用自己的 capability token、过自己的审批。这和 ADR-K1-01 §7「不允许模块间任意调用」是同一条规则。
   - **能力不调用技能，但可以向本体发事件或提请求**（领域 OS 的事件 callback、完整系统经 ACP 桥提请求）。由本体按用户配置的触发规则、经审批后决定是否运行技能、运行哪个技能；能力不能指定技能。
   - **本体可以消费实现了本体服务契约的能力**：模型来源（iDoris 实现 `ModelProvider`）、向量化、通信投递。这是本体对**契约**的依赖，不是对某个组件的依赖——换组件只改锁（ADR-038 D8），本体不改代码。
2. **本体不依赖任何能力就能启动。** 记忆、调度、审批、能力管理在没有任何能力时照常工作。**最小可用配置**是本体加一个模型来源：本地模型能力（iDoris，一个组件）或本体内置的云端订阅配置（属于本体，不是组件）。没有模型来源时，本体以「不能思考」状态运行并明确提示，不静默失败。其他能力全部按需安装。技能要声明自己依赖哪些能力：安装或运行技能时，缺哪项就提示用户去装，不能静默失败。
3. **技能是自进化的主要对象。** 技能的改动必须有版本、通过评测、经过审批，并且可以回滚。系统不得静默修改技能。能力负责稳定可靠，技能负责越用越好。

## 4. 对外与对内

**对外**（用户、文档、能力中心）只用三个词：**Agent24**、**能力**、**技能**。能力中心分「能力」「技能」两栏。

**对内**用下面这些实现名词，不对用户暴露：

| 内部名词 | 含义 | 规范 |
|---|---|---|
| **组件**（component） | 能力的安装包。一个组件提供一项或多项能力，也可以附带技能。清单里提供的能力写在 `provides`，需要本体给的权限写在 `requires`；**不再有叫 `capabilities` 的字段** | ADR-038 D9 |
| **模块**（module） | ADR-K1-01 / K1-03 和 `DomainOsManifest` 里的 module，就是组件；`module_id` = 组件 id。新文档统一写组件 | ADR-038 D9 |
| **运行形态** | 组件怎么跑：进程内、子进程 CLI、常驻服务（HTTP）、附着（attach）、sidecar、MCP server、远端服务 | ADR-038 D4 |
| **工具**（tool） | 能力暴露给技能和 agent 的调用接口，有 schema 和风险等级，统一走审批。工具名是 `<组件 id>.<operation>` | ADR-K1-01 |
| **资源** | 本体管理的工作区、文件、会话。完整系统的工作区也是这里的资源 | 现有 workspace 设计、ADR-004 |

### 4.1 英文名（jason 2026-11-01 拍板）

| 中文 | 英文 | 说明 |
|---|---|---|
| 能力 | **Capability** | 界面上已经在用（侧边栏 Capabilities、能力中心），保持不变 |
| 技能 | **Skill** | 有意和业界开放的 Agent Skill 格式（`SKILL.md`）用同一个词，便于导入社区技能（#1037 的外部导入） |

**消歧规则**：CORE-2 的权限机制在代码和文档里一律写全称 **capability token**（能力令牌）。单独出现的 Capability 只指能力。不改现有代码标识符。新文档和新界面文案必须遵守这条规则；旧文档在下次修改时顺手改过来。

旧名词统一按下表归类，新文档和界面不再把它们当独立概念使用：

| 旧名词 | 归为 |
|---|---|
| 进程内 DomainModule | 组件，运行形态是进程内 |
| 模块 / `module_id`（ADR-K1-01、K1-03、manifest `name`） | 组件 / 组件 id |
| 领域 OS（Sin90 / Cos72） | 组件（领域包），里面的每一项各自归为能力或技能 |
| 附着模块（AgentEar） | 组件，运行形态是 attach |
| Sidecar（Open Design） | 组件，运行形态是 sidecar，提供完整系统能力 |
| MCP server | 组件，运行形态是 MCP，只提供工具 |
| iDoris / Hyphae / Knowledge / Documents | 组件，提供服务能力 |
| workspace | 资源 |
| Skill | 技能 |

## 5. 新东西怎么归类

先拆：如果它是一个包（领域包、带技能的组件），把包拆成一项一项，再对每一项提问。

按顺序问三个问题：
1. 它是用户的一个目标、要组合几项能力才能完成吗？或者它是用户可见的一步式 prompt 模板？是 → **技能**（后者是零依赖技能）。
2. 它能被安装、卸载，提供某种「能做什么」吗？是 → **能力**，用组件交付。只是某项能力的一个调用入口 → 是那项能力的**工具**，不单列。
3. 都不是 → 它属于**本体**，要改内核，并且单独写 ADR。

对照：OCR → 能力（原子）；Open Design → 能力（完整系统）；Sin90 → 组件，里面的领域模型和工具是能力、「90 天规划」是技能；MCP server → 能力（只有工具）；iDoris → 能力（服务，同时是最小可用配置里的模型来源）；「周报」→ 技能；知识库检索 → 「知识库」能力的工具；「改成正式邮件」模板 → 零依赖技能；记忆 → 本体。

不允许为新东西发明新的顶层名词。
