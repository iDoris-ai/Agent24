## 1. 当前在做什么

本节初始阶段状态已由文末 Wave 9 增量更新。目标仍是把 Open Design 作为 Agent24 的 Creative Workspace 集成，而不是直接合并两个代码库：

- Agent24 是唯一 AI control plane，负责身份、session/run、模型、工具、审批、审计和 workspace authority；
- Open Design 保留 project、conversation、Studio、Design System、Preview、Export 和 artifact lifecycle；
- Agent24 Electron 是唯一桌面 main process；Open Design 作为受管 sidecar 和隔离 WebContentsView 运行；
- 两边通过 opaque `workspace_id`、ACP 和受限 capability 连接，Open Design 不取得 Agent24 product-host authority。

因此当前阶段主要在补 Agent24 的安全契约和宿主基础，还没有开始最终 Creative 页面接线。

## 4. Workspace 在 Agent24 中是什么

一句话定义：**workspace 是 Agent24 内核拥有的、可审计且有生命周期的运行资源作用域。**

它不是一个普通目录。一个 workspace 至少由这些内容组成：

- opaque `workspace_id`；
- 内部 canonical root 和不可替换的文件系统 identity/generation；
- provenance、base revision 和 writeback policy；
- lifecycle owner、state、TTL、revision；
- Run/host leases 与 concurrency policy；
- 与 run、tool、approval、event、audit 的关联。

普通 REST、ACP、renderer 和 Open Design 只看到 ID 和必要的公开状态，不看到 canonical host path。可信 registry 在绑定 Run 时，把记录变成不可由工具伪造的 `WorkspaceHandle`。

它也不是：

- VM、容器或完整 OS sandbox；
- Domain OS/module/plugin；
- 单独的一张权限票据；
- session、run 或 project 的同义词；
- 允许调用方自行提交的 `cwd`/绝对路径。

## 5. 与内核调用、OS、Capability 和模块的关系

```text
用户 / Creative principal
        │  action + resource capability
        ▼
Agent24 kernel ── registry/state/lease ── Workspace
        │                                  │
        │ Run/Session 显式绑定              │ immutable WorkspaceHandle
        ▼                                  ▼
 policy + approval ── ToolContext ── fs/shell/MCP/tool call
                                           │
                                           ▼
                                  OS 文件与进程原语

Domain module/plugin ── KernelCtx capability handles ── kernel services
        （独立扩展轴；不会因为安装或授权模块而自动获得 workspace）
```

### 5.1 与 Agent24 kernel 的关系

kernel 是 workspace 的 authority：创建 ID、保存内部 root、推进状态、发放 lease、绑定 Run，并在恢复时核对 identity。ACP、Electron、Open Design 和工具都是消费者，不能维护第二套 root 映射。

Workspace 因此是 kernel 的资源对象；`workspace_id` 类似稳定引用，`WorkspaceHandle` 才是运行时可使用的内核签发句柄。

### 5.2 与 tool/kernel call 的关系

模型发起 `fs_read`、`fs_write` 或 `shell_exec` 时，不直接把路径交给 OS。目标链路是：

```text
tool request → capability whitelist → policy/approval
             → ToolContext(workspace_id + private handle)
             → workspace-relative OS operation
```

`fs_read/fs_write` 使用 pinned directory handle 和 beneath-only 原语；`shell_exec` 的 cwd 固定为 workspace root；explorer/subagent/self-wake 继承同一个 handle。网络/MCP 工具即使不使用目录，也携带 workspace ID 用于 policy 和 audit。

### 5.3 与 host OS 的关系

OS 提供文件、目录、进程、fd/handle 和权限机制；workspace 用这些原语落实边界，但不等于 OS 本身。

v1 保证文件工具按 pinned root 运行，并把 shell cwd、审批和审计绑定到 workspace。它**不宣称**任意 shell 命令都无法访问 root 外路径；那需要后续 per-workspace sandbox/container/OS policy。改变到更强 sandbox 时，opaque ID、lease 和 Run binding 可以保持不变。

### 5.4 与 capability 的关系

Capability 回答“谁能对什么资源做哪些动作”；workspace 回答“这次运行的资源边界、状态和生命周期是什么”。两者不能互相替代。

Creative token 会绑定 workspace、principal、session/attachment、daemon/host/sidecar generation 和 TTL。即使 token 允许创建 Run，workspace 已过期、owner 不匹配或 lease 冲突时仍必须拒绝。

可把最终授权理解为：

```text
允许操作 = 身份/action capability
         ∩ workspace scope/state/lease
         ∩ policy/approval
         ∩ OS enforcement
```

### 5.5 与 Domain OS、plugin/module 的关系

Module/plugin 是“安装了什么代码和领域能力”；workspace 是“某次 session/run 可以操作哪一份任务资源”。它们是两条正交轴：

- `DomainModule` 通过经过校验的 manifest 挂载自己的路由和 store；
- `KernelCtx` 只交付获批的 events、memory、approval 等 capability handle；
- module 的持久化 data directory 不等于用户任务 workspace；
- module 获得 kernel capability，不代表自动获得任意 workspace、路径或 Run；
- 将来 module 若参与 workspace 操作，也必须收到当前 Run 的窄化 handle，不能从字符串或全局目录自行构造。

Open Design 在当前方案中也不是 Agent24 Domain OS module。它是独立 fork + sidecar + ACP consumer；若未来改为 Domain OS mount，需要新 ADR，不能悄悄混入当前实现。

## 6. 一个具体例子

用户在 Agent24 打开 Creative 项目时，Agent24 创建 `ws_...` scratch workspace。Electron host 取得短期 host lease，并把受限 handoff 给 Open Design sidecar。Open Design 通过 ACP 发起 prompt；ACP 只能把已经绑定的 `workspace_id` 传给 Agent24 Run。

模型要求写入 `index.html` 时，Agent24 校验 Creative capability、workspace active/lease、审批和 tool policy，然后使用 Run 持有的 `WorkspaceHandle` 写入 scratch root。Open Design 可以 preview/export 结果，但不能凭 `cwd` 获得其他目录，也不能直接 writeback 源仓库。最终保留、导出或发布由 workspace 外的显式 orchestrator 流程决定。
