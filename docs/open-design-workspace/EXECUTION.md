# 如何启动 Agent24 × Open Design 工作

## 1. 不需要运行命令

这项工作可以直接在当前对话中启动，不需要用户打开终端、执行脚本或手动创建 agent。

推荐启动口令：

> **计划通过，按多 Agent 模式开始执行 P0–P9；允许按计划创建分支/worktree、提交、推送和 PR。阶段门禁通过后自动继续，只有重大设计变化、需要新增权限或真正阻塞时再停下来问我。**

这句话同时表达：

- 批准当前 `PLAN.md` 与 `AGENT24-DEPENDENCIES.md` 的默认选择；
- 授权开始实施，而不只是继续讨论；
- 授权使用多个子代理、创建隔离 worktree/分支；
- 授权执行计划内的远端 fork、push 和 PR 操作；
- 允许在已冻结设计与验收范围内自动继续下一阶段；
- 不授权超出计划的产品方向改变或破坏性操作。

如果只想先走一个阶段，可以说：

> **计划通过，只开始 P0；完成并汇报后暂停。**

如果只想在本地验证、不产生远端写入，可以说：

> **计划通过，先本地执行 P0–P2，不创建远端 fork、不 push、不开 PR。**

## 2. “开始 P0–P9”不等于全部同时启动

P0–P9 有依赖关系。主线程按依赖图分波次调度，只并行满足以下条件的任务：

- 输入契约已经冻结；
- 不依赖另一个尚未完成的阶段；
- 不同时修改同一组高冲突文件；
- 每个 agent 有独立 branch/worktree；
- 每个工作包有明确验收命令和完成定义。

当前环境包含主线程在内最多 4 个并发槽，因此单轮最多启动 3 个子代理。典型一轮是：

```text
主线程：冻结设计、分配文件所有权、集成结果
├─ Luna A：实现工作包 A
├─ Luna B：实现工作包 B
└─ Luna C：实现工作包 C

三者结束并测试
        ↓
5.6-SOL：只读代码审查
        ↓
Luna：修复确认属实的问题
        ↓
5.6-SOL：复审
        ↓
主线程：合并并更新依赖台账
```

## 3. 模型分工

| 角色 | 模型策略 | 工作范围 |
| --- | --- | --- |
| 设计/裁决 | 高能力模型，high/xhigh | ADR、协议、依赖图、验收标准、跨仓库边界 |
| 实现 | `gpt-5.6-luna` medium/high | 范围清晰、文件边界明确的代码、测试和文档 |
| 审查 | `gpt-5.6-sol` high/xhigh | 正确性、安全、并发、兼容、测试缺口、上游侵入 |
| 集成 | 主线程 | 调度、冲突处理、测试汇总、是否放行下一阶段 |

Luna 不独立改变已冻结架构。发现规格缺口时必须停止该工作包并返回主线程，而不是自行扩大范围。

## 4. 每个工作包必须包含

- 精确目标和非目标；
- 基线 commit；
- 允许修改的文件/目录；
- 禁止触碰的边界；
- 输入/输出契约；
- 必须新增或更新的测试；
- 验收命令；
- 对应依赖 ID；
- 失败、阻塞和回滚说明。

提交与 PR 以单一、可独立审查的功能切片为边界：日常目标为 200–300 个变更行，
500 个变更行为硬上限。只有不可合理拆分的原子事务、状态机，或实现与其必要负向测试
必须共同审查时，才可使用 301–500 行；此类 PR 必须经过两次独立 SOL exact-head review，
并在正文写清不可拆原因、排除范围和回退点。超过 500 行必须拆分，禁止用无关改动凑批次。

外部 PR review 队列较长时，默认每 3 小时做一次完整 scoped 状态核对；不再用 15 分钟
轮询占用开发时段。CI 主动失败、external `REQUEST_CHANGES` 或明确 approval 通知可提前触发
一次核对；合并仍必须同时满足 exact head、external `APPROVED`、检查全绿和依赖就绪。

## 5. 阶段门禁

每个阶段依次经过：

1. 设计冻结；
2. Luna 实现；
3. 本地测试和 schema/生成物漂移检查；
4. 5.6-SOL review；
5. 修复与复审；
6. 主线程验收；
7. 更新 `PLAN.md`、依赖台账和 commit/PR 状态；
8. 进入下一阶段。

以下情况必须暂停并向用户汇报：

- 需要改变已经批准的产品/源码/authority 边界；
- 需要新增未授权的远端仓库、凭据、部署或发布动作；
- 主干出现与冻结契约冲突的新变化；
- 测试证明当前选择不可行，预计变更成本超出计划表；
- 出现会影响用户其他 worktree 或数据的破坏性操作。

普通代码问题、测试失败和可逆的小范围修复不需要用户逐项批准。

## 6. 对话中的控制口令

不需要特殊 slash command，直接说自然语言即可：

| 用户说法 | 行为 |
| --- | --- |
| `计划通过，开始` | 按推荐策略从 P0 开始 |
| `只做 P0` | 完成 P0 后暂停 |
| `继续` | 从上一个已验收门禁继续 |
| `暂停` | 不再启动新工作包；正在安全结束的任务完成后汇报 |
| `停止并汇报` | 停止可停止的子代理，给出分支、commit、测试和未完成项 |
| `现在进度如何` | 只汇报状态，不改变执行方向 |
| `只 review，不修改` | 启动只读审查，不实施修复 |
| `同步 main 后继续` | 审计并 merge 最新 `origin/main`，验证后继续 |

## 7. 用户可见的进度格式

阶段执行期间的汇报至少包含：

- 当前阶段和依赖 ID；
- 活跃 agent/工作包；
- 分支、worktree 和基线 commit；
- 已完成测试；
- SOL review 的真实发现及处理状态；
- 是否满足进入下一阶段的门禁；
- 主干是否发生变化。
